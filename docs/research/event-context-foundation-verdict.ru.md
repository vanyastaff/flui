# Фундамент событий и состояния: условия принятия

Дата: 2026-09-27. Объект исследования — рабочее дерево
`codex/event-context-catalog`, базовый коммит `e330fc413` и незакоммиченная

утверждение о готовности всего FLUI. Рендер, текст, IME и платформы здесь

## Как принимается решение

### Продуктовые требования, а не абстрактные потребители

Источником требований служат `design/` и план миграции. При сверке 2026-09-27
`git diff --no-index -- D:/flui/design/architecture.md design/architecture.md`
не показал различий. Документ задаёт целевую архитектуру, а не утверждает, что
все перечисленные возможности уже реализованы.

| Потребитель и источник | Следствие для текущего фундамента | Проверка в порядке продуктовой необходимости |
|---|---|---|
| Notes: signals, Router, Form; чистый внешний consumer ([решение S2](../../design/decisions.md#s2-notes-is-the-hero-application), [выход H0](../plans/2026-09-25-architecture-migration-plan.md#h0-exit)) | Контекст должен естественно проходить через редактирование, сохранение формы и переход между экранами; внешний код не должен зависеть от внутренних crates | Сначала внешний Notes-подобный сценарий edit → validate/save → navigate, включая отказ и удаление экрана |
| Material, Cupertino и сторонние авторы виджетов ([архитектура §4 и §6.2](../../design/architecture.md)) | Рабочий SDK-контракт, borrowed payload, обработка ошибок; локальные callbacks не должны требовать Send | Проверка внешнего компонента и завершение уже запланированной совместной миграции callback/Send до первой публикации |
| Люди, агенты, devtools и flui-testing ([стратегия S1](../../design/decisions.md#s1-positioning), архитектура §11.4 и §12) | Действия через MCP/semantics и обычный ввод должны достигать согласованного поведения; отказ доставки должен быть различим в соответствующем протоколе | Один сценарий Notes через ввод и агентный путь, общие finders и нормализованное наблюдаемое состояние; не требовать сериализации каждого Rust-замыкания |
| IO/compute-потребители и удаляемые экраны (архитектура §8.5) | Отмена Spawner при unmount уже задана целью, это не новая придуманная потребность | Проверить существующий Spawner/continuation путь после unmount и remount, прежде чем предлагать второй механизм отмены; request freshness проверяется отдельно |
| Несколько презентаций и изолированных realms (архитектура §8.2, §9) | Корректный адресат, запрет смешения состояний и ограниченная работа владельца уже требуются | Использовать существующие multi-presentation routing/close сценарии; shared-document опыт — дополнительный stress-case, не установленное требование Notes H0 |
| A2UI и изменяемые коллекции (архитектура §9 и §12, H1) | Пакетное изменение и стабильные ключи не должны доставлять старое событие новой строке | Переместить/удалить keyed-строку с ожидающим действием и проверить target identity; не добавлять LLM-клиент в core |
| Большие списки, редактор, анимация (архитектура §14) | Стоимость пропорциональна изменению, idle не создаёт кадры, анимация не требует лишних rebuild/layout | Сначала существующие счётчики idle/10k-list/text-change; дополнить стоимостью callback-доставки. Целевой opacity-контракт: 0 rebuild, 0 relayout, 1 layer patch; не приписывать эту гарантию всем animation-виджетам |

Текстовые edit-транзакции и undo прямо названы в §9; универсальные транзакции
произвольных callback из этого не следуют. Поддержка нескольких окон задана,
но именно одновременное редактирование одного документа в двух окнах в прочитанных
требованиях Notes не закреплено. Этот опыт полезен для проверки расширяемости,
а не как самовольно добавленный блокер ближайшего релиза.

Поэтому первой проверкой служит уже выбранный продукт Notes и его внешние
потребители, а не новая универсальная entity/reducer архитектура. Принятое владельцем
направление typed writes не открывается заново без конкретного противоречия этим
требованиям; проверяется его достаточность и незакрытые условия ADR-0086.

Количество согласных исследователей не является доказательством. Для каждого
решения нужны: конкретный потребитель, отказной сценарий, альтернатива, цена
перехода и проверка, способная опровергнуть выбранный вариант. Удобство пяти
callback-вызовов в пилоте ADR-0086 доказывает только их удобство; оно не доказывает
корректность модели общего документа в нескольких окнах.

Предварительный вывод: узкую явную capability для чтения/записи состояния
презентации разумно сохранить как кандидат. Нельзя замораживать её как универсальный
контекст событий, асинхронных задач и общего состояния приложения. Ни полный
перезапуск архитектуры, ни окончательное принятие текущей формы пока не следуют
из имеющихся результатов.

## Разделить три ответственности

| Ответственность | Нынешнее поведение | Что ещё нужно доказать |
|---|---|---|
| Доступ к графу | `EventCx`/`WriterSource`, проверка идентичности графа, runtime-guard build | Достаточность границы после удаления переходного доступа через `Reactive`; требования будущих layout/paint/compute-фаз |
| Жизнь получателя | Виджеты добавляют собственные mounted-проверки; слот сигнала имеет generation | Отмена по конкретному экземпляру владельца, освобождение захватов, запоздавший результат предыдущего запроса |
| Доменное действие | Callback выполняет произвольный Rust-код | Общий документ, undo/redo, команды другого окна, наблюдаемость и воспроизведение |

Один `&mut EventCx` не объединяет эти гарантии. `WriterSource::write` открывает
контекст независимо от физического события; копии source могут открыть несколько
контекстов того же графа. Lifetime заимствования запрещает сохранить сам borrowed
контекст, но не запрещает сохранить source. Это не транзакция, не эксклюзивная
блокировка графа и не автоматически отзываемый доступ после unmount.

## Минимальные различающие эксперименты

Это критерии будущих опытов, не результаты уже выполненных нагрузочных тестов.

| Опыт | Что наблюдать | Условие пересмотра фундамента |
|---|---|---|
| Один документ, два окна, независимые selection/focus | Изменения текста видны в обоих окнах; локальный UI не смешивается; закрытие одного окна не удаляет документ | Для обычной операции нужны обход `ForeignGraph`, ambient writer или дублирование авторитетного состояния |
| Поиск A, затем B; B заканчивается первым | Приложение может проверить revision запроса и применить свою latest-wins политику; ошибку/отмену можно отличить от успеха | API мешает такой проверке до эффекта; живой owner или graph/slot generation сами по себе не обеспечивают freshness |
| Unmount, повторный mount, старый queued callback | Ни изменения нового экземпляра, ни пользовательского вызова после отзыва; отдельно измерить удержание захватов без следующего кадра | Каждый виджет вынужден независимо изобретать generation и cancellation; необходимость немедленного освобождения определяется бюджетом памяти |
| Один FormHandle монтируется дважды | Первая привязка остаётся целой; вторая отклонена до изменения storage через определённый API | Документация «нельзя» остаётся единственной защитой от перезаписи владельца |
| Накопление progress и terminal событий при паузе кадров | Размер очереди, удержанные байты, число вызовов, задержка другого окна, порядок terminal событий | Рост work на кадр не ограничивается оговорённой политикой; coalescing теряет completion |
| Паника после частичной записи, затем продолжение | Значение, invalidation, восстановление очереди и поведение host согласованы | «Можно продолжить» требует гарантий, которых реактивный граф не даёт |
| Сторонний пакет с событиями и async | Компиляция без внутренних imports, штатная обработка отказов, понятные ошибки и достаточная диагностика | Потребитель постоянно открывает новые writers вместо передачи полученного контекста |

Нагрузочные размеры: 1/10/100 окон или владельцев и 1/100/10 000 событий,
если соответствующий драйвер позволяет такие размеры. Это параметры эксперимента,
не обещание продуктовой поддержки 100 окон. Сравнивать baseline и кандидат на
одном host, без параллельной сборки; записывать toolchain, commit, профиль, число
повторов, p50/p95/p99 и peak memory. Абсолютный бюджет кадра задаётся для выбранной
частоты обновления и сцены до опыта. Результат теста на корректность не заменяет
измерение задержки.

## Решения, которые пока не стоит связывать

- Typed callback можно оставить, не превращая каждый пользовательский эффект в
  сериализуемую команду. Команды документа нужны там, где действительно нужны
  undo, replay или межоконная координация.
- Owner-targeted очередь может быть полезна для deferred delivery, не заменяя
  синхронные pointer/key callbacks. Универсальная отложенная доставка изменит
  порядок и ответ маршрутизации.
- Lifetime экземпляра и freshness запроса — разные оси. Generation слота не
  решает порядок ответов A/B, пока сам слот остаётся живым.
  Latest-wins — политика приложения или явно выбранного оператора, а не
  универсальное поведение всех результатов: некоторые операции должны завершиться
  независимо от появления более нового запроса.
- Общий документ не обязан жить в графе конкретного окна. Но отдельная модель
  документа должна иметь настоящую интеграцию с invalidation обоих окон, а не
  оставаться рекомендацией в документации.
- Переименование `EventCx` само по себе не исправит контракт. Если к нему
  добавляются target, propagation или transaction, сначала нужен единственный
  производственный путь, который обеспечивает эти данные и их время жизни.

Прежде чем добавлять registry адресованных событий, сравнить самый простой
кандидат: существующая очередь замыканий, слабая ссылка на состояние получателя,
generation привязки и очистка callback при dispose. Registry оправдан только
дополнительными измеренными преимуществами. Обычное уточнение возвращаемого
`Result<(), EventError>` не считается провалом вывода lifetime параметра callback.

## Проверенные границы доказательств

В `reactive/writer.rs` source хранит сильный `Reactive`; `check_context` проверяет
graph id и `building`. В текущем `Reactive::Inner` нет действующего compute/layout/
paint guard: соответствующие ADR описывают дальнейший дизайн. Не следует ссылаться
на будущий `WrittenDuringCompute` как на уже работающую защиту.

В `ui_realm/presentations.rs::signal_graph_for` выбирается граф, а не жизнеспособность
конкретного запроса. `commands.rs` затем вызывает `apply`. Следовательно, routing
по графу сам по себе не является отменой пользовательского кода для устаревшего
слота или запроса. Этот сценарий требует отдельного исполняемого теста.

Поведение panic в сигнале уже закреплено тестом
`a_panicking_closure_returns_the_loaned_value_and_marks_nobody`: частично изменённое
значение возвращается в слот, но invalidation не происходит. Это существующий
контракт, не регрессия данной миграции. Сохранение хвоста scheduler не должно
рекламироваться как восстановление целостности всего приложения после panic.

## Проверка внешних аргументов

Прежний raw-отчёт `2026-09-25-architecture-review/decisions/q7_callback_writer.md`
содержит ошибочное обоснование, что Xilem не допускает запись при построении view.
В опубликованном примере Xilem `app_logic` принимает `&mut State`. Это прецедент
явного доступа к состоянию, не доказательство compile-time phase purity FLUI.
Исторический отчёт не переписываем; используем исправленную интерпретацию.
[Документация Xilem](https://docs.rs/xilem/latest/xilem/).

Готовую generational arena следует сравнить с собственной до проектирования
lease-хранилища. Но одна замена контейнера не решит идентичность презентации,
request revision и политику отмены. Например, `slotmap` документирует ABA-защиту
версионными ключами, но ключ другой карты того же типа сам по себе не опознаётся.
Это аргумент за проверку зрелой библиотеки, не за слепую замену графа.
[slotmap 1.0.7](https://docs.rs/slotmap/1.0.7/slotmap/).

## Исполняемые продуктовые проверки

После исследования добавлены проверки в действующие тестовые цели, без нового
executor, registry или расширения публичного фасада под тест.

| Проверка | Наблюдение | Граница доказательства |
|---|---|---|
| Внешний Notes, `tests/fixtures/notes_workflow.rs` | Оба сценария прошли: keyboard edit, отказ validator, исправление, save в signal, Router и layout сохранённого текста; активация pointer и semantic action | Отдельный Cargo-пакет с локальной зависимостью только на публичный `flui`; не публикация crates.io, native IME или MCP end-to-end |
| Реальный `FutureBuilder` и `AsyncDriver` | Unmount/remount с прежним ключом и смена ключа отменяют старого producer до его completion-effect | Отмена принадлежащей подписке future, не произвольной уже отделённой внешней работы и не реализация будущего Spawner |
| Чувствительность async-тестов | Временная замена drop токена на `mem::forget` ломает оба теста: остаётся pending task и выполняется старый effect; после восстановления оба проходят | Generation-проверка результата сама по себе не удовлетворяет этим тестам |
| Pointer callback с 1/100/10 000 записями | Два подписчика перестраиваются каждый один раз; root и независимый подписчик не перестраиваются; следующий idle tick не добавляет builds | Счётчики работы, не p99, allocations или fairness между окнами |
| Ожидающие assistive requests при уничтожении owner | Пользовательский callback не вызван, его mounted capture освобождён ровно один раз | Запросы объединяются до build; это не доказательство освобождения уже поставленных post-frame closures |

Команды воспроизведения:

```text
cargo test --locked -p flui --test facade_consumer external_notes_consumer_executes_edit_save_and_navigation -- --nocapture
cargo nextest run --locked -p flui-view -p flui-widgets -E 'test(future_builder_remount_cancels_old_producer_before_its_completion_effects) | test(future_builder_replaced_key_cannot_overwrite_newer_completed_subscription) | test(raw_button::)'
```

Вторая команда: 10 passed. Первая команда запускает два downstream-теста и
проверяет, что оба действительно выполнены. При первой сборке были исправлены
ошибочные imports теста: публичные keyboard-типы уже доступны через curated
`flui::interaction`; внутренний test builder не является частью этого фасада.

`cargo xtask perf --check`: 4 passed, все 40 счётчиков совпали с существующим
baseline без `--bless`. Idle за 10 секунд: 0 кадров и 0 работы; изменение текста:
3 builds и 3 layout nodes; scroll списка из 10 000 строк: 126 builds и 132 layout
nodes. Это регрессионный бюджет этих сцен, не доказательство O(1) для любой сцены.

Итоговый `cargo xtask check-changed` завершился с кодом 0: fmt, clippy,
`8122 tests run: 8122 passed (1 leaky), 0 skipped`, строгий rustdoc, doctest,
Windows clippy CLI и два прохода по 56 feature-конфигурациям (библиотеки, затем
tests/benches/examples). `leaky` относится к существующему CLI-тесту
`devices_output_closes_even_when_a_probe_leaves_a_daemon_running`, а не к оценке
удержания callback. Android и wasm targets не установлены; iOS runner требует
macOS. Эти проверки были явно пропущены локальным gate и остаются обязанностью CI.
Native smoke, полный GPU-прогон и p99/peak-memory этим результатом не покрыты.
`cargo xtask checks` также завершился с кодом 0: ссылки, слои, reach, module DAG,
globals, WGSL, toolchain, formatting, file-length и changelog проверены.

## Следующий критерий готовности

До заморозки публичного фундамента остаются проверка опубликованного Notes,
late-result/unmount испытание через запланированный Spawner, когда его контракт
будет реализован, и измерение очереди относительно существующих бюджетов.
Испытания текущего AsyncDriver выше не подменяют эти требования.
Общий документ в двух окнах — дополнительный
опыт на расширяемость, а не новое обязательство выхода H0. Принять узкую
миграцию callback-сигнатур и принять весь будущий state/runtime фундамент — разные
решения. Первое может продвигаться с точными ограничениями и зелёными проверками;
второе пока преждевременно. Новый generic executor, transaction manager или
глобальный writer без этих опытов не добавляется.
