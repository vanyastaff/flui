# Market survey: Market survey: fine-grained reactivity and state (Leptos/Sycamore/Solid, Dioxus Signals/Stores, Compose snapshots, SwiftUI @Observable, Xilem, iced/Elm, Floem, GPUI, TC39/alien-signals) and what it changes in FLUI's global architecture, crate topology and ecosystem

_Raw output of the `market:reactivity_state` agent (2026-09-25). Unedited; each claim carries the source the agent cited._

## Findings

- **FLUI baseline: one graph placed at the spine layer, a second reactive primitive two layers lower** — The signal graph (Reactive: Rc<RefCell<Inner>>, generational slots, per-element reader SmallVecs) sits in flui-view (layer 5) behind a non-default `signals` feature. The render and animation layers use a different primitive: flui-foundation's Listenable/ChangeNotifier (layer 1), which is `Send + Sync` and backed by `Arc<Mutex<HashMap<ListenerId, callback>>>`. flui-rendering reaches it through the CustomPainter/FlowDelegate `repaint()` listenable. So FLUI already has two unrelated reactivity mechanisms in two layers, and the render-phase one takes a lock on per-node state. _Relevance:_ Structural. plan.md's open question 'element-level or render-level granularity' can't be answered while the graph lives at layer 5, because flui-rendering (layer 4) and flui-animation (layer 3) can't depend on it. AGENTS.md's 'locks guard shared infrastructure only' rule is already broken by Listenable on the paint path. ([source](crates/flui-view/src/reactive/mod.rs:58-72,161-163; crates/flui-view/Cargo.toml:110,123,173; Cargo.toml:642-645 (`signals` not in default); crates/flui-foundation/src/notifier.rs:46,78,151; crates/flui-foundation/src/notifier_generic.rs:41-45; crates/flui-rendering/src/delegates/custom_painter.rs:9,129-140; crates/flui-foundation/Cargo.toml:78 (layer 1)))
- **Compose: state reads are tracked per phase** — Compose tracks which state is read in each of its three phases (composition, layout, draw) and notifies only the phase that needs to run. A read inside drawBehind or Canvas re-runs only the draw phase. Measure and placement have separate restart scopes. The documented main performance technique is to defer reads into layout or draw lambdas. _Relevance:_ This is the production answer to FLUI's 'element vs render granularity' question: both, with one graph whose subscribers are phase-typed (Element rebuild, RenderObject needs_layout, needs_paint). It supports moving the graph core below flui-rendering and retiring the Arc<Mutex> Listenable path for repaint and animation. That fits H2 (damage and layer caching) directly: an animated colour that repaints without a rebuild. ([source](https://developer.android.com/develop/ui/compose/phases ; https://developer.android.com/develop/ui/compose/performance/bestpractices))
- **Rust reactive libraries all ship the graph as a UI-independent bottom crate** — Leptos ships `reactive_graph` and `reactive_stores` as standalone crates. Dioxus ships `dioxus-signals` on top of `generational-box`. Sycamore rewrote the separate `sycamore-reactive` crate around a single `Root` that manages the graph. Floem ships `floem_reactive`, with the whole runtime in one thread-local Runtime struct. _Relevance:_ This argues for a 'move shared code down a layer' change (AGENTS.md): a realm-owned graph core (arena, node states, propagation, owner disposal) at layer 1–2, with flui-view, flui-rendering and flui-animation each registering a subscriber kind. FLUI's own plans disagree on where it lives: ADR-0074 puts it in flui-view; roadmap.md:766 plans a new crate `flui-state`; the Cargo.toml:72-77 comment says 'there is deliberately NO signals crate'. The topology should settle this in one ADR. ([source](https://docs.rs/reactive_graph/latest/reactive_graph/ ; https://docs.rs/reactive_stores/latest/reactive_stores/ ; https://docs.rs/generational-box/latest/generational_box/ ; https://sycamore.dev/post/announcing-v0-9-0 ; https://lapce.dev/floem/floem_reactive/index.html))
- **Global versus scoped arenas** — Leptos's arena is process-global (`static MAP: OnceLock<RwLock<SlotMap>>`) unless the `sandboxed-arenas` feature swaps in a thread-local one. Floem keeps the runtime in one thread-local. Sycamore uses one singleton Root. FLUI's Reactive is realm-owned: a process-unique graph id on every slot, and `ForeignGraph` errors. _Relevance:_ FLUI's realm scoping is ahead of the market and matches principle 3 (no global state) and multi-window H2. Keep it when moving the core down a layer. The graph must stay a realm resource, not a static, and `cargo xtask`'s ambient-reach ratchet should cover it. ([source](docs/research/state-model-2026.md §2 (quoting leptos reactive_graph/src/owner/arena.rs); https://lapce.dev/floem/floem_reactive/index.html ; crates/flui-view/src/reactive/mod.rs:72-81))
- **Glitch freedom: the push-pull algorithm the market converged on** — The TC39 Signals proposal (Stage 1) gets glitch freedom from push-pull: computeds are evaluated lazily on `.get()`, while writes may notify watchers at once. alien-signals uses push-pull with dirty-flag propagation. It deliberately avoids Array/Set/Map and recursion in its core and reports that algorithmic simplicity beat complex scheduling. Its core was ported into Vue 3.6 and XState. Leptos implements the three-state Clean/Check/Dirty node with `update_if_necessary`. _Relevance:_ ADR-0075 (Proposed) records that FLUI's first Computed prototype had diamond glitches and eager recomputation (docs/adr/ADR-0075-derived-state-and-effects.md 'What the prototype got wrong' 3-4). The graph core should implement mark-then-pull coloring with intrusive links in slab indices (no HashMap per edge). reactive/mod.rs:145-148 uses HashMap<ElementId, SmallVec> today; #1248 tracks the slab form. ([source](https://github.com/tc39/proposal-signals ; https://github.com/stackblitz/alien-signals ; docs/research/state-model-2026.md §2 (leptos graph/node.rs)))
- **Effects: frameworks own scheduling, and it must be a named frame phase** — TC39 leaves effect() out on purpose. It offers only a Watcher with a synchronous notify, because 'Effects inherently tie into scheduling and disposal, which are managed by frameworks'. Leptos runs effects 'on the next tick' after synchronous work. Solid 2.0 (beta 2026-03, RC later) split createEffect into compute and apply phases and made batching microtask-based with `flush()`, calling the result 'fully deterministic'. _Relevance:_ The effects phase belongs to flui-scheduler's frame phases (build → effects → layout → paint), not to flui-testing's pump_frame. ADR-0075 requirement 1 records that the prototype ran effects only in the harness. Solid's compute/apply split maps onto FLUI's synchronous frame path: compute in the effects phase, apply side effects (IO) through the async edge. That keeps 'no async in build/layout/paint'. ([source](https://github.com/tc39/proposal-signals ; docs/research/state-model-2026.md §2 (Leptos Effect docs) ; https://www.infoq.com/news/2026/05/solidjs-2-async/ ; https://github.com/solidjs/solid/discussions/2596))
- **Sources disagree on when a read sees a write (synchronous or batched)** — Solid 2.0 changed so that reads do not reflect a write until the batch flushes (microtask). Leptos, Sycamore and Floem stay synchronous. Compose isolates writes with MVCC snapshots. FLUI's ADR-0074 makes writes synchronous on the value and coalesces only the element scheduling per frame. _Relevance:_ FLUI has to choose explicitly before the H3 freeze: synchronous value plus frame-coalesced invalidation (today), or Solid-style deferred visibility. The choice fixes what the agent protocol and record/replay (G7) observe. Recommendation: stay synchronous; FLUI's frame boundary already gives Solid's determinism for invalidation. Record the choice in the effects ADR. ([source](https://github.com/solidjs/solid/discussions/2596 ; docs/research/state-model-2026.md §6 (Compose MVCC) ; docs/adr/ADR-0074-realm-scoped-signals.md §5.3))
- **Copy arena handles: the ergonomics win and its failure mode** — Sycamore 0.9 made signals `'static + Copy` specifically to drop `.clone()` noise and lifetimes. Dioxus signals are Copy through generational-box. Leptos offers both an arena Copy `RwSignal` and a refcounted `ArcRwSignal`. The cost is run-time failure. Leptos apps panic with 'Tried to access a reactive value that has already been disposed' when unscoped spawn_local tasks or in-flight effects outlive their owner. Dioxus panics when a read guard is held across a write or an await. _Relevance:_ FLUI's closure-scoped `with`, `Released`/`Reentrant` errors and value-on-loan design avoids Dioxus's guard-across-write panic (ADR-0074 §5.3). The async edge is the risk: the planned async Task API must be owner-scoped (cancelled at element unmount) so a task can't read a released slot. `get` still panics on a stale handle; for Stable tier consider making async-context reads `try_`-only. ([source](https://sycamore.dev/post/announcing-v0-9-0 ; https://docs.rs/reactive_graph/latest/reactive_graph/signal/struct.ArcRwSignal.html ; https://github.com/yurvon-screamo/origa/pull/631 ; https://github.com/akarras/ultros/pull/1610 ; https://docs.rs/dioxus-signals/latest/dioxus_signals/struct.Signal.html))
- **Rust language: ergonomic ref-counting is unresolved** — The Rust project goal names Dioxus, Sycamore and Leptos as motivation. An experimental nightly RFC #3680 (`.use`, `use ||` closures, a UseCloned trait) competes with an automatic-cloning alternative, and the lang team has not chosen between them. _Relevance:_ Copy arena handles are FLUI's hedge against a language feature that may land before or after 1.0. Keep Signal Copy, but don't design Stable APIs that assume Rc clones will stay noisy. `SignalSender` and future Arc-style handles should follow whatever trait the language adopts, so they need an Evolving-tier marker. ([source](https://goals.rust-lang.org/2025h2/ergonomic-rc.html))
- **Reactive collections (A8): Stores with path-scoped triggers** — Dioxus Stores 'lazily create signals for each field/member of the data structure as needed', derive `Store` for scoped accessors, and handle Vec and HashMap so that only subscribers to the changed part re-render. Leptos reactive_stores keeps an `Arc<RwLock<T>>` plus a trigger map per field path. 'Updating a field will notify its parents and children, but not its siblings'. Keyed access is supported, and `Patch` replaces a whole value while notifying only the changed fields. Compose's SnapshotStateList gives element-level invalidation. Solid 2.0 stores made setters draft-first. _Relevance:_ A8 should be a derive in flui-macros (layer 0) over path-keyed triggers in the graph core, not N nested Signal<T>. Keyed collection triggers must line up with the keys FLUI's reconciler and virtualised lists already use, or 100k-row lists (H2) will still re-diff. A `Patch`-style diff-on-assign is how server-pushed or A2UI data (H1) lands without whole-tree invalidation (the A2UI link is a hypothesis). ([source](https://docs.rs/dioxus-stores/latest/dioxus_stores/ ; https://docs.rs/reactive_stores/latest/reactive_stores/ ; https://medium.com/@suraj.raj/improve-android-app-performance-using-snapshotstatelist-in-jetpack-compose-7c7b709a4fa3 (secondary source) ; https://github.com/solidjs/solid/discussions/2596))
- **SwiftUI @Observable: per-property tracking works, collections are the weak spot** — Observation tracks property access in `body` and invalidates only on the properties read (SE-0395, WWDC23). Practitioners report that in-place array mutations (append, swapAt, subscript) on observable models cause view re-initialisation, and that ForEach tracks by id while Observation tracks by reference. _Relevance:_ Collection identity (key) and observation identity (slot) must be the same concept in FLUI, or A8 reproduces this mismatch. Pin it with a test: moving a row keeps its element and does not rebuild its siblings. ([source](docs/research/state-model-2026.md §5 ; https://github.com/pointfreeco/swift-composable-architecture/discussions/2973 ; https://developer.apple.com/forums/thread/782576))
- **Reader-count guidance leaks into the user API** — ADR-0074 measured 1.3–1.8 µs extra per reader on fan-out (600 readers: 1.77 ms against 1.01 ms with setState). It tells users to pick Signal under about 50 readers and InheritedView with field masks above that. It keeps two registries (signal readers and InheritedBehavior dependents) and leaves their unification to #1254. _Relevance:_ Compose, SwiftUI and Solid don't ask authors to choose a primitive by reader count; that is an implementation cost exposed as API guidance. Batched scheduling (#1249) and one registry (#1254) belong in the graph-core redesign before signals reach Stable tier (plan.md Governance), or the guidance freezes into the 1.0 contract. ([source](docs/adr/ADR-0074-realm-scoped-signals.md §5.5, §5.10, §8.1))
- **Elm/iced and Xilem: the counter-position, and what it buys** — iced 0.14 (Dec 2025) kept the Elm architecture and added reactive rendering and time-travel debugging. Time travel works because state is mutated only in `update` in response to a Message, so any state can be rebuilt from the initial state and the message log. Xilem remains 'experimental' with a React/SwiftUI/Elm-style view tree diffed over Masonry's retained widgets and uses memoization rather than signals. GPUI uses coarse per-entity `cx.notify()`/`observe` plus typed `subscribe` events. _Relevance:_ Signals lose the Elm property that every mutation is an observable, replayable message. FLUI's bets on record/replay (G7), agent inspection over MCP (principle 4) and hot reload want it back. Route every Signal write through the realm (it already requires `&Reactive`, ADR-0074 §5.1) and expose a write-journal hook (slot id, element, frame) to devtools and flui mcp. Hypothesis: that recovers most of iced's time-travel value without Elm's ceremony. ([source](https://github.com/iced-rs/iced/releases/tag/0.14.0 ; https://byteiota.com/iced-0-14-rust-gui-gets-reactive-rendering-time-travel/ (secondary source) ; https://github.com/linebender/xilem ; https://docs.rs/gpui/latest/gpui/struct.Context.html))
- **Cross-thread writes: typed in FLUI, a hidden panic elsewhere** — In Floem, setting a signal from another thread panics on an unwrap of None inside signal.rs; users discover the ext_event channel helpers only after hitting it. Leptos LocalStorage panics on cross-thread access. FLUI's Signal is `!Send`; cross-thread writes go through `detach()` to a `Send` SignalSender and `UiCommand::SignalWrite`, but both are `pub(crate)` until an async Task API exists. _Relevance:_ FLUI's compile-time split (Signal `!Send`, SignalSender `Send`) follows 'make rules types'. The public surface waits on the runtime's async model (plan.md Runtime row: explicit Task/Worker, tokio optional). Treat 'async Task that vends SignalSender and is owner-scoped' as a single runtime-state contract, not two tracks. ([source](https://github.com/lapce/floem/issues/534 ; docs/research/state-model-2026.md §2 ; docs/adr/ADR-0074-realm-scoped-signals.md §5.8))
- **Signal-aware widget props** — Leptos's `MaybeProp` wraps either a static value or a signal (an `Option<Signal<Option<T>>>` with flattened getters), so component libraries accept both without consumers distinguishing them. Dioxus components take read-only signals as props. _Relevance:_ C1 as amended allows catalog widgets to accept Signal<T> inputs (docs/FOUNDATIONS.md:91), but the catalog doesn't yet and the feature is off by default (Cargo.toml:642-645). Material, Cupertino and community packages (H4) will each invent a prop shape unless core defines a `MaybeSignal`-like input type before the catalog grows. Treat it as a Stable-tier API decision. ([source](https://docs.rs/leptos/latest/leptos/prelude/struct.MaybeProp.html ; https://docs.rs/dioxus-signals/latest/dioxus_signals/struct.Signal.html))
- **Doc and contract drift on state (evidence of a topology problem)** — FOUNDATIONS C1 still opens 'the sole canonical state model' and says catalog crates 'never take a dependency on a signals crate', then appends the ADR-0074 amendment. The root Cargo.toml comment says 'contract C1 locks the catalog to the setState/Inherited model' and 'there is deliberately NO signals crate'. The roadmap plans a new `flui-state` crate. _Relevance:_ By AGENTS.md's ADR policy, silent disagreement between code, ADRs and manifests is a defect. The state layer's home (module in flui-view, new crate, or core moved down a layer) needs one ADR that supersedes the placement clause and cleans the C1 text and the manifest comment together. ([source](docs/FOUNDATIONS.md:89-91; Cargo.toml:72-77; C:/Users/vanya/AppData/Local/Temp/claude/D--flui/bbb28042-f972-4a10-8e94-731819e26161/scratchpad/roadmap.md:766 (roadmap.md, 'новый крейт flui-state (experimental)')))

## Pitfalls others hit

- Leptos: a process-global arena (OnceLock<RwLock<SlotMap>>) forced a later `sandboxed-arenas` feature for isolation (docs/research/state-model-2026.md §2).
- Leptos 0.7: 'Tried to access a reactive value that has already been disposed' panics from unscoped spawn_local and in-flight effects outliving their owner (https://github.com/yurvon-screamo/origa/pull/631, https://github.com/akarras/ultros/pull/1610).
- Dioxus: holding a read guard across a write, or a read across an .await, panics through generational-box borrow checks (https://docs.rs/dioxus-signals/latest/dioxus_signals/struct.Signal.html).
- Floem: using a signal from another thread panics on an unwrap(None) with no type-level hint; the channel helpers are found only after the crash (https://github.com/lapce/floem/issues/534).
- Solid: after years in production, 2.0 broke the effect API (split compute/apply) and batching semantics (microtask, reads defer until flush) to get deterministic scheduling (https://www.infoq.com/news/2026/05/solidjs-2-async/). Effect scheduling is the part most likely to need a breaking redesign, so it must be settled before the API freeze.
- Sycamore: went through three reactivity designs (clone-heavy, then lifetimes plus cx, then 'static Copy with a single Root) before settling (https://sycamore.dev/post/announcing-v0-9-0).
- SwiftUI Observation: in-place collection mutations and the mismatch between ForEach ids and object-reference observation cause view re-init and missed refreshes (https://github.com/pointfreeco/swift-composable-architecture/discussions/2973).
- Flutter: shipping only setState, InheritedWidget and ValueNotifier pushed application state into a fragmented ecosystem (docs/research/state-model-2026.md §8; ADR-0074 §1.1).
- FLUI itself: flui-reactivity (a global runtime, Arc<Mutex<T>>, hook-index identity) was removed with zero consumers (ADR-0074 §3; Cargo.toml:72-77). The first Computed/Effect prototype had diamond glitches, graph poisoning on panic, and effects that ran only in the test harness (ADR-0075).

## Patterns to adopt

- Move the reactive graph core (realm-owned arena, node states, propagation, owner disposal, write journal) down to layer 1–2, following 'shared code moves down a layer'. flui-view registers an Element subscriber; flui-rendering registers needs_layout and needs_paint subscribers (Compose's per-phase reads, https://developer.android.com/develop/ui/compose/phases). Retire the Arc<Mutex> Listenable repaint path onto it. Needs an ADR superseding ADR-0074's placement.
- Use push-pull three-state (Clean/Check/Dirty) propagation with lazy computeds and intrusive slab-index links. No HashMap per edge, no recursion (alien-signals, Leptos reactive_graph, TC39 Signals).
- Make effects a named phase of the binding frame in flui-scheduler (build → effects → layout → paint), called by every runner, with compute and apply split so side effects leave through the async edge (Solid 2.0; ADR-0075 requirements 1, 5, 6).
- Build reactive collections (A8) as a `#[derive(Store)]` in flui-macros over path-keyed triggers: parents and children notified, siblings not; keyed collection access tied to reconciler keys; a Patch-style diff-on-assign for bulk and server-pushed data (Dioxus Stores, Leptos reactive_stores).
- Keep realm-affine `!Send` signals with a typed `Send` sender, and ship them together with an owner-scoped async Task API that is cancelled at unmount (avoids the Floem and Leptos failure modes).
- Record every signal write through the realm into a journal (slot, writer, frame) exposed to devtools and flui mcp and used by record/replay (G7). This recovers iced's time-travel property within FLUI's own protocol (hypothesis; iced 0.14 release notes).
- Define one signal-or-value prop type (like Leptos MaybeProp) in core before Material, Cupertino and community catalogs grow, so every package accepts reactive inputs the same way.
- Unify the signal reader registry and the InheritedView field-mask registry, and batch fan-out scheduling (#1249, #1254), so 'choose by reader count' disappears from user guidance before Stable tier.

## Patterns to avoid

- Process-global or thread-local reactive runtimes (Leptos default arena, Floem thread-local Runtime, the old flui-reactivity SIGNAL_RUNTIME). They violate principle 3 and multi-window realms.
- Hook-order identity (use_signal by call index). ADR-0074 §5.7 already rejects it; keep it out of the catalog and macros too.
- Arc<Mutex<...>> notifier state touched on the layout and paint path (the current flui-foundation Notifier). It adds per-frame locking contrary to AGENTS.md's frame-path rule.
- Two unrelated reactive primitives at different layers with separate registries (today's Listenable and Signal, plus InheritedBehavior dependents). Each new consumer (animation, render, A2UI data) would pick a different one.
- Effects driven only by a test harness, or scheduled implicitly by writes. Effects must be a framework frame phase (TC39 rationale; ADR-0075).
- Collections modelled as nested Signal<Vec<Signal<T>>> or whole-value signals. That gives either whole-list invalidation or identity mismatch with keys (SwiftUI ForEach versus Observation).
- Freezing signal semantics (sync versus batched visibility, effect API, prop shape) into Stable tier before an H2 workload (100k rows, 1 MB editor) has exercised them. Solid needed a major version to fix exactly these.
- Letting the state layer's placement drift across FOUNDATIONS C1, the Cargo.toml comment, ADR-0074 and the roadmap's planned flui-state crate without one superseding ADR.
