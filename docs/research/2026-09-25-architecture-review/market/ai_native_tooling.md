# Market survey: AI-native UI frameworks and tooling (2026): how a framework should expose catalog, semantics, diagnostics and actions to agents — lessons for FLUI's global architecture, crate topology and ecosystem

_Raw output of the `market:ai_native_tooling` agent (2026-09-25). Unedited; each claim carries the source the agent cited._

## Findings

- **MCP core spec 2026-07-28 (stateless)** — The 2026-07-28 MCP revision removes protocol-level sessions and the initialize handshake. Cross-call state must use explicit server-minted handles passed as ordinary tool arguments. Tasks moved out of core into an extension. Roots, Sampling and Logging are deprecated. Tools/list should be ordered deterministically. inputSchema/outputSchema now accept any JSON Schema 2020-12 keyword, and structuredContent accepts any JSON value. _Relevance:_ This supports ADR-0080's shape: session handles w3/e12/s2, typed replies with an outputSchema, and a fixed error-code vocabulary (docs/adr/ADR-0080-agent-protocol-desktop-contract.md:31-44, 67-90). Two consequences. First, handles must stay valid across calls without any MCP session, so the handle table belongs to the backend (the realm or the desktop worker), not to the transport. Second, FLUI should not build on Sampling or Logging, and should treat tasks as an optional extension. Diagnostics should go out as OpenTelemetry/tracing, not as MCP logging. ([source](https://modelcontextprotocol.io/specification/2026-07-28/changelog (Major changes 1,2,6,7; Minor 3,10; Deprecated 1)))
- **MCP Apps (SEP-1865, Final)** — MCP Apps let a server declare ui:// resources that a tool links to through _meta.ui.resourceUri. The host renders them in a sandboxed iframe, and they talk JSON-RPC over postMessage. The only content type is text/html;profile=mcp-app; other formats are deferred and native rendering is not addressed. _meta.ui.visibility ['app'] hides a tool from the model. _Relevance:_ MCP Apps is the HTML/iframe route to agent-generated UI and cannot carry a native wgpu renderer. The plan's 'no webview hybrids' bet (plan.md, Ставки продукта) rules it out as FLUI's runtime generative-UI path, so A2UI stays the right H1 choice. A cheap interop route does exist: a FLUI wasm/web build could be served as a ui:// resource. That makes it a web-platform deliverable, not a core contract. ([source](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx ; https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp))
- **A2UI v0.9/v0.9.1** — A2UI is framework-agnostic. The agent streams createSurface, updateComponents (a flat adjacency list of components with ID references), updateDataModel (bound by JSON Pointer) and deleteSurface. The client sends action and error messages back. Catalogs are JSON Schema documents with URI catalogIds that the client owns. v0.9 adds catalog negotiation, where the client advertises its catalogs and the agent locks one per surface. Functions are named, catalog-declared references (validation, formatting), so the server never sends code. Validation errors carry JSON-pointer paths so the model can correct itself. 'Standard' was renamed 'Basic' so developers bring their own components. _Relevance:_ This decides the G6 shape. For 'G6 catalog = A2UI catalog' (plan.md, extension points) to hold, G6 must emit JSON Schema per component with stable URI catalog IDs and versioning. It also needs a data model separate from the view structure and a registry of named functions. Reactive state that is realm-scoped and addressable by path (ADR-0074 signals) is what an A2UI renderer binds to, so signals need a path/serde projection. The flat-ID component list lines up with FLUI's ID model. flui-a2ui can therefore be a thin interpreter crate at the widget-catalog layer or above, if the catalog metadata is generated from the widgets themselves. ([source](https://a2ui.org/specification/v0.9.1-a2ui/ ; https://developers.googleblog.com/a2ui-v0-9-generative-ui/ ; https://www.infoq.com/news/2026/07/google-a2ui-genui/))
- **Flutter GenUI SDK (alpha, May 2026 redesign)** — GenUI builds a surface from the app's own widget catalog (CatalogItems carrying a schema and a builder). The May 2026 redesign removed ContentGenerator, moved the schema from API-level constraints into system prompts (a 'prompt-first' PromptBuilder), renamed the core types (SurfaceController, A2uiTransportAdapter, Conversation), and left LLM wiring to the developer. The trade-off: more boilerplate, and dependence on the model following instructions rather than on strict constrained output. The package is alpha. _Relevance:_ Flutter separated the renderer and catalog (framework side) from the LLM or transport (app side) and dropped its provider-coupled generator. flui-a2ui should do the same from the start: surface controller plus catalog plus transport adapter trait, with no LLM client in core. The prompt text should be generated from the same catalog metadata as G6. ([source](https://flutter.dev/blog/new-updates-to-a2ui-and-flutters-genui-package ; https://docs.flutter.dev/ai/genui ; https://pub.dev/packages/genui))
- **egui 0.35 inspection protocol + egui_mcp** — egui 0.35 adds egui_inspection, a strictly request→response wire protocol (GetTree = the AccessKit tree, HandleEvents, Screenshot, Resize) using MessagePack over TCP on 127.0.0.1:5719. PROTOCOL_VERSION/MAGIC constants version it. eframe starts it when EGUI_INSPECTION=1. The docs warn it has no authentication. egui_mcp is a separate MCP server that consumes this protocol. A kittest inspector and frame streaming are planned consumers, and the design aims to serve any AccessKit-based Rust UI. _Relevance:_ This is the closest Rust precedent for G1/G2, and it takes the topology the roadmap describes (roadmap.md:239 'semantics + inspector + test driver = one protocol, CLI and MCP thin clients'). The protocol types live in a small shared crate. The app side is a plugin attached through an environment variable. MCP is an out-of-process consumer, and the vocabulary is AccessKit. FLUI's pieces exist but are scattered: flui-devtools (layer 9, 2.5k LOC, inspector counters and timeline only, no transport; crates/flui-devtools/Cargo.toml:18-40), flui-testing::a11y (AccessKit queries; crates/flui-testing/src/a11y.rs:1-30), and tools/desktop-mcp (rmcp, with no flui dependency; tools/desktop-mcp/Cargo.toml:31). Also, kittest may make an AccessKit-generic inspector available for free if flui-semantics keeps emitting standard accesskit::TreeUpdate. ([source](https://docs.rs/egui_inspection/latest/egui_inspection/ ; https://newreleases.io/project/github/emilk/egui/release/0.35.0 ; https://github.com/rerun-io/kittest_inspector))
- **Slint MCP (July 2026)** — Slint's MCP server is compiled into the application rather than run as an external service. It lists windows, queries element trees and accessibility properties, clicks, drags, sends key events, and takes screenshots in headless mode (SLINT_BACKEND=headless). Slint frames it as giving the AI the real layout tree instead of guessing from source or pixels. The post names no transport or security details. _Relevance:_ This sits at the opposite end of the topology from egui, which runs MCP out of process over its own protocol. Sources disagree here. For FLUI, putting MCP in process would pull rmcp and serde into every app build and into the framework's layer graph. Out of process, with a versioned devtools wire protocol, keeps the core free of MCP and lets DevTools, the CLI and tests share one transport, which is principle 4 in plan.md. The headless-backend screenshot point matters, though: FLUI's E7 CPU reference renderer should also be the agent's screenshot path in CI. ([source](https://slint.dev/blog/slint-and-AI-MCP))
- **Dart & Flutter MCP server / DTD** — The Dart and Flutter MCP server exposes get_widget_tree, get_runtime_errors and hot_reload. These require connect_dart_tooling_daemon first: the MCP server is a client of the Dart Tooling Daemon, the same protocol the IDEs and DevTools use. _Relevance:_ Flutter confirms the layering: one tooling daemon/protocol, with MCP as a thin adapter over it. It also sets a baseline tool set for G2 of tree, runtime errors (FLUI's layout.overflow and diagnostics events, roadmap.md:309) and hot reload. flui-cli currently has no devtools or mcp subcommand (crates/flui-cli/src/main.rs:103 Commands enum; commands/ holds analyze, build, clean, completions, create, devices, doctor, emulators, format, ios, platform, run, test, upgrade). ([source](https://dart.dev/tools/mcp-server ; https://startdebugging.net/2026/05/dart-flutter-mcp-server-claude-code-cursor/))
- **Playwright MCP accessibility snapshots** — Playwright MCP returns a YAML-style accessibility snapshot with refs (e5), valid until the page changes. Tools take refs in preference to selectors and return a fresh snapshot after each action. browser_snapshot takes target (subtree), depth and boxes options. Screenshots are kept for genuinely visual problems. Third-party measurements put snapshots at roughly 10-100x fewer tokens than screenshots. _Relevance:_ ADR-0080 already adopts the outline format '- role "name" [ref=e12] …' with scope, max_depth and max_nodes (ADR-0080:67-74). The lesson for the in-process backend is to return the post-action tree or diff from every action tool, so the agent does not need a separate read round trip. The same outline text should be the semantic-golden file format for G3, so tests and agents read one artifact. ([source](https://playwright.dev/mcp/snapshots ; https://dev.to/pointchecknote/browser-automation-with-claude-playwright-mcp-why-accessibility-snapshots-beat-screenshots-2pke ; https://qaskills.sh/blog/playwright-mcp-accessibility-snapshots-reference))
- **Chrome DevTools MCP** — Chrome DevTools MCP exposes CDP capabilities to agents: performance traces (one-shot and session-scoped) with analysis, console messages with source-mapped stack traces, network inspection, and CPU and network throttling. The agent can measure, diagnose, fix and re-measure in one loop. _Relevance:_ Frame timing and trace export belong on the agent protocol, not only in a human DevTools. flui-devtools already exports Chrome-trace JSON from FrameSnapshot (crates/flui-devtools/Cargo.toml:25-40). That exporter should become a G1 method ('record trace for N frames'), which also feeds H2 performance work run by agents. ([source](https://github.com/ChromeDevTools/chrome-devtools-mcp ; https://developer.chrome.com/blog/chrome-devtools-mcp))
- **Xcode 26.3 MCP / Android CLI + AppFunctions** — Xcode 26.3 ships a built-in MCP server (xcrun mcpbridge, about 20 tools) that includes RenderPreview, which returns a PNG of any #Preview. Android's 2026 Android CLI exposes Compose preview rendering, semantic symbol resolution and end-to-end 'Journeys' UI tests to any agent. Android AppFunctions let apps act as on-device MCP servers that contribute tools to assistants. _Relevance:_ Platform vendors have moved the agent entry point into the toolchain CLI, which matches plan.md's 'flui CLI is the single entry point … mcp'. 'Render a preview of this View headlessly' is table stakes: FLUI needs a preview registry (per-widget example entries), which G6 examples could supply, rendered through the CPU reference renderer. AppFunctions points to an H1 PlatformCapability: apps built with FLUI exposing their own actions to OS assistants. That is a separate protocol role (app-as-tool) from framework introspection and should not be conflated with it. ([source](https://rudrank.com/exploring-xcode-using-mcp-tools-cursor-external-clients ; https://jasonmoon.dev/blog/2026-03-05-xcode-26-mcp-agentic-coding ; https://android-developers.googleblog.com/2026/05/17-things-android-developers-google-io.html))
- **Storybook MCP + component manifests** — Storybook 10.3 generates /manifests/components.json from static analysis of stories plus prop-type extraction. Each entry carries id, name, import path, stories as code snippets, props with types, descriptions and defaults, and JSDoc. MCP tools serve it so agents reuse existing components with fewer tokens. JSDoc on components and props is the main quality lever. _Relevance:_ This is the direct template for G6 ('machine-readable widget catalog (JSON: props, semantics, examples) generated from rustdoc', roadmap.md:559). The manifest should be generated from the code, with examples that compile as tests, and served both as a file and as an MCP tool. FLUI's deny(missing_docs) is what makes the prose part useful. ([source](https://storybook.js.org/docs/ai/manifests ; https://storybook.js.org/docs/ai/mcp/overview))
- **rustdoc JSON / cargo doc for agents** — rustdoc's JSON output is still unstable (nightly); `cargo doc --output-format=json` landed as an unstable option in 2026. cargo issue #16720 proposes `--output-format=markdown`, built on rustdoc JSON, for version-matched agent docs, and cites Vercel data (task success rising from 53% to 100% with exact pinned API surface). It is labelled S-blocked-external / S-needs-design. _Relevance:_ Plan item G6 reads 'generated from rustdoc', but that ties the catalog to nightly and to a format that changes. A derive or attribute on View structs, next to the existing flui-macros View derives, would emit catalog metadata (props, JSON Schema, semantics role, example IDs) on stable, with the same source feeding A2UI and G6. rustdoc JSON can stay an optional nightly enrichment for prose. ([source](https://github.com/rust-lang/cargo/pull/17025 ; https://github.com/rust-lang/cargo/issues/16720 ; https://crates.io/crates/rustdoc-types))
- **llms.txt** — Adoption is 10-50% depending on site cohort, but a traffic study found almost no AI-lab crawler fetches. Chrome calls it a 'temporary crutch' for coding tools. It is still recommended for developer and API docs: Anthropic and OpenAI use it, and Lighthouse's Agentic Browsing audit checks for it. The MCP site itself serves /llms.txt as its doc index. _Relevance:_ Sources disagree on its value. It is cheap and worth keeping (D:\flui\llms.txt exists, 69 lines), but it must not be the main machine-readable surface. Agents working in a FLUI repo get more from version-matched catalog and API data via the CLI or MCP, and from a compressed index in the always-loaded context (next finding). ([source](https://ahrefs.com/blog/llmstxt-study/ ; https://www.digitalapplied.com/blog/llms-txt-in-practice-adoption-evidence-2026 ; https://modelcontextprotocol.io/specification/2026-07-28/changelog (page header points to /llms.txt)))
- **Passive context vs tool retrieval (Vercel evals)** — In Vercel's evals, an 8KB compressed docs index embedded in AGENTS.md reached a 100% pass rate. Skills reached at most 79%, and in 56% of cases the agent never invoked the skill. _Relevance:_ This conflicts with a tools-only design such as Storybook's, where the manifest is behind MCP. The answer for FLUI is both. `flui create` templates should ship an AGENTS.md carrying a compressed catalog index (generated from G6 metadata, versioned with the crate). MCP tools then serve depth on demand. It also shows the metric 'agent scenarios 0→3→10' (plan.md, Метрики) needs an eval harness, not only a demo. ([source](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals))
- **Anthropic tool-design guidance** — Anthropic recommends pagination, filtering and truncation with sensible defaults, a response_format parameter ('concise' vs 'detailed'), a search for the smallest high-signal token set, and notes Claude Code caps tool responses at 25k tokens by default. _Relevance:_ ADR-0080's max_depth, max_nodes, truncated and format: outline|json already follow this. Every G1 read method should carry the same bounds: element tree, render tree, layer tree, diagnostics and frame traces. The render and diagnostics trees (DiagnosticsNode::to_string_deep, used in tests/agent_workflow.rs) are currently unbounded strings. ([source](https://www.anthropic.com/engineering/writing-tools-for-agents ; https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))
- **Golden testing determinism (Flutter/Alchemist, Roborazzi)** — Cross-OS text rasterization breaks pixel goldens. Flutter defaults tests to the Ahem font. Alchemist keeps two golden sets: readable platform goldens for local use, and CI goldens with text drawn as blocks so they are OS-independent. Roborazzi writes a *.uitree.json of Compose semantics and view hierarchy next to each screenshot, in a grep-first one-node-per-line format, and has fixed non-deterministic toString in dumps. _Relevance:_ This supports the E7/G3 decision: a CPU reference renderer with an embedded font, and no cross-OS pixel parity promised in production (roadmap.md:475-477, 544-546). Two refinements. First, the semantic golden should be the default and cheapest assertion, with pixels opt-in, and every dump must be deterministic: stable IDs, sorted properties, no Debug-derived pointers. Second, one line per node lets agents grep. FONT_SYSTEM as a process global (context.md) undermines deterministic goldens under nextest parallelism; this is further evidence for per-realm text. ([source](https://github.com/Betterment/alchemist ; https://api.flutter.dev/flutter/flutter_test/matchesGoldenFile.html ; https://github.com/takahirom/roborazzi/releases))
- **AG-UI vs A2UI vs MCP Apps (landscape)** — Commentators describe the stack as MCP (agent↔tools), A2A (agent↔agent), AG-UI (agent↔frontend event/state transport) and A2UI (declarative UI payload), with MCP Apps as the iframe/HTML alternative. Reception of A2UI is mixed: skeptics cite security, impersonation and 'disposable UI' homogenization, while CopilotKit calls v0.9 ready for the mainstream. Vercel json-renderer and Oracle Agent Spec also compete. _Relevance:_ Generative-UI formats are not settled. flui-a2ui should be an official package outside the core semver surface ('Evolving' tier), with a transport-adapter seam so AG-UI, A2A and MCP can each carry it. The catalog metadata it consumes is the durable core contract. ([source](https://www.copilotkit.ai/ag-ui-and-a2ui ; https://a2ui.org/introduction/agent-ui-ecosystem/ ; https://www.infoq.com/news/2026/07/google-a2ui-genui/))
- **MCP localhost security** — The MCP TypeScript and Python SDKs shipped HTTP servers with DNS-rebinding protection off by default (GHSA advisories). CVE-2025-49596 (MCP Inspector RCE) was exploitable from the browser. The MCP security best practices recommend stdio for local servers, Origin/Host validation, and auth even on localhost. egui_inspection binds loopback with no auth and warns against non-loopback binding. _Relevance:_ An in-app devtools port is a remote-control surface for a real app. G1 must be off in release builds by construction: a cargo feature plus a runtime opt-in, never only an environment variable, following the plan's 'make rules types' stance. It should prefer a pipe, a Unix socket or a Windows named pipe with a per-launch token over TCP. `flui mcp` should use the stdio transport. This belongs in the ADR that settles ADR-0080's open 'in-process backend's transport' (ADR-0080 'Not decided here'). ([source](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-w48q-cv73-mx4w ; https://www.oligo.security/blog/critical-rce-vulnerability-in-anthropic-mcp-inspector-cve-2025-49596 ; https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices ; https://docs.rs/egui_inspection/latest/egui_inspection/))

## Pitfalls others hit

- An MCP server built on protocol features that were later removed: 2026-07-28 dropped sessions, the initialize handshake, ping, logging/setLevel and resource subscribe, moved tasks to an extension and deprecated Sampling, Roots and Logging (modelcontextprotocol.io 2026-07-28 changelog). FLUI should use only tools, structured output and resources, and keep the handle state in its backend.
- The GenUI SDK was redesigned at alpha: ContentGenerator removed, types renamed, the schema moved from API constraints to prompts (flutter.dev May 2026 blog). Coupling the generative-UI renderer to an LLM provider API forced the break.
- Local debug and MCP HTTP ports shipped with DNS-rebinding protection off, and MCP Inspector had a browser-reachable RCE (GHSA-w48q-cv73-mx4w, CVE-2025-49596). egui_inspection has no auth at all.
- Pixel goldens broke across macOS and Linux CI because of font hinting and antialiasing. The industry answers are the Ahem font or two golden tiers (Alchemist), which confirms that FLUI's CPU reference renderer must own its font.
- Non-deterministic tree dumps (toString fallbacks) made semantic goldens flaky in Roborazzi until fixed.
- Relying on agents to invoke optional tools or skills: in Vercel's evals the skill was never invoked in 56% of cases, and passive AGENTS.md context won 100% vs 79%.
- Screenshot-first agent loops cost 10-100x more tokens and need vision models (Playwright MCP sources, Slint blog); Slint and Playwright both moved to the tree first.
- llms.txt treated as a strategy: widely published and rarely fetched (Ahrefs, 137k sites).
- Catalog generation tied to unstable rustdoc JSON: cargo-public-api has to keep a compatibility matrix against nightly versions.
- Legacy recorders that stamped events with wall-clock time and dropped timing; FLUI already replaced one (crates/flui-testing/src/replay.rs:1-25). This is the same trap every record/replay tool hits.

## Patterns to adopt

- One wire protocol with many thin clients, as egui_inspection and egui_mcp do, as DTD does for the Dart MCP server, and as roadmap.md:239 states. Define the protocol types (requests, replies, error codes, AccessKit-vocabulary nodes, handles) in one small serde-only crate low in the graph. Implement the backend in a realm-side plugin, with DevTools UI, `flui mcp`, `flui test` and tools/desktop-mcp as clients.
- Move ADR-0080's contract (AccessibilityBackend at tools/desktop-mcp/src/a11y/mod.rs:498, the reply and error types) out of the tools/ binary into that shared crate. Under the layer rule, a crate may never depend on a tool (Cargo.toml:88-90), so today the in-process FLUI backend cannot implement the trait ADR-0080 names as its extension point.
- Use AccessKit TreeUpdate as the one semantics interchange: flui-semantics already emits it unconditionally (crates/flui-semantics/Cargo.toml:35-38), and flui-testing::a11y deliberately has no second vocabulary (crates/flui-testing/src/a11y.rs:1-10). This also keeps FLUI compatible with kittest and future AccessKit-generic inspectors.
- Use the ref-annotated outline format (ADR-0080:67-74, the Playwright aria snapshot) for both the agent reply and the committed semantic golden file. Make it deterministic, one node per line (Roborazzi uitree), and have every action return the post-action tree or diff.
- Generate a single catalog source per View from code on stable Rust (derive/attribute metadata next to flui-macros), with JSON Schema props, semantics role, examples that compile as tests, and docs. From it derive (a) the G6 JSON manifest in the Storybook components.json style, (b) the A2UI catalog under a URI catalogId with versioning, (c) the GenUI-style prompt text, (d) the compressed index in `flui create`'s AGENTS.md (Vercel), and (e) llms.txt.
- A2UI-ready state: a JSON-Pointer projection of realm-scoped signals (ADR-0074), a registry of named pure functions (validation and formatting) declared in the catalog, and a surface controller that runs in the realm. The LLM client and transport stay outside core behind an adapter trait, following GenUI after May 2026.
- Bounded reads everywhere (scope, depth, max nodes, truncated, concise|detailed) per Anthropic's tool guidance. Apply them to the element, render and layer trees, diagnostics and traces, not only semantics.
- Diagnostics and frame traces as structured events with stable codes (layout.overflow and similar, roadmap.md:309), exported as OpenTelemetry/Chrome trace. This follows Chrome DevTools MCP and the MCP deprecation of Logging in favour of OTel.
- Headless preview rendering as a first-class tool (Xcode RenderPreview, Android CLI Compose previews), backed by the E7 CPU renderer and the catalog's example entries.
- Record/replay as a portable, versioned, virtual-clock event log in the same protocol types, so an agent's reproduction file and a test fixture are the same artifact (G7). Extend the existing PointerScript replay (crates/flui-testing/src/replay.rs) to realm-level input, IME and time.
- Security by type and feature: devtools protocol compiled out of release builds, loopback or pipe transport with a per-launch token, and stdio for `flui mcp`.
- Keep generative-UI and agent-protocol packages outside the Stable API tier (the Evolving tier in plan.md governance), because A2UI, AG-UI and MCP Apps are still moving; freeze only the catalog metadata and semantics vocabulary.

## Patterns to avoid

- Embedding an MCP server (rmcp/serde/JSON-RPC) inside framework crates or every app build, as Slint does. It pulls tooling dependencies into the layer graph and binds the core to one agent-protocol version; keep MCP in `flui mcp` or tools.
- A separate test-only or agent-only semantics vocabulary alongside AccessKit.
- Screenshots as the primary agent observation channel; keep them for visual checks.
- MCP Apps (HTML iframe) as FLUI's generative-UI runtime; it contradicts the no-webview principle. It is acceptable only as an optional web-build interop.
- Generating the catalog only from rustdoc JSON (nightly, format churn); treat it as optional enrichment.
- Relying on llms.txt or on-demand skills as the main way agents learn FLUI.
- Coupling flui-a2ui to a specific LLM provider or transport (Flutter had to undo this).
- Unauthenticated TCP debug ports enabled by environment variable alone in shipped binaries (egui_inspection's documented risk; the MCP SDK DNS-rebinding advisories).
- Designing on MCP sessions, Sampling, Logging or server-initiated requests, all removed or deprecated in 2026-07-28; use explicit handles and multi-round-trip results.
- Unbounded or non-deterministic tree dumps (DiagnosticsNode::to_string_deep as an agent reply, Debug-derived output in goldens).
- Scattering the protocol across flui-devtools (layer 9, no transport), flui-testing::a11y (layer 6), flui-cli (no devtools/mcp command) and tools/desktop-mcp (no flui dependency) with no shared type crate. Today they are four partial implementations of principle 4 (hypothesis: they will drift unless consolidated before G1 lands).
