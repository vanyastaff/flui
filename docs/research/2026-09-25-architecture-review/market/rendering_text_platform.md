# Market survey: Market survey: rendering, text and platform stacks 2025-2026 (Vello CPU/GPU, Parley/HarfRust/fontique/glifo, cosmic-text/glyphon, Skia Graphite, Impeller, wgpu practice, damage/partial present, CPU reference renderers for goldens, AccessKit, IME, ui-events vs winit vs native backends, system-compositor integration / Subduction), and what it changes in FLUI's global architecture

_Raw output of the `market:rendering_text_platform` agent (2026-09-25). Unedited; each claim carries the source the agent cited._

## Findings

- **Vello: the renderer family was re-cut, and the CPU renderer is the mature one** — The Vello README now lists three renderers. `vello_cpu` is 'the most mature choice when predictable CPU rendering, software rendering, or support for devices without a suitable GPU is required'. `vello_gpu` (formerly Vello Hybrid) does path preprocessing on the CPU and raster/compositing on the GPU, needs no compute shaders, has WebGL2 and wgpu backends, and 'is intended to become the primary renderer for production GPU use cases'. The original compute `vello` crate is now 'experimental'. Both sparse-strip renderers share `vello_common` and `glifo`. The Q1 2026 blog called Hybrid 'roughly beta quality', and ColorMatrix and rect fast-path work landed Jul-Sep 2026. Caveat: vello_cpu does not yet support complex filter graphs (they panic), and in multi-threaded mode even simple filters are unsupported. _Relevance:_ FLUI's roadmap keeps 'Vello for paths' at H4 'only if lyon loses' (plan.md trajectory table) and lists 'rewrite render on Vello' as a non-goal. The market has moved: the Vello project that matters now is the sparse-strips pair, not compute Vello. It offers the one thing FLUI plans to build separately twice: a CPU renderer for goldens (E7) and a software fallback for weak GPUs (H2). The choice is no longer 'swap the renderer for Vello'. It is 'does FLUI own a second, CPU raster implementation of its whole layer/effect vocabulary, or borrow one'. ([source](https://raw.githubusercontent.com/linebender/vello/main/README.md ; https://linebender.org/blog/tmil-25/ ; https://github.com/linebender/vello/pull/1623 ; https://github.com/linebender/vello/pull/1926 ; search summary of docs.rs/vello_cpu (filter limitation)))
- **Masonry/Xilem put a rendering abstraction ('imaging') between the widget framework and the rasterizer** — Masonry moved from being hardcoded to Vello classic to 'imaging', an abstraction over 2D renderers, and can now run on Vello CPU without a GPU. Xilem exposes the backends as features (`imaging_vello` default, `imaging_vello_hybrid`, `imaging_skia`); the reviewer accepted feature flags for backend choice only as an interim step. Linebender abandoned a unified CPU/GPU API in favour of the AnyRender (ergonomics) and imaging (performance) layers. AnyRender is a trait-only crate (`PaintScene`) with vello_cpu and vello_hybrid backends. _Relevance:_ FLUI has no such seam. The display list (`flui-painting`, ADR-0065) and the layer tree (`flui-layer`) are consumed by exactly one 74k-LOC crate, `flui-engine`, which is welded to wgpu. Evidence that a second consumer drifts: `crates/flui-engine/src/headless.rs:15-24` documents that the windowless capture path already renders BackdropFilter (no blur), ShaderMask (no mask) and Follower (no leader offset) differently from the windowed `Renderer`. Two raster paths inside one crate have already diverged, and a CPU reference renderer would be a third. The lesson for the architecture: define a raster contract crate (layer + display-list semantics, glyph-run keys, effect catalog, conformance tests) that GPU, CPU and headless backends all implement. Keep backend choice as a type or runtime parameter of the presenter, not as a fork of the walk. ([source](https://linebender.org/blog/tmil-25/ ; https://github.com/linebender/xilem/pull/1847 ; https://github.com/dioxuslabs/anyrender ; https://lib.rs/crates/anyrender_vello_cpu))
- **Parley in 2026: HarfRust shaping, ICU4X analysis, a shared font collection, and glyph rendering split out into glifo** — Parley replaced Swash with HarfRust (a HarfBuzz port) for 'production-quality shaping for all scripts' and replaced Swash with ICU4X for analysis (bidi, segmentation, normalization). Its key dependencies are Fontique, HarfRust, Skrifa and ICU4X. Skrifa produces 'scaled, hinted vector paths suitable for rasterisation'. In Q1 2026 Linebender split glyph rendering (outlines, color emoji) out of Parley into `glifo` and moved it into the Vello repo 'to facilitate atlas-based glyph caching'. Parley also added CoreText font enumeration and AccessKit text properties. Bevy switched to Parley. v0.10 added a `complex-scripts` feature (dictionary breaking for CJK/Thai/Khmer…); v0.9 added floating boxes. The latest release is 0.11.1, which matches FLUI's spike pin. The release page as fetched showed 2023-2024 dates, which contradicts the Q1 2026 blog and the ICU4X switch that the Dec 2025 post reports as recent, so treat the exact dates as unreliable. _Relevance:_ This confirms the ADR-0077 direction (`docs/adr/ADR-0077-migrate-to-parley.md`, Proposed; `tools/text-spike/Cargo.toml:23` pins parley =0.11.1) and changes what the one-week spike should test. Swash is not in Parley's path any more, so rasterizing into the ADR-0067 atlas means Skrifa outlines (hinted) plus a rasterizer (zeno/tiny-skia/vello_cpu) or glifo. glifo is unstable and lives in the Vello repo. Because ICU4X arrives with Parley, FLUI's separate `unicode-segmentation` dependency (`crates/flui-painting/Cargo.toml:45`, `crates/flui-widgets/Cargo.toml:50`) and a planned `unicode-bidi` would duplicate Unicode data and could disagree with the shaper on boundaries. One Unicode source should own segmentation for both layout and editing. ([source](https://github.com/linebender/parley (README via search) ; https://github.com/linebender/parley/releases ; https://linebender.org/blog/tmil-25/ ; https://linebender.org/blog/tmil-24/))
- **Per-realm fonts without duplication: fontique already has a shared-collection mode** — `fontique::CollectionOptions { shared, system_fonts }`: with `shared: true`, 'the font collection will use a secondary shared store guaranteeing that any changes to the collection will be visible to all clones'. For single-threaded use this is 'pure overhead and should be disabled'. _Relevance:_ FLUI's remaining process global is `static FONT_SYSTEM: OnceLock<Arc<Mutex<FontState>>>` (`crates/flui-painting/src/text_layout/layout.rs:124`), against principle 3 ('no global state', ratchet to 0). The Parley shape maps directly onto the realm model (ADR-0027): a per-realm `FontContext`/`LayoutContext` (mutable, no lock on the frame path) over a cloned shared `Collection` (fonts registered once and visible to all realms), and a glyph atlas owned per GPU device in the engine (ADR-0067). This removes the global mutex from layout, which AGENTS.md's 'locks guard shared infrastructure only' rule requires anyway. ([source](https://docs.rs/fontique/latest/fontique/struct.CollectionOptions.html))
- **cosmic-text and glyphon are now a minority stack** — cosmic-text uses HarfRust for shaping and swash for rendering, and has about one maintainer. glyphon (cosmic-text + etagere + wgpu) remains iced's text renderer. Zed/GPUI uses DirectWrite on Windows, CoreText on macOS and cosmic-text on Linux. Its open issue #13951 proposes a single HarfBuzz-based text system because the per-platform stacks lack full font-feature support, lack fontconfig, lack complete metrics and duplicate caching between GPUI and the platform text system. _Relevance:_ The sources disagree on production text. GPUI chose platform-native text and now regrets the fragmentation. Flutter and Parley users choose one shaper everywhere. FLUI's plan says 'golden on CPU reference with embedded font; in production, OS hinting' (plan.md product bets). If that means OS rasterization (DirectWrite/CoreText) in production, FLUI takes on GPUI's split, with divergent metrics between test and production. The safer reading: one shaper and layout (Parley) everywhere, with only the glyph rasterizer and hinting varying per platform behind the ADR-0067 `rasterize(GlyphKey)` door. Pin that down in ADR-0077. ([source](https://github.com/pop-os/cosmic-text (via search) ; https://socket.dev/cargo/package/cosmic-text ; https://github.com/grovesNL/glyphon ; https://github.com/zed-industries/zed/issues/13951 ; https://zed.dev/blog/windows-progress-report))
- **Skia Graphite and Impeller both designed for 'no runtime pipeline surprises'** — Graphite: Recorders produce Recordings on multiple threads, depth-buffer z-ordering reorders opaque draws to cut overdraw and state changes, and pipelines are consolidated so Chrome can compile them at startup and avoid 'surprising performance cliffs'. It uses Dawn (WebGPU) as the abstraction over Metal/Vulkan/D3D, and path rasterization is expected to move to compute because MSAA has quality limits. Impeller compiles all shaders and reflection offline, builds all pipeline state objects up front and caches explicitly. It is default on iOS, Android API 29+ (GLES fallback below), macOS, Linux and Windows as of Flutter 3.47; web still uses Skia. Flutter 3.44 removed Skia for Android 10+ with no opt-out. _Relevance:_ FLUI composes shaders at run time (`naga_oil`, `crates/flui-engine/src/shader_composer.rs`) and specializes pipelines lazily by key (`crates/flui-engine/src/pipeline_cache.rs`). There is no `wgpu::PipelineCache` use in `crates/flui-engine/src` (grep empty). Hypothesis: first-use pipeline creation causes first-frame or first-effect jank on DX12/Metal, where wgpu has no driver cache. Architecturally, the effect vocabulary (blur, backdrop, shader mask, advanced blends, custom shaders at H2) should be a closed, enumerable pipeline set that can be warmed at startup, and custom shaders should enter through a registration step, not ad hoc per frame. Recording on another thread (Graphite) matches FLUI's planned raster lane (A5). ([source](https://blog.google/chromium/introducing-skia-graphite-chromes/ ; https://docs.flutter.dev/perf/impeller ; https://levelup.gitconnected.com/flutter-just-removed-skia-from-every-modern-android-device-impeller-vulkan-is-now-mandatory-b52de5038587))
- **wgpu cannot present with damage, and partial rendering needs buffer-age knowledge** — wgpu issue #682 ('Present with damage region', VkPresentRegionKHR) was closed as not planned, noting there is no mechanism in the WebGPU spec. iced's damage-tracking issue #367 depends on it and is still open. Flutter's Metal partial repaint keeps 'Accumulated damage for each framebuffer; Key is address of underlying MTLTexture for each drawable', which requires knowing which swapchain image is being reused. Flutter derives damage by diffing consecutive layer trees (DiffContext). Slint's software renderer tracks buffer reuse explicitly (`RepaintBufferType`, `extra_draw_region` for the previous frame's dirty region). _Relevance:_ ADR-0061 already picked Flutter's layer-diff approach (good). But `Renderer::render_scene` applies the damage scissor to 'the intermediate … or directly at the swapchain otherwise' (`crates/flui-engine/src/renderer.rs:2290-2330`). Hypothesis, to verify before E1: a scissored render straight into a rotating wgpu swapchain image leaves stale pixels outside the scissor from frame N-2/N-3, because wgpu exposes neither buffer age nor present regions. Correct partial repaint over wgpu needs a persistent retained target plus a blit to the swapchain (saves shading, not bandwidth or compositor work), or per-platform presenters that own the swapchain (DXGI Present1 dirty rects, CAMetalLayer, EGL buffer_age). The OS-energy win (the compositor skipping unchanged regions) is unreachable through the plain wgpu surface. That pushes toward presentation living in a presenter abstraction rather than inside `flui-engine`'s `Renderer`. ([source](https://github.com/gfx-rs/wgpu/issues/682 ; https://github.com/iced-rs/iced/issues/367 ; https://github.com/flutter-team-archive/engine/pull/28801 ; https://codebrowser.dev/flutter_engine/flutter_engine/flutter/flow/diff_context.h.html ; https://docs.rs/slint/latest/slint/platform/software_renderer/struct.SoftwareRenderer.html))
- **System-compositor integration: Subduction (forest-rs) and Flutter HCPP** — Subduction (forest-rs/subduction, Bruce Mitchener) is a 2026 workspace with `subduction_core`: a no_std retained layer tree with multi-channel dirty tracking (TRANSFORM/OPACITY propagate; CLIP/CONTENT local; TOPOLOGY rebuild), a `Presenter` trait and trace hooks. It has backends for Windows (DirectComposition; visuals are property-only and apps attach GPU content via `SetContent`), Apple, Wayland (frame callbacks plus `wp_presentation` feedback, and an embedded mode where the host owns the event queue), Android, X11, web, and a wgpu fallback compositor that allocates a texture per SurfaceId. A separate `frameclock` crate turns platform ticks and host `FrameDemand` (INPUT / CONTINUOUS_INPUT / ANIMATION / BACKGROUND) into `FramePlan`s (frame_start, sample_time, target_present) and adapts from present feedback. It 'intentionally does not own windows, event loops, layer trees, renderers, swapchains'. Linebender's Q1 2026 post says compositor integration is 'the best way to stitch native widgets into a GPU-accelerated rendering surface' and is needed for efficient video. Flutter 3.44 shipped Hybrid Composition++ (opt-in): compositing is delegated to Android through Vulkan hardware-buffer swapchains and SurfaceControl transactions, requiring API 34+ and Vulkan, with fallback to the old modes. _Relevance:_ This is the biggest structural lesson for H1/H2 external content (plan.md: compositor spike H1, embedding H2). FLUI today renders the whole `LayerTree` into one wgpu surface (ADR-0063). `PlatformViewLayer` exists in the vocabulary (`crates/flui-layer/src/layer/platform_view.rs`), but the engine's handler is a no-op, 'Platform views are composited by the platform embedder' (`crates/flui-engine/src/layer_render.rs:381-384`), and no embedder does it. That is unwired surface. External content is limited to `TextureLayer` via `ExternalTextureRegistry` (sampled into FLUI's pass, so no zero-copy video and no native widgets on top). Both Subduction and HCPP show the target shape: FLUI's layer tree is lowered into (a) N rasterized surfaces and (b) a native compositor tree of those surfaces plus foreign surfaces, with the single-swapchain case as the fallback presenter. `frameclock`'s demand/plan model is also a ready reference for the planned 'frame demand unification' (#1172) and ADR-0058. Decide the seam (layer tree → presenter) before 1.0, because it changes the `flui-engine`/`flui-platform`/`flui-app` contract. ([source](gh api repos/forest-rs/subduction/contents (subduction_core/README.md, frameclock/README.md, subduction_backend_windows/src/lib.rs, subduction_backend_wgpu/src/lib.rs, subduction_backend_wayland/src/lib.rs; last push 2026-09-17) ; https://linebender.org/blog/tmil-25/ ; https://x.com/FlutterDev/status/2069088026190295195 ; https://github.com/flutter/flutter/issues/163073))
- **Single portable GPU API vs native renderers per platform: sources disagree** — Zed removed Blade and reimplemented its Linux renderer on wgpu for stability (NVIDIA/Wayland freezes) and to share ecosystem fixes. On Windows it left Vulkan for DirectX 11 plus DirectWrite after ARM64 and driver reliability problems, at the cost of a third shader implementation (HLSL beside MSL and WGSL). Chrome's Graphite chose Dawn (a WebGPU implementation) as its abstraction over Metal/Vulkan/D3D. _Relevance:_ FLUI's principle 'one renderer everywhere' holds with wgpu, but the backend set is thin. `crates/flui-engine/Cargo.toml:105-112` compiles only dx12 on Windows, metal on Apple, and vulkan on Linux and Android, with no GLES. Android devices without usable Vulkan (Flutter keeps a GLES fallback below API 29) and Linux VMs or old GPUs would get no renderer. That makes the CPU/software backend a production requirement, not just a test oracle. ([source](https://github.com/zed-industries/zed/pull/46758 ; https://zed.dev/blog/windows-progress-report ; https://blog.google/chromium/introducing-skia-graphite-chromes/))
- **CPU reference rendering for golden tests: what others actually achieved** — Flutter says golden files made on one OS 'often won't match' another. Tests default to Ahem/FlutterTest block glyphs, and the usual practice is one OS (Linux) as golden source of truth. egui_kittest renders snapshots through wgpu, prefers software rasterizers, and still needs per-test thresholds (0.6, and 2.1 for a bezier demo) because backends differ in AA. Masonry's TestHarness uses `assert_render_snapshot` PNGs, and Xilem issue #845 proposed removing most tree snapshot tests as redundant. tiny-skia is maintained (0.12.0, Feb 2026) and is the CPU renderer behind resvg. vello_cpu is the other mature option. _Relevance:_ FLUI's B3/G3 exit ('golden diff between OSes is zero', CPU reference plus embedded font) is stricter than anyone in the survey has shipped. It is feasible only if the CPU renderer is bit-deterministic across OS and CPU. Hypothesis: SIMD-dispatching rasterizers such as vello_cpu (fearless_simd runtime detection) or f32 vs u8 pipelines may differ per CPU level, so pin the SIMD level and pipeline in test mode. It also forces a choice on the effect vocabulary: FLUI's GPU-only effects (backdrop blur, advanced blends, shader masks, the planned custom WGSL shaders) either get CPU implementations or are excluded from pixel goldens (semantic goldens only). Otherwise the golden tier tests a different renderer than the one that ships, which is `headless.rs`'s divergence again at a bigger scale. ([source](https://api.flutter.dev/flutter/flutter_test/matchesGoldenFile.html ; https://github.com/emilk/egui/pull/5506 ; https://docs.rs/egui_kittest ; https://docs.rs/masonry_testing ; https://github.com/linebender/xilem/issues/845 ; https://github.com/linebender/tiny-skia/blob/main/CHANGELOG.md))
- **AccessKit in 2026: adapters for all five platforms, and multi-tree support** — On 2026-09-25 AccessKit released accesskit 0.25.1 (JSON schema gains `tree_id` for multiple trees), accesskit_android 0.9.0 (sliders, live regions, thread-safety fixes), accesskit_unix 0.24.0, accesskit_windows 0.35.1, accesskit_macos 0.27.1, accesskit_ios 0.2.1 and accesskit_winit 0.34.1. `html_id` was added in August 2026. The design is push-based (initial full tree, then incremental updates, modelled on Chromium), and the recommended toolkit integration is the winit adapter or direct per-platform adapters. _Relevance:_ FLUI uses only the desktop adapters: `accesskit_unix` 0.23 (one behind), `accesskit_windows`, `accesskit_macos`, all behind the optional `a11y` feature (`crates/flui-platform/Cargo.toml:221,288,295,310`). There is no android or iOS adapter, although roadmap F6 needs an iOS tree and the plan says 'AccessKit on by default for beta'. `tree_id` is the hook for multi-window realms and for embedded foreign content (a WebView's own tree) in the H1/H2 compositor work. Since ADR-0080 makes AccessKit the agent-protocol vocabulary, the AccessKit version is effectively a public protocol version: pin and upgrade it as one cohort (the Cargo.toml comments already coordinate accesskit_windows to the 0.25 cohort), and version the agent protocol separately so an AccessKit bump does not silently change the MCP schema. ([source](https://github.com/AccessKit/accesskit/releases ; https://accesskit.dev/how-it-works/))
- **IME: Windows needs TSF, and FLUI's Windows backend has no IME path at all** — Microsoft blocks IMEs implemented on IMM32 in Windows apps and requires TSF for IMEs. Edge's TSF explainer says apps built on legacy IMM32 'must do additional work' to get text-intelligence services: suggestions, shapewriting, IME reconversion after commit, and touch-keyboard integration. IME candidate lists must be UIA-accessible for Narrator. winit 0.31 (beta.3, PR #4678, Sep 2026 per search) adds atomic `request_ime_update`, `Ime::DeleteSurrounding`, more `ImePurpose` and `ImeHints` (surrounding-text APIs). ui-events 0.3.0 (2026-09-12) covers pointer and keyboard only, with no IME types. _Relevance:_ `grep -rn -E "WM_IME|Ime[A-Z]|ImeEvent|set_ime|ime_" crates/flui-platform/src/platforms/windows` returns nothing. The platform trait has `PlatformInput::Ime` (`crates/flui-platform/src/traits/input.rs:148`), but only the macOS backend implements a text-input client (`platforms/macos/text_input.rs`). Yet 'Windows + Narrator + Japanese IME' is an exit criterion of B1. The architectural point: the IME contract (composition, surrounding text, delete-surrounding, caret rect, purpose/hints, reconversion) should be a platform capability trait shaped after TSF/NSTextInputClient/text-input-v3 and winit 0.31's vocabulary, owned by the text-editing layer, not an event enum. Build it on TSF from the start on Windows, not IMM32. ([source](https://learn.microsoft.com/en-us/windows/apps/develop/input/input-method-editor-requirements ; https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/TSF1/explainer.md ; https://github.com/rust-windowing/winit/pull/4678 ; https://github.com/rust-windowing/winit/releases ; https://docs.rs/ui-events/latest/ui_events/))
- **ui-events vs winit vs native backends** — Masonry is moving IME and other system integration onto ui-events to reduce its winit dependency, which 'opens the door to deployments not dependent on winit', for example VST plugin embedding via baseview. winit 0.31 turns `Window` and `ActiveEventLoop` into traits, unifies pointer events, and replaces resumed/suspended with `can_create_surfaces` for Android, but was still in beta as of Sep 2026. GPUI and Slint keep native per-OS backends. _Relevance:_ FLUI already made Masonry's choice: native backends plus the ui-events vocabulary (`crates/flui-platform/Cargo.toml:40`, `crates/flui-interaction/Cargo.toml:34`), with winit only as a fallback (primary on Linux, `crates/flui-platform/Cargo.toml:312-314`). `ui-events-winit` pins winit ^0.30 (Cargo.toml:54-58), so the 0.31 migration is a coordinated bump. The open plan question 'winit fallback after 1.0?' has a clear answer from the market: keep a winit path for unusual hosts (plugins, kiosks), but the IME and a11y contracts cannot be expressed through winit alone. The embedding direction (FLUI inside a host window: VST, another app, a game engine) is an H4 ecosystem extension point and needs the platform layer split so a host-owned window and event loop can drive a realm. ([source](https://linebender.org/blog/tmil-25/ ; https://github.com/rust-windowing/winit/releases ; https://github.com/rust-windowing/winit/pull/4678))

## Pitfalls others hit

- GPUI/Zed: Vulkan on Windows hit ARM64 and driver reliability problems and forced a DX11 port with a third shader language. Blade on Linux caused freezes on NVIDIA/Wayland and was replaced by wgpu (zed.dev/blog/windows-progress-report; zed PR #46758).
- GPUI/Zed: per-platform text systems (DirectWrite/CoreText/cosmic-text) led to missing font features, no fontconfig, incomplete metrics and duplicated glyph caching; an open issue proposes unifying on HarfBuzz (zed #13951).
- Flutter: platform views went through Virtual Display, Hybrid Composition (slow, flutter #167547) and TLHC before HCPP needed Vulkan + SurfaceControl + API 34. Embedding native content is a multi-year compositor problem, not a widget (docs.flutter.dev platform-views; flutter #163073).
- Flutter/egui: pixel goldens are not portable across OSes or backends. Flutter uses Ahem block glyphs and one golden OS; egui_kittest needs per-test AA thresholds (api.flutter.dev matchesGoldenFile; egui PR #5506).
- Xilem: snapshot tests kept 'out of inertia' became maintenance weight and most were proposed for removal (xilem #845).
- wgpu: present-with-damage was requested in 2020 and closed as not planned. Toolkits on wgpu (iced #367) still have no OS-level partial present.
- Flutter: layer diffing ran even with partial repaint disabled, a wasted-cost bug (flutter #95681). Damage machinery needs an off switch that actually removes the cost.
- Chromium: IMM32-based text input lost suggestions, shapewriting, reconversion and touch-keyboard integration and had to migrate to TSF (MSEdgeExplainers TSF1).
- Linebender: a single unified CPU/GPU renderer API was abandoned in favour of layered abstractions (AnyRender / imaging) (tmil-25). Do not expect one trait to serve both ergonomics and peak performance.
- Impeller: the Android GLES fallback path has renderer-specific bugs (gradients wrong after Vulkan → GLES fallback, flutter #179268). Every extra backend is a conformance burden.

## Patterns to adopt

- Put a raster contract crate between flui-layer/flui-painting and the backends (layer + display-list semantics, effect catalog, glyph-run keys, a conformance test suite that every backend runs). The GPU (wgpu), CPU (vello_cpu or tiny-skia based) and headless paths implement it, which ends the divergence already documented in crates/flui-engine/src/headless.rs:15-24. Model: Masonry's 'imaging' / Dioxus AnyRender.
- Make the CPU renderer one production backend serving three jobs: deterministic goldens (E7), software fallback for GPU-less or old devices (H2), and CI without a GPU. vello_cpu is described by its authors as the mature choice for exactly this.
- Split presentation out of the renderer into a presenter abstraction (the Subduction `Presenter` + frameclock shape): the layer tree lowers to N surfaces plus a native compositor tree (DirectComposition / CoreAnimation / Wayland subsurfaces / SurfaceControl), with the one-swapchain wgpu presenter as fallback. This is the prerequisite for external content (video, WebView, maps) in H1/H2 and for real OS-level partial present.
- Adopt frameclock-style frame demand classes (INPUT, CONTINUOUS_INPUT, ANIMATION, BACKGROUND) and present-feedback-driven scheduling for the planned frame-demand unification (#1172) and ADR-0058, or depend on frameclock directly (no_std, owns no window, loop or renderer).
- Text: one shaper and layout everywhere (Parley: HarfRust + ICU4X + fontique), per-realm FontContext/LayoutContext over a fontique Collection with `shared: true`, and a per-GPU-device glyph atlas. Only rasterization and hinting vary per platform behind ADR-0067's `rasterize(GlyphKey)` door. Use ICU4X from Parley as the single Unicode source for editor segmentation and bidi instead of adding unicode-segmentation and unicode-bidi separately.
- Make the effect and pipeline vocabulary closed and enumerable so pipelines can be prewarmed at startup (Impeller/Graphite). Persist `wgpu::PipelineCache` on Vulkan. Register custom shaders (H2) through a declared step, not ad hoc.
- Treat the IME as a platform capability with a surrounding-text contract (composition range, caret rect, delete-surrounding, purpose/hints, reconversion), matching winit 0.31's IME API and TSF on Windows. Implement TSF first on Windows because it is the B1 exit platform.
- Ship accesskit_android and accesskit_ios adapters in flui-platform, turn `a11y` on by default, and use AccessKit's `tree_id` for multi-window and embedded foreign-content trees. Version the agent protocol (ADR-0080) independently of the AccessKit crate version.
- Keep ui-events as the input vocabulary and native backends as primary (the Masonry direction), and design the platform layer so a host-owned window or event loop can drive a realm (baseview/VST, game-engine embedding) as an H4 extension point.

## Patterns to avoid

- Do not grow a second and third hand-written raster walk inside flui-engine (windowed Renderer, headless, a CPU reference). Each extra path diverges silently, as headless.rs already has on three layer kinds.
- Do not treat damage as a scissor on the swapchain image. wgpu gives neither buffer age nor present regions (wgpu #682), so scissoring into a rotating swapchain image risks stale pixels (hypothesis on crates/flui-engine/src/renderer.rs:2290-2330). Use a retained target + blit, or a presenter that owns the swapchain.
- Do not ship layer vocabulary with no consumer: PlatformViewLayer renders as a no-op (crates/flui-engine/src/layer_render.rs:381-384). Remove it until the compositor/presenter work lands, or wire it behind that work.
- Do not promise 'zero golden diff across OSes' unless the CPU renderer's SIMD level and pipeline are pinned and every effect in the goldens has a CPU implementation. Otherwise use semantic goldens for GPU-only effects, as Flutter and egui do in practice.
- Do not use platform-native text layout (DirectWrite/CoreText) in production and a different shaper in tests. That combines GPUI's fragmentation with test/production metric drift.
- Do not build Windows IME on IMM32. It loses reconversion, suggestions and touch-keyboard support and is the path Chromium had to migrate off.
- Do not keep a single-backend-per-OS wgpu feature set (dx12 / metal / vulkan only, crates/flui-engine/Cargo.toml:105-112) without a CPU or GLES fallback. Flutter keeps GLES on Android for non-Vulkan devices, and Zed hit driver trouble even with mainstream APIs.
- Do not put backend choice in Cargo feature flags on the widget crate (Xilem's interim approach, accepted with reservations). Choose it at the presenter/renderer seam at run time, so one binary can fall back to CPU.
- Do not re-embed a 'Vello rewrite' as an all-or-nothing H4 decision. Evaluate vello_cpu now as the CPU backend and vello_gpu later against the lyon path, both behind the raster contract.
