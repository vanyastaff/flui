# Market survey: Market survey: Flutter, Jetpack Compose and SwiftUI. Their architecture, the regrets they have documented, and what FLUI should copy, avoid or fix at the level of workspace, crate topology, runtime and ecosystem. There is no .flutter/ clone at D:\flui (`ls D:/flui/.flutter` gives "No such file"), so every external claim below comes from web primary sources. Local claims are cited as path:line.

_Raw output of the `market:flutter_compose_swiftui` agent (2026-09-25). Unedited; each claim carries the source the agent cited._

## Findings

- **Flutter: Material and Cupertino taken out of the framework** — Contributions to Material and Cupertino in flutter/flutter were frozen on 7 April 2026. The libraries were re-released as pkg:material_ui and pkg:cupertino_ui 1.0.0 on pub.dev in August 2026 and now follow independent semver. Old imports are deprecated in the Fall 2026 stable and removed in 2027. The stated reasons: framework upgrades dragged design changes along with them, the design libraries needed a faster release cadence, and the widgets library had to fill gaps so that other design languages (macos_ui, fluent_ui, shadcn) get a stronger base. Flutter took 12 years to reach this and needs a two-stage migration to finish it. _Relevance:_ This directly confirms the plan's delivery layer 'official packages: Material, Cupertino' (plan.md §Платформа и экосистема), yet flui-material (26.9k LOC) and flui-cupertino still live in the workspace (context.md). The cheap moment is now, before publishing: once flui-material ships to crates.io in lockstep with core, FLUI repeats Flutter's 12-year debt. Flutter's lesson that 'the widgets library must fill the gaps' is exactly the Raw-primitives-first decision. Treat 'Material builds using only the public API of flui-widgets' as the exit test, not the repository move itself. ([source](https://flutter.dev/blog/decoupling-material-cupertino ; https://flutter.dev/blog/flutters-material-and-cupertino-code-freeze ; https://docs.flutter.dev/release/breaking-changes/material-ui-and-cupertino-ui))
- **Flutter: InheritedWidget, BuildContext and aspect dependencies** — Plain InheritedWidget rebuilds every dependent whenever updateShouldNotify is true. Flutter bolted on InheritedModel aspects afterwards and retrofitted MediaQuery into an InheritedModel with sizeOf and paddingOf (PR #114459). The docs now tell users to prefer MediaQuery.sizeOf over MediaQuery.of because .of rebuilds on any field change. Compose's CompositionLocal documentation repeats the lesson: implicit dependencies are hard to reason about, putting a ViewModel in a CompositionLocal is an explicit anti-pattern, and staticCompositionLocalOf recomposes the whole provided subtree, not just the readers. _Relevance:_ FLUI already builds in the fix: depend_on_field takes a FieldMask and promotes an empty mask to a whole-provider dependency (crates/flui-view/src/context/build_context.rs:648-667). The whole-provider depend_on remains the easiest path (build_context.rs:691). Recommendation: for H3 Stable tiering, make the field-granular read the default derived API, for example derive(InheritedView) that generates per-field accessors, as Flutter did with sizeOf. Treat whole-provider depend_on as the MediaQuery.of trap. Add a lint or diagnostic that counts whole-provider dependencies on high-fan-out providers such as Theme and MediaQuery. ([source](https://api.flutter.dev/flutter/widgets/InheritedModel-class.html ; https://github.com/flutter/flutter/pull/114459 ; https://api.flutter.dev/flutter/widgets/MediaQuery-class.html ; https://developer.android.com/develop/ui/compose/compositionlocal))
- **Flutter: Navigator 1.0/2.0 split** — Flutter's docs no longer recommend named routes. They recommend go_router (or another routing package) or Navigator plus MaterialPageRoute. Named routes cannot customise deep-link handling and do not support the browser forward button. Page-backed routes (Router) are deep-linkable. Pageless routes (Navigator.push, showDialog) are not, and they are silently removed when the page-backed route below them is removed. Flutter UXR ran a comparative study of the navigation-package zoo (flutter/uxr#7). _Relevance:_ This supports A3 (Router as the primary API, roadmap.md:262-263). The concrete structural lesson is the pageless/page-backed split: if FLUI keeps Navigator::push as 'a thin facade', every push must produce a URL-addressable entry in the same stack. Otherwise FLUI inherits the two-kinds-of-route semantics. SwiftUI made the same correction in iOS 16: NavigationView was deprecated for data-driven NavigationStack/NavigationPath (https://www.hackingwithswift.com/articles/250/whats-new-in-swiftui-for-ios-16). Both mature toolkits converged on 'the navigation state is a value'. Dialogs and overlays need an explicit, documented answer on whether they are part of that state. ([source](https://docs.flutter.dev/ui/navigation ; https://github.com/flutter/uxr/issues/7))
- **Flutter: text input and IME on Windows** — Flutter's Windows embedder uses IMM32, not TSF. As of February 2026, Windows voice typing and dictation tools cannot write into Flutter TextFields for two reasons: the fields expose no UIA Value/TextEdit providers, and without a TSF ITextStoreACP, TSF-routed input (speech, handwriting, Win+H) has nowhere to go (flutter#182876, P2, open). The original 'Full IME support for Windows' issue dates from September 2020 (flutter#65574). Flutter's IME bugs are platform-protocol bugs, not text-shaping bugs. _Relevance:_ FLUI has no Windows IME path yet. A grep for WM_IME|ImmGet|ITf|Composition under crates/flui-platform/src/platforms/windows finds no IME handling, although the roadmap puts the Japanese IME and Narrator in the B1 exit. Choose TSF (ITextStoreACP/ITextStoreACP2) from the start, not IMM32, and couple it to the UIA TextPattern/ValuePattern that the accessibility track is building. They are one contract, and Flutter's six-year gap came from treating them as two. ([source](https://github.com/flutter/flutter/issues/182876 ; https://github.com/flutter/flutter/issues/65574 ; https://github.com/flutter/flutter/issues/191196))
- **FLUI text-input contract is push-only (structural, from local evidence)** — PlatformTextInput carries only set_ime_allowed and set_ime_cursor_area. Its doc states it does not model a text buffer or selection (crates/flui-platform/src/traits/text_input.rs:24-45). The macOS NSTextInputClient answers attributedSubstringForProposedRange with nil/NSNotFound because 'this view holds no attributed text' (crates/flui-platform/src/platforms/macos/text_input.rs:430-445). OS text protocols (NSTextInputClient, TSF ITextStoreACP, Android InputConnection.getTextBeforeCursor, iOS UITextInput) query the text store synchronously for reconversion, autocorrect, dictation and surrounding text. Flutter mirrors editing state into the embedder (the multi-step IME TextInputModel in flutter/engine#21682). Compose Multiplatform 1.11 moved iOS input onto a native UIView implementing UITextInput/UIKeyInput to get native caret, selection, autofill and translate. _Relevance:_ This is a cross-crate contract gap, not a bug. A push-only IME event stream (the winit shape) cannot serve Windows TSF, Android InputConnection or iOS UITextInput. A 'text editing contract' ADR is needed that puts a synchronous, read-only text-store query surface (text in a range, selection, rect for a range, index for a point) into flui-platform. Its implementation lives in flui-interaction/widgets and is reached without a lock on the frame path. Otherwise H1 mobile (Android/iOS) will force the break after publishing. Hypothesis: this should be decided together with Parley (ADR-0077), because the rect-for-range and index-for-point queries come from the layout. ([source](local paths above; https://github.com/flutter/engine/pull/21682 ; https://kotlinlang.org/docs/multiplatform/whats-new-compose-111.html))
- **Compose: moving TextField from value/onValueChange to state-based** — Google now recommends the state-based BasicTextField(TextFieldState). With value/onValueChange, asynchronous state round-trips (such as a ViewModel StateFlow) desync the keyboard and the field, causing flicker and lost cursor position. TextFieldState encapsulates the whole input flow, applies InputTransformation synchronously 'right after user input is detected', handles offsets automatically through OutputTransformation, and has an edit{} transaction and undo. The docs recommend treating it as a data dependency backed by snapshot state. _Relevance:_ FLUI's TextEditingController already has the correct owner-of-truth shape, but it is Arc<Mutex<ControllerInner>> plus ChangeNotifier (crates/flui-widgets/src/text/controller.rs:261-267). That is a per-node lock touched in build/paint, which AGENTS.md 'Frame path is synchronous' forbids, and it is outside the signal system (ADR-0074). It also has no transaction/edit API, no input/output transformations and no undo. Recommendation for the Text editing contract ADR: the text-field state is a realm-scoped signal-backed store with an edit(|buf| ..) transaction, input/output transforms (for Form/validation and masks) and undo. Never offer a value+callback-only field, which is Compose's documented mistake. ([source](https://developer.android.com/develop/ui/compose/text/migrate-state-based ; https://medium.com/androiddevelopers/effective-state-management-for-textfield-in-compose-d6e5b070fbe5))
- **Flutter: platform channels versus direct interop and thread merge** — Flutter now names four problems with method channels: hand-written glue, serialization errors surfacing at run time, async-only calls, and the inability to pass non-serializable objects between plugins. Pigeon adds type safety but uses the same StandardMessageCodec at the same cost. The long-term direction is FFIgen/JNIgen direct, synchronous interop. To make that possible Flutter merged the UI and platform threads, on iOS/Android in 3.29 and on macOS/Windows in 3.35, because platform callbacks such as accessibility, IME and app delegates are synchronous. Build hooks (hook/build.dart, 'code assets') are stable since 3.38, and FFI packages are the recommended template. _Relevance:_ This validates two FLUI bets. First, 'PlatformCapability: typed, no string channels, a plugin is a normal crate with #[cfg(target_os)]' (plan.md §Точки расширения). Second, the single-writer UI thread co-located with the platform thread, where Flutter paid a multi-year migration to reach what Rust gets for free. It also carries a constraint. FLUI's existing capabilities (PlatformTextInput, PlatformHaptics) are traits inside flui-platform reached through Option<Arc<dyn _>> accessors on PlatformWindow (text_input.rs:1-17), so it is a closed set: a third-party crate cannot add a capability without editing flui-platform. H1's '5 plugins built outside the repo' needs an open registry, for example a realm-scoped TypeId-keyed capability map populated by the app builder. Cargo already does what Dart build hooks add, so FLUI needs no second build system (Principle 2), except for Android/iOS packaging of Kotlin/Swift sources. ([source](https://flutter.dev/blog/flutters-path-towards-seamless-interop (2025-05-20) ; https://docs.flutter.dev/release/breaking-changes/macos-windows-merged-threads ; https://github.com/flutter/flutter/issues/150525 ; https://dart.dev/tools/hooks ; https://docs.flutter.dev/packages-and-plugins/developing-packages ; https://pub.dev/packages/pigeon))
- **Flutter: federated plugins** — Flutter splits a plugin into an app-facing package, a platform_interface package and per-platform implementation packages. Implementations can be 'endorsed' (default_package) or non-endorsed, added by the user. Breaking changes to the platform interface should be avoided in favour of non-breaking additions. Kotlin Multiplatform's docs likewise recommend interfaces plus factory functions over expect/actual classes, for testability and for more than one implementation per platform. _Relevance:_ For the PlatformCapability design, copy the separation between the interface crate and the implementation crates, and the endorsed-default mechanism: a Cargo feature per platform that pulls the default implementation. Avoid Flutter's global mutable `Platform.instance = ...` registration. In FLUI the registration should be per-realm or app-builder data (Principle 3, no global state), and a typed Unsupported result is needed for missing implementations. Hypothesis: `flui-plugin` (the interface and registry) is a substrate-layer crate next to flui-platform, and the H4 community catalogue validates plugins against it. ([source](https://docs.flutter.dev/packages-and-plugins/developing-packages ; https://kotlinlang.org/docs/multiplatform/multiplatform-expect-actual.html))
- **Flutter Impeller: renderer design goals** — Impeller's goals are predictable performance (all shaders and pipeline state compiled offline), instrumentability (every GPU resource labelled, frames capturable), portability (shaders authored once and converted per backend), and concurrency (one frame's work spread across threads). It replaced Skia because runtime shader compilation caused first-run jank. Flutter 3.47 makes it the default on all native platforms, but not on web, which still uses Skia/CanvasKit. _Relevance:_ FLUI's wgpu/WGSL engine gets offline-validated shaders cheaply (the wgsl gate exists), but pipeline creation on first use still causes jank on Metal/Vulkan. Pipeline-cache warmup and labelled resources should be engine contracts in the H2 perf work. Flutter carrying two renderers for years (Skia web versus Impeller native) is the counter-example to Principle 2 'one renderer everywhere': FLUI keeps the principle only if the WebGL2 fallback (H1) goes through the same wgpu path and not a second renderer. ([source](https://docs.flutter.dev/perf/impeller))
- **Flutter: embedder API and platform views** — Flutter's embedder API is one C header with a stable ABI, and a frozen subset (such as FlutterSemanticsNode) guarantees forward compatibility. The thread that calls FlutterEngineRun is the platform thread. Platform views carry permanent trade-offs. On Android, Texture Layer has good performance but breaks accessibility and magnification for SurfaceView. Hybrid Composition has full fidelity but merges the raster and platform threads, hurting FPS. HC++ (API 34+, Vulkan) solves both but has stacking limitations. The architectural overview says the synchronization overhead is 'inevitable' and that platform views suit only controls such as maps. _Relevance:_ flui-platform already has traits/embedder.rs, so an embedder seam exists. For H4 (embedded/kiosks) decide which part is ABI-stable. Hypothesis: a Rust trait, not a C ABI, suffices until someone embeds FLUI in a non-Rust host. For the H1 'system compositor spike' (video, WebView, maps), design OS-compositor overlays (CALayer, DirectComposition visual, SurfaceControl) from day one, which is where Flutter ended up with HC++. Texture-copy embedding should be the fallback, and accessibility of the native view must be part of the contract. ([source](https://github.com/flutter/flutter/blob/main/docs/engine/Custom-Flutter-Engine-Embedders.md ; https://github.com/flutter/engine/pull/39963 ; https://docs.flutter.dev/platform-integration/android/platform-views ; https://docs.flutter.dev/resources/architectural-overview))
- **Flutter: keep-alive as an opt-in mixin** — AutomaticKeepAliveClientMixin requires build to call super.build and requires updateKeepAlive whenever wantKeepAlive may change. Forgetting either silently fails to keep the state. Compose has no keep-alive: lazy items lose remember state, and rememberSaveable or SaveableStateHolder save and restore the state for disposed subtrees instead. _Relevance:_ FLUI already chose a better shape: an RAII lease whose Drop is the release, refcounted holders, and targets resolved from the tree at eviction time (crates/flui-view/src/owner/keep_alive.rs:1-35). The roadmap row 'Keep-alive как свойство sliver-протокола' is effectively done at the element level. The remaining lesson from Compose is state restoration: a saveable-state mechanism for evicted children and back-stack routes is the cheaper default for most rows, and it also serves Router state restoration and hot reload. Consider one 'saveable state' contract shared by keep-alive, Router and Subsecond rather than three. ([source](https://api.flutter.dev/flutter/widgets/AutomaticKeepAliveClientMixin-mixin.html ; https://developer.android.com/develop/ui/compose/state-saving))
- **Compose: snapshot state system** — Compose state lives in MVCC snapshots. Reads and writes are tracked by read and write observers. Mutable snapshots isolate writes from other threads until apply, and conflicting applies fail unless a SnapshotMutationPolicy merges them. Compose wraps composition in a snapshot and recomposes only the scopes that read changed state. Background threads can write state without locks because the change becomes visible atomically when the global snapshot advances. _Relevance:_ The realm-scoped signals (ADR-0074, Computed/Effect ADR-0075 Proposed) get Compose's granularity but not its concurrency story. Writes from IO or raster lanes (A5) must be marshalled into the realm. That is consistent with 'async delivers results to the next frame', but it should be written into ADR-0075 as the answer to 'why not snapshots'. Compose also shows the costs FLUI avoids: a global snapshot is process-wide state, against Principle 3, and conflict policies are an API most users never understand. Recommendation: keep single-writer signals and add a batched transaction (write N signals, notify once) to get the atomicity benefit without MVCC. ([source](https://blog.zachklipp.com/introduction-to-the-compose-snapshot-system/))
- **SwiftUI Observation (SE-0395)** — Apple replaced ObservableObject/@Published (Combine) with the @Observable macro. Its problems were per-property annotation fatigue, willSet-before-value semantics, Darwin-only availability and whole-object invalidation. The macro rewrites stored properties so that getters call access(keyPath:) and setters call withMutation. withObservationTracking records the properties a closure read and fires a one-shot onChange on the first mutation, so views update only when a property they read changes. Third-party write-ups report large reductions in redundant body evaluations. _Relevance:_ This validates A4 and ADR-0074 (read-is-depend, no manual subscribe). The transferable idea is macro-generated observable structs: a derive that turns a plain Rust struct's fields into per-field tracked reads. That is the model-side equivalent of FieldMask for inherited views, and it would stop users from hand-wrapping every field in Signal<T>. The one-shot onChange semantics match a dirty-mark-then-rebuild model and avoid long-lived subscription objects. FLUI already has flui-macros, so the derive belongs there. The performance percentage cited is from a blog, not Apple, so treat it as indicative. ([source](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0395-observability.md ; https://www.avanderlee.com/swiftui/observable-macro-performance-increase-observableobject/))
- **Compose: stability inference and strong skipping, Modifier.Node** — Compose made strong skipping the default in Compose Compiler 2.0: every restartable composable is skippable, unstable parameters are compared by identity and lambdas are auto-remembered. Before that, stability inference was a constant source of performance surprises. Compose also deprecated composed{} modifiers in favour of Modifier.Node, because composed modifiers are never skipped and allocate per recomposition. Nodes persist across recompositions and can invalidate only draw or only measure. _Relevance:_ Two lessons for FLUI's View layer. (1) Skipping rules users must reason about ('is my type stable?') become a performance tax. FLUI's Rust-native equivalent (PartialEq on View config, or identity via keys) should be one documented rule decided before the H3 freeze, not inferred. (2) Compose re-learned that the persistent node, not the per-build config, is the right owner for attached behaviour. FLUI's RenderObject tree already is that. Keep decorations and gestures as render-level or element-level nodes with separate paint and layout invalidation, not as wrapper views rebuilt every frame. This is relevant to the 'element-level vs render-level granularity' open question in plan.md. ([source](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping ; https://github.com/JetBrains/kotlin/blob/master/plugins/compose/design/strong-skipping.md ; https://developer.android.com/develop/ui/compose/custom-modifiers))
- **Compose runtime as a general tree engine; Compose Multiplatform** — The Compose runtime and compiler are independent of Compose UI. The Applier interface lets any tree be managed: Molecule uses it for presenters that produce StateFlow, and Cash App's Redwood drives native UIKit/Android views and server-driven UI (Treehouse) from the same runtime. Compose Multiplatform renders via Skiko on iOS (stable since 1.8, May 2025) and web (Wasm, Beta in 1.9), with UIKitView interop, concurrent rendering by default in 1.11 and native text input as an opt-in. _Relevance:_ For crate topology: a reconciliation and signal runtime that does not depend on rendering has independent value, for headless logic tests, A2UI server-side trees and agents. Hypothesis to measure with `cargo tree -p flui-view`: if flui-view currently links flui-rendering, splitting the element/signal runtime from the render binding would give the A2UI and agent work (H1) a UI-free core. Compose Multiplatform also shows the realistic mobile compromise, which sources disagree on: self-drawn everywhere, except text input and platform widgets, which go native. ([source](https://code.cash.app/native-ui-and-multiplatform-compose-with-redwood ; https://github.com/cashapp/redwood ; https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/ ; https://blog.jetbrains.com/kotlin/2025/09/compose-multiplatform-1-9-0-compose-for-web-beta/ ; https://kotlinlang.org/docs/multiplatform/whats-new-compose-111.html))
- **SwiftUI identity and type erasure** — SwiftUI distinguishes explicit identity (id/data) from structural identity (the static type and position in the view builder). Apple advises avoiding AnyView because type erasure hides structure from the diffing engine and hurts both performance and correctness of state preservation. _Relevance:_ FLUI's View layer uses &dyn View (build_context.rs:640 example). Identity is by type plus position plus Key, as in Flutter, which is fine. The lesson is that pervasive type erasure costs optimisation opportunities. Before the H3 freeze, decide whether a statically-typed child path (as in Xilem or SwiftUI) is needed for hot lists, or whether Keys plus the sumtree are enough. Measure on the H2 100k-row benchmark rather than guess. ([source](https://developer.apple.com/videos/play/wwdc2021/10022/ ; https://developer.apple.com/videos/play/wwdc2023/10160/))
- **Flutter: the window singleton and multi-view** — Flutter deprecated the global `window` singleton (SingletonFlutterWindow split into FlutterView and PlatformDispatcher, View.of(context)) to prepare for multiple views and windows. Desktop multi-window was still an in-progress design years later. _Relevance:_ This validates Principle 3 and per-window UiRealm (ADR-0027). The remaining process global, FONT_SYSTEM (crates/flui-painting/src/text_layout/layout.rs:124: `static FONT_SYSTEM: OnceLock<Arc<Mutex<FontState>>>`), is the same class of debt, and AGENTS.md already flags it as a source of test flakiness. It should be removed as part of the Parley migration, with a shared glyph cache as explicit infrastructure owned by the app, not the process. ([source](https://docs.flutter.dev/release/breaking-changes/window-singleton ; https://github.com/flutter/flutter/issues/116929))
- **Flutter GenUI and A2UI** — A2UI is an Apache-2.0 declarative UI protocol, made public on 15 Dec 2025 and at v0.9 in May 2026 with a 'prompt first' change to flat discriminators and renamed properties. An app exposes a widget catalogue, the agent composes surfaces from it, and data binds by JSON path to an observable DataModel so that only dependent widgets rebuild. The genui package is alpha, and the transport is pluggable (A2uiTransportAdapter). _Relevance:_ This matches the flui-a2ui plan (H1) and 'catalogue G6 = A2UI catalogue'. The protocol is pre-1.0 and changed property names at v0.9, so flui-a2ui must be an official package outside core with its own version, never inside the Stable tier. Data binding by path onto an observable store maps onto realm signals, which is a reason to give signals stable, addressable paths or IDs (Principle 4). ([source](https://flutter.dev/blog/new-updates-to-a2ui-and-flutters-genui-package (2026-05-14) ; https://docs.flutter.dev/ai/genui ; https://pub.dev/packages/genui))
- **Flutter deprecation tooling** — Flutter ships data-driven fixes: packages declare fixes alongside their deprecations, and `dart fix --apply` or IDE quick-fixes apply them across a codebase. Flutter's deprecation lifetime policy governs removal. _Relevance:_ The H3 plan has 'deprecation 2 minors + flui migrate'. Make migrations data shipped by each crate (declarative rename or move tables consumed by `flui migrate`, or rust-analyzer assists), not a hand-maintained monolith in flui-cli. Official packages on an independent release train then carry their own fixes, which is what makes the Material/Cupertino split survivable for users. ([source](https://docs.flutter.dev/tools/flutter-fix))

## Pitfalls others hit

- Flutter shipped Material and Cupertino inside the framework and needed 12 years, a code freeze and a two-release deprecation to move them out (flutter.dev/blog/decoupling-material-cupertino). FLUI still has them in-workspace.
- Flutter's Navigator 2.0 was so hard to use that the official docs now point to a package (go_router). Page-backed and pageless routes coexist with different deep-link semantics (docs.flutter.dev/ui/navigation). SwiftUI likewise deprecated NavigationView for NavigationStack.
- Flutter's InheritedWidget rebuilt every dependent. Aspects (InheritedModel, MediaQuery.sizeOf) were retrofitted and users still reach for .of by default. Compose documents CompositionLocal overuse as an anti-pattern.
- Flutter on Windows used IMM32 rather than TSF and lacked UIA text patterns, so dictation and voice typing cannot enter text as of 2026 (flutter#182876). The full-IME issue dates from 2020 (#65574).
- Compose's value/onValueChange TextField desynced the IME under asynchronous state and had to be replaced by the state-based TextFieldState (developer.android.com migrate-state-based).
- Flutter's platform channels were async-only, stringly typed and unable to pass objects between plugins. Pigeon fixed typing but not the cost. Flutter then had to merge UI and platform threads across all platforms (3.29, 3.35) to allow synchronous interop.
- Skia's runtime shader compilation caused first-frame jank, which forced a new renderer (Impeller). Web still runs a different renderer, so 'one renderer everywhere' was not held.
- Platform views (embedded native views) in Flutter carry permanent perf, fidelity and accessibility trade-offs across three composition modes (docs.flutter.dev platform-views).
- Flutter's AutomaticKeepAliveClientMixin fails silently if super.build or updateKeepAlive is forgotten.
- Compose's stability inference led to years of 'why does this recompose' confusion until strong skipping became the default in Compose Compiler 2.0. Its composed{} modifiers were never skippable and were deprecated for Modifier.Node.
- SwiftUI's ObservableObject invalidated whole objects and fired before the value was set. Apple replaced it with the Observation macro (SE-0395).
- Flutter's global `window` singleton blocked multi-view and had to be deprecated (docs.flutter.dev window-singleton).
- The A2UI protocol renamed core properties at v0.9 within 5 months of release, so a framework that embeds it in core would break with it.

## Patterns to adopt

- Design systems as separately-versioned official packages built only on the public API of a core Raw-primitives widget layer. Make 'Material compiles against public flui-widgets only' a gate before first crates.io publish (after Flutter 2026).
- Navigation state is a value: one typed route stack is the source of truth, and imperative push/pop just edits it, with no second, non-addressable kind of route (Flutter's go_router guidance, SwiftUI NavigationStack).
- Field-granular inherited reads as the default derived API, with whole-provider reads as the explicit exception (MediaQuery.sizeOf lesson; FLUI depend_on_field at crates/flui-view/src/context/build_context.rs:648).
- A macro-derived observable model struct with per-field read tracking and one-shot invalidation, on top of realm signals (SwiftUI @Observable, SE-0395).
- A state-object text field: a signal-backed buffer with an edit{} transaction, input and output transformations and undo. No value+callback-only field (Compose TextFieldState).
- A synchronous, read-only text-store query surface in the platform IME contract (text in range, selection, rect for range, index for point) to serve TSF, NSTextInputClient, UITextInput and InputConnection. On Windows, TSF plus UIA TextPattern from day one.
- Typed, synchronous native capabilities with no message channel, and an open, per-realm registry so plugins outside the repo can add capabilities. Separate interface and implementation crates with an endorsed default per platform through Cargo features (Flutter federated plugins and direct interop, KMP interfaces plus factories).
- Renderer contracts in the style of Impeller: pipeline-state warmup and caching, labelled GPU resources, frame capture as instrumentation. One renderer path including the web fallback.
- OS-compositor overlays (DirectComposition, CALayer, SurfaceControl) as the primary design for embedded native content, with texture copy as the fallback (Flutter HC++ direction).
- Saveable state as one contract shared by lazy-list eviction, Router back-stack and hot reload (Compose rememberSaveable and SaveableStateHolder). This complements FLUI's existing RAII keep-alive lease.
- Keep the reconciliation and signal runtime usable without rendering (Compose runtime used by Molecule and Redwood), for A2UI server trees, agent tests and headless logic.
- Data-driven migrations shipped per crate for `flui migrate` (dart fix model).
- Batched signal transactions to get Compose-snapshot atomicity (N writes, one notify) without MVCC or global state.

## Patterns to avoid

- Bundling Material and Cupertino into the core release train or the Stable API tier.
- Two navigation APIs with different deep-link and restoration semantics (Navigator 1.0/2.0, pageless vs page-backed routes).
- Stringly-typed or async-only message channels to native code, and global mutable plugin registration (`Platform.instance = ...`).
