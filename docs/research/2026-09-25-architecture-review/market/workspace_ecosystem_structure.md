# Market survey: workspace_ecosystem_structure: how mature UI frameworks lay out repos, crates/packages and ecosystems, and what that means for FLUI's crate topology, delivery layers (core / official / community) and horizons H0-H4

_Raw output of the `market:workspace_ecosystem_structure` agent (2026-09-25). Unedited; each claim carries the source the agent cited._

## Findings

- **Flutter: Material/Cupertino decoupling (3.47)** — Material and Cupertino were frozen in flutter/flutter (contributions frozen from 3.44 / 7 Apr 2026) and re-released as pkg:material_ui and pkg:cupertino_ui 1.0.0 on pub.dev with Flutter 3.47 (12 Aug 2026). The packages release weekly; the core ships a stable every 3 months. Migration is automatic (`dart fix --apply --code=migrate_design_widgets`), and a MaterialUiCompatibilityBridge lets unmigrated dependencies coexist. The stated reasons: upgrade friction (a framework upgrade forced design changes on apps), a worst-case 16-week lag from submission to stable, and 'architectural bloat', meaning foundational widgets had been built inside the design libraries instead of the base widgets library. _Relevance:_ FLUI's plan already puts Material/Cupertino in official packages, but today they are in-repo layer-7 crates and the facade defaults to them (Cargo.toml `default = ["material"]`). Flutter's third reason is the lesson that matters most structurally: move Material out only after its foundational pieces (ink, focus, overlay, text field) are Raw primitives in flui-widgets. Otherwise the split copies Flutter's bloat. The freeze → re-release → compat bridge → auto-migration sequence is the template for FLUI's own H3 extraction. ([source](https://flutter.dev/blog/decoupling-material-cupertino ; https://docs.flutter.dev/release/breaking-changes/material-ui-and-cupertino-ui ; https://flutter.dev/blog/flutters-material-and-cupertino-code-freeze))
- **Flutter: localizations moved into the design packages** — After decoupling, Material/Cupertino localization delegates and translated strings ship inside material_ui/cupertino_ui instead of flutter_localizations. `GlobalMaterialLocalizations.delegates` now includes the Cupertino and Widgets delegates. _Relevance:_ FLUI has flui-localizations as a separate layer-8 crate (about 0.3k LOC) above the design systems (Cargo.toml:91-103; crates/flui-localizations/Cargo.toml depends only on flui-widgets and flui-types). Flutter's current shape argues for each catalog owning its translations and dropping the standalone layer 8. This matches the roadmap's own note that flui-localizations should merge (roadmap.md:256). ([source](https://docs.flutter.dev/release/breaking-changes/material-ui-and-cupertino-ui))
- **Flutter: federated plugins** — A federated plugin is split into an app-facing package, a platform-interface package, and per-platform implementation packages. An endorsed implementation is added by the app-facing package, so apps get it automatically; a non-endorsed one must be depended on explicitly. Implementers must `extends` the interface (enforced by plugin_platform_interface), not `implements` it, so that adding a method does not break them. There is a long-standing request for a way to override an endorsed implementation. _Relevance:_ This is the direct precedent for H1 `PlatformCapability`. The Rust equivalents: a trait crate plus #[cfg(target_os)] impl crates. An 'endorsed' impl becomes a target-specific dependency of the facade crate. Evolvability comes from sealed traits or default methods. Design an override path for the endorsed impl on day one, since Flutter still lacks one. ([source](https://docs.flutter.dev/packages-and-plugins/developing-packages ; https://github.com/flutter/flutter/issues/80374))
- **Flutter: monorepo vs separate engine repo** — Flutter kept flutter/engine separate for years and documented why: they were separate products, the framework consumed engine binaries, and a shared repo invites accidental cross-API dependencies. It still merged engine and framework into one monorepo in December 2024. _Relevance:_ The sources disagree over time, and even Flutter reversed itself. The takeaway: repo boundaries are a coordination cost, and API boundaries need their own enforcement. For a bus-factor-1 project, a monorepo with enforced layer rules (FLUI's `cargo xtask workspace`) is closer to where Flutter ended up than to its old split. Separate repos for official packages (plan.md delivery layers) should wait until a package has its own release cadence. ([source](https://github.com/flutter/flutter/wiki/Why-we-have-a-separate-engine-repo/f451d81da45fd403739385c5492813fc3f2a4131 ; https://github.com/flutter/flutter/issues/160628))
- **Bevy: crate-per-subsystem plus facade** — Bevy is a workspace of 80+ bevy_* crates. The `bevy` facade re-exports bevy_internal, which aggregates features. Cargo features map to plugins/crates so unused subsystems are not compiled. Dynamic linking (`dynamic_linking` feature / bevy_dylib) is described as 'the most impactful compilation time decrease' for iteration. _Relevance:_ FLUI already has the facade + features shape (root Cargo.toml [features]). Bevy's biggest compile-time lever is dylib linking, not crate count. FLUI could add a dev-only dylib facade feature cheaply. That is a different lever from crate splitting and fits the 2026-09-23 'don't split widgets' decision. ([source](https://bevy.org/learn/quick-start/getting-started/setup/ ; https://docs.rs/bevy_dylib ; https://deepwiki.com/bevyengine/bevy/1.2-crate-organization))
- **Bevy: crate tiers** — Bevy issue #16172 proposes three tiers. Tier 1 is the `bevy` facade, which must build cross-platform with documented features and examples. Tier 2 is standalone crates (bevy_ecs, bevy_reflect), which must pass Miri on unsafe code, build no_std, and build without default features. Tier 3 is everything else, used mostly by plugin authors and 'lacking in documentation'. _Relevance:_ FLUI's H3 governance defines API tiers (Stable/Evolving/Experimental) per surface, but it has no per-crate tier that says which of the 27 published crates are meant for direct third-party use. Adopting 'facade = tier 1; flui-rendering/flui-geometry/flui-tree = standalone tier with stronger gates; the rest = internal' would bound the semver surface. ([source](https://github.com/bevyengine/bevy/issues/16172))
- **Bevy: staged stabilization** — Cart proposed a `bevy_platform` meta-crate that re-exports only the stable core (bevy_ecs, bevy_app, bevy_reflect, bevy_time) so plugin authors get a stability window before 1.0. The same discussion notes that Cargo's semver rules block stabilizing a crate that exposes pre-1.0 dependencies such as glam in its API. _Relevance:_ This affects H3 directly. FLUI's Stable surface cannot re-export pre-1.0 upstream types: wgpu, accesskit 0.25, ui-events 0.3, kurbo 0.13, cosmic-text/parley. Every public signature that leaks one of them is a structural 1.0 blocker. A leak audit should be an H2 exit criterion. A 'stable subset' meta-crate is a pattern FLUI can use for the H1 plugin surface (PlatformCapability + LifecycleContext) before a full freeze. ([source](https://github.com/bevyengine/bevy/discussions/9789))
- **Bevy: ecosystem lag after breaking releases** — The unofficial cheat book says most third-party Bevy plugins took two to eight weeks to update after Bevy 0.15. Bevy's own plugin guide asks authors to publish version-compatibility tables, depend on bevy with `default-features = false`, use the `bevy_` prefix but ask before taking generic names, and list crates in Bevy Assets. _Relevance:_ H4's metric '10 community crates with 1k+ downloads' needs a thin, slow-moving surface for extension authors, or every minor (planned every 6-8 weeks) breaks them. The lesson for FLUI: publish plugin-author guidance (naming, a minimal feature set of the facade, compatibility table) and keep the render-object/PlatformCapability extension protocol on a slower cadence than the widget catalog. ([source](https://bevy-cheatbook.github.io/setup/unofficial-plugins.html ; https://bevy.org/learn/quick-start/plugin-development/))
- **Linebender: shared ecosystem crates** — Linebender maintains independent, separately versioned crates that are shared across Rust UI projects: kurbo (curves/paths), peniko (brush/color/style types), Parley + Fontique (text), Vello (rendering, now GPU, CPU and hybrid variants), AccessKit, and ui-events (a winit-independent pointer/keyboard/IME model with a ui-events-winit adapter). Peniko moved Font/Blob into a 'Linebender Resource Handle' crate so the same type is shared across peniko versions. Bevy is migrating bevy_text from cosmic-text to Parley (issue #21765, PR #22879; the 0.18→0.19 migration guide), citing better shaping/layout performance, inline-box layout for widgets, and a simpler API. _Relevance:_ FLUI already uses ui-events 0.3, accesskit 0.25 and an optional kurbo 0.13 bridge (Cargo.toml:144,301; crates/flui-geometry/Cargo.toml:37), and it plans Parley (ADR-0077). Converging on Linebender's vocabulary types, rather than parallel FLUI-only types, lowers the cost of H4 interop (Vello, velato, community renderers) and lets agents reuse known APIs. The price: these are all pre-1.0, which is the Bevy/glam semver trap above. ([source](https://linebender.org/ ; https://linebender.org/blog/tmil-24/ ; https://linebender.org/blog/tmil-11/ ; https://crates.io/crates/ui-events-winit ; https://github.com/bevyengine/bevy/issues/21765 ; https://bevy.org/learn/migration-guides/0-18-to-0-19/))
- **Xilem/Masonry crate split** — The xilem repo splits into xilem_core (framework traits), xilem_masonry (native binding), xilem (a batteries-included winit wrapper), xilem_web (DOM), masonry_core (engine, embeddable into existing wgpu apps), masonry (widgets and theming), masonry_winit and masonry_android_view (backends), masonry_testing (harness), and tree_arena. Masonry was split into masonry_core and masonry so the core can be embedded in existing apps and alternative drivers can exist without winit. _Relevance:_ Linebender splits along backend/embedding seams (core vs platform runner vs testing), not along widget features. That matches FLUI's 2026-09-23 decision (layers yes, feature crates no). It also points at a seam FLUI lacks: an embeddable realm core without the flui-app run loop. The H1 'external GPU content' and H4 embedded/kiosk horizons both need to host FLUI inside someone else's loop. ([source](https://github.com/linebender/xilem/blob/main/ARCHITECTURE.md ; https://linebender.org/blog/tmil-15/ ; https://docs.rs/crate/masonry_core/latest))
- **Dioxus: many small crates plus AI surface** — The Dioxus 0.7 workspace groups crates into about 14 families (renderers ×5, core ×4, fullstack ×4, state ×3 with generational-box/signals/hooks, web ×6, native/Blitz ×3, assets ×5, router ×2, hot reload ×3, CLI ×3, and others) so third-party renderers depend only on the core. 0.7 ships an auto-generated first-party llms.txt (about 242k tokens) and an MCP server for editors. _Relevance:_ Dioxus shows that fine granularity can coexist with AI discoverability, but it gets there through a generated llms.txt and MCP, not through fewer crates. For FLUI, that suggests the answer to 'agents can't find existing code' (the stated reason against splitting, roadmap.md:64) is a generated catalog/llms.txt from rustdoc plus G6. The crate count can then be set by build and semver needs. ([source](https://dioxuslabs.com/learn/0.7/beyond/project_structure/ ; https://dioxuslabs.com/blog/release-070/ ; https://context7.com/llmstxt/dioxuslabs_learn_0_7_llms-full_txt))
- **Slint: internal vs public crates, multi-workspace** — Slint keeps internal crates under internal/ (compiler, core, backends, renderers). They are not semver-stable and are exact-version pinned. The public api/ crates (Rust, C++, Node, Python, wasm) carry the stable 1.x guarantee. The Renderer trait is sealed so internals can evolve. examples/, demos/, tests/ and ui-libraries/material/ are separate workspaces sharing one target dir, which keeps rust-analyzer fast and builds common crates once. A 2024 issue found duplicate dependency versions across Slint crates (bitflags 1/2, base64 0.21/0.22) inflating build time and binary size. _Relevance:_ FLUI already exact-pins internal deps (`version = "=0.2.0-dev"`, e.g. crates/flui-localizations/Cargo.toml) and centralises [workspace.dependencies], so half the Slint pattern is in place. The missing half: all 27 crates are `publish = ["crates-io"]` with no internal/public distinction, so every crate looks like a supported API. Marking layers 0-6 internal (docs, a naming convention like Slint's i-slint-*, or at least a README banner) and keeping semver-checks on the facade plus a few standalone crates would cut the H3 freeze surface sharply. Slint's Material also lives as a separate workspace in the same repo, an in-between step before separate repos. ([source](https://github.com/slint-ui/slint/blob/master/AGENTS.md ; https://deepwiki.com/slint-ui/slint/4.1-rust-api ; https://github.com/slint-ui/slint/issues/5183))
- **Iced: renderer-agnostic core, pluggable renderers** — Iced splits iced_core, iced_widget, iced_runtime, iced_winit (shell), iced_wgpu and iced_tiny_skia (software fallback). The runtime is renderer-agnostic, and renderers are chosen by facade features. _Relevance:_ Iced treats the software renderer as a peer crate behind a trait, not a special mode of the GPU engine. FLUI's H0 CPU reference renderer (E7, golden tests) and H2 software fallback would be more natural as a second backend crate implementing the engine's layer-consumer contract than as code inside flui-engine (74k LOC). ([source](https://docs.rs/crate/iced/latest/features ; https://deepwiki.com/iced-rs/iced/4.1-wgpu-renderer))
- **GPUI/Zed: framework trapped in an app monorepo** — gpui lives in zed-industries/zed/crates/gpui. crates.io has gpui 0.2.2 (last updated 22 Oct 2025, 7 versions), but the community has built extractions and forks: gpui-ce, gpui-pre-* snapshots, and longbridge/gpui-fast, which extracts gpui plus the 27-crate transitive closure 'so it can be built without checking out or compiling the editor'. gpui-component (60+ components) is a third-party catalog. _Relevance:_ This is the counter-example: a framework co-developed with one product and published irregularly produces forks and ecosystem fragmentation. FLUI's H0 exit ('clean consumer builds Notes from crates.io') and a regular publish train are the structural guard against this. The hero app should consume FLUI only through the published facade, never through path dependencies on internals. ([source](https://crates.io/api/v1/crates/gpui ; https://github.com/longbridge/gpui-fast ; https://crates.io/crates/gpui-ce ; https://crates.io/crates/gpui-component))
- **Jetpack Compose: layers built only on lower layers' public API** — Compose is layered runtime → ui → foundation (design-agnostic building blocks) → material. 'Each layer builds on public APIs of the lower layers to verify the module boundaries and enable you to replace any layer.' A BOM pins mutually compatible versions of the separately versioned libraries. _Relevance:_ This is the strongest precedent for the 'Raw primitives first, skins next' decision. The enforceable form: flui-material and flui-cupertino may use only the pub API of flui-widgets (no `__private` seams or #[doc(hidden)] hooks). A Rust crate boundary gives that for free, which is an argument for keeping design systems as separate crates even while they stay in the monorepo. The BOM corresponds to FLUI's facade with exact pins. ([source](https://developer.android.com/develop/ui/compose/layering ; https://developer.android.com/develop/ui/compose/bom))
- **Crate granularity vs compile time** — rustc's LLVM codegen for one crate is largely serial. Feldera cut a generated 100k-line crate's build from about 30 min to 2m10s by splitting it into 1,106 crates (all 128 threads busy). matklad warns that splitting helps only if the graph is wide, not a deep chain, and that generics crossing crate boundaries are monomorphised downstream, giving 'accidentally-quadratic' compile times. Proc macros stall pipelining. More codegen units trade code quality for parallelism. _Relevance:_ FLUI's graph is a deep 11-layer chain (Cargo.toml:91-103), and flui-widgets (about 83k LOC) is one serial codegen unit near the top. Splitting it into sibling crates at the same layer would widen the graph only if they don't depend on each other. The 2026-09-23 decision (roadmap.md:55-72) rests on '32 cores, small win'. That is a hypothesis that `cargo build --timings` on flui-widgets would settle; the sources suggest the win depends on graph width, not core count. Separately, generic-heavy public APIs in lower layers (RenderBox protocol, arity types) push monomorphisation into flui-widgets and user crates. ([source](https://www.feldera.com/blog/cutting-down-rust-compile-times-from-30-to-2-minutes-with-one-thousand-crates ; https://matklad.github.io/2021/09/04/fast-rust-builds.html ; https://nnethercote.github.io/2023/07/11/back-end-parallelism-in-the-rust-compiler.html))
- **Multi-crate publishing** — Rust 1.90 stabilized `cargo publish --workspace` / `-p a -p b`. It publishes interdependent crates in dependency order and verifies the full set as if published. It is still non-atomic, so a server error can leave a partial release. _Relevance:_ This removes most of the need for custom publish-order tooling in roadmap track H1 (crates.io pipeline). Each published crate still adds non-atomic release risk and a crates.io name to own forever. That is an argument for publishing fewer crates rather than more. ([source](https://www.infoworld.com/article/4060262/rust-1-90-brings-workspace-publishing-support-to-cargo.html ; https://github.com/rust-lang/cargo/pull/15636))
- **Official vs community package signals** — pub.dev combines verified publishers (identity only, 'not code quality'), automated pub points (pana analysis on every publish) and a committee-curated Flutter Favorite badge (license, tags matching versions, docs, runtime behaviour, dependency quality). _Relevance:_ This maps onto the plan's 'community catalog with verifiable badges'. The machine-checkable part (a CI-style score: builds against current flui, has harness tests for its render objects, semantics snapshots, no unsafe without SAFETY) can be a `flui` CLI or xtask check that community authors run. That fits principle 4 (machine-readable) and the AI-native bet better than a human committee, which a bus-factor-1 project cannot staff. ([source](https://pub.dev/help/scoring ; https://docs.flutter.dev/packages-and-plugins/favorites))

## Pitfalls others hit

- Flutter: foundational widgets grew inside Material instead of the base widgets library. Extracting Material years later then needed a code freeze, a compat bridge, and an automated `dart fix` migration (flutter.dev/blog/decoupling-material-cupertino).
- Flutter: design-system changes rode the framework's quarterly train, so fixes waited up to 16 weeks and upgrades forced visual changes on apps (same source).
- Flutter federated plugins: there is still no clean way to override an endorsed platform implementation (flutter/flutter#80374). Implementers using `implements` instead of `extends` break when the interface grows (docs.flutter.dev developing-packages).
- Bevy: frequent breaking releases left third-party plugins 2-8 weeks behind each release (bevy-cheatbook unofficial-plugins). Tier-3 crates used by plugin authors are under-documented (bevy#16172).
- Bevy: a 1.0 is blocked by pre-1.0 upstream types (glam) in the public API, because Cargo semver cannot stabilise over them (bevy discussion #9789).
- Bevy: text on cosmic-text had to be migrated to Parley after the fact, with breaking changes to glyph APIs (bevy#21765, 0.18→0.19 migration guide). Bevy had earlier re-exported all of cosmic_text and then removed the re-exports (bevy PR #19516).
- Slint: separately managed crates drifted to duplicate dependency versions (bitflags, base64, async-channel), inflating build time and binary size (slint#5183).
- GPUI: developed inside the Zed monorepo and published irregularly (crates.io gpui 0.2.2, last update Oct 2025), which led to community extractions and forks (gpui-ce, gpui-fast with 27 extracted crates).
- Crate splitting without a wide graph gives little: a deep chain stays serial, and generics crossing crate boundaries recompile downstream (matklad fast-rust-builds).

## Patterns to adopt

- Split by seams that differ in release cadence, platform or embedding (core vs backend runner vs testing vs design system), not by widget feature. This follows Masonry (core/winit/android_view/testing), Iced (core/widget/winit/wgpu/tiny_skia) and Flutter (widgets vs material_ui). It is consistent with FLUI's 2026-09-23 layers-not-features decision.
- Classify every crate as public or internal, as Slint (internal/ exact-pinned, api/ semver) and Bevy tiers do. Semver-check only the facade and a few standalone crates (geometry, tree, rendering protocol, and the PlatformCapability trait crate). Document the rest as internal even though they must be published.
- Before extracting Material/Cupertino, build the Raw primitives into flui-widgets and forbid the design crates from using non-pub seams (Compose: 'each layer builds on public APIs of the lower layers'). Then follow Flutter's freeze → re-release → compat shim → auto-migration sequence (a `flui migrate` rule).
- Move each catalog's localizations into the catalog crate, as Flutter now does, and drop the standalone localization layer.
- Model PlatformCapability on federated plugins, translated to Rust: an app-facing API crate, a sealed or default-method interface trait, per-target implementation crates pulled in by `[target.'cfg(..)'.dependencies]` as 'endorsed', and an override hook from day one.
- Offer a stable-subset meta-crate for extension authors before 1.0, as Bevy's proposed bevy_platform does: re-export only the render-object protocol, PlatformCapability and LifecycleContext, on a slower cadence than the catalog.
- Converge on Linebender vocabulary crates (kurbo, peniko, parley/fontique, ui-events, accesskit) at the edges, but wrap them in the Stable API rather than exposing them, until they reach 1.0.
- Use a dev-only dynamic-linking facade feature (Bevy's `dynamic_linking`) as the main iteration-time lever, and measure with `cargo build --timings` before any split decision.
- Solve AI discoverability with generated artifacts: llms.txt from rustdoc, a widget catalog, and MCP (Dioxus 0.7). Don't let it drive crate count.
- Use `cargo publish --workspace` (Rust 1.90) for the release train, and keep the published-crate count as low as the layering allows, since publishing is non-atomic.
- Publish plugin-author guidance (naming prefix policy, minimal facade features, a compatibility table, and a listing in an official catalog with automated badges), as Bevy does and like pub points, not a committee.
- Put the CPU reference and software renderers in a separate backend crate implementing the engine contract (Iced's tiny_skia peer), not as a mode inside flui-engine.

## Patterns to avoid

- Co-developing the framework inside a product repo and publishing irregularly (the GPUI/Zed forks). The hero app must consume the published facade.
- Re-exporting a pre-1.0 upstream crate wholesale from a stable surface (Bevy's cosmic_text re-export, removed later; the glam semver block).
- Letting design systems reach into core internals, or growing foundational widgets inside Material (Flutter's 'architectural bloat').
- Splitting crates by feature along a deep dependency chain and expecting compile-time wins without measuring graph width (matklad).
- Releasing the extension surface as fast as the catalog (Bevy's plugin lag). Plugins and render-object protocols need a slower, tiered cadence.
- Separate repos for official packages before they have an independent cadence. Flutter merged its engine back into a monorepo in 2024, and Slint keeps Material in the same repo as a separate workspace.
- Per-crate dependency versions drifting apart (Slint#5183). Keep [workspace.dependencies] as the only place versions are set, which FLUI already enforces with cargo-shear/cargo-deny.
- Treating every published crate as equally supported. 27 crates on crates.io without tiers become 27 semver promises at H3.
