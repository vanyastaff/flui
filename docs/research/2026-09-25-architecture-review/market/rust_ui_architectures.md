# Market survey: Market survey: runtime architectures of Rust UI frameworks (2026): Xilem/Masonry, GPUI, Iced, egui, Slint, Dioxus (+Blitz, Subsecond), Makepad, Floem, Vizia, Freya, and what they mean for FLUI's global and crate architecture

_Raw output of the `market:rust_ui_architectures` agent (2026-09-25). Unedited; each claim carries the source the agent cited._

## Findings

- **Xilem/Masonry: widget ownership and passes** — In 2024 Masonry was reworked from 'widgets own children' to 'widgets own keys into arena storage' (a new tree_arena crate). Recursive per-widget event handling was consolidated into framework-owned passes that access the arena directly, which removed per-widget reimplementation of tab focus, pointer icons and similar behavior. The author reports that 'reworking internals' was planned for after feature work but took most of the year. _Relevance:_ This confirms FLUI's slab arenas plus NonZeroUsize IDs. Cross-cutting behavior (focus traversal, cursor, semantics, hit-test) should be framework passes over the arena, not trait methods each widget re-implements. The same post-mortem warns that internals rework postponed behind features eats the schedule, which argues for FLUI settling the H2 runtime shape (damage, raster lane, per-realm text) before the H3 freeze. ([source](https://poignardazur.github.io/2025/03/24/plan-for-linebender-post-mortem/))
- **Masonry crate split (core / testing / winit backend)** — Masonry split out masonry_core (for compile parallelism) and a separate Masonry Testing crate (so test code cannot reach release binaries). It uses ui-events types for event handling and IME, which reduces its winit dependency and allows non-winit hosts such as baseview for VST plugins. _Relevance:_ FLUI already depends on ui-events (D:\flui\Cargo.toml:301; crates/flui-interaction/Cargo.toml:34) and has ui-events-winit optional in crates/flui-platform/Cargo.toml:58. The market direction supports FLUI's layer model: the core never sees winit, and the windowing host is a replaceable backend. It also supports keeping flui-testing as a separate layer crate rather than a cfg(test) module. ([source](https://linebender.org/blog/tmil-25/ ; https://docs.rs/masonry_winit/latest/masonry_winit/))
- **Xilem View layer: critical review (2026)** — A 2026 critical review argues that Xilem's generics-heavy View traits (about 30 traits, about 70 View implementations) produce obtuse errors and long compile times, and make architectural iteration impossible. It says two-way bindings don't fit Rust ownership and that side effects inside views are a mistake. It proposes a non-generic, type-erased Component and accepting slightly slower code for less complexity. Lobsters commenters add that simple APIs and fast compiles matter more than peak performance. _Relevance:_ This is the main warning for FLUI's public View API before the H3 Stable tier: keep View/State/Element object-safe or type-erased at the edges, and don't let compile-time arity types leak into user-facing signatures. It also supports ADR-0074's rule that signals are never written in build (no side effects in build). Sources disagree: Linebender's own post-mortem says the Masonry backend is healthy and names only three remaining architectural changes (styling, layout, widget creation). ([source](https://hackmd.io/@s_haMSbyTAOWfoXc1aYNUg/Hka74gCwZg ; https://lobste.rs/s/bccwjx/critical_review_xilem_2026))
- **Linebender renderer and text direction 2026** — In Q1 2026 Masonry moved onto an 'imaging' abstraction so it can use backends other than Vello. The 'unified API' effort for Vello was abandoned in favor of imaging/AnyRender. Vello Hybrid/CPU (sparse strips) reached beta quality. Glyph and emoji rendering was extracted into a new crate, Glifo, with atlas-based glyph caching. Parley gained full AccessKit text-property support and is adopted by Bevy, Gosub and others. _Relevance:_ This supports FLUI keeping its own painting DisplayList → flui-engine seam (renderer swappable behind one crate) and not betting on Vello (the plan defers Vello to H4). Parley's AccessKit text properties and Glifo's atlas caching bear directly on the pending ADR-0077 rasterization spike: the spike should evaluate Glifo as an alternative to hand-rolling Parley-to-ADR-0067-atlas glue. ([source](https://linebender.org/blog/tmil-25/))
- **Parley convergence (Bevy)** — Bevy migrated bevy_text from cosmic-text to Parley (listed in the 0.18→0.19 migration guide). Glyph byte_index/byte_length were dropped because Parley does not expose them in GlyphRuns. _Relevance:_ This is independent evidence for ADR-0077 (Parley). The Bevy PR shows a concrete API loss (glyph-to-byte mapping) that FLUI's editable text and caret/selection code must plan around. FLUI is still on cosmic-text 0.19 (crates/flui-painting/Cargo.toml:33), with Parley only in tools/text-spike/Cargo.toml:23. ([source](https://bevy.org/learn/migration-guides/0-18-to-0-19/ ; https://github.com/bevyengine/bevy/pull/22879))
- **GPUI: ownership/state model** — GPUI has a single App that owns all entities. Entity<T> handles are identifiers, not owners, and Rc<RefCell> was judged inadequate. An entity is leased out of App (moved to the stack) during an update. notify()/emit() queue effects, and flush_effects runs to completion, which prevents reentrancy bugs. _Relevance:_ This is the closest precedent for FLUI's realm-owned, Copy-handle signals (ADR-0074) and single-writer UiRealm. Two lessons to adopt: an explicit effects queue flushed at a defined point in the frame (so Effect/Computed in ADR-0075 cannot re-enter build), and lease-style mutable access instead of locks on per-node state, which matches AGENTS.md's rule that there are no locks on the frame path. ([source](https://zed.dev/blog/gpui-ownership))
- **GPUI: element/layout per frame and a performance fork** — Upstream GPUI runs request_layout → prepaint → paint with Taffy. The longbridge gpui-fast fork found that the engine cleared its whole Taffy tree every frame, so the per-node cache was never reused. Keeping layout nodes, keying elements by path, reusing shaped text and using an R-tree-like bounds tree cut a 2500-label grid from 8.27 ms to 3.71 ms (static) on M4. _Relevance:_ Retained layout caches and stable identity are where the performance comes from. FLUI's retained Element/RenderObject trees already have this, but FLUI repaints fully every frame (DamageTracker has no producer, per context.md). The fork shows that the payoff of retention appears only once caches actually survive frames, so damage and layer caching (H2) should be treated as architecture, not polish. ([source](https://github.com/longbridge/gpui-fast ; https://gpui-kit.com/docs/element/))
- **GPUI renderer: Blade replaced by wgpu** — Zed removed the Blade graphics library from GPUI's Linux renderer and reimplemented it on wgpu (merged February 2026). The PR calls Blade 'a mess' causing freezes on NVIDIA/Wayland and calls wgpu the de facto Rust standard that benefits from Bevy/Iced contributions. A later PR adds Linux headless rendering on gpui_wgpu. _Relevance:_ This strongly validates FLUI's single wgpu renderer (principle 2) and argues against custom per-OS GPU backends. The headless wgpu path mirrors FLUI's need for a CI-runnable render (golden via CPU reference, E7). ([source](https://github.com/zed-industries/zed/pull/46758 ; https://github.com/zed-industries/zed/pull/64718))
- **GPUI: deterministic testing** — #[gpui::test] runs tests on a deterministic dispatcher seeded from SEED. It supports seeds(...), iterations = N and retries. The seed controls task interleaving across ForegroundExecutor/BackgroundExecutor, with fake time via TestAppContext. _Relevance:_ FLUI has a virtual-clock frame driver (flui-testing) but async is driven by its own AsyncDriver (crates/flui-scheduler/src/async_driver.rs). A seeded, interleaving-randomizing executor is the model to adopt when FLUI makes its Task/Worker async model explicit (plan: 'явная async-модель, tokio опционален'). It also fits G7 record/replay. ([source](https://docs.rs/gpui/latest/gpui/attr.test.html))
- **Iced: architecture evolution 0.12–0.14** — Iced added multi-window and TextEditor (0.12). 0.13 brought the Program/Task/Daemon APIs (Task replacing Command) and a type-driven renderer fallback (wgpu with a tiny-skia CPU fallback). 0.14 (December 7) brought reactive rendering, time-travel debugging, hot reloading, Comet devtools with presentation metrics, first-class headless end-to-end testing (iced_test) and IME. _Relevance:_ Iced moved away from full per-frame redraw and made a CPU renderer a first-class fallback. Both match FLUI's H0 (CPU reference renderer for golden tests) and H2 (damage, software fallback) goals. Iced's time travel works because Elm-style messages are data, which argues that FLUI's record/replay (G7) should record input events at the platform→interaction seam, not widget state. ([source](https://github.com/iced-rs/iced/releases ; https://github.com/iced-rs/iced/releases/tag/0.14.0))
- **Iced hot reload via Subsecond** — Iced's hot reloading uses Subsecond through a generic cargo-hot tool. User code does not change, but changes to the application State or Message types require a cold restart. _Relevance:_ A second framework besides Dioxus confirms the Subsecond decision, and also confirms its ceiling: struct-shape changes restart. FLUI's hot-reload contract should state this limit explicitly: build/logic edits preserve state, State struct edits restart the realm. ([source](https://github.com/iced-rs/iced/pull/3000))
- **Subsecond integration contract** — Subsecond is a jump table plus HotFn/subsecond::call integration points. Calling a stale function version triggers a caught panic and a retry. It cannot hot-reload struct layout, so frameworks must dispose or re-instance state. New statics leak their destructors. Thread-locals in the tip crate appear to reset on each patch. It supports Windows, macOS, Linux, Android, iOS (not device) and wasm. _Relevance:_ FLUI's current flui-hot-reload is a dlopen/ABI-token design with documented unsoundness (crates/flui-hot-reload/src/lib.rs:1-40) and no subsecond dependency (crates/flui-hot-reload/Cargo.toml:32-38). Adopting Subsecond means deleting or shrinking this crate, not wrapping it. The thread-local reset directly conflicts with any remaining thread_local!/OnceLock state in user-reachable crates (for example FONT_SYSTEM at crates/flui-painting/src/text_layout/layout.rs:124). This is one more concrete reason for principle 3 (no global state): realm-owned state survives patching. ([source](https://docs.rs/subsecond/latest/subsecond/))
- **Dioxus 0.7: Subsecond, Stores, Blitz, llms.txt** — Dioxus 0.7 ships Subsecond hot-patching on web, desktop and mobile, with explicit integration points and no automatic struct migration. It adds Stores (nested reactive state that marks only changed items dirty, e.g. BTreeMap entries) and an llms.txt to reduce LLM hallucinations. Blitz (Stylo CSS + Taffy + Parley + Vello) powers dioxus-native, is a work in progress, and has AccessKit behind a feature. _Relevance:_ Stores are the precedent for FLUI's reactive collections (A8): per-key dirtiness instead of whole-collection signals. llms.txt is a cheap AI-native deliverable next to G6's machine-readable catalog. Blitz shows the cost of a CSS/web-engine path, which FLUI rightly rejects as a non-goal. ([source](https://dioxuslabs.com/blog/release-070/ ; https://docs.rs/dioxus-native/latest/dioxus_native/))
- **Freya 0.4: left Dioxus to own its reactive core** — Freya 0.1–0.3 were built on Dioxus core crates. In 0.4 Freya was rewritten with its own reactive and component model because depending on a large external framework meant being 'affected by any upstream change and design decision'. It keeps Skia rendering, its own Torin layout, headless freya-testing, devtools, hot reload and multi-window. _Relevance:_ This supports FLUI owning the spine crates (flui-view reactivity, reconciliation) while borrowing leaf crates (Parley, AccessKit, wgpu, ui-events). The dividing line: own anything that defines the user's mental model (principle 1), and depend on anything that is a replaceable implementation detail. ([source](https://freyaui.dev/posts/0.4 (via search summary; direct fetch returned HTTP 429) ; https://github.com/marc2332/freya))
- **Vizia: lenses replaced by signals** — Vizia ships a MIGRATION_LENS_TO_SIGNALS guide. State is created as Signal::new, held as handles in models, mutated only via .set()/.update(), and reached through cx. _Relevance:_ A third framework (after Floem and Dioxus) converged on signals with context-scoped handles. This supports ADR-0074. It also shows the migration cost of changing the state primitive late, so FLUI should freeze the signals surface before H3 and keep setState only as a documented low level. ([source](https://github.com/vizia/vizia/blob/main/MIGRATION_LENS_TO_SIGNALS.md))
- **Floem: signals plus build-once view tree** — Floem uses reactive primitives inspired by leptos_reactive and builds the view tree only once, so the view-generation function is not a bottleneck. It uses Taffy flex/grid layout and several renderers (vger/wgpu, Vello, Skia) with a tiny-skia CPU fallback. _Relevance:_ Fine-grained signals with a build-once tree is the alternative to FLUI's rebuild-and-reconcile model. It maps to the plan's open question 'element-level или render-level гранулярность': Floem answers render/property-level. FLUI can keep rebuild semantics for users while letting signals dirty render-object properties directly for hot paths (animation, text). ([source](https://github.com/lapce/floem))
- **egui: immediate mode trade-offs, and an AccessKit-based agent protocol** — egui acknowledges immediate-mode limits: layout needs the size before position (it relies on frame-delayed sizing or request_discard second passes), and very large scroll contents are slow because they are laid out every frame. egui now has an inspection protocol (EGUI_INSPECTION=1, port 5719) that streams AccessKit tree updates and accepts action requests. egui_mcp sits on it, and it is intended to be framework-agnostic for kittest/AccessKit users. _Relevance:_ The egui/kittest protocol is exactly the 'AccessKit vocabulary as agent vocabulary' shape of ADR-0080, but in-process. FLUI's tools/desktop-mcp drives apps from outside through UIA, capture and real input (commit d6ac4f936). The market evidence says both are needed: in-app semantics-tree and action-request transport as the primary channel (portable to Linux, macOS and web CI), with OS-level UIA as the live-smoke verification of the platform adapter. Adopting or co-designing the egui_inspection wire format would give FLUI a standard instead of a private protocol. ([source](https://github.com/emilk/egui ; https://github.com/rerun-io/kittest_inspector))
- **Slint: compiled DSL, property tracking, MCU, MCP** — Slint compiles .slint into Rust/C++ with a runtime PropertyTracker for dependency tracking. Its software renderer supports line-by-line rendering for MCUs, and an 'unsafe-single-threaded' feature replaces thread_local on no_std. Slint 1.15 (Feb 2026) added mobile safe area and keyboard insets and wgpu 28. Slint's MCP server (July 2026) is compiled into the app, runs headless via SLINT_BACKEND=headless, and exposes the element tree, accessibility properties, input and screenshots. The rationale is that screenshots 'burn' tokens compared with a structured tree. _Relevance:_ Slint and egui independently shipped in-process, headless-capable MCP. This makes FLUI's H0 exit ('агент проходит сценарий через flui mcp') table stakes rather than a differentiator by 2027. FLUI's differentiation has to be the single catalog/contract across hot reload, agent and A2UI. Slint's safe-area/keyboard-inset properties are the H1 mobile table stakes. ([source](https://deepwiki.com/slint-ui/slint/2.2-property-system-and-data-binding ; https://docs.rs/slint/latest/slint/docs/mcu/index.html ; https://slint.dev/blog/slint-1.15-released ; https://slint.dev/blog/slint-and-AI-MCP))
- **Makepad 2.0: Splash DSL for AI generation** — Makepad 2.0 positions itself as an AI development environment around Splash, a live, readable UI DSL for screens, widgets, layout, style and state, so models can generate UI in small reviewable steps. It has a script engine for live editing. _Relevance:_ Makepad bets on a DSL for AI generation, which FLUI explicitly rejects (no own markup language). FLUI's equivalent is A2UI over the G6 catalog. This is a real market disagreement: Makepad and Slint argue a compact DSL is easier for models, while FLUI and Flutter GenUI argue that a typed catalog plus a standard protocol (A2UI) is. FLUI should measure this (agent success rate on the same task) rather than assert it. ([source](https://makepad.nl/))
- **Cross-framework convergence on leaf dependencies** — By 2026 the ecosystem converges on wgpu (Zed/GPUI, Iced, Bevy, Masonry, Slint), AccessKit (egui, Masonry, Vizia, Blitz, Slint via its a11y tree, Parley text props), Parley (Masonry, Bevy, Blitz), ui-events (Masonry) and Taffy (GPUI, Floem, Blitz). Frameworks own their reactive core (Freya's exit from Dioxus; GPUI's entity model). _Relevance:_ FLUI is aligned on wgpu, AccessKit and ui-events, and misaligned on text (cosmic-text plus a global FONT_SYSTEM mutex, crates/flui-painting/src/text_layout/layout.rs:124) and paths (lyon, crates/flui-engine/Cargo.toml:72). Layout is FLUI's own Flutter box/sliver protocol, a deliberate difference that competitors don't have and a moat if kept strict. ([source](https://github.com/zed-industries/zed/pull/46758 ; https://linebender.org/blog/tmil-25/ ; https://bevy.org/learn/migration-guides/0-18-to-0-19/ ; https://freyaui.dev/posts/0.4))

## Pitfalls others hit

- Xilem: generics-heavy View traits (about 30 traits, about 70 impls) led to obtuse errors, long compile times and an architecture too large to iterate on. Critics call its higher-order component signatures 'not an acceptable public API' (hackmd 2026 review).
- Xilem/Masonry: internals rework (arena ownership, passes) was scheduled after features and consumed most of 2024. Design work such as styling took months and 'can't be short-circuited' (PoignardAzur post-mortem).
- Freya: building on another framework's reactive core (Dioxus) tied it to upstream decisions and forced a full rewrite in 0.4.
- Vizia: changed its core state primitive late (lenses to signals), which needed a migration guide for all users.
- GPUI: a custom GPU abstraction (Blade) caused NVIDIA/Wayland freezes and was replaced by wgpu in 2026.
- GPUI upstream: cleared the Taffy tree every frame so the layout cache never hit. A fork got about 2x back just by keeping nodes and keying elements by path.
- egui: immediate mode needs frame-delayed sizing or discard passes, and very long scroll content is slow because everything is laid out every frame.
- Subsecond (Dioxus, Iced): struct/State/Message type changes still need a cold restart. Thread-locals in the patched crate reset, and new statics never run their destructors.
- Bevy/Parley migration: lost glyph byte_index/byte_length, so editor code that maps glyphs to text offsets had to change.
- Dioxus Blitz: a CSS/web-engine native renderer is still a work in progress with no performance focus after years, which shows the cost of a second rendering model.

## Patterns to adopt

- Framework-owned passes over a slab arena for cross-cutting behavior (focus traversal, cursor, semantics, hit-test), not per-widget reimplementation (Masonry).
- Run-to-completion effect queue flushed at a fixed frame phase, plus lease-style mutable access to realm-owned state instead of locks (GPUI). Apply this to ADR-0075 Computed/Effect.
- Per-key dirtiness for reactive collections (Dioxus Stores) as the design for A8.
- Keep the windowing host a replaceable backend behind ui-events types, and split the core from the host and from testing into separate crates so test code cannot reach release builds (Masonry core/testing/winit).
- A seeded deterministic executor with SEED/ITERATIONS for async interleavings and fake time (GPUI #[gpui::test]). Fold this into flui-testing when the Task/Worker async model is made explicit.
- A CPU renderer as a first-class fallback and golden reference (Iced tiny-skia, Floem, Slint software renderer, Vello CPU), behind the same DisplayList seam.
- In-process, headless-capable agent protocol whose vocabulary is the AccessKit tree plus action requests (egui_inspection/egui_mcp, Slint MCP). Consider adopting or co-designing the egui_inspection wire format instead of a private one, and keep external UIA-based desktop-mcp as live platform verification.
- Subsecond for hot reload with a stated contract: logic and build edits preserve state, State type changes restart the realm (Iced's documented limit). Keep hot-reloadable state realm-owned, never in thread-locals.
- Ship llms.txt / machine-readable catalog docs as an AI-native deliverable (Dioxus 0.7).
- Own the spine (reactivity, reconciliation, the layout protocol); depend on converged leaf crates (wgpu, AccessKit, Parley, ui-events). Evaluate Glifo for glyph atlas caching in the ADR-0077 spike.

## Patterns to avoid

- Exposing compile-time generic machinery (arity types, typed view sequences, OneOf) in the Stable public View API. Type-erase at the user boundary before the H3 freeze.
- Two-way bindings or side effects during build/view evaluation (Xilem critique). Keep ADR-0074's read-only-in-build guard.
- Building the reactive/component core on top of another UI framework's core (Freya's forced rewrite).
- A custom GPU abstraction layer instead of wgpu (GPUI/Blade).
- Clearing layout or paint caches every frame. A retained tree without surviving caches gives none of the payoff (gpui-fast finding), and FLUI's DamageTracker with no producer is the same failure.
- A custom UI DSL or markup as the AI-generation surface (Makepad Splash, Slint). This contradicts FLUI's principle 2 and would fork the catalog. Use typed catalog plus A2UI, and measure it.
- A dlopen/ABI-token hot-reload design that carries documented unsoundness (current crates/flui-hot-reload). The market has converged on Subsecond.
- Process globals or thread_local state in crates user code reaches (FONT_SYSTEM). They break multi-realm isolation, parallel tests and Subsecond patching.
- A second rendering model such as a CSS/web engine (Blitz), which multiplies the conformance surface for a small team.
