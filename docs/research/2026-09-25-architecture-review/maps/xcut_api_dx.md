# Codebase map: xcut_api_dx — cross-cutting public API and developer experience (facade prelude, authoring model, state, navigation, extension points, docs/agent discoverability, compile cost)

_Raw output of the `map:xcut_api_dx` agent (read-only review of main @ cab06137d, 2026-09-25). Unedited; claims are the agent's and were only partly re-verified._

## Summary

How it works today (main cab06137d). An app depends on the `flui` facade (src/lib.rs, 278 lines) with `default = ["material"]`. `flui::prelude` = `flui_widgets::prelude::*` (itself globbing `flui_view::prelude::*`) + run_app/AppConfig/window fns + ~40 curated Material names (src/lib.rs:256-278). The facade also re-exports whole crates as modules (`flui::view`, `flui::widgets`, `flui::types`, `flui::foundation`, `flui::app`, `flui::animation`, `flui::geometry`; src/lib.rs:120-152) and hand-curated authoring modules `flui::rendering`, `flui::painting`, `flui::interaction`, `flui::testing`.

Sketches using only the facade (real signatures):
- Counter (examples/counter.rs): `#[derive(Clone, StatelessView)] struct App;` wrapper (because `run_app<V: View + StatelessView + Clone>` rejects a stateful root, crates/flui-app/src/app/runner/mod.rs:216), then `#[derive(Clone, StatefulView)] struct CounterView;` + `struct CounterState { count: StateCell<usize> }` + `impl StatefulView { type State; fn create_state(&self) }` + `impl ViewState<CounterView> { fn init_state(&mut self, ctx: &dyn LifecycleContext) { self.count.bind(ctx) } fn build(&self, _: &CounterView, _: &dyn BuildContext) -> impl IntoView }`, clone the cell into `on_pressed(move || count.update(|n| n+1))`; `column!` must be imported from `flui::widgets`. ~45 lines, two derive+impl pairs, one bind step.
- Todo with form: there is no Form/FormField/TextFormField/validator; examples/todo.rs uses StateHandle<Vec<_>> + TextEditingController, 4 hand clones for two callbacks (todo.rs:130-133), a raw codepoint for the delete icon (no `Icons` catalog, todo.rs:31), and `ListView::new(item_extent: f32, children)` with a guessed fixed extent (todo.rs:39). A validated field (examples/material_demo/tree.rs:420-470) needs manual `add_listener(Arc::new(..))` → `RebuildHandle::schedule` → `remove_listener` in `dispose`, and reaches `flui_view::RebuildReason` outside the prelude.
- Two screens: no Router; `NavigatorHandle::new()` in `create_state`, `seed_initial(SimpleRoute::new(|ctx| ... .into_view().boxed()))`, `Navigator::new(handle.clone())`, then `handle.push(PageRoute::new(|ctx, anim, sec| ... .boxed()))` with `T: Send + Clone` and ~30 imperative push/pop variants (string names, RouteKey, generated routes).
- Custom render object: works through facade only (tests/fixtures/facade_extensions.rs): `impl RenderBox { type Arity = Leaf; type ParentData = BoxParentData; fn perform_layout(&mut self, ctx: &mut BoxLayoutContext<'_, Leaf, BoxParentData>) -> Size; fn paint(&self, ctx: &mut PaintCx<'_, Leaf>) }` + `#[derive(Diagnosticable)]` + `impl RenderView { type Protocol; type RenderObject: ... + Send + Sync; create_render_object; update_render_object -> RenderUpdateImpact }` + `flui::view::impl_render_view!(LeafView);` — a macro_rules path, unlike the derive path for Stateless/Stateful.
- Platform capability: impossible today. `LifecycleContext` offers only rebuild/post-frame/text-input/hit-test/keep-alive/focus/pipeline/async handles (crates/flui-view/src/context/build_context.rs:392-565). Clipboard exists in flui-platform and is installed into the app runtime, but its accessor is `#[expect(dead_code, reason = "no production caller yet")]` (crates/flui-app/src/app/runtime.rs:1636); open_url/prompt_for_paths live on flui-platform's owner, which the facade doesn't expose. There is no `PlatformCapability` trait anywhere.

State: five parallel APIs (StateCell, StateHandle, ValueNotifier+listeners, RebuildHandle, Signal behind the off-by-default `signals` feature), and the ADR-0074 "canonical" one isn't in the prelude, examples or book. Strengths: good `diagnostic::on_unimplemented` coverage, a facade-only headless test path, compile-time arity. The weak points are the state and navigation story, the Send discipline, the prelude and path hygiene, missing capability wiring, and docs/agent discoverability.

## Responsibilities and boundaries

The facade (`flui`, src/) owns the application-facing contract: prelude curation, feature selection (material/cupertino/localizations/hot-reload/signals/testing/serde), entry points, and the authoring modules for render objects, painting, interaction and testing. Leaks: (1) whole-crate re-exports (`pub use flui_view as view`, `flui_widgets as widgets`, `flui_types`, `flui_foundation`, `flui_app`, `flui_geometry`, `flui_animation`) make every `pub` item of those ~8 crates (~5.8k `pub` declarations by grep) part of the facade's semver surface, so the curated modules are not a boundary. (2) `flui_view::prelude` is not an app prelude but a framework-internal one: it exports `BuildOwner`, `ElementOwner`, `ElementTree`, `ElementNode`, `RootElement` and the `tracing` macros `debug/error/info/trace/warn` (crates/flui-view/src/lib.rs:252,283,285), and the facade prelude globs it through `flui_widgets::prelude::*`. (3) The same type is reachable by 3-5 paths (e.g. CursorIcon via flui::interaction, flui::rendering, flui::widgets, the prelude; crates/flui-rendering/src/hit_testing/mod.rs:92). (4) Platform services have no app-facing seam: flui-platform owns them, flui-app holds them in a runtime slot, and nothing reaches View code. What belongs elsewhere: `column!`/`row!` live in flui-view but are widget sugar; Navigator/route API lives in flui-widgets and will be superseded by the planned Router; the app prelude should be a separate, deliberately small module owned by the facade, not a transitive glob of the layer preludes.

## Dependencies

In: the facade depends on flui-app, flui-widgets, flui-view, flui-types, flui-geometry, flui-foundation, flui-animation, flui-rendering, flui-painting, flui-interaction, flui-tree, flui-macros, and optionally material/cupertino/localizations/hot-reload/testing. `cargo tree -p flui -e normal --target x86_64-pc-windows-msvc` lists 191 unique packages, including wgpu 30 + naga 30, cosmic-text 0.19, lyon, accesskit 0.25, windows 0.62, and tokio 1.53 with `rt-multi-thread,sync,time`, pulled by flui-app and flui-platform (`cargo tree -i tokio`). Every hello-world therefore links a multi-thread tokio runtime (the plan wants tokio optional by 1.0). Out: the CLI templates (crates/flui-cli/src/templates/*.rs) emit `flui = ...` and `use flui::prelude::*`, the book and llms.txt teach APIs, and examples consume a mix of the facade and internal crates: 25 example files import internal crates directly (`use flui_types` 24 times, flui_view 14, flui_platform 7, flui_layer 7, flui_engine 5, flui_objects 5), against 10 facade-only files.

## Fit with the plan

H0 exit ("a clean consumer builds Notes from crates.io; an agent runs a scenario via `flui mcp`"; 2027 criterion "a form with IME and Narrator in 10 minutes"). The API currently blocks it on three table stakes: no Form/validation, no Router, and no canonical state in the prelude. Notes cannot be written in the idiom the plan describes (signals + Router). Each widget added now on StateCell/NavigatorHandle patterns becomes migration debt for A3/D1. H1 (PlatformCapability plugins, 5 plugins outside the repo): no capability trait, registry or `LifecycleContext` extension seam exists, and even the one capability already implemented (clipboard) is unreachable from app code. The ADR-0078 rule ("capabilities only on LifecycleContext") is sound, but LifecycleContext is a sealed, closed trait in flui-view, so an out-of-repo plugin cannot add a method to it. A typed-extension seam (e.g. `ctx.capability::<C>() -> Result<C, Unsupported>`) must be designed before H1. H1 A2UI / G6 catalog: there is no machine-readable widget catalog (book/src/widgets/catalog.md explicitly declines to list widgets), and the widget API mixes builders, struct literals (InputDecoration { .. Default::default() }) and positional args, which makes a schema-derived catalog harder. H3 stability tiers (the prelude, View/State, the layout protocol, Router and signals as Stable): whole-crate re-exports and an internals-laden prelude mean a freeze would freeze BuildOwner/ElementTree/tracing macros too, and there is no `unstable` feature or semver-checks gate yet. Delivery layers: Material is the default feature and half the prelude, which contradicts "Material/Cupertino as official packages" and "Raw primitives first". An out-of-repo Material could not contribute to `flui::prelude`, so the prelude shape must change before the split. Principle 3 (no global state) and ADR-0027 (UI callbacks and render trees are !Send): the Send+Sync bounds on RenderView::RenderObject, CustomPainter, Draggable/PageView/Localizations callbacks and HeroController disagree with ADR-0027 line 106.

## Strengths

- A facade-only acceptance path exists: tests/fixtures/facade_extensions.rs mounts, lays out and paints a custom RenderBox and a proxy using only `flui::*` paths, and tests/agent_workflow.rs is a facade-only agent scenario
- Diagnostic quality: `#[diagnostic::on_unimplemented]` on View, IntoView, StatelessView, StatefulView, InheritedView, RenderObject, RenderBox, RenderSliver and ParentData (crates/flui-view/src/view/*.rs, crates/flui-rendering/src/traits/*.rs), with actionable notes
- Rules as types: capabilities are only on LifecycleContext (ADR-0078), BuildContext is sealed with compile_fail doctests (build_context.rs:90-105), and compile-time child arity (Leaf/Single/Variable) appears in the render-object signatures
- Absent-not-empty feature modules and a written prelude curation rule, including the recorded TextField/RawTextField collision decision (src/lib.rs:224-255, ARCHITECTURE.md:7-10)
- `impl IntoView` return (RPITIT) in build avoids boxing in the common static case; ViewSeq tuples up to 16 give static child lists
- Field-granular inherited dependencies are exposed to apps (Theme::depend_on_fields with FIELD_* masks from #[derive(InheritedData)])
- #![deny(missing_docs)] on the facade and flui-widgets; the facade has an honest feature table and layer table in its crate docs
- Headless testing is reachable from the facade (`flui/testing`: HeadlessBinding, lay_out, RenderTester), and the CLI counter template emits a facade-only test

## Problems

### No canonical state model at the API surface: five parallel mechanisms, and the ADR-0074 one is hidden

- **Kind:** plan_misfit · **Severity:** critical
- **Evidence:** The prelude exports StateCell/StateHandle (crates/flui-widgets/src/lib.rs prelude; flui-view/src/lib.rs:284). Signal<T> is behind the `signals` feature, off by default in flui-view/Cargo.toml:123 and in root Cargo.toml:645, and absent from the facade feature table (src/lib.rs:35-41). No example uses Signal (grep `Signal<` over examples/: 0 hits). The book says 'This book does not describe a reactive signals system: there is no such primitive in crates/' (book/src/concepts/state.md:45; book/src/mapping.md:36). A validated form (examples/material_demo/tree.rs:420-436) hand-wires ValueNotifier listener → RebuildHandle → dispose. The root Cargo.toml:642-644 gate reason ('until the #1090 field-mask registry lands') looks stale, since Theme::depend_on_fields with masks already ships (crates/flui-material/src/theme.rs:88-95); that staleness is a hypothesis to confirm.
- **Impact:** H0: Notes and the counter→todo→notes tutorial get written on StateCell. Every widget and example added now becomes A3 migration debt. The H3 Stable tier lists 'signals', yet nobody uses them, so the API is being frozen untested by real apps. Agents and humans learn five idioms.
- **Direction:** Decide go/no-go on ADR-0074 now. If go: turn `signals` on by default, put Signal and the ADR-0075 Computed/Effect in the prelude, rewrite counter/todo/form and the book on them, and demote StateCell/StateHandle to `flui::view::state` as the setState-level escape hatch. Make Signal writes ergonomic: a Copy handle whose `set`/`update` resolve the realm via the handle (or a captured `SignalSender`) rather than `&Reactive` + `Result`, with a panicking/`expect`-free default and a `try_` twin.

### No platform-capability seam: the one implemented capability is dead code and plugins cannot extend a sealed LifecycleContext

- **Kind:** extension_point · **Severity:** critical
- **Evidence:** LifecycleContext (crates/flui-view/src/context/build_context.rs:392-565) exposes only framework handles. Clipboard is installed per runner (crates/flui-app/src/app/runner/main_window.rs:547, android.rs:137, web.rs:67) but its accessor carries `expect(dead_code, reason = "no production caller yet -- a Clipboard capability through BuildContext is future wiring")` (crates/flui-app/src/app/runtime.rs:1636). EditableText and TextField docs say 'Clipboard (copy / paste / cut) are not wired' (crates/flui-widgets/src/text/editable_text.rs:322, controller.rs:206). open_url, prompt_for_paths and reveal_path exist only on flui-platform's owner (crates/flui-platform/src/traits/owner.rs:313-331), which the facade does not export. grep for `PlatformCapability` finds 0 hits in crates/ and docs/. BuildContext/LifecycleContext are sealed (build_context.rs:106).
- **Impact:** Blocks the H1 exit ('5 plugins built outside the repo'), the 2027 criterion (a form with copy/paste), and table-stakes text editing in H0. Adding each capability as a new sealed-trait method in flui-view makes every capability a core-crate change, the opposite of the plugin delivery layer.
- **Direction:** Before H1, design an ADR-level typed capability registry owned by the realm. For example, `trait PlatformCapability: 'static { fn install(host: &mut CapabilityHost) -> Result<Self, Unsupported> }` and `LifecycleContext::capability::<C>() -> Result<Rc<C>, Unsupported>` (one generic method, so the sealed trait stays closed while the set stays open). Registration goes through AppConfig/Application builders. Ship clipboard as the first built-in capability through that exact seam and wire EditableText to it.

### Send+Sync bounds in public API contradict ADR-0027 and make the Rc-based state types unusable in some callbacks

- **Kind:** api_dx · **Severity:** high
- **Evidence:** ADR-0027 says views, contexts, UI callbacks and render trees are '!Send + !Sync — single writer, structurally' (docs/adr/ADR-0027*.md:106). Yet `RenderView::RenderObject: RenderObject<P> + Send + Sync` (crates/flui-view/src/view/render.rs:451), `CustomPainter: Send + Sync + Debug` (crates/flui-rendering/src/delegates/custom_painter.rs:105), `Draggable::on_drag_started(impl Fn() + Send + Sync)` (crates/flui-widgets/src/interaction/draggable.rs:299-339), `DragTarget` callbacks (drag_target.rs:199-227), `PageView::on_page_changed(impl Fn(usize) + Send + Sync)` (scroll/page_view.rs:502), `Localizations`/`WidgetsApp` read closures (localization/localizations.rs:547, app/widgets_app.rs:616), and `HeroController::new() -> Arc<Self>`. Meanwhile GestureDetector::on_tap, ElevatedButton::on_pressed and Checkbox::on_changed take plain `impl Fn() + 'static` stored in Rc. StateCell/StateHandle are `Rc<Cell>`/`Rc<RefCell>` (state_cell.rs:141-143,311-313). flui-widgets carries `#![expect(clippy::arc_with_non_send_sync)]` (lib.rs:58-62). 42 `Send + Sync` hits in pub fns/impls in widgets+material.
- **Impact:** Failure scenario: capturing a StateCell in `PageView::on_page_changed` or `Draggable::on_drag_completed` fails to compile with a trait-bound error far from the cause. A custom render object cannot hold an Rc handle. Per the AGENTS ADR policy, code that silently disagrees with an accepted ADR is a defect, and freezing these bounds at H3 makes them permanent.
- **Direction:** Sweep once: every UI-thread callback, delegate, painter and RenderView::RenderObject drops Send+Sync; Arc→Rc where the owner is realm-local. Add a gate (a compile test with an `Rc` captured in every public callback setter, or a clippy-style xtask check that no `pub fn on_*` in flui-widgets/material/cupertino carries `Send`). Record the rule in the widget authoring guide.

### Navigation is an imperative, handle-plumbed API with ~30 push/pop variants and no Router

- **Kind:** missing_capability · **Severity:** high
- **Evidence:** A two-screen app needs `NavigatorHandle::new()` in create_state, `seed_initial(SimpleRoute::new(|ctx| ... .into_view().boxed()).named("/"))`, and `Navigator::new(handle.clone())` in build (examples/vertical_slice_demo/tree.rs:160-206, whose doc explains why seeding in build is a bug). PageRoute<T: Send + Clone>::new takes `Fn(&dyn BuildContext, &RouteAnimation, &RouteAnimation) -> BoxedView` (crates/flui-widgets/src/navigator/page_route.rs:203-226). NavigatorHandle exposes push, push_replacement, push_replacement_with, push_and_remove_until, pop, pop_with, pop_until, maybe_pop, push_named, push_named_typed, push_keyed, route_keyed, push_replacement_named(_with), pop_and_push_named(_with), push_named_and_remove_until, on_generate_route and on_unknown_route (navigator.rs:1108-2300). Lookup is only `maybe_of`, with no `of`. There is no Router type (grep `pub struct Router`: 0) and no Router ADR in docs/adr.
- **Impact:** H0 table stakes (D1 Router with URL as the source of truth) and the Notes app are blocked. Three parallel identity schemes (string names, RouteKey<T>, generated routes) will all have to be kept as the 'thin facade' after D1, or broken later, and they sit in the prelude (Navigator, NavigatorHandle, PageRoute, SimpleRoute, PopupRoute) that H3 wants Stable.
- **Direction:** Write the Router ADR first (typed enum routes + derive, URL ⇄ state, nested routers), then shrink Navigator to push/pop/replace over the Router stack. Move the named/keyed/generated variants out of the prelude now (to `flui::widgets::navigator`) so they are not frozen by accident.

### The prelude is a transitive glob of layer preludes and leaks runtime internals and tracing macros into every app module

- **Kind:** api_dx · **Severity:** high
- **Evidence:** The facade prelude does `pub use flui_widgets::prelude::*` (src/lib.rs:277), which does `pub use flui_view::prelude::*`, which exports `tracing::{debug, error, info, trace, warn}` (crates/flui-view/src/lib.rs:252), `BuildOwner, ElementOwner, RebuildReasons, ElementNode, ElementTree, RootElement, ElementSlot, IndexedSlot` (lib.rs:278-285) and `Memo` (the C1 combinator, while signals renamed their derived type to Computed to avoid the clash). Common names like `Action`, `Intent`, `Image`, `Table`, `Flex`, `Key`-adjacent types and `Brightness` all land in user scope.
- **Impact:** `use flui::prelude::*` shadows or becomes ambiguous with a user's own `error`/`info` items or `log` macros. Internals become de facto Stable at the H3 freeze. Agents autocompleting from the prelude reach BuildOwner/ElementTree, which apps must never touch.
- **Direction:** Give the facade its own explicit, enumerated `flui::prelude` (no globs of lower preludes). Keep layer preludes for framework crates only, drop the tracing re-export from any prelude, and add a gate that snapshots the facade prelude's name list (a `cargo public-api`-style snapshot test) so every addition is a reviewed diff.

### Whole-crate re-exports make the facade's semver surface ~6k items and give every type several canonical paths

- **Kind:** api_dx · **Severity:** high
- **Evidence:** `pub use flui_view as view; flui_widgets as widgets; flui_types as types; flui_foundation as foundation; flui_app as app; flui_animation as animation; flui_geometry as geometry` (src/lib.rs:120-152). `pub` declarations by grep: widgets 1498, types 1349, geometry 875, view 686, material 495, foundation 360, animation 349, app 185. CursorIcon is re-exported by flui-interaction (lib.rs:219,315), flui-rendering (hit_testing/mod.rs:92, lib.rs:146), the widgets prelude and flui::interaction. SemanticsTextDirection exists as a rename alias to dodge a collision.
- **Impact:** H3 stability tiers are unenforceable when everything is reachable. Rustdoc and rust-analyzer show the same type under 3-5 paths, which confuses humans and agents about the canonical import, and moving code between layers (A-track refactors) becomes a breaking change for apps.
- **Direction:** Make the facade modules curated (like flui::rendering/painting/interaction already are) instead of crate aliases, and mark each with its tier (Stable/Evolving/`unstable` feature). Adopt cargo-public-api or cargo-semver-checks on the facade only (H1 in the roadmap) as the contract. Document one canonical path per type.

### Material is the default feature and half of the prelude, which contradicts the delivery-layer plan

- **Kind:** plan_misfit · **Severity:** high
- **Evidence:** `default = ["material"]` (root Cargo.toml features). The prelude conditionally includes ~40 Material names (src/lib.rs:268-276). counter.rs and the CLI counter template rely on the Material `ElevatedButton`/`Theme` from the prelude (examples/counter.rs:17-57; crates/flui-cli/src/templates/counter.rs:66). The plan puts Material/Cupertino in official packages in separate repos, and the roadmap says 'Raw primitives first, M3 skin next'.
- **Impact:** Once Material leaves the repo (H1-H3), a facade cannot glob an external crate into its prelude without a dependency cycle in the release train, so every app's imports break at once. Cupertino is structurally second-class (not in the prelude, src/lib.rs:249-254). The raw primitive layer (RawTextField, raw buttons) is not what the prelude teaches.
- **Direction:** Decide the target shape now: `flui::prelude` is catalog-neutral (Raw primitives), and each design system ships `flui_material::prelude` that apps glob alongside. Flip the default off (or to a `material` convenience meta-crate), and have counter/todo/templates show both imports. Doing this pre-beta is cheap; after crates.io it is a mass break.

### No form layer and thin input catalog; the everyday todo/form needs hand-rolled validation, icons and list extents

- **Kind:** missing_capability · **Severity:** high
- **Evidence:** grep `pub struct Form|FormField|TextFormField|Slider|DropdownMenu`: 0 hits. examples/todo.rs:11 says 'No form/validation widget is used — none exists in this codebase yet'. The delete icon is a raw codepoint (todo.rs:31, no Icons constants). The code uses `ListView::new(item_extent: f32, children)` with a guessed 56.0 (crates/flui-widgets/src/scroll/list_view.rs:101; todo.rs:39). InputDecoration is a pub-field struct literal with `..Default::default()` while neighbouring widgets are builders. book/src/cookbook/forms.md just points at material_demo.
- **Impact:** This is exactly the 2027 metric ('a form with IME and Narrator in 10 minutes') and C1/C2 in H0. Designing Form after signals (A3) is correct, but the form API is where builder-vs-struct and state-binding conventions get locked.
- **Direction:** Design Form/FormField on top of the chosen state model (a signal-backed field value + validator closures + focus traversal). Generate an `Icons` constant table for the bundled icon font, make ListView extent optional (measure or estimate), and write a one-page 'configuration objects: builder vs struct' rule (pub-field structs only for pure data like decorations, with `#[non_exhaustive]` + builder for widgets).

### Two different authoring mechanisms for views: derives for Stateless/Stateful, macro_rules for Render/Inherited/Proxy/ParentData/Animated

- **Kind:** api_dx · **Severity:** medium
- **Evidence:** flui-macros has derives only for StatelessView, StatefulView, InheritedData, Diagnosticable and Animatable (crates/flui-macros/src/lib.rs:107-281). RenderView needs `flui::view::impl_render_view!(T)` after the impl plus `flui_view::single_child_view_children!()` inside it (crates/flui-view/src/view/render.rs:510-545; widgets/src/paint/colored_box.rs:83-86). Similar impl_* macros exist for inherited/proxy/parent_data/animated. The derive also requires a separate `impl StatelessView for X`, and the user writes the trait name twice. The facade rendering module doc (src/rendering.rs:1-6) does not mention impl_render_view!, so only the fixture test shows it.
- **Impact:** The extension point 'custom render objects for third-party catalogs' (H0/H4) has undiscoverable glue: forgetting `impl_render_view!` yields 'X is not a View' far from the cause. Two mechanisms mean agents guess wrong half the time.
- **Direction:** Unify on derives: `#[derive(RenderView)]` with `#[view(child)]`/`#[view(children)]` field attributes generating both `View` and the child-visiting methods, plus a derive for InheritedView/ParentDataView. Keep macro_rules internal. Document the full render-object recipe in the flui::rendering module docs, with a doctest.

### `column!`/`row!` are aliases for tuple syntax that collide with std macros and must be imported per file

- **Kind:** api_dx · **Severity:** low
- **Evidence:** `macro_rules! column { ($e0:expr, $e1:expr) => { ($e0, $e1) } ... }` (crates/flui-view/src/macros/mod.rs:42-56). Row/Column::new(children: C) already accept any ViewSeq tuple (crates/flui-widgets/src/flex/flex.rs:197-210). Every example and template does `use flui::widgets::{column, row}` (examples/counter.rs:12, todo.rs:24, crates/flui-cli/src/templates/counter.rs:67) because the prelude can't glob them over std::column!.
- **Impact:** Noise in every file, and `Column::new(column![..])` reads as duplication. Newcomers hit the std `column!()` (a line-number macro) if they forget the import, which produces a confusing type error.
- **Direction:** Teach `Column::new((a, b, c))` directly, or rename the macros to `children![]`/`views![]` (no std clash, can live in the prelude) with a variadic arm that switches to Vec<BoxedView> beyond 16.

### Clone noise and boxing are structural: the Rc-handle-per-closure pattern and no Option/Either views

- **Kind:** api_dx · **Severity:** medium
- **Evidence:** examples/todo.rs:100-133 clones `items` 4 times and the controller 3 times for two callbacks. examples/material_demo/tree.rs has 28 `.clone();` statements in 977 lines. There are 39 `.boxed()` calls in examples and 110 in flui-material. There is no `impl View for Option<V>` or Either (grep `for Option<` in crates/flui-view/src: 0), so conditional UI is `match { .. => X.boxed(), None => SizedBox::shrink().boxed() }` (material_demo/tree.rs:458-461).
- **Impact:** This is the ergonomics the plan targets ('Copy signal handles: closures without .clone()', roadmap A3). Every example written now teaches clone-heavy code that agents will reproduce.
- **Direction:** Copy handles (signals, controllers as arena ids) remove most clones. Add `View for Option<V>` and an `Either`/`one_of!` combinator so branches don't box. Consider a `clone!`-free callback convention (`on_pressed(|cx| ..)` receiving a handle context) once signals land.

### Unit and constructor inconsistency: f32 vs Pixels in the same snippet

- **Kind:** api_dx · **Severity:** medium
- **Evidence:** `Padding::all(value: f32)` and `SizedBox::height(f32)` (crates/flui-widgets/src/layout/padding.rs:36, sized_box.rs:47) versus `EdgeInsets::all(px(8.0))`, generic over Pixels (crates/flui-geometry/src/edges.rs:50). Both appear in the widgets crate-doc example (crates/flui-widgets/src/lib.rs:39-47). By grep there are 132 pub fns in widgets/material taking `: f32` against 4 taking Pixels. `AppBar::toolbar_height(f32)` (crates/flui-material/src/app_bar.rs:282).
- **Impact:** The unit system (NonZero IDs, no From<f32> for units, gated by compile_fail doctests) is undermined at the widget surface. Users and agents must memorize which constructors want px(). Freezing at H3 locks the inconsistency.
- **Direction:** Pick one rule: widget-level lengths take `impl Into<Pixels>` with `From<f32>` allowed only for Pixels at the widget boundary, or f32 everywhere at the widget layer with EdgeInsets::all(f32). Enforce it with an xtask/public-API lint over flui-widgets/material.

### Docs and agent discoverability: llms.txt, the book and examples teach internal crates and stale facts; no machine-readable catalog

- **Kind:** docs · **Severity:** high
- **Evidence:** llms.txt's canonical snippet imports `flui_app::run_app` and `flui_widgets::prelude::*` instead of the facade (llms.txt 'Writing a view' section). The book says no signals exist (book/src/concepts/state.md:45). book/src/widgets/catalog.md declines to list widgets. 25 example files import internal crates (`use flui_types` ×24, flui_platform ×7, flui_engine ×5, flui_layer ×7, flui_objects ×5) against 10 facade-only files. The counter and the CLI template import `SafeArea` explicitly although it is already in the prelude (examples/counter.rs:12). The CLI has no `mcp`/`devtools`/catalog command (crates/flui-cli/src/commands/). Nothing is on docs.rs.
- **Impact:** The H0 metric (time to first screen < 3 min) and 'everything machine-readable' (principle 4) suffer. An agent reading llms.txt or examples writes non-facade code that breaks when the crates are split or unpublished. The G6 catalog, which is the A2UI catalog, has no source of truth.
- **Direction:** Generate llms.txt/llms-full.txt and the book's widget catalog from rustdoc JSON of the facade (an xtask). Add a gate that doc snippets and non-internal examples compile against `flui::` only (move engine/platform demos under tools/ or mark them internal). Emit a JSON widget catalog (name, constructor, props, semantics role) that doubles as the G6/A2UI schema.

### Entry-point shape forces wrapper types and splits across targets

- **Kind:** api_dx · **Severity:** medium
- **Evidence:** `run_app<V: View + StatelessView + Clone + 'static>` (crates/flui-app/src/app/runner/mod.rs:214-226), so examples/counter.rs:14-21 and todo.rs:66-72 define a StatelessView wrapper just to host a StatefulView. There are separate `run_app_android(_with_config)`, `run_app_ios(_with_config)` (android.rs:38, ios.rs:57), `Application` builder and `open_window` entry points, the last cfg-gated out of mobile/web in the prelude (src/lib.rs:258-266). `Theme::of` panics without a Theme ancestor (crates/flui-material/src/theme.rs:68-73) and examples wrap `Theme::new` by hand instead of MaterialApp.
- **Impact:** Boilerplate in every hello-world, and a cross-platform main needs cfg branches. Two ways to root a Material app (Theme+SafeArea vs MaterialApp) with different navigator behaviour.
- **Direction:** `run_app(impl View)` with any view kind, and one `App::new(root).config(..).run()` builder that compiles on every target (mobile entry attributes via a `#[flui::main]` attribute macro). Make MaterialApp the documented root, or give Theme::of a fallback theme as Flutter does.

### Every app pays a heavy compile and link graph, including a multi-thread tokio runtime

- **Kind:** performance · **Severity:** medium
- **Evidence:** `cargo tree -p flui -e normal --target x86_64-pc-windows-msvc | sort -u | wc -l` → 191 packages: wgpu 30, naga 30, cosmic-text 0.19, lyon 1.0, accesskit 0.25, windows 0.62, and tokio 1.53 with features `default,rt,rt-multi-thread,sync,time` via flui-app and flui-platform (`cargo tree -i tokio`). The journal records a Material lib rebuild of 15-17 s after an edit. No clean-app build time has been measured (hypothesis: the edit-compile loop for an app is dominated by the flui-widgets/material monoliths plus link time).
- **Impact:** H0 'first screen < 3 min' and the hot-reload loop. The plan says tokio becomes optional by 1.0, but today it is an unconditional runtime dependency of every app.
- **Direction:** Measure `flui create` → first `cargo run` cold and incremental on the 3 desktops as a tracked metric. Make tokio an optional feature of flui-app (the AsyncDriver/IO lane behind a trait) and trim rt-multi-thread. Consider dylib/`-Zshare-generics`-style dev profiles as part of the Subsecond hot-reload work.

### Boilerplate on extension traits: required `as_any`, mandatory Diagnosticable, RenderUpdateImpact accumulation

- **Kind:** api_dx · **Severity:** low
- **Evidence:** `CustomPainter::as_any(&self) -> &dyn Any` is required with no default (crates/flui-rendering/src/delegates/custom_painter.rs:180), and every implementer writes `fn as_any(&self) -> &dyn Any { self }` (tests/fixtures/facade_extensions.rs:37-39). RenderBox requires `Diagnosticable` (render_box.rs:83). update_render_object hand-ORs impacts (widgets/src/paint/colored_box.rs:72-81).
- **Impact:** Small per item, but it is the stable extension surface for third-party render objects and painters (H0/H4). MSRV tracks latest stable, so trait upcasting (`dyn CustomPainter` → `dyn Any`, stable since 1.86) makes as_any unnecessary.
- **Direction:** Make `CustomPainter: Any` and drop as_any. Give Diagnosticable a blanket/derive default in the RenderView derive. Consider a `#[derive(RenderView)]` with `#[render(set = set_decoration)]` field mapping to generate update_render_object.

- AppRuntime platform clipboard accessor: installed on every runner but `expect(dead_code, reason = "no production caller yet")` (crates/flui-app/src/app/runtime.rs:1630-1645); EditableText/TextField have no copy/paste
- Signal<T>/Reactive/BuildContext::reactive: accepted ADR-0074 surface behind a default-off feature, with no example, template, book page or facade doc using it (crates/flui-view/src/reactive/mod.rs; root Cargo.toml:645)
- flui-platform owner services (open_url, reveal_path, open_path, prompt_for_paths, data_transfer) with no path from View code or the facade (crates/flui-platform/src/traits/owner.rs:248-331)
- `bon` builder dependency: flui-widgets crate docs say bon is 'reserved for the widest configuration objects', but its only user is flui-tree/src/iter/slot.rs:84 (`cargo tree -i bon` → flui-tree only)

## Open questions

- Is ADR-0074 go or no-go? The API cannot converge (prelude, examples, Form, Router state restoration) until one state model is canonical. Is the root Cargo.toml:642 gate reason (#1090) still the blocker, given field masks shipped?
- Should the facade's prelude be catalog-neutral now (each design system brings its own prelude) in anticipation of Material/Cupertino moving to official packages? This changes every example and template, so it is cheapest before the beta.
- What is the capability-extension mechanism: a generic `ctx.capability::<C>()` on the sealed LifecycleContext, a realm-owned registry installed via AppConfig/Application, or plugin crates contributing InheritedView providers? It needs an ADR before H1.
- Is the Send+Sync on RenderView::RenderObject and CustomPainter a remnant, or is it load-bearing for a planned raster/paint lane (ADR-0027 says the commit artifact, not render objects, crosses threads)? Hypothesis: a remnant.
- Units at the widget boundary: f32 or impl Into<Pixels>? A decision plus a lint is needed before any public-API freeze.
- Should examples that use engine/platform/layer crates directly (platform_window, direct_render, wgpu_window, scene_render…) move to tools/ or an `internal-examples` package, so `examples/` only teaches the facade?
- Hypothesis to measure: cold `flui create` → first window time and incremental edit→run time on Windows/macOS/Linux; no current number exists for an app (only for workspace crates).
