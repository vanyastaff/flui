## Context

Hot reload loads a worker `cdylib` with `dlopen`/`LoadLibrary` and re-runs `build()` in a host that
owns every element and its state ([`docs/hot-reload.md`](../hot-reload.md)). A project generated by
`flui create --hot-reload` has three crates: host, worker and shared types. That design has four
costs:

- **Its safety rests on a discipline the compiler cannot check.** A returned `Scene` can hold
  `Arc<dyn …>` values whose vtables live in the plugin image, and no lifetime ties them to the
  unload. ADR-0108 makes the scene callback's obligation explicit, and ADR-0111 keeps every admitted
  worker image mapped until the process exits.
- **Framework code is shaped around the plugin boundary.** `REGISTRY_STACK` in `flui-view` is
  `ManuallyDrop` because the module can be instantiated in a hot-reload `cdylib`, and a worker
  `cdylib` links its own copy of each framework static it touches.
- **The host named the dev tool.** `flui-app` had an optional dependency on `flui-hot-reload`.
  That edge is gone and ADR-0311 keeps the host on the installed-hook seam. The facade's separate
  opt-in re-export is standing aggregation under ADR-0315, not a host dependency.
- **The user pays a project shape for it.** Code that should reload must live in the worker crate,
  and the state it keeps in the host.

Subsecond (Dioxus) patches a running binary instead: calls go through a jump table, and only the
changed code of the crate that contains `main` is linked as a patch against the first build. It
needs no project split. Bevy 0.17 ships system hot patching on it.

### What the spike showed (2026-09-26, Windows 11 x64 only)

The spike ran on branch `spike/subsecond` at `51d223fa5`, with dx and subsecond 0.7.10. It is not
merged.

- **Stock `dx` cannot patch a FLUI app on Windows x64.** Its missing-symbol stub is
  `mov rax, imm64; jmp rax`, and RAX carries `__chkstk`'s argument. 14 call sites in the patch DLL
  probe a huge stack, and the app exits with `0xc000041d`. The 0.8.0-alpha.1 source has the same
  stub. The one-line fix is `jmp [rip+0]` followed by the address, which `dx`'s non-Windows branch
  already uses.
- **With the patched `dx`:**
  - A logic edit keeps state (a `born` field stays constant, a `ticks` counter keeps counting).
    The signal path was not exercised: its `count` stayed 0.
  - A `State` size change (`extra: [u64; 8]`) is caught by a fingerprint of size, alignment, drop
    glue and type name, and the root is remounted with fresh state. That was a remount in the
    same UI runtime, primary presentation only, not a fresh UI runtime.
- **Statics and thread-locals in the patched crate break.** Every patch gets a zeroed copy of
  each app-crate `static`. A `thread_local!` in the app crate crashes on first access from patched
  code (`0xc000041d`, an exception inside a window callback; the mechanism is unknown). Framework
  statics survived. A framework thread-local read inlined into the patch returned the right
  value; why is not understood, and it stays unverified. std's `HashMap::new` did not crash; its
  consistency was not tested. The spike's `dx_tls*` runs are invalid, because their probe flag
  lived in a zeroed app static; only its `dx_p*` runs count.
- **Patch reach.** Patches reached elements whose vtables predate them **only for calls wrapped
  by the hook**: `StatelessView::build`, `ViewState::build`, `init_state` and `create_state`.
  `ElementBase` methods (`build_into_views`, update, `dispose`, `did_update_view`,
  `did_change_dependencies`) and user render objects' layout and paint still ran pre-patch code.
  6 of 33 build calls per pass were redirected.
- **A frame-level hook would reach nothing** (an inference; not run). A frame-level
  `call(&mut dyn FnMut())` goes through framework symbols, which have no jump-table entry.
  Neither that mode nor `HotFn` was run.
- **Canonicalisation is required.** Subsecond keys its table by the original binary's
  addresses, so the hook must map every earlier patch address back to its original. Without that
  mapping, edits after a restart never arrived.
- **Numbers.**
  - Edit to patch applied: 1.7–3.8 s end to end.
  - `dx`'s "Hot-patching took": 1.05–4.53 s.
  - `apply_patch`: 380–780 ms.
  - Patch to rebuilt frame (and to remount): under the driver script's 100 ms poll interval;
    `dx`'s timestamps put both in the same 10 ms tick. Neither is a measurement.
  - Jump table: 5,548–5,771 entries.
  - Patch DLL: 816–830 KB plus a 5.9 MB PDB.
  - A cold fat build of 381.9 s and launch to first frame of 14–58 s were reported and not
    re-checked.
- **Not run:** macOS, Android, input after a patch, the pairing with dynamic linking, a
  same-size `State` change, an edit to a `View` type.
- **The §5 criteria were not judged under §4**, because framework globals had not come down
  first. The app-crate failures stand regardless: they come from the app crate, not the
  framework.


## What was proposed

§1. **A runtime hook that names no reload tool.** One optional hook per UI runtime, called at the
element seam once for each framework call into a user `View` or `ViewState` method
(`call(entry, data)`, so a patcher can route it through its jump table), with a `poll` that reports
nothing, patched code, or a change that needs a fresh UI runtime (`RestartRequired`). The trait
lives in `flui-view` and the application installs it explicitly. The poll-driven half of this hook
was built and is accepted on its own as ADR-0311; the per-call seam and `RestartRequired` were
never built.

§2. **No core crate below the facade depends on the reload package.** `flui-app`'s feature and
edge go when `flui-hot-reload` moves into the official packages; ADR-0311 §6 states that host
boundary now. The facade's separate opt-in `hot-reload` feature and re-export remain standing
aggregation under ADR-0315.

§3. **The package implements the hook on Subsecond**, with `flui run` driving the patch build, a
derive-generated structural hash over every retained `View` and `ViewState` type to detect a type
edit, canonical patch addresses, patches applied on the owner thread, and no `static` or
`thread_local!` in reloadable app-crate code.

§4. **Globals come down before the spike is judged**: at least `REQUEST_REBUILD`,
`REGISTRY_STACK`'s `ManuallyDrop` form and `FONT_SYSTEM`.

§5. **The dlopen path is deleted only after the spike passes** on Windows, macOS and Android. The
record would be accepted only when the `dx` stub fix was upstream or carried by `flui run`, the
rule against statics in reloadable code was enforced, the structural hash existed, patches were
applied on the owner thread, and the spike had run on macOS and Android and again on Windows.

## Why it is rejected

- **The tool cannot patch a FLUI app on Windows x64, and upstream has not changed.** The stub that
  broke the spike is unchanged at `v0.8.0-alpha.3` (Sources: `patch.rs:1036-1046`, `movabs rax,
  imm64; jmp rax`); the fix the spike found is the `jmp [rip+0]` the non-Windows branch already
  uses (`:1107`).
- **None of §5's conditions holds**, and three of them (the upstream fix, the macOS and Android
  spikes, the Windows re-run) are not in the project's hands or not runnable on the Linux CI host.
- **§3–§5 are pinned to `dx` 0.7.10** and to criteria nobody is working toward, while fifteen
  manifest exceptions named this `Proposed` record as their exit, an exception with no exit.
- **The hook does not depend on the tool.** The half that was built is held by tests and the
  runtime, so it is accepted as its own record (ADR-0311). ADR-0316 supports the dynamic-image
  development cycle independently; no live manifest exception relies on this rejected proposal.

## More information

- The spike's findings are historical evidence for any future proposal: app-crate statics and
  thread-locals break, only hook-wrapped calls reach patched code, and patch addresses must be
  canonicalised. They do not establish a return condition or supersede ADR-0316's supported cycle.
- Dynamic linking (ADR-0096) and Subsecond are independent; the dynamic linking study found them
  compatible after [dioxus#4174](https://github.com/DioxusLabs/dioxus/pull/4174) but did not test
  the pair on Windows. Windows keeps MSVC's PDBs (`.cargo/config.toml`), which Subsecond reads.
- `dioxus_devtools::connect` runs its callback on a spawned thread, so the spike's patch
  application raced the UI thread's jump-table reads; any future proposal applies patches on the
  owner thread.
