## Context

Hot reload today loads a worker `cdylib` with `dlopen`/`LoadLibrary` and re-runs `build()` in
a host that owns every element and its state (`docs/hot-reload.md`, "Critical insight"). A
project generated by `flui create --hot-reload` has three crates, host, worker and shared types
(`crates/flui-cli/src/commands/create.rs:21-22`; `examples/hot_reload_counter/{host,logic,types}`).
The design has four costs.

**Its safety depends on a discipline the compiler cannot check.** The crate documents the
residue itself: a returned `Scene` can hold `Arc<dyn …>` values whose vtables live in the
plugin image, "and no lifetime ties it to `dlclose`" (`crates/flui-hot-reload/src/lib.rs:24-30`);
the mounted pipeline is leaked on unload rather than dropped
(`crates/flui-hot-reload/src/plugin.rs:224-230`). The worker path has two more hazards the
crate does not document. Both are **hypotheses from reading the code; neither was run**:

1. `WorkerReloadDriver::poll` unloads the old image (`crates/flui-hot-reload/src/worker.rs:458`)
   and loads the new one (`worker.rs:460`) before the realm reassembles
   (`crates/flui-app/src/app/hot_reload.rs:226-228`). The element tree still holds views and
   closures built by the old image — the worker returns a `BoxedView`
   (`examples/hot_reload_counter/logic/src/lib.rs:29`) with an `on_tap` closure (`lib.rs:36`).
   On Windows `FreeLibrary` unmaps at refcount zero, so dropping or comparing those views during
   reassemble would read unmapped vtables. macOS defers unmapping (`docs/hot-reload.md:41-45`),
   which would hide it there.
2. The worker is a `cdylib` (`examples/hot_reload_counter/logic/Cargo.toml:11`) and links its own
   copy of the framework. Its `on_tap` calls `request_rebuild()` (`lib.rs:38`), which reads the
   worker's copy of `REQUEST_REBUILD` (`crates/flui-hot-reload/src/dispatch.rs:24`, read at
   `dispatch.rs:78-85`); the host registered its hook in the host's copy. The same duplication
   already forced a fix for the worker's own `FONT_SYSTEM` (`docs/hot-reload.md:213`,
   `crates/flui-painting/src/text_layout/layout.rs:124`).

**Framework code is shaped around the plugin boundary.** `REGISTRY_STACK` is `ManuallyDrop`
"because this module can be instantiated in a hot-reload cdylib"
(`crates/flui-view/src/key/registry.rs:198-206`). ADR-0045 keeps Android on the inline raster
lane because a plugin `Scene` could drop on the raster thread while the dylib unloads on the
owner thread (`docs/adr/ADR-0045-raster-lane.md:295-296`).

**A core crate names the dev tool.** `flui-app` has a `hot-reload` feature and an optional
dependency on `flui-hot-reload` (`crates/flui-app/Cargo.toml:65`, `:108-110`), and its realm
takes `flui_hot_reload::HotReloadTier` in production code
(`crates/flui-app/src/app/ui_realm/presentations.rs:487`). The facade re-exports the crate
(`src/lib.rs:136-138`) behind its own `hot-reload` feature (`Cargo.toml:630`). Three reach
facts keep the edge optional (`FACTS` in `tools/xtask/src/workspace/reach.rs`, ADR-0081 §2). Once
`flui-hot-reload` becomes an official package (ADR-0088), those edges are a core crate naming an
official package, which ADR-0088 forbids: core must build, version and release without knowing
which official packages exist, and an optional edge still ties the core's semver to the
package's. They are not a dependency cycle: the package depends on `flui-layer`, `flui-foundation`,
`flui-view` and `flui-rendering` today (`crates/flui-hot-reload/Cargo.toml:33-38`) and on
`flui-sdk` after ADR-0088, never on `flui-app` or the facade, and the review's probe found a cycle
only when a package depends on the crate that holds the optional edge
([`judges-and-verification.md`](../research/2026-09-25-architecture-review/judges-and-verification.md)).

**The user pays a project shape for it.** Code that should reload must live in the worker
crate, and the state it keeps must live in the host.

Subsecond (Dioxus) patches a running binary instead: calls go through a jump table, and only the
changed code of the crate that contains `main` is linked as a patch against the first build. It
needs no project split. Bevy 0.17 ships system hot patching on it. Its behaviour on Windows,
where it reads symbols from PDBs, and on Android is not verified for FLUI.

## Decision

### 1. The runtime exposes a hook; it names no reload tool

The runtime (`flui-runtime`, ADR-0083; `flui-app` until that crate exists) owns one optional
hook:

```rust
pub trait DevReloadHook: 'static {
    /// Run one unit of framework work (a frame's build pass) through the hook,
    /// so a code patcher can route it through its jump table.
    fn call(&self, work: &mut dyn FnMut());
    /// What changed since the last poll: nothing, patched code, or a change that
    /// needs a fresh realm.
    fn poll(&mut self) -> ReloadEvent;
}
```

- The hook is installed explicitly on the application builder (`Application`,
  `crates/flui-app/src/app/application.rs:53`), by the application, never discovered. With no hook, the runtime calls the work directly and pays nothing else.
- `ReloadEvent::Patched` becomes an owner-queued hot reload in every realm (ADR-0027 §9), which
  runs the existing reassemble: every element dirty, state kept
  (`WidgetsBinding::perform_reassemble`, `crates/flui-view/src/binding.rs:1173`).
- `ReloadEvent::RestartRequired` tears the realm down and hosts a fresh one on the same loop
  (ADR-0039 §6). State is lost; the process and its windows are not.
- The reload tier type belongs to the runtime. `flui_hot_reload::HotReloadTier` leaves
  `flui-app`'s signatures.

### 2. No core crate depends on the reload package

`flui-app`'s `hot-reload` feature and optional dependency, the facade's `hot-reload` feature and
`pub use flui_hot_reload as hot_reload` are removed in the change that moves `flui-hot-reload`
into the official packages. The application adds the package itself, and the `flui create`
template adds it for development builds. The three hot-reload facts of the reach gate
(ADR-0081 §2) are replaced in this change by the "core names no official
crate" rule (ADR-0081 §3, ADR-0088 §2), whose dated exceptions for these edges expire here.

### 3. The package implements the hook on Subsecond

The official hot-reload package implements `DevReloadHook` with `subsecond::call` for `call`
and Subsecond's patch notification for `poll`. `flui run` drives the Subsecond build side
(the patch linker and the file watcher). A State type edit must surface as
`RestartRequired`; how the package detects it (Subsecond's own report, or a layout
fingerprint of the `ViewState` types, which the framework does not have today) is an output of
the spike, not assumed here.

### 4. Globals come down before the spike is judged

A code patcher that keeps the original image keeps its statics; one that resets thread-locals,
or a patch that brings its own copy, splits whatever state lives in them. The process-global
state that ADR-0097 lists is reduced first, and at least the entries this design touches —
`REQUEST_REBUILD`, `REGISTRY_STACK`'s `ManuallyDrop` form, `FONT_SYSTEM` — are gone or
realm-owned before the spike's "no residual TLS or static breakage" criterion is evaluated.

### 5. The dlopen path is deleted only after the spike passes

The spike runs a logic edit and a State type edit on Windows, macOS and Android. It passes
when a logic edit keeps state, a State type edit restarts the realm, and nothing breaks through
a remaining static or thread-local. Then, and not before, the following are deleted together:
the worker/host/types template, the `--scene` scene plugin, the dlopen driver in
`flui-hot-reload`, the `hot_reload_counter` and `hot_reload_lifecycle_fixture` examples, and
ADR-0045's Android inline-lane constraint. If the spike fails on a platform, that platform
keeps no hot reload rather than the dlopen path, and the failure is recorded here.

Until deletion, the two worker hazards in Context are either reproduced on Windows or written
into `flui-hot-reload`'s crate docs.

## Alternatives considered

- **Keep the dlopen worker.** Rejected: its safety rests on unchecked unload discipline, it
  forces a three-crate project, it shapes framework code (`ManuallyDrop` statics, the Android
  inline lane), and it has two undocumented hazards on the worker path.
- **A facade `hot-reload` feature over a packaged `flui-hot-reload`.** Rejected: the facade
  would name an official package, so the facade's release would track the package's semver and
  the "core names no official crate" gate (ADR-0081, ADR-0088) would need a permanent exception.
- **Swap a framework dylib, Fyrox style.** Rejected as a reload mechanism: Fyrox describes its
  own code hot reloading as "based on wildly unsafe functionality", and trait-object vtables
  become invalid after unload — the same class of hazard as the current worker. A shared
  framework dylib would remove the duplicated-globals hazard but not the unload one. Dynamic
  linking for build speed is a separate question (ADR-0096).
- **Interpret the UI description at run time (Makepad's Live DSL).** Rejected: FLUI's UI is Rust
  code, and a second UI language is out of scope.
- **Keep `flui-app → flui-hot-reload` and move only the implementation.** Rejected: it keeps a
  core crate naming an official package, which ADR-0088 forbids.

## Consequences

- A hot-reloadable application is an ordinary single-crate application with the package added.
- Framework code stops carrying plugin-image constraints once the dlopen path is gone.
- Windows keeps MSVC's PDBs (`.cargo/config.toml:19-21`); Subsecond reads symbols from them, so
  `/DEBUG:NONE` must not return.
- Dynamic linking (ADR-0096) and Subsecond are independent; neither needs the other, and the
  dynamic linking study found them compatible after
  [dioxus#4174](https://github.com/DioxusLabs/dioxus/pull/4174) but did not test the pair on
  Windows.
- The macOS device check of the worker loop (`cargo xtask device`, `MacosHotReloadLoop`, `tools/xtask/src/device.rs:201-212`)
  is rewritten for the Subsecond loop when the dlopen path is deleted.
- Web keeps no in-process hot reload (`docs/hot-reload.md`, "WASM / Web"). iOS support depends on
  the spike.
- Migration for users of `flui create --hot-reload`: merge the worker and types crates back into
  the application crate and add the package; state no longer needs to be split out.

## Verification

None of these exists yet.

- **No edge.** The reach gate (ADR-0081) proves `flui-hot-reload` is absent from the normal
  dependency graph of every core crate under every facade feature combination, and
  `cargo xtask workspace` rejects a core manifest that names it even optionally (ADR-0088).
- **Hook contract, headless.** A test installs a fake `DevReloadHook` that counts `call`s and
  scripts `poll`: every build pass runs through `call`; `Patched` re-runs `build()` with a
  stateful counter's value preserved; `RestartRequired` mounts a fresh realm whose counter is
  back at its initial value; with no hook the frame runs unchanged.
- **Spike acceptance,** recorded in this ADR before it is accepted: logic edit keeps state,
  State type edit restarts the realm, no residual static or thread-local breakage, on Windows,
  macOS and Android.
- **Live loop.** The device check drives `flui run` on the Subsecond loop through the CLI's
  `--json` events: an edit reloads with state kept, a syntax error is refused with the app
  alive, the fix reloads.
