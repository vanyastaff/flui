# ADR-0044: The three-owner frame split and the driver-loop hybrid

*Logical update scheduling, physical per-presentation pacing, and raster capacity are three separate owners (`UpdateScheduler`, `FrameClock`, and the raster owner). This record's own scope, so far, is the first two owners plus the actuator that connects `FrameClock`'s demand mask to the platform: the pre-existing wake channel remains the sole produce trigger on every backend, edge-triggered against the demand mask so repeated ticks collapse into one platform-facing poke; a genuinely compositor-paced `RedrawRequested` additionally feeds pacing-feedback bookkeeping, but — this is the corrected, load-bearing part of this record — marks no demand of its own, because nothing at that call site can tell a self-triggered tick apart from a platform-driven one, and marking demand from a signal that fires on every production pump would make the demand-mask gate inert. Raster backpressure and hidden-surface/wall-clock gating extend this record in later work on the same issue; neither has landed as of this draft.*

## Context

Before this record, one component (`Scheduler`, since renamed `UpdateScheduler`) combined logical phase/callback/task scheduling, a fixed 60fps assumption, and the frame-drive loop's own dirty predicate. Splitting this into owners that "know" different things — logical time, physical per-surface time, and raster capacity — needed each piece decided before wiring it into the runner, per the ownership rule:

| Owner | Owns | Answers | Never knows |
|---|---|---|---|
| `UpdateScheduler` (realm) | logical time: phases, transient/persistent/post-frame callbacks, the task queue, async drive | "what runs, in what order, within the granted slice" | a refresh rate, a display, a surface, a GPU |
| `FrameClock` (one per presentation) | physical time for one surface: demand coalescing, actuator-edge coalescing, compositor pacing feedback, first-frame deferral, visibility gating, a produce-capacity threshold, frame timestamps | "does this surface produce a frame now, and by when" | phases, callbacks, element trees |
| Raster scheduling (engine seam, future work on this issue) | capacity: latest-frame-wins mailbox, an in-flight counter, GPU backpressure | "will the GPU accept another frame" | demand, ordering, widget state |

Flow rule (normative): demand flows up (clock → realm aggregate wake → platform); frames flow down (logical pass → clock-gated segment → raster submit); backpressure flows up (retire → decrement + owner wake → clock re-fires, once the raster owner exists). No cross-level reads.

An earlier design pass split this into two pieces of work specifically because the driver loop — *who calls `FrameClock::poll`, and what actually drives the pump between polls* — was underspecified. `UpdateScheduler`'s reshape and `FrameClock` itself landed first, deliberately keeping the pump's own driver mechanism untouched and behavior-identical at the single-presentation topology this workspace still ships (proven by an executable equivalence table over the `woken`/`has_pending_work` predicate `FrameClock::poll` replaced). This record is what that first pass explicitly deferred: the actuator.

### What already existed, verified against this tree before deciding anything

- **The pump's own frame-production call site is `bootstrap_desktop`'s `window.on_request_frame` closure** (`crates/flui-app/src/app/runner.rs`), which every desktop backend (winit-backed X11/Wayland, and the native Win32/AppKit backends sharing the same `run_desktop` bootstrap) wires identically. `PlatformWindow::request_redraw()` — called from `UiRealm::wake_frame`'s underlying `FrameWakeHandle` — is what the winit backend's `WinitWindowEvent::RedrawRequested` handler responds to by calling `win.callbacks().dispatch_request_frame()`, which is exactly this closure. There is a **second, separate** `WindowEvent::RedrawRequested` the winit backend also dispatches through its generic `lease_window_event_handler()` path — but `runner.rs`'s `PlatformToUi` enum has no variant for it, and `flui_platform::traits::Platform::on_window_event` has zero callers in `flui-app`, so that specific plumbing genuinely drives nothing. The functional actuator — what a caller means by "the wake channel" — has always been `on_request_frame`/`dispatch_request_frame`, under a name that does not mention `RedrawRequested` anywhere in `runner.rs` outside a comment. **This record does not add a second, parallel produce path off the same native event** — doing so would double-produce every delivered `RedrawRequested`. Instead, the existing `on_request_frame` closure gains the two capabilities below.
- **`request_redraw()` (the native platform call) fires unconditionally today, once per `wake()` invocation**, from several call sites (`WidgetsBinding::set_on_need_frame`, `BuildOwner::set_on_build_scheduled`, and — before this record — `draw_frame_entered`'s vsync-continuation check on every tick a controller was running). On real winit this is harmless (the platform's own `request_redraw()` already coalesces to at most one pending event), but nothing in FLUI's own layer modeled or tested that coalescing discipline, and a deterministic test double has no such coalescing for free.
- **Wayland's frame-callback pacing is not a free-running signal — but it is not the ONLY reason `RedrawRequested` fires, either.** `WinitWindowEvent::RedrawRequested` on Wayland fires in response to a prior `request_redraw()` call, at the compositor's next frame-callback slot, and only while the surface is visible (see ADR-0029's own occlusion-semantics section) — winit's own docs and behavior also deliver it for OS-driven signals FLUI never asked for (an expose/damage event after another window stops occluding this one, a resize-triggered redraw), which have nothing to do with a prior `request_redraw()` call at all. X11 delivers the equivalent event immediately, with no compositor pacing at all. Neither "always caused by our own request" nor "always compositor-paced" is a universal property of `RedrawRequested` — both are per-platform, per-event facts, which is why the table below exists as a checked deliverable rather than an assumption baked into one code path, and why §3 below could not simply treat every delivered tick as demand.
- **`Vsync::has_running()`, sampled to decide whether to keep the pump alive across an animation's duration, was never wired to mark `FrameClock`'s own `DemandKind::Animation`.** A running controller with no other tree-visible side effect (no listener dirtying a widget) would keep the platform loop alive (`wake_frame()` fired every tick) but the segment gate itself would never see nonzero demand from that fact alone — silently diverging from Flutter's own `Ticker`-driven `scheduleFrame`, where the running ticker alone is sufficient to schedule a frame.

## Decision

### 1. The demand mark: Animation, sampled before the tick

`draw_frame_entered`'s vsync-continuation loop now samples `vsync.has_running()` **before** `tick_all(now)`, not only after. If a controller was running entering this tick, `presentation.clock().mark_demand(DemandKind::Animation)` is marked unconditionally — this is what makes a running controller with zero other dirty state still flush its own segment every tick, and it is what makes the tick that completes a controller still flush that completion's final value and status change, mirroring `.flutter/packages/flutter/lib/src/scheduler/ticker.dart`'s `_tick` (:272-285): `_onTick` runs unconditionally before `shouldScheduleTick` is even consulted. This is a Flutter-fidelity fix, verified correct against `.flutter/`, independent of §2's own finding below.

### 2. The actuator edge: `FrameClock::try_arm_redraw_request`, and where it must NOT live

A new, pure (`Cell`-backed) latch on `FrameClock`: test-and-set semantics, `true` at most once per pending demand mask, `false` on every following call until the next granted `poll` produce clears both the mask and the latch.

**Where this latch is consulted matters, and getting it wrong is a real, production-confirmed stall, not a hypothetical.** The first version of this record placed the "should the NEXT pump be scheduled" check — `if vsync.has_running() && try_arm_redraw_request() { wake_frame(); }` — inside `draw_frame_entered`'s vsync loop, sampled **after** `tick_all`, alongside §1's before-tick demand mark. This is wrong: `draw_frame_entered` runs, and produces a scene, *before* the render that scene feeds into; `UiRealm::render_frame_entered` (the caller) then either retries or calls `mark_rendered()`, which unconditionally clears `needs_redraw` to `false` — clobbering, within the SAME callback, any `wake_frame()` call `draw_frame_entered` already made. On the real desktop path, the next platform callback's own dirty gate (`wake_action`, `runner.rs`) reads `needs_redraw()`/`has_pending_work()` fresh, before `draw_frame_entered` runs again — and neither flag stays true for a running controller with no other tree-visible effect once that clobber happens. The result: the controller renders its anchor frame and then silently never ticks again.

This was settled with a production-sequence probe, not by reading the code: `crates/flui-app/src/app/runner.rs`'s `a_running_controller_with_no_other_dirty_state_keeps_producing_across_the_real_wake_action_gate` drives the exact `record_compositor_tick` → `wake_action`'s dirty gate → `render_frame_entered` sequence `bootstrap_desktop`'s closure uses (not `draw_frame_entered` called directly, which never reaches `wake_action` and could not have caught this) — 40 simulated platform callbacks, 16ms apart, well past the test controller's 100ms duration. Under the first version: 1 render, 39 consecutive skips, final animation value stuck at `0`. Every pre-existing pinned test called `draw_frame_entered`/`draw_frame` directly, bypassing `wake_action` entirely, which is why none of them caught this.

**Fix:** the continuation check moved to `UiRealm::render_frame_entered`, positioned AFTER `mark_rendered()`/the retry check, not inside `draw_frame_entered`:

```rust
// In render_frame_entered, after mark_rendered()/the retry check:
for presentation in self.presentations.iter() {
    if presentation.vsync().has_running() {
        presentation.clock().mark_demand(DemandKind::Animation);
        if presentation.clock().try_arm_redraw_request() {
            self.wake_frame();
        }
    }
}
```

`presentation.vsync().has_running()` here reads the same post-tick state the old in-loop check did (the tick already ran, earlier in this same call, via `draw_frame_entered`) — only the WHEN of the wake call changed, not the underlying "is Flutter's `shouldScheduleTick` true" signal. The demand mark here is fresh (this pump's own mask was already cleared by the produce that ran moments earlier) — a genuinely separate concern from §1's before-tick mark, which feeds only THIS pump's own segment.

N ticks that land before a produce actually clears the mask — GPU backpressure (once the raster owner is wired), a configured throttle window, or several ticks in a row that all skip for the same reason — still collapse into exactly one platform-facing wake instead of one per tick; the coalescing property is unaffected by the move, only its timing relative to `mark_rendered()` changed. One observable, pinned-not-implicit consequence: the SAME callback that frees backpressure capacity and produces now also re-arms and wakes again in that same callback (the check runs after `poll()` already reset the latch), where the pre-fix in-loop check — running before `poll()` — would have deferred that wake to a separate, later callback.

**Honest limitation, stated rather than assumed away:** reaching `poll` is necessary but not sufficient to disarm this latch. A `poll` that returns `Skip(Hidden)` or `Skip(Backpressure)` retains both the mask and the latch, so a caller stuck on either reason stays armed-but-withheld until something else causes a produce to succeed — and neither of the two edges that would close that gap structurally (a raster retire waking the owner; an unhide waking the owner) exists yet; both belong to work later on this issue. Dormant today because nothing in production yet engages either `Skip` reason — but wiring either knob into production ahead of its own wake edge would turn this into a real stall of the same shape §2 just fixed. `clear_demand` disarms the latch when it empties the mask outside a produce (an `AnimationController` completing and clearing its own demand bit without a poll in between is exactly this case), which is a different, already-closed gap from the liveness one above.

**Honest limitation, not glossed over:** reaching `poll` is necessary but not sufficient to disarm this latch. A `poll` that returns `Skip(Hidden)` or `Skip(Backpressure)` retains BOTH the mask and the latch, so a caller stuck on either reason stays armed-but-withheld until something else causes a produce to actually succeed — and this clock has no mechanism of its own to make that happen. The two edges that would close the gap structurally (a raster retire waking the owner once capacity frees; an unhide waking the owner once visibility returns) belong to the raster-backpressure and hidden-surface-gating work still to come on this issue, and neither exists yet. Today this dependency is dormant, not a live bug: nothing in production yet calls `set_hidden` or `set_max_in_flight`/`record_submit` against a real presentation's clock, so `poll` never actually returns either `Skip` reason in production — but wiring either knob into production before the corresponding wake edge lands would turn this into a real stall, and that ordering constraint is binding on whichever of those two pieces of work lands first.

A caller settling its OWN demand away (via `clear_demand`) without ever reaching a produce is a different, already-handled case: `clear_demand` disarms the latch itself when it empties the mask, so a later genuinely-new mark can still arm a fresh request — this is what stops `clear_demand`'s own documented use (an `AnimationController` completing and clearing its `Animation` bit outside a produce) from permanently stranding the actuator.

### 3. Pacing feedback: `FrameClock::record_compositor_tick` marks NO demand

A second new method, called unconditionally from `bootstrap_desktop`'s `on_request_frame` closure on every fire, before the existing dirty/`wake_action` gate decides whether anything actually runs this pump. It records the interval between consecutive ticks (`last_compositor_tick_interval`, diagnostic data — no produce decision reads it in this record) and does nothing else.

**This was not the first design tried, and the first one was wrong — recorded here rather than silently corrected.** The first version also marked `DemandKind::Host`, on the theory that "the host platform asked for a frame directly" (that variant's own pre-existing doc) is exactly what a delivered compositor tick is, and that this would only matter as a rare safety net since a tick normally follows a `request_redraw()` already made for a real `Dirty`/`Animation` reason. That reasoning is false in two ways the "What already existed" section above states plainly: (a) `record_compositor_tick` is called on **every single production pump** on every desktop backend, not just on the rare unsolicited tick — so if it marks demand, `poll` can never return `Skip(NoDemand)` on that path, which makes the demand-mask gate — the entire point of `FrameClock`, and of this whole issue — **inert** wherever this method is called; (b) `RedrawRequested` is not always "the host asking for a frame with no dirty state of its own" the way the `Host` variant's doc assumes — winit also delivers it for OS-driven expose/resize signals FLUI never requested, so even the narrower "only mark it for genuinely unsolicited ticks" reading is not implementable at this exact call site, because nothing here can distinguish a self-triggered tick from a platform-driven one; the two cases are indistinguishable by the time `record_compositor_tick` runs. This was caught with a direct probe, not inferred: an idle `UiRealm` (nothing attached, nothing dirty) that calls `record_compositor_tick` then `draw_frame_entered` produced a frame every single pump under the first version; the fix removes the demand mark entirely, and the same probe now reports zero produces over 50 pumps — pinned as `an_idle_presentation_stays_idle_through_the_production_call_sequence_with_compositor_ticks` (`crates/flui-app/src/app/ui_realm.rs`), which is deliberately a DIFFERENT test from the one that predates this fix (`an_idle_presentation_produces_and_flushes_exactly_zero_over_many_pumps`, which never calls `record_compositor_tick` and so could not have caught this).

If a genuinely unsolicited tick ever needs to become its own demand source, the caller — not this method — would need to distinguish the two cases before calling it, and mark `DemandKind::Host` itself in the unsolicited branch only; that is not something this record attempts.

### 4. The per-platform table (this record's own checked deliverable)

| Platform | Does `RedrawRequested` carry compositor pacing? | What actually triggers a produce | The real pacer today |
|---|---|---|---|
| Wayland (winit) | Yes — per-surface frame callbacks, delivered only while visible, in response to a prior `request_redraw()` call OR an OS-driven expose signal | `on_request_frame` (fed by the compositor-paced native event; produce itself still requires a real `Dirty`/`Animation`/`Host` demand mark from elsewhere, per §3) | Compositor cadence + the blocking Fifo present (ADR-0029) |
| X11 (winit) | No — delivered immediately, no compositor pacing (self-wake, degenerate case) | `on_request_frame` (fed immediately) | Blocking Fifo present + the no-present fallback throttle (ADR-0029) |
| Windows native | Not run in CI (`cross-typecheck` type-checks only; see AGENTS.md's CI section) | `on_request_frame` (same `bootstrap_desktop` bootstrap as winit) | Fifo present; DWM's own vsync feed is not wired as a distinct signal — named future work, not part of this record |
| macOS (AppKit) native | Not run in CI (same `cross-typecheck`-only coverage) | `on_request_frame` (same `bootstrap_desktop` bootstrap) | Fifo present; `CADisplayLink` is not wired as a distinct signal — named future work, not part of this record |
| Headless (`flui-testing`) | N/A — no native window at all | A scripted pacing feed calling `FrameClock::poll` (or, for the multi-presentation registry, `HeadlessBinding::pump_presentation`/`pump_all`) directly | The test script itself |
| wasm32/web | RAF-shaped in principle, but not wired this record — see the honesty note below | The existing wake-channel path (unchanged) | Browser `requestAnimationFrame` throttling, informally; not measured or asserted here |
| Android | Suspend is *surface loss*, not occlusion — a different lifecycle transition entirely (`Suspended`, presentation.rs) | The existing wake-channel path (unchanged) | Fifo present |

**Honesty notes, not silently assumed:**
- **Wayland is unmeasured too, and it is the table's single load-bearing row** — the entire justification for `record_compositor_tick`'s existence rests on it. This is not omitted by oversight: CI's dedicated `flui-platform` step runs under `FLUI_HEADLESS=1`/`xvfb-run`, i.e. an X11 (virtual) display, never a Wayland compositor — see AGENTS.md's Testing Quirks section. Every claim in this table's Wayland row (frame-callback pacing, visibility-gated delivery, the OS-driven-expose caveat above) is sourced from ADR-0029's own prior measurement session (a real Wayland/GNOME desktop, recorded there with its own evidence) and from winit's documented behavior, not from a fresh measurement taken for this record.
- wasm32/web keeps the wake-channel driver exactly as before this record. `WaitUntil` on web is `setTimeout`-emulated (a 4 ms nested-timer clamp; background tabs throttled to ≥1 s), and the web renderer is `Arc<Mutex<Option<Renderer>>>` (a registry-documented gap, tracked cleanup on a later issue) — wiring RAF as a genuine compositor-paced actuator is deferred, not attempted here.
- Android's suspend transition tears down the `SurfaceView`'s swapchain outright; there is no occlusion-shaped `RedrawRequested` to make targeted in the first place. Clock gating for that transition belongs to the hidden-surface-gating work still to come on this issue, not this record.
- Windows/macOS native backends are compiled (typechecked) but never linked or executed by CI — this record's claims about them are architectural (the code path is identical to winit's `bootstrap_desktop`), not measured on those platforms.

### 5. What this is not

- **Not a second produce mechanism.** Every produce still traces back to exactly one call to `FrameClock::poll` per presentation per pump, from `draw_frame_entered`'s existing segment loop. The generic `WindowEvent::RedrawRequested` platform-event path (§ above, "context") remains genuinely unconsumed — this record does not wire it, to avoid a second trigger for the identical native event `on_request_frame` already handles.
- **Not a change to raster backpressure or hidden-surface gating.** `FrameClock::set_max_in_flight`/`record_submit`/`record_retire`/`set_min_produce_interval` and `set_hidden`/`is_hidden` are unit-tested capabilities with no live wiring yet. This record's own invariant (below) does not depend on either being wired — see §2's honest limitation note for exactly where that dependency will bind once they are.
- **Not a claim that any platform's produce cadence changed.** The demand-marking and edge-triggering additions (§1, §2) are platform-agnostic — they run identically regardless of which backend eventually calls `on_request_frame` — so a platform whose `RedrawRequested` was never compositor-paced to begin with sees the identical produce decisions it had before this record: `record_compositor_tick` marks no demand (§3), so it cannot itself cause a produce that would not otherwise have happened, on ANY platform. What changes is bookkeeping only: fewer, not more, native `request_redraw()` calls under sustained demand (the edge-triggered latch), and a new pacing-feedback sample with no consumer yet.

## End-state invariant

Every produce still has exactly the trigger it always had — a demand mark (`Dirty`/`Animation`, or an explicit `Host` request from a caller that itself decided one is warranted) consumed by `FrameClock::poll`, reached via the wake-channel pump (armed by `try_arm_redraw_request`, consumed by `wake_frame()`). `record_compositor_tick` is not a trigger at all — it is pacing-feedback bookkeeping with no demand-mask side effect, precisely so it cannot become a second, uncontrolled trigger firing on every pump. No `request_redraw()`-shaped actuator exists whose delivered event feeds nothing: the generic `WindowEvent::RedrawRequested` path is the one remaining dangling wire, named and left unconsumed deliberately (§5), not silently forgotten. Platforms whose `RedrawRequested` carries no compositor pacing (X11, and every platform in the table's fallback column) are byte-identical, in produce cadence, to the pre-this-record baseline — and, per the correction in §3, so is Wayland: this record adds a bookkeeping sample there, not a new way to produce.

## Consequences

**Positive:**
- The driver loop is now a named, documented mechanism instead of an implicit consequence of how `wake()`/`request_redraw()` happen to interact with winit's own event delivery.
- A running animation with no other tree-visible effect now correctly flushes every tick (a real behavioral fix, Flutter-faithful, verified against `.flutter/`), closing a latent gap the previous slice explicitly deferred rather than silently left in place.
- The actuator-edge and pacing-feedback primitives are pure, `Cell`-backed, and unit-tested entirely inside `flui-scheduler` — no live window, no winit event loop, and no flakiness risk, satisfying this workspace's stated limits on what a live winit smoke test can prove here.
- The demand-mask gate — the reason `FrameClock` exists at all — stays load-bearing on every platform that calls `record_compositor_tick`, including the desktop backends this record actually wires: caught before merge by a direct probe (§3), not left as a design assumption.
- A running controller with no other tree-visible effect now genuinely keeps producing across real platform callbacks instead of silently stalling after its anchor frame — a second real bug (§2) caught before merge the same way: a production-sequence probe through `wake_action`, not a read of the code.

**Negative / deferred:**
- The generic `WindowEvent::RedrawRequested` platform-event path stays unconsumed. A future embedder-facing use for it (an app author wanting to observe raw platform redraw requests) would need its own design, not an accidental side effect of this record.
- `last_compositor_tick_interval`'s cadence data has no consumer yet — a future exportable-frame-telemetry effort on this issue is where a jank-analysis consumer would read it.
- The table's Wayland row (the load-bearing one) and the Windows/macOS/Android/web rows are none of them freshly measured for this record — see the honesty notes in §4 for what each claim is actually sourced from.
- `try_arm_redraw_request`'s latch has a documented liveness dependency on work that has not landed yet (§2) — a caller-visible gap if either raster backpressure or hidden-surface gating is wired into production ahead of the corresponding wake edge.

## Follow-on (tracked, not part of this draft)

Later work on issue #556 extends this record in three ways, in no particular committed order relative to each other:

- **Hidden-surface gating and wall-clock wake** extends this record with the visibility axis, and is what closes §2's honest limitation for the `Hidden` skip reason (an unhide must wake the owner, not just retain the latch).
- **Raster backpressure** extends this record with the third owner's real wiring — `FrameClock`'s in-flight/throttle knobs gain a live raster-owner counterpart, and the retire→wake edge this record's demand model already accommodates structurally, closing §2's honest limitation for the `Backpressure` skip reason.
- **Configuration and observability work** adds this record's eventual "What this buys" section (a deterministic per-presentation test clock, exportable per-input-attributed telemetry building on `last_compositor_tick_interval`, demand-driven idle as a headline capability) and flips this ADR's status once every piece above has landed.
