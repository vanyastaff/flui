# ADR-0044: The three-owner frame split and the driver-loop hybrid

*Logical update scheduling, physical per-presentation pacing, and raster capacity are three separate owners (`UpdateScheduler`, `FrameClock`, and the raster owner). This record's own scope now covers the first two owners fully, plus the actuator that connects `FrameClock`'s demand mask to the platform: the pre-existing wake channel remains the sole produce trigger on every backend, edge-triggered against the demand mask so repeated ticks collapse into one platform-facing poke; a genuinely compositor-paced `RedrawRequested` additionally feeds pacing-feedback bookkeeping, but marks no demand of its own, because nothing at that call site can tell a self-triggered tick apart from a platform-driven one. Hidden-surface gating and wall-clock wake (`ControlFlow::WaitUntil`) HAVE landed (§6/§7): a hidden presentation produces and submits nothing, its ungate→wake edge does not strand retained demand, and gesture-arena deadlines resolve on an idle loop via a computed wall-clock deadline. Raster backpressure — the third owner's real wiring — extends this record in later work on the same issue and has not landed as of this draft.*

## Context

Before this record, one component (`Scheduler`, since renamed `UpdateScheduler`) combined logical phase/callback/task scheduling, a fixed 60fps assumption, and the frame-drive loop's own dirty predicate. Splitting this into owners that "know" different things — logical time, physical per-surface time, and raster capacity — needed each piece decided before wiring it into the runner, per the ownership rule:

| Owner | Owns | Answers | Never knows |
|---|---|---|---|
| `UpdateScheduler` (realm) | logical time: phases, transient/persistent/post-frame callbacks, the task queue, async drive | "what runs, in what order, within the granted slice" | a refresh rate, a display, a surface, a GPU |
| `FrameClock` (one per presentation) | physical time for one surface: demand coalescing, actuator-edge coalescing, compositor pacing feedback, first-frame deferral, visibility gating, a produce-capacity threshold, frame timestamps | "does this surface produce a frame now, and by when" | phases, callbacks, element trees |
| Raster scheduling (engine seam, future work on this issue) | capacity: latest-frame-wins mailbox, an in-flight counter, GPU backpressure | "will the GPU accept another frame" | demand, ordering, widget state |

Flow rule (normative): demand flows up (clock → realm aggregate wake → platform); frames flow down (logical pass → clock-gated segment → raster submit); backpressure flows up (retire → decrement + owner wake → clock re-fires, once the raster owner exists). No cross-level reads.

An earlier design pass split this into two pieces of work specifically because the driver loop — *who calls `FrameClock::poll`, and what actually drives the pump between polls* — was underspecified. `UpdateScheduler`'s reshape and `FrameClock` itself landed first, deliberately keeping the pump's own driver mechanism untouched and behavior-identical at the single-presentation topology this workspace still ships (proven by an executable equivalence table over the `woken`/`has_pending_work` predicate `FrameClock::poll` replaced). This record is what that first pass explicitly deferred: the actuator.

### What already existed, verified against this tree before deciding anything

- **The pump's own frame-production call site is `bootstrap_desktop`'s `window.on_request_frame` closure** (`crates/flui-app/src/app/runner.rs`), which every desktop backend (winit-backed X11/Wayland, and the native Win32/AppKit backends sharing the same `run_desktop` bootstrap) wires identically. `PlatformWindow::request_redraw()` — called from `UiRealm::wake_frame`'s underlying `FrameWakeHandle` — is what the winit backend's `WinitWindowEvent::RedrawRequested` handler responds to by calling `win.callbacks().dispatch_request_frame()`, which is exactly this closure. There is a **second, separate** `WindowEvent::RedrawRequested` the winit backend also dispatches through its generic `lease_window_event_handler()` path — but `runner.rs`'s `PlatformToUi` enum has no variant for it, and `flui_platform::traits::Platform::on_window_event` has zero callers in `flui-app`, so that specific plumbing genuinely drives nothing. The functional actuator — what a caller means by "the wake channel" — has always been `on_request_frame`/`dispatch_request_frame`, under a name that does not mention `RedrawRequested` anywhere in `runner.rs` outside a comment. **This record does not add a second, parallel produce path off the same native event** — doing so would double-produce every delivered `RedrawRequested`. Instead, the existing `on_request_frame` closure gains the two capabilities below.
- **`request_redraw()` (the native platform call) fires unconditionally today, once per `wake()` invocation**, from several call sites (`WidgetsBinding::set_on_need_frame`, `BuildOwner::set_on_build_scheduled`, and — before this record — `draw_frame_entered`'s vsync-continuation check on every tick a controller was running). On real winit this is harmless (the platform's own `request_redraw()` already coalesces to at most one pending event), but nothing in FLUI's own layer modeled or tested that coalescing discipline, and a deterministic test double has no such coalescing for free.
- **Wayland's frame-callback pacing is not a free-running signal — but it is not the ONLY reason `RedrawRequested` fires, either.** `WinitWindowEvent::RedrawRequested` on Wayland fires in response to a prior `request_redraw()` call, at the compositor's next frame-callback slot, and only while the surface is visible (see ADR-0029's own occlusion-semantics section) — winit's own docs and behavior also deliver it for OS-driven signals FLUI never asked for (an expose/damage event after another window stops occluding this one, a resize-triggered redraw), which have nothing to do with a prior `request_redraw()` call at all. X11 delivers the equivalent event immediately, with no compositor pacing at all. Neither "always caused by our own request" nor "always compositor-paced" is a universal property of `RedrawRequested` — both are per-platform, per-event facts, which is why the table below exists as a checked deliverable rather than an assumption baked into one code path, and why §3 below could not simply treat every delivered tick as demand.
- **`Vsync::has_running()`, sampled to decide whether to keep the pump alive across an animation's duration, was never wired to mark `FrameClock`'s own `DemandKind::Animation`.** A running controller with no other tree-visible side effect (no listener dirtying a widget) would keep the platform loop alive (`wake_frame()` fired every tick) but the segment gate itself would never see nonzero demand from that fact alone — silently diverging from Flutter's own `Ticker`-driven `scheduleFrame`, where the running ticker alone is sufficient to schedule a frame.

## Decision

### 1. The demand mark: Animation, sampled before the tick

`draw_frame_entered`'s vsync-continuation loop now samples `vsync.has_running()` **before** `tick_all(now)`, not only after. If a controller was running entering this tick, `presentation.clock().mark_demand(DemandKind::Animation)` is marked unconditionally — this is what makes a running controller with zero other dirty state still flush its own segment every tick, and it is what makes the tick that completes a controller still flush that completion's final value and status change, mirroring `.flutter/packages/flutter/lib/src/scheduler/ticker.dart`'s `_tick` (:272-285): `_onTick` runs unconditionally before `shouldScheduleTick` is even consulted. This is a Flutter-fidelity fix, verified correct against `.flutter/`, independent of §2's own finding below.

### 2. The actuator edge: `FrameClock::try_arm_redraw_request`, and where it must NOT live

A new, pure (`Cell`-backed) latch on `FrameClock`: test-and-set semantics, `true` at most once per pending demand mask, `false` on every following call until the next granted `poll` produce clears both the mask and the latch.

**Where this latch is consulted matters, and getting it wrong is a real, production-confirmed stall, not a hypothetical.** The first version of this record placed the "should the NEXT pump be scheduled" check — `if vsync.has_running() && try_arm_redraw_request() { wake_frame(); }` — inside `draw_frame_entered`'s vsync loop, sampled **after** `tick_all`, alongside §1's before-tick demand mark. This is wrong: `draw_frame_entered` runs, and produces a scene, *before* the render that scene feeds into; `UiRealm::render_frame_entered` (the caller) then either retries or calls `mark_rendered()`, which unconditionally clears `needs_redraw` to `false` — clobbering, within the SAME callback, any `wake_frame()` call `draw_frame_entered` already made. On the real desktop path, the next platform callback's own dirty gate (`wake_action`, `runner.rs`) reads `needs_redraw()`/`has_pending_work()` fresh, before `draw_frame_entered` runs again — and neither flag stays true for a running controller with no other tree-visible effect once that clobber happens. The result: the controller renders its anchor frame and then silently never ticks again.

This was settled with a production-sequence probe, not by reading the code: `crates/flui-app/src/app/runner.rs`'s `a_running_controller_with_no_other_dirty_state_keeps_producing_across_the_real_wake_action_gate` drives the exact `record_compositor_tick` → `wake_action`'s dirty gate → `render_frame_entered` sequence `bootstrap_desktop`'s closure uses (not `draw_frame_entered` called directly, which never reaches `wake_action` and could not have caught this) — 40 simulated platform callbacks, 16ms apart, well past the test controller's 100ms duration. Under the first version: 1 render, 39 consecutive skips, final animation value stuck at `0`. Every pre-existing pinned test called `draw_frame_entered`/`draw_frame` directly, bypassing `wake_action` entirely, which is why none of them caught this.

**Fix:** the continuation check moved to `UiRealm::render_frame_entered`, positioned AFTER `mark_rendered()`/the retry check, not inside `draw_frame_entered`:

```rust
// In render_frame_entered, after mark_rendered()/the retry check:
for presentation in self.presentations.iter() {
    if presentation.vsync().has_running() {
        presentation.clock().mark_demand(DemandKind::Animation);
        if presentation.clock().try_arm_redraw_request() {
            self.wake_frame();
        }
    }
}
```

`presentation.vsync().has_running()` here reads the same post-tick state the old in-loop check did (the tick already ran, earlier in this same call, via `draw_frame_entered`) — only the WHEN of the wake call changed, not the underlying "is Flutter's `shouldScheduleTick` true" signal. The demand mark here is fresh (this pump's own mask was already cleared by the produce that ran moments earlier) — a genuinely separate concern from §1's before-tick mark, which feeds only THIS pump's own segment.

N ticks that land before a produce actually clears the mask — GPU backpressure (once the raster owner is wired), a configured throttle window, or several ticks in a row that all skip for the same reason — still collapse into exactly one platform-facing wake instead of one per tick; the coalescing property is unaffected by the move, only its timing relative to `mark_rendered()` changed. One observable, pinned-not-implicit consequence: the SAME callback that frees backpressure capacity and produces now also re-arms and wakes again in that same callback (the check runs after `poll()` already reset the latch), where the pre-fix in-loop check — running before `poll()` — would have deferred that wake to a separate, later callback.

**Honest limitation, stated rather than assumed away:** reaching `poll` is necessary but not sufficient to disarm this latch. A `poll` that returns `Skip(Hidden)` or `Skip(Backpressure)` retains both the mask and the latch, so a caller stuck on either reason stays armed-but-withheld until something else causes a produce to succeed — and neither of the two edges that would close that gap structurally (a raster retire waking the owner; an unhide waking the owner) exists yet; both belong to work later on this issue. Dormant today because nothing in production yet engages either `Skip` reason — but wiring either knob into production ahead of its own wake edge would turn this into a real stall of the same shape §2 just fixed. `clear_demand` disarms the latch when it empties the mask outside a produce (an `AnimationController` completing and clearing its own demand bit without a poll in between is exactly this case), which is a different, already-closed gap from the liveness one above.

**Honest limitation, not glossed over:** reaching `poll` is necessary but not sufficient to disarm this latch. A `poll` that returns `Skip(Hidden)` or `Skip(Backpressure)` retains BOTH the mask and the latch, so a caller stuck on either reason stays armed-but-withheld until something else causes a produce to actually succeed — and this clock has no mechanism of its own to make that happen. The two edges that would close the gap structurally (a raster retire waking the owner once capacity frees; an unhide waking the owner once visibility returns) belong to the raster-backpressure and hidden-surface-gating work still to come on this issue, and neither exists yet. Today this dependency is dormant, not a live bug: nothing in production yet calls `set_hidden` or `set_max_in_flight`/`record_submit` against a real presentation's clock, so `poll` never actually returns either `Skip` reason in production — but wiring either knob into production before the corresponding wake edge lands would turn this into a real stall, and that ordering constraint is binding on whichever of those two pieces of work lands first.

A caller settling its OWN demand away (via `clear_demand`) without ever reaching a produce is a different, already-handled case: `clear_demand` disarms the latch itself when it empties the mask, so a later genuinely-new mark can still arm a fresh request — this is what stops `clear_demand`'s own documented use (an `AnimationController` completing and clearing its `Animation` bit outside a produce) from permanently stranding the actuator.

### 3. Pacing feedback: `FrameClock::record_compositor_tick` marks NO demand

A second new method, called unconditionally from `bootstrap_desktop`'s `on_request_frame` closure on every fire, before the existing dirty/`wake_action` gate decides whether anything actually runs this pump. It records the interval between consecutive ticks (`last_compositor_tick_interval`, diagnostic data — no produce decision reads it in this record) and does nothing else.

**This was not the first design tried, and the first one was wrong — recorded here rather than silently corrected.** The first version also marked `DemandKind::Host`, on the theory that "the host platform asked for a frame directly" (that variant's own pre-existing doc) is exactly what a delivered compositor tick is, and that this would only matter as a rare safety net since a tick normally follows a `request_redraw()` already made for a real `Dirty`/`Animation` reason. That reasoning is false in two ways the "What already existed" section above states plainly: (a) `record_compositor_tick` is called on **every single production pump** on every desktop backend, not just on the rare unsolicited tick — so if it marks demand, `poll` can never return `Skip(NoDemand)` on that path, which makes the demand-mask gate — the entire point of `FrameClock`, and of this whole issue — **inert** wherever this method is called; (b) `RedrawRequested` is not always "the host asking for a frame with no dirty state of its own" the way the `Host` variant's doc assumes — winit also delivers it for OS-driven expose/resize signals FLUI never requested, so even the narrower "only mark it for genuinely unsolicited ticks" reading is not implementable at this exact call site, because nothing here can distinguish a self-triggered tick from a platform-driven one; the two cases are indistinguishable by the time `record_compositor_tick` runs. This was caught with a direct probe, not inferred: an idle `UiRealm` (nothing attached, nothing dirty) that calls `record_compositor_tick` then `draw_frame_entered` produced a frame every single pump under the first version; the fix removes the demand mark entirely, and the same probe now reports zero produces over 50 pumps — pinned as `an_idle_presentation_stays_idle_through_the_production_call_sequence_with_compositor_ticks` (`crates/flui-app/src/app/ui_realm.rs`), which is deliberately a DIFFERENT test from the one that predates this fix (`an_idle_presentation_produces_and_flushes_exactly_zero_over_many_pumps`, which never calls `record_compositor_tick` and so could not have caught this).

If a genuinely unsolicited tick ever needs to become its own demand source, the caller — not this method — would need to distinguish the two cases before calling it, and mark `DemandKind::Host` itself in the unsolicited branch only; that is not something this record attempts.

| Headless (`flui-testing`) | N/A — no native window at all | A scripted pacing feed calling `FrameClock::poll` (or, for the multi-presentation registry, `HeadlessBinding::pump_presentation`/`pump_all`) directly | The test script itself |

**Honesty notes, not silently assumed:**
- **Wayland is unmeasured too, and it is the table's single load-bearing row** — the entire justification for `record_compositor_tick`'s existence rests on it. This is not omitted by oversight: CI's dedicated `flui-platform` step runs under `FLUI_HEADLESS=1`/`xvfb-run`, i.e. an X11 (virtual) display, never a Wayland compositor — see AGENTS.md's Testing Quirks section. Every claim in this table's Wayland row (frame-callback pacing, visibility-gated delivery, the OS-driven-expose caveat above) is sourced from ADR-0029's own prior measurement session (a real Wayland/GNOME desktop, recorded there with its own evidence) and from winit's documented behavior, not from a fresh measurement taken for this record.
- wasm32/web keeps the wake-channel driver exactly as before this record. `WaitUntil` on web is `setTimeout`-emulated (a 4 ms nested-timer clamp; background tabs throttled to ≥1 s), and the web renderer is `Arc<Mutex<Option<Renderer>>>` (a registry-documented gap, tracked cleanup on a later issue) — wiring RAF as a genuine compositor-paced actuator is deferred, not attempted here.
- Android's suspend transition tears down the `SurfaceView`'s swapchain outright; there is no occlusion-shaped `RedrawRequested` to make targeted in the first place. §6's `set_presentation_hidden` wiring is stamped-`presentation_id`-addressed and reachable from any backend that dispatches `PlatformToUi::WindowVisibility` for a real visibility signal — Android's own surface-lost lifecycle transition is a DIFFERENT signal (`presentation.rs`'s `Suspended` state, not an occlusion event) that this record does not wire into it; remains named future work.
- Windows/macOS native backends are compiled (typechecked) but never linked or executed by CI — this record's claims about them are architectural (the code path is identical to winit's `bootstrap_desktop`), not measured on those platforms.

### 5. What this is not

- **Not a second produce mechanism.** Every produce still traces back to exactly one call to `FrameClock::poll` per presentation per pump, from `draw_frame_entered`'s existing segment loop. The generic `WindowEvent::RedrawRequested` platform-event path (§ above, "context") remains genuinely unconsumed — this record does not wire it, to avoid a second trigger for the identical native event `on_request_frame` already handles.
- **Not a change to raster backpressure.** `FrameClock::set_max_in_flight`/`record_submit`/`record_retire`/`set_min_produce_interval` remain unit-tested capabilities with no live raster-owner wiring yet. §6 below DOES wire `set_hidden`/`is_hidden` into production (closing half of §2's honest limitation note — the `Hidden` skip reason); the `Backpressure` skip reason's own retire→wake edge remains the unbuilt half.
- **Not a claim that any platform's produce cadence changed.** The demand-marking and edge-triggering additions (§1, §2) are platform-agnostic — they run identically regardless of which backend eventually calls `on_request_frame` — so a platform whose `RedrawRequested` was never compositor-paced to begin with sees the identical produce decisions it had before this record: `record_compositor_tick` marks no demand (§3), so it cannot itself cause a produce that would not otherwise have happened, on ANY platform. What changes is bookkeeping only: fewer, not more, native `request_redraw()` calls under sustained demand (the edge-triggered latch), and a new pacing-feedback sample with no consumer yet.

### 6. Hidden-surface gating and the ungate→wake edge

`FrameClock::set_hidden`/`is_hidden` existed since the clock's own introduction, unit-tested in isolation, with **zero production callers** — the gap this section closes. `UiRealm::set_presentation_hidden(presentation_id, hidden)` calls `FrameClock::set_hidden` on exactly the addressed presentation and is wired from `PlatformToUi::WindowVisibility`'s real dispatch arm, using the `presentation_id` every `PlatformToUi` event is already stamped with at enqueue time — additive alongside, never replacing, the pre-existing loop-scoped `AppLifecycleState` derivation that same event also drives. While hidden, `FrameClock::poll` returns `Skip(Hidden)`: the segment gate in `draw_frame_entered`'s second loop skips build/layout/paint entirely for that presentation, so `render_frame_entered` never reaches `render_scene` — zero GPU submits, demand mask retained.

**The critical liveness dependency this section closes.** §2's own honest limitation stated that a `poll` returning `Skip(Hidden)` retains both the mask and the `try_arm_redraw_request` latch, and that "an unhide waking the owner" was one of two structural edges not yet built — dormant only because nothing called `set_hidden` in production. Since this section *does* wire `set_hidden` into production, that dependency stops being dormant: wiring the gate without also wiring the ungate→wake edge in the same change would strand every presentation that gets dirtied while hidden.

The fix is `set_presentation_hidden`'s own unhide branch: it wakes the platform loop **unconditionally** when the retained demand mask is nonempty — deliberately **not** gated on `try_arm_redraw_request`'s own return value. The latch is untrustworthy here: it may already be armed from a demand mark that occurred *before* this presentation went hidden (a poke the loop already delivered and wasted, since that poll saw `Skip(Hidden)` and skipped) — consulting it at unhide time would read `false` (already armed, nothing new to arm) and incorrectly stay silent, stranding the presentation gated forever with retained demand nobody ever wakes for. An idle (never-dirtied) presentation's unhide correctly wakes nothing — there is no retained demand to act on.

Verified with the full sequence, not just the two ends in isolation: `occlude_then_dirty_then_unocclude_wakes_exactly_once_and_produces_exactly_once` (`crates/flui-app/src/app/ui_realm.rs`) drives occlude → dirty (a real pipeline `mark_needs_paint`, not just the wake-only redraw bit — so the eventual unhide pump has something to actually paint) → three pumps confirming zero produces/zero submits/zero *additional* wakes while hidden (the render pipeline's own independent `on_need_visual_update` wake fires once for the clean→dirty transition, a pre-existing, unrelated mechanism the test isolates rather than conflates with) → unhide, asserting exactly one more wake and exactly one produce/submit on the very next pump, then confirms settling (no further produce). `unoccluding_an_undirtied_presentation_does_not_wake` pins the negative case. Both mutant-confirmed: removing the unconditional-wake branch (mutating it to `if false && ...`) makes the occlude/dirty/unocclude test fail red (`left: 1, right: 2`); reverted, re-confirmed green.

Gesture-arena deadlines are the other half of the gating story, and were already correct by construction *before* this section, not newly fixed by it: `draw_frame_entered`'s gesture-deadline tick (`presentation.gestures().tick_deadlines()`) runs unconditionally in the realm's FIRST per-presentation loop, before the second loop's `FrameClock::poll` gate is even consulted — so a gated presentation with an in-flight long-press still resolves it through the arena's own callback, with zero GPU submits, exactly matching §2 of this issue's plan ("arena deadlines are input-correctness, not frame production" — they survive clock gating structurally, by not being inside the gated loop at all). Pinned by `gated_long_press_resolves_through_the_arenas_own_callback_with_zero_submits`; mutant-confirmed by temporarily no-op'ing the `tick_deadlines()` call, which fails the test red (the long-press never fires).

**Honest scope, backend-conditional — corrected after review, verified against winit's own source rather than assumed.** An earlier draft of this section named Wayland as the compositor-conditional case; that was wrong. Checked directly against winit 0.30.13's `platform_impl` and its own `WindowEvent::Occluded` doc: the emitting backends are **X11** (Xlib's `VisibilityFullyObscured` state — fires only on FULL obscuration, never partial), **macOS**, **iOS**, and **Web**. Winit's own doc states plainly: "Android / Wayland / Windows / Orbital: Unsupported." **There is no Wayland emitter anywhere in `platform_impl` at all** — not a compositor-dependent one, none. On this workspace's own Wayland/GNOME desktop reference, `set_presentation_hidden(true)` is therefore never called via this path today; on X11 (this repo's actual CI device, via `xvfb-run`) it fires only when a window is fully covered, which a compositing window manager may rarely or never produce. Where the signal is never delivered, this presentation's clock is simply never marked hidden and behavior is unchanged from before this section — the no-present fallback throttle (ADR-0029) still bounds the degenerate spin case regardless. `flui-platform`'s CI coverage for this backend runs under `FLUI_HEADLESS=1`/`xvfb-run` (X11) — this section's own automated evidence is at the `UiRealm`/`FrameClock` level (the gate itself, proven correct once told to gate) and the storage/wiring level, not a live-window occlusion measurement on any backend.

### 7. Wall-clock wake: `ControlFlow::WaitUntil`

`about_to_wait` no longer sets `ControlFlow::Wait` unconditionally. It consults a newly registered hook (`Platform::set_wake_deadline_hook`, a default-no-op trait method the winit backend overrides, mirroring `set_exit_policy_hook`'s exact existing seam) fresh every idle iteration, and sets `ControlFlow::WaitUntil(deadline)` when that hook answers `Some`, falling back to `Wait` when it answers `None` — the previously-unconditional behavior for the case where nothing anywhere needs a wall-clock wake.

**Why this exists at all.** An idle `ControlFlow::Wait` loop only re-enters `on_request_frame` on an actual external event or an explicit `wake()`/`request_redraw()` call. A pending gesture-arena deadline (an armed long-press hold, a double-tap give-up window) needs *nothing else* to be dirty for it to eventually need resolving — without a wall-clock wake, `tick_deadlines` would never run again once the loop goes idle, and the deadline would silently never fire until some *unrelated* input happened to wake the loop first.

**`ControlFlow::WaitUntil` alone does not run a pump — it needs an actuator, and an earlier version of this section shipped without one (caught in review, not before).** When a `WaitUntil` deadline expires, winit calls `WinitApp::new_events` with `StartCause::ResumeTimeReached` — but delivers no `WindowEvent`. Nothing dirty, nothing redrawn, no `dispatch_request_frame`. Without an explicit actuator, `about_to_wait` runs again immediately, re-consults the SAME hook (nothing has changed, so it answers the same now-past deadline), and re-arms `WaitUntil` at an instant already behind `Instant::now()` — winit fires it again on the very next iteration, unboundedly: a `WaitUntil` with nothing on the other side degenerates into a busy-spin, not a wake, and the deadline it was meant to serve never actually resolves either.

**Measured, not asserted — with a standalone probe, because this slice did not write a live-loop test, not because one is impossible.** `flui-platform`'s own `build_test_event_loop` builds a real `EventLoop` off the main thread (`EventLoopBuilderExtX11::with_any_thread`, Linux and Windows; `#[ignore]`d on macOS), and four tests already drive `run_app` on it under `xvfb-run` — the genuine constraints are one `EventLoop` per process and macOS main-thread affinity. A throwaway winit 0.30.13 binary reproducing this exact shape (armed deadline already past, no `new_events` override) showed 657,403–678,159 `about_to_wait` iterations in a 500 ms window (~1.3–1.4 MHz, one core pegged) across repeated runs — the same order of magnitude an independent measurement of the identical bug found. The fix: `WinitApp::new_events` calls `request_redraw()` on every window this platform currently tracks when `StartCause::ResumeTimeReached` fires — this queues a REAL `WindowEvent::RedrawRequested` for the next iteration, re-entering `dispatch_request_frame`/`on_request_frame`/`wake_action` exactly like any other wake in this backend, never a second, parallel produce path. The same probe shape, with the actuator added and a genuinely-armed 100 ms deadline standing in for a real long-press, showed **6** `about_to_wait` iterations over the same 500 ms window (down from ~660,000+) and the deadline resolving 14–78 µs after its own instant across repeated runs — bounded, and effectively instant. This probe is a manual, one-off verification artifact, not part of this repo's automated suite — see the honest-scope note this fact drives in `docs/runtime-contract.toml`'s `timer-service-for-frozen-tickers` contract.

**The deadline itself, and why a boolean was not enough.** The gesture arena's pre-existing `has_pending_deadline`/`has_pending_deadlines` answer only "is one armed", never "when". `GestureArenaMember` gains a parallel `next_deadline(&self) -> Option<web_time::Instant>` (default `None`, mirrors `has_pending_deadline`'s own default-false shape), implemented for `LongPressGestureRecognizer` (`down_time + long_press_timeout()`, guarded by the same `Possible`-phase check `has_pending_deadline` uses) and `DoubleTapGestureRecognizer` (`first_tap_time + double_tap_timeout()`, guarded by the same `WaitingForSecond`-phase check) — both computed from state the recognizer already held privately, not a new clock read. `GestureArena::next_deadline`/`GestureBinding::next_deadline` aggregate the min over live members, same snapshot discipline as `has_pending_deadlines`. `GestureTimerService::next_deadline` (the separate, standalone timer utility — see the honest-scope note below) peeks its already-sorted earliest entry's own absolute deadline directly, no clock read needed.

**N realms on one loop thread.** `UiRealm::next_wake` is the min over that realm's own presentations' `GestureBinding::next_deadline`; `AppRuntime::next_wake` is the min over every hosted realm's `next_wake`, folded with `GestureTimerService::next_deadline` — the loop-owning `AppRuntime` is the only component that can see every realm at once (a realm cannot see its siblings). `next_wake_is_the_min_deadline_across_every_installed_realm` (`crates/flui-app/src/app/runner.rs`) proves the aggregate takes the EARLIER of two realms' deadlines regardless of install order (a far 5s timeout on realm A installed first, a near 50ms one on realm B installed second) — mutant-confirmed: swapping `.min()` for `.max()` in `AppRuntime::next_wake` makes the test fail red (observes ~5s instead of ~50ms until wake). A realm currently checked out for dispatch (`slot.realm` is `None`) contributes nothing — correct, since `next_wake` is only ever consulted from `about_to_wait`, after every dispatch for that iteration has already returned every realm to its slot.

**Honest scope on `GestureTimerService` (not overclaimed).** This is `flui-interaction`'s standalone, general-purpose timer utility, architecturally distinct from the gesture arena's own frame-polled deadline mechanism — and it has **zero production callers today**, unchanged by this section (see `dropping_realm_a_cannot_wake_realm_b`'s own doc, `ui_realm.rs`). Folding its `next_deadline()` into `AppRuntime::next_wake` is forward-composing, not aspirational: an embedder or a future recognizer that *does* register a timer through it is honored without a second wiring pass, at zero behavioral cost while nothing does (it always answers `None` in this workspace's actual production wiring).

### 8. What this buys: demand-driven idle, measured with a real wall clock

An earlier slice on this issue already proved the zero-produce half at the clock level (an empty mask, no gating, `poll` returns `Skip(NoDemand)` every pump). This section adds the measured, real-wall-clock counterpart with a genuinely *live* realm: `idle_presentation_over_a_real_wall_clock_window_produces_zero_then_responds_instantly` (`crates/flui-app/src/app/runner.rs`'s `desktop_pacing_tests`, alongside the `wake_action`-gate tests it reuses — not `ui_realm.rs`, where an earlier version of this test lived).

**Corrected in review: an earlier version of this test drove a bare fixed-5ms-interval poll loop calling `render_frame_entered` directly, bypassing the real dirty gate entirely.** That made "zero produces" true, but for the wrong reason — it didn't prove idle costs nothing, it just asserted that many artificial extra pumps each individually produced nothing. The real hazard it hid: `has_pending_work` includes `gestures().has_pending_deadlines()`, so a pending gesture-arena deadline keeps `dirty == true` for its entire armed lifetime; driven through the REAL gate, any wake while it is armed-but-not-due reads `dirty == true` → `WakeAction::Render` → a full (unpainting) pump → `presented == false`, which — with the gate still open afterward — is exactly the condition `no_present_fallback_pace` sleeps on. The corrected test drives `wake_action`, `keeps_frame_gate_open`, and `no_present_fallback_pace` — the same real gate `a_running_controller_with_no_other_dirty_state_keeps_producing_across_the_real_wake_action_gate` (§2) already exercises — and wakes ONLY at `UiRealm::next_wake`'s own computed instant, never on a fixed interval. Over a real ~100 ms window (a genuine gesture-arena long-press deadline, armed and resolving naturally), this leaves exactly **one** real callback for the whole window — not dozens — confirming the loop is genuinely, not just numerically, idle: produced-count and submit-count stay at their pre-window values, the live `spawn_local` async task is confirmed to have been polled exactly once (at that one callback), and the armed deadline is confirmed to have resolved by the end of the window. A subsequent, freshly-requested redraw then produces and submits within the very next real callback, not "eventually". This is the direct battery/idle contrast with an always-vsync engine (Flutter's own scheduler asks for vsync whenever anything at all is scheduled): FLUI's produce path burns zero frames and zero GPU work at any visibility, demand-driven, and idle is structurally the empty mask rather than a mode a caller opts into.

## End-state invariant

Every produce still has exactly the trigger it always had — a demand mark (`Dirty`/`Animation`, or an explicit `Host` request from a caller that itself decided one is warranted) consumed by `FrameClock::poll`, reached via the wake-channel pump (armed by `try_arm_redraw_request`, consumed by `wake_frame()`). `record_compositor_tick` is not a trigger at all — it is pacing-feedback bookkeeping with no demand-mask side effect, precisely so it cannot become a second, uncontrolled trigger firing on every pump. No `request_redraw()`-shaped actuator exists whose delivered event feeds nothing: the generic `WindowEvent::RedrawRequested` path is the one remaining dangling wire, named and left unconsumed deliberately (§5), not silently forgotten. Platforms whose `RedrawRequested` carries no compositor pacing (X11, and every platform in the table's fallback column) are byte-identical, in produce cadence, to the pre-#2/#3 baseline — and, per §3's own correction, so is Wayland: those sections added a bookkeeping sample there, not a new way to produce.

**Extended by §6/§7:** a hidden presentation produces zero segments and zero submits regardless of demand, with the mask retained and released exactly once on unhide (no stranding, no double-produce). Wall-clock time is no longer invisible to the driver loop: `about_to_wait` wakes at the earliest instant any hosted realm's own armed gesture-arena deadline (or, forward-composing but inert today, `GestureTimerService`) needs it to, computed fresh every idle iteration, never a stale snapshot from whenever the hook was installed — AND, critically, `WinitApp::new_events`'s `ResumeTimeReached` actuator turns that expiry into a real `RedrawRequested`, so the wake genuinely re-enters the exact same `on_request_frame`/`wake_action` gate every other wake already goes through, with no bypass of the demand-mask decision (§7's own probe evidence: 6 iterations and microsecond-scale resolution latency, not the unbounded spin an un-actuated `WaitUntil` produces). Neither addition changes what counts as a produce trigger — a gated presentation's deadline resolves through the arena's own callback, never through `FrameClock::poll`.

## Consequences

**Positive:**
- The driver loop is now a named, documented mechanism instead of an implicit consequence of how `wake()`/`request_redraw()` happen to interact with winit's own event delivery.
- A running animation with no other tree-visible effect now correctly flushes every tick (a real behavioral fix, Flutter-faithful, verified against `.flutter/`), closing a latent gap an earlier slice explicitly deferred rather than silently left in place.
- The actuator-edge and pacing-feedback primitives are pure, `Cell`-backed, and unit-tested entirely inside `flui-scheduler` — no live window, no winit event loop, and no flakiness risk, satisfying this workspace's stated limits on what a live winit smoke test can prove here.
- The demand-mask gate — the reason `FrameClock` exists at all — stays load-bearing on every platform that calls `record_compositor_tick`, including the desktop backends this record actually wires: caught before merge by a direct probe (§3), not left as a design assumption.
- A running controller with no other tree-visible effect now genuinely keeps producing across real platform callbacks instead of silently stalling after its anchor frame — a second real bug (§2) caught before merge the same way: a production-sequence probe through `wake_action`, not a read of the code.
- A hidden presentation now genuinely burns zero GPU work — closing the other half of §2's own honest liveness gap (the `Hidden` skip reason), with the ungate→wake edge proven not to strand retained demand (§6).
- Gesture-arena deadlines survive an idle, fully-gated platform loop: `about_to_wait`'s `ControlFlow::WaitUntil`, actuated through `new_events`'s `request_redraw` poke, means a long-press/double-tap timeout resolves within microseconds of its own instant (probe-measured) instead of waiting for an unrelated wake to happen to occur first — and does so WITHOUT the unbounded busy-spin an un-actuated `WaitUntil` would otherwise cause (§7).

**Negative / deferred:**
- The generic `WindowEvent::RedrawRequested` platform-event path stays unconsumed. A future embedder-facing use for it (an app author wanting to observe raw platform redraw requests) would need its own design, not an accidental side effect of this record.
- `last_compositor_tick_interval`'s cadence data has no consumer yet — a future exportable-frame-telemetry effort on this issue is where a jank-analysis consumer would read it.
- The table's Wayland row (the load-bearing one) and the Windows/macOS/Android/web rows are none of them freshly measured for this record — see the honesty notes in §4 for what each claim is actually sourced from; the same is true of §6's occlusion-delivery claims (no live Wayland minimize/restore pass in this environment).
- `try_arm_redraw_request`'s latch STILL has one open half of its documented liveness dependency (§2): the `Backpressure` skip reason's own retire→wake edge is unbuilt (raster backpressure remains unwired — the `Hidden` half closed in §6).
- `GestureTimerService::next_deadline` composes into `AppRuntime::next_wake` but has zero production callers, same as before this record — an app-level timeout that isn't a gesture-arena recognizer has no wall-clock wake of its own yet.
- A REALM fully backgrounded via the coarser, pre-existing `AppLifecycleState`-driven `frames_enabled`/`WakeAction::PumpAsync` gate still skips `tick_deadlines` entirely (that arm never calls `draw_frame_entered` at all) — a genuinely different, larger change than this record's own bounded scope, named rather than silently left unexamined.
