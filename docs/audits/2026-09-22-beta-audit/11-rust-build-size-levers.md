# Rust/Cargo build-size & CI-time levers for a 28-crate wgpu/naga/cosmic-text/lyon workspace (315 integration-test files, 74 examples)

Toolchain in question: rustc/cargo 1.98.1, MSRV 1.97, edition 2024. Researched against stable releases 1.90→1.98 (Sept 2025 → Sept 2026) plus nightly/RFC status as of 2026-09-22.

## Summary table

|---|---|---|---|
| `rust-lld` default linker on `x86_64-unknown-linux-gnu` | **Stable since Rust 1.90.0** (2025-09-18), on by default. Opt-out: `-C linker-features=-lld`. macOS/Windows: **not the default** (macOS already used a fast native linker path; no rust-lld default there as of 1.98). [Rust 1.90.0](https://blog.rust-lang.org/2025/09/18/Rust-1.90.0/), [Phoronix](https://www.phoronix.com/news/Rust-1.90-LLD-Linking) | Up to 7× faster incremental link, ~20-40% full-build wins on large binaries with much debuginfo — exactly your 315-binary problem on Linux CI. | **Yes** — verify Linux CI runners are actually getting it (they will, it's default); no config needed. Nothing to do for macOS dev boxes (see split-debuginfo instead). |
| `wild` linker | **Not stable, not in-tree.** Standalone project (0.9 as of May 2026, 0.8 Jan 2026), Linux-only, macOS/Wasm support "being drafted." Now under the Rust Foundation's Rust Innovation Lab. [Phoronix](https://www.phoronix.com/news/Wild-Linker-0.9), [Rust Foundation](https://rustfoundation.org/media/welcoming-wild-to-the-rust-innovation-lab/) | Reportedly faster than lld on many-core Linux boxes for very large link jobs. | **No, not yet** — Linux-only, external dependency, immature; rust-lld already gives most of the win for free. Revisit in 6-12 months once macOS support lands. |
| `build.build-dir` config (separate intermediate artifacts dir from final `target/`) | **Stable since Cargo 1.91.0** (2025-10-30). Syntax: `[build]` / `build-dir = "/fast-disk/cargo-build"` in `.cargo/config.toml` (supports path templating with `{workspace-root}` etc). Note: a *separate*, still-experimental "build-dir layout v2" (reorganizes by package/hash) had a stabilize→revert→re-stabilize cycle (PR #16807 stabilized, reverted for perf/scaling bugs, re-stabilized in PR #17354, landing around Cargo 1.100 per that PR's target milestone — this is the internal layout reshuffle, not the `build-dir` **config knob** itself, which has been stable and usable since 1.91). [Cargo CHANGELOG](https://doc.rust-lang.org/cargo/CHANGELOG.html), [PR #15833](https://github.com/rust-lang/cargo/pull/15833), [PR #17354](https://github.com/rust-lang/cargo/pull/17354) | Lets you point intermediate (`.fingerprint`, `deps/*.o`-equivalents, incremental caches) at fast/ephemeral storage (tmpfs, local NVMe scratch) while keeping final artifacts (`target/debug/{binary,examples}`) on the persistent/cached path — directly attacks "target/debug is 13-20 GB" by letting you cache only the final-artifacts subtree and let CI runners regenerate/discard intermediates each run. | **Yes** — biggest structural win available. Point `build-dir` at runner-local scratch disk in CI, keep `target-dir`/final artifacts on the path GH Actions cache addresses; on dev machines point it at a tmpfs or a scratch SSD to keep the checked-in `target/` link-only. |
| `hint-mostly-unused` (`[profile.*.package.<name>] hint-mostly-unused = true` or a crate's own `[hints] mostly-unused = true`) | **Nightly-only as of 2026-09-22.** Introduced/plumbed Cargo 1.89 (`-Zhint-mostly-unused` profile option) and 1.90 (`[hints]` table, tracking issue [#15644](https://github.com/rust-lang/cargo/issues/15644)), "call for testing" post July 2025. No stabilization PR/version yet. Requires `cargo +nightly -Zprofile-hint-mostly-unused`. [Inside Rust: Call for Testing](https://blog.rust-lang.org/inside-rust/2025/07/15/call-for-testing-hint-mostly-unused/) | 23-51% clean-build-time reduction measured on crates with huge, mostly-unused APIs (windows-sys is the canonical example; wgpu/naga's own huge surface — e.g. unused backends/features — is a plausible candidate). Only helps if the *hint-carrying* dependency really is mostly unused by your code; can regress if most of its surface actually is used across many of your binaries. | **No for now (stable CI), yes to trial on nightly.** Your MSRV is 1.97 stable — shipping a workspace-wide reliance on a nightly-only flag breaks MSRV/stable CI. Worth an experimental nightly job to hint `windows-sys`/similarly huge transient deps pulled in by wgpu, and re-evaluate once it stabilizes. |
| `-Zno-embed-metadata` / `-Zembed-metadata=no` (split/omit crate metadata from rlibs) | **Nightly-only**, introduced Cargo 1.89 ([#15378](https://github.com/rust-lang/cargo/pull/15378), tracking [#15495](https://github.com/rust-lang/cargo/issues/15495)). An Aug 2026 Inside Rust post describes an *experiment* defaulting it on for nightly-vs-nightly builds only — explicitly "not currently headed for stabilization" as a permanent flip, evaluation-only. [Kobzol's blog](https://kobzol.github.io/rust/rustc/2025/06/02/reduce-cargo-target-dir-size-with-z-no-embed-metadata.html), [Inside Rust Aug 2026](https://blog.rust-lang.org/inside-rust/2026/08/18/reducing-target-dir-size-on-nightly/) | Measured: **-36.3%** target-dir size on release-without-debuginfo builds; only **-9.5%** on dev+incremental+debuginfo builds (debuginfo/incremental dominate there). Std `.so` shrank 13 MiB → 3 MiB. Compile-time effect is "miniscule" on SSD — this is a **disk-size**, not link-time, lever. | **No** — nightly-only, and your workspace's dev-profile pain (13-20 GB) is dominated by debuginfo/incremental, exactly the case where this lever gives the smallest (-9.5%) return. Not worth the nightly dependency yet. |
| `-Zshare-generics` | **Still unstable/nightly-only** as of 2026; implicitly on for `opt-level=s`/`z` in some contexts but never exposed as a stable dev/test-profile flag. No stabilization PR found. [rust-lang/rust#142164](https://github.com/rust-lang/rust/issues/142164) | Would reduce duplicate generic-instantiation codegen across your 315 test binaries + 74 examples (each monomorphizing the same wgpu/naga/lyon generics) if usable with dylibs — the actual mechanism CI-relevant here is duplicate codegen units across separate test binaries, which this doesn't fully solve since each test binary is a separate crate-graph compile, not a shared dylib. | **No** — not stable, and even if it were, doesn't apply cleanly to per-binary integration-test compiles unless you also switch to `-C prefer-dynamic`/shared dylibs, which is a bigger and riskier architecture change. |
| `-Zthreads` (parallel rustc frontend) | **Nightly-only**, default `threads=1` even on nightly. 2026 is an explicit official Rust Project Goal to push toward stabilization (test-suite hardening, Cargo enablement, stabilization report) but **not landed on stable** as of 1.98. [Project Goal: Parallel Front End 2026](https://rust-lang.github.io/rust-project-goals/2026/parallel-front-end.html), [compiler-team#1005](https://github.com/rust-lang/compiler-team/issues/1005) | Would parallelize per-crate frontend work (parsing/typeck), helping wall time on your huge naga/wgpu crates specifically, independent of the "too many test binaries" problem. | **No, not yet actionable** — track the 2026 goal; nothing to configure today on stable. |
| `-Zcodegen-backend=cranelift` (rustc_codegen_cranelift, "rustc-codegen-cranelift-preview" rustup component) | **Nightly-only preview component**, ships for Linux/macOS/Windows x86_64 nightlies but **not published as a rustup component for `aarch64-apple-darwin`** — Apple Silicon users must build it from source; known gaps around debuginfo on macOS ARM as of April 2026. [rustc_codegen_cranelift#1502](https://github.com/rust-lang/rustc_codegen_cranelift/issues/1502) | 2-3× faster debug codegen typically, but doesn't reduce *linking* (still one link per test binary) and has known incompatibilities with heavy `unsafe`/SIMD/inline-asm code paths that wgpu/naga's SPIR-V and shader-compiler-adjacent code likely hits. | **No** — your dev machines are macOS aarch64 (per your CLAUDE/RTK memory notes on macOS-specific work), where this isn't even installable via rustup; and it's nightly-only, conflicting with a 1.97 MSRV policy. |
| `split-debuginfo` | **Stable, long-standing** (`unpacked`/`packed`/`off`), but **default values differ by platform and this differs from your stated config.** macOS: defaults to `unpacked` (debug info in per-object `.o`/`.dSYM`-adjacent files) whenever debug info is enabled — already a target-dir-size win vs old macOS default. Linux: defaults to `off` (embedded in binary/object files) unless you opt in. [Cargo Profiles reference](https://doc.rust-lang.org/cargo/reference/profiles.html) | Setting `split-debuginfo = "unpacked"` explicitly on Linux CI too (not just relying on macOS's default) avoids re-embedding duplicate debuginfo into every one of your 315+74 binaries; combined with `debug = "line-tables-only"` (already set) this is close to minimal useful debuginfo. | **Yes for Linux CI** — add `split-debuginfo = "unpacked"` under `[profile.dev]`/`[profile.test]` in `.cargo/config.toml` for Linux runners (macOS already gets it by default); keeps stack traces meaningful while cutting per-binary duplication. |
| `codegen-units`, `lto`, `opt-level=1` (dev) already set | Stable, standard. Cargo's own dev-profile defaults are `opt-level=0`, `lto=false`, `codegen-units=256`, `incremental=true`, `panic=unwind`. Your workspace already overrides `opt-level=1`, `incremental=false`. | `incremental=false` + `codegen-units` at default (256) is a reasonable CI trade for reproducibility, but 256 CGUs per crate multiplies the object-file/link input count across 389 binaries. Lowering `codegen-units` (e.g. to 16) for the **test** profile trades some parallel-codegen speed for less linker input and slightly smaller/more optimizable code, but is workload-dependent — measure, don't assume. | **Maybe** — worth an A/B: try `[profile.test] codegen-units = 16` on Linux CI; keep 256 (default) for local dev where incremental+parallel codegen matters more than link input size. |
| `panic = "abort"` for `[profile.test]` | **Not allowed / silently ignored by Cargo** — Cargo explicitly ignores `panic` config for `test`/`bench` profiles because they link libtest, which requires unwind (issue behavior confirmed since cargo#3175). A nightly-only `-Zpanic-abort-tests` exists (tracking issue [rust-lang/rust#67650](https://github.com/rust-lang/rust/issues/67650)) with **no stabilization plan committed** ("it's currently unclear how this feature will be stabilized"). Cargo 1.92 instead stabilized an unrelated `panic = "immediate-abort"` profile variant (not for tests). [Cargo unstable reference](https://doc.rust-lang.org/cargo/reference/unstable.html) | Would shrink test binaries and speed per-test compile if it worked, but doesn't apply to your stable-toolchain constraint. | **No** — not usable on stable; do not attempt via profile override, Cargo will ignore it. |
| `[profile.test]` inheriting from `[profile.dev]`, `debug = "none"` for tests | Stable, standard profile inheritance. Setting `[profile.test] debug = "none"` (or `0`) is allowed and stable. | Removes almost all debuginfo from test binaries → biggest single easy win on the 13-20 GB target/debug figure and on link time (way less debug-symbol data to write per binary), **but** it degrades nextest/libtest failure output to raw addresses with no useful backtraces or line numbers on panic, and disables source-level debugger attachment (`nexte.st` debugger integration assumes debuginfo is present). | **Partial yes** — use `debug = "line-tables-only"` (already your workspace default, inherited into test) rather than dropping to `"none"`; this is already close to optimal (keeps `RUST_BACKTRACE=1` line numbers, drops full variable/type debug info). Do **not** go further to `"none"` given you rely on nextest's `--nocapture`/panic diagnostics across 315 test files — that trade is asymmetric (small extra size win, large diagnosability loss). |
| cargo-nextest `nextest archive` / build reuse | **Stable, current nextest feature** (`cargo nextest archive --archive-file`, `cargo nextest run --archive-file ... --extract-to`). Docs: [nexte.st CI archiving](https://nexte.st/docs/ci-features/archiving/) | Lets you build test binaries **once** in a build job and fan out to N test-execution jobs without rebuilding/relinking 389 binaries per shard — directly cuts CI wall time when you already shard/partition. | **Yes** — if CI currently rebuilds per shard, switch to build-once-archive-once-reuse-many. Combine with nextest partitioning (`--partition count:K/N`, hash or count-based). |
| cargo-nextest `--build-jobs`, `cargo nextest run --no-run` for sizing | Stable. `--no-run` builds without executing, useful for measuring/benchmarking link time and archive size in isolation. | Operational/diagnostic value for measuring the effect of the other levers above (e.g. "how much did switching `debug` level shrink the archive"). | **Yes, as a measurement tool**, not a fix by itself. |
| matklad's "one integration-test binary per crate" pattern | Not a Cargo/rustc feature — a **project convention**: consolidate many `tests/foo.rs`, `tests/bar.rs`, … files (each its own binary+link) into one `tests/it/main.rs` with submodules. Documented result on `rust-analyzer`/cargo itself: **3× faster test-suite compile, 5× smaller on-disk artifacts** after applying it. [matklad: Delete Cargo Integration Tests](https://matklad.github.io/2021/02/27/delete-cargo-integration-tests.html) | Directly attacks your stated root cause — "315 integration-test files each become a separate test binary linking the whole stack." Consolidating per-crate (or per logical test-suite) collapses N link steps into 1 per crate, each paying the wgpu/naga/lyon/cosmic-text link cost once instead of N times. | **Yes — this is the single highest-leverage lever for your specific numbers.** With 28 crates and 315 files, even collapsing to ~28-50 test binaries (one or a few per crate) instead of 315 should cut link-time-dominated CI wall time by roughly the same 3-5× matklad measured, and directly shrinks `target/debug` (fewer duplicated copies of statically-linked wgpu/naga/lyon/cosmic-text per binary). No native Cargo/`harness` feature does this automatically as of 1.98 — see below. |
| Native cargo support for combining integration tests / `harness` improvements / `cargo test --all-in-one` | **Does not exist on stable.** Open feature request [rust-lang/cargo#13450](https://github.com/rust-lang/cargo/issues/13450) ("option to run all tests under the same binary") remains open/unresolved as of 2026; no RFC has landed. `libtest-mimic` is a *harness replacement* crate (lets you write a custom `fn main` runner with libtest-like output) that projects use to hand-roll the same consolidation matklad describes, but it is not a Cargo feature — it's a workaround crate you opt into per test binary via `harness = false`. | Nothing changed here since 2021; the "one binary" pattern is still manual, not automated by Cargo. | **Use `libtest-mimic` only if** you need a fully custom multi-suite runner; for straightforward consolidation, plain `tests/it/main.rs` + `mod` files (matklad's approach, requiring no extra crate) is simpler and sufficient. |
| sccache | Stable, third-party, widely used in Rust CI. Caches compiler invocations (works with rustc directly; wrapper via `RUSTC_WRAPPER=sccache`). | Speeds up **rebuilds of unchanged deps** across CI runs/branches — high value when 28 crates' dependency graph (wgpu/naga/etc.) is rebuilt from scratch on every CI run. Doesn't reduce link time or binary count, only recompilation of unchanged crate objects. | **Yes** — pair with `build.build-dir` (point sccache's own cache dir at persistent cache storage, keep ephemeral build-dir on local scratch) and GH Actions cache for the sccache cache dir itself. |
| `cargo sweep` / `cargo-cache` | Stable, third-party. `cargo sweep` prunes stale `target/` artifacts by build age/git-branch heuristics; `cargo-cache` reports/cleans the global `~/.cargo` registry+git caches. | Addresses long-lived dev-machine and self-hosted-runner target-dir growth (matches your memory note about a 460 GB shared target dir issue class), not ephemeral GH-hosted-runner CI (which starts clean each job). | **Yes for self-hosted runners / dev machines only** — irrelevant for ephemeral GitHub-hosted runners, but you should run it if any CI runners are self-hosted/persistent, or as a periodic dev-machine `just` task. |
| GitHub Actions cache size limits (2026) | As of **Nov 20, 2025**, GH Actions cache can now exceed the old flat 10 GB/repo cap via a pay-as-you-go model; every repo still gets 10 GB free. A **Jan 16, 2026** change added a **200 uploads/minute** rate limit per repo (uploads only, not downloads) — relevant if many parallel CI jobs each try to write large `target/`-derived caches simultaneously. [GH Changelog Nov 2025](https://github.blog/changelog/2025-11-20-github-actions-cache-size-can-now-exceed-10-gb-per-repository/), [GH Changelog Jan 2026](https://github.blog/changelog/2026-01-16-rate-limiting-for-actions-cache-entries/) | With 315+74 binaries this workspace's naive "cache all of target/" strategy will blow past 10 GB free tier fast (your own figure: 13-20 GB just for target/debug). The rate limit also means fan-out matrix jobs that all try to upload a cache at job end can throttle each other. | **Yes, act on this** — (a) either pay for cache beyond 10 GB, or (b) cache only the sccache object cache + the registry/git dependency cache (small, high hit-rate) and rely on `nextest archive` to distribute build output within a single CI run instead of caching the whole `target/` across runs, and (c) reduce the number of jobs that upload caches concurrently to stay under the 200/min upload rate limit. |

## Ordered recommendation list (highest leverage first)

1. **Consolidate the 315 integration-test files into far fewer test binaries** (matklad's `tests/it/main.rs` + submodules pattern, one per crate or per logical suite instead of per file). This is a pure code-organization change, needs no new Cargo/rustc feature, and is the single biggest lever for both link time and target-dir size given your numbers — expect roughly 3-5× on test-suite compile time and artifact size, mirroring the measured rust-analyzer/cargo result. Do the same for the 74 examples where multiple examples share near-identical setup code (merge into fewer `examples/*.rs` files or move shared setup into a dev-dependency helper crate) if they don't need to stay separate for documentation/discoverability reasons.
2. **Adopt `build.build-dir` (stable since Cargo 1.91)** to physically separate intermediate build artifacts (which is what balloons to 13-20 GB) from final artifacts, and point it at fast ephemeral/local storage on CI runners and dev machines, while caching only the final-artifacts path (or nothing at all if using nextest archive — see #3).
3. **Switch CI to `cargo nextest archive` + `cargo nextest run --archive-file` with partitioning**, so the whole 28-crate workspace is built once per CI run and fanned out to N test-execution shards, instead of rebuilding per shard. Measure archive size with `cargo nextest run --no-run` before/after step 1 to quantify the win.
4. **Add `split-debuginfo = "unpacked"` explicitly for Linux CI** under `[profile.dev]`/`[profile.test]` (macOS already defaults to it); keep the existing `debug = "line-tables-only"` — do not drop to `debug = "none"` given reliance on nextest failure diagnostics across many test files.
5. **Confirm rust-lld is active on Linux CI runners** (default since 1.90, should be automatic) and, if link time is still a bottleneck after #1-#3, evaluate `wild` on Linux-only self-hosted runners once its macOS story matures (not yet, as of Sept 2026).
6. **Wrap CI/dev builds with `sccache`**, targeting its own cache directory at the persistent GH Actions cache (small, high-hit-rate: compiled objects for unchanged deps), separately from whatever nextest-archive/build-dir handles for the actual test/link output — and budget for GH Actions' 2025-11 pay-as-you-go cache tier or trim what's cached, given the 10 GB free-tier default and the Jan 2026 200-upload/minute rate limit on concurrent job caches.
7. **Track, but do not adopt yet on stable CI:** `hint-mostly-unused` (nightly-only, promising for windows-sys-sized transitive deps wgpu pulls in — pilot on a nightly-only side job), the 2026 parallel-frontend (`-Zthreads`) stabilization goal, and `-Zno-embed-metadata`'s nightly default-on experiment. Re-run this analysis when any of these lands on a stable release ≥1.98, or when MSRV policy allows dropping to a newer floor.
8. **Do not pursue:** `-Zshare-generics` (unstable, doesn't fit the per-binary-integration-test architecture without a bigger dylib-sharing redesign), `panic = "abort"` for `[profile.test]` (Cargo ignores it; no stable path), `cranelift` codegen backend (nightly-only and not installable via rustup on your macOS aarch64 dev machines).
