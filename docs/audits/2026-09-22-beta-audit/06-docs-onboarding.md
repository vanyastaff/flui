# FLUI Documentation & Onboarding Audit

Date: 2026-09-22. Read-only audit of the FLUI repo (main, commit fbed9408) as a newcomer (both prospective app author and prospective contributor) would experience it.

---

## 1. User docs (README, getting-started, llms.txt, examples)

**What exists:**
- `README.md` (11.3K) — status badges (CI, license, MSRV), a one-paragraph pitch, a "Status" table of crates by layer, a Quick Start (`cargo build --workspace`, `cargo run --example widgets_gallery`), a "Choosing a catalog" feature-flag guide with a full `widgets_gallery.rs` excerpt (Material/Cupertino selection, hello-world-shaped code).
- `docs/getting-started.md` (4.6K) — genuinely good: prerequisites table (Rust 1.97, cargo-ndk, wasm-pack), clone/build, a table of *all* bundled examples with commands and one-line purpose, WASM and Android instructions, a toolchain-verification recipe, a symptom→cause troubleshooting table (`error: package 'flui-X' not found` → disabled workspace member, etc.), and a `RUST_LOG` logging section.
- `llms.txt` (3.9K) — an LLM-oriented sitemap: links to README/getting-started/architecture/FOUNDATIONS/crates/testing/hot-reload, a full "Writing a view" code sample (the same Gallery example as the README), a one-paragraph explanation of Stateless/Stateful/InheritedView, and a "For contributors and agents" section pointing to AGENTS.md/PORT.md/ROADMAP.md/PANIC-POLICY.md/contributing.md. This is unusually complete for an `llms.txt` — better curated than the human-facing docs in places.
- `examples/README.md` — thin and stale: only documents `windows11_demo`, `hello_world`, `window_features`. It does **not** mention `widgets_gallery`, `material_demo`, `cupertino_demo`, `sliver_demo`, `hot_reload_counter`, `vertical_slice_demo`, `web_demo`, `web_counter` (untracked, new), `android_*`, or a dozen others that exist in `examples/`. A newcomer scanning this file gets a badly incomplete picture of what's runnable.
- 35+ example binaries/crates exist (`examples/`), including `hot_reload_counter`, `widgets_gallery`, `material_demo`, `cupertino_demo`, `sliver_demo`, `vertical_slice_demo`, `web_demo`/`web_counter`, several Windows/Android/iOS demos. No index page ties them to a learning path — they read as internal smoke-test fixtures more than a curated "learn by example" gallery (no per-example screenshot, no difficulty/topic tagging beyond the one stale README).

**What is missing versus flutter.dev / iced book / egui docs / Dioxus / Slint:**
- **No step-by-step tutorial** ("build a counter app", "build a todo app") anywhere. `widgets_gallery.rs` is the closest thing to a "first app," but it is presented as a feature showcase, not walked through concept-by-concept (no explanation of why `StatelessView`, why `IntoView`, what `BuildContext` capability-scoping means, incrementally).
- **No cookbook** ("how do I do X" task-oriented recipes: navigation, forms, async data fetch, animations, theming) — Flutter, Dioxus, and the iced book all have this; FLUI has none. `rg` for "cookbook" across docs/README returns nothing.
- **No widget catalog reference with screenshots.** `flui-widgets` and `flui-material` clearly implement a large widget set (Scaffold, Drawer, DataTable, Navigator, PageView, etc. — confirmed via source), but there is no rendered/visual catalog page. Flutter's widget catalog (with live screenshots per widget) has no analog here. `find`/`rg` for `.png`/`.gif` outside `platforms/web/favicon.png` returns nothing — the repo contains **zero screenshots or GIFs** of the framework running.
- **No Flutter→FLUI migration/concept-mapping guide for app authors.** The conceptual mapping (StatefulWidget→?, BuildContext→?, setState→?) exists, but only *inside* internal engineering documents (`docs/PORT.md`, `docs/FOUNDATIONS.md`, `docs/ROADMAP.md`) aimed at contributors doing the Flutter port/verification work — phrased as "mapping decisions" and "refusal triggers," not as a "coming from Flutter? here's how FLUI differs" page for a framework *user*. A Flutter developer evaluating FLUI has no dedicated on-ramp.
- **No API guide/book** beyond rustdoc itself (see §2) — no mdBook, no docs site (see §5).

## 2. Rustdoc quality

- **`#![warn(missing_docs)]` / `#![deny(missing_docs)]`**: present in 25 of the crate `lib.rs` files (`rg -l missing_docs crates/*/src/lib.rs` → 25 hits), including `flui-widgets` and `flui-material` at `#![deny(missing_docs)]`. This is enforced at compile time, which is the strongest possible guarantee — undocumented `pub` items simply do not build. Crates *not* in that list (`flui-app`? — actually included; check shows only ~25 of ~28 crates gated — a few, e.g. facade-adjacent or newer crates, may lack the lint) should be spot-checked before beta, but the bulk of the surface is covered.
- **Sampled coverage** (flui-widgets: `navigator.rs`, `focus.rs`, `page_view.rs`; flui-material: `data_table.rs`, `drawer.rs`, `theme_data.rs`): initial grep undercounted because doc comments sit above `#[derive(...)]` attributes rather than immediately above `pub struct`/`pub fn`; manual inspection confirmed structs and fields *are* documented in practice (e.g. `theme_data.rs` — every `pub struct *ThemeData` carries a multi-line `///` block referencing the Flutter oracle tag it mirrors). Combined with `deny(missing_docs)`, actual coverage is effectively 100% of the compiled public surface — the compiler will not allow otherwise.
- **Facade crate-level docs** (`src/lib.rs`, the `flui` crate): excellent. Opens with a `//!` block explaining FLUI is a facade over the workspace, gives a complete "Quick start" doc-example (`StatelessView` + `run_app`), then a feature-flag table (`material`/`cupertino`/`localizations`/`hot-reload`) explaining what each does and the "absent, not empty" behavior of disabled features. This single doc block teaches the mental model better than the README does.
- **Doc-tests**: 154 fenced code blocks (```` ``` ````) found across crate `lib.rs` files via `rg -c` sum — a real number of doctests exist and presumably run under `cargo test --doc` (part of `just ci`). `run_app`/`run_app_android`/`run_app_ios` each carry runnable doc examples. Did not find a doc-test directly on `View`/`State`/`Element`/`Navigator` trait definitions in the sampled files (the navigator's 50 `pub` items are documented with prose but the sampled grep found no fenced code block in `navigator.rs` itself) — worth a targeted check before beta, since Navigator is a top-3 API newcomers will reach for.
- **No visible rustdoc "book" glue** (no `#![doc = include_str!(...)]` root architecture diagram, no rendered rustdoc hosted anywhere — see §5 for hosting).

## 3. Contributor docs

- **`CONTRIBUTING.md`** (648 bytes) — intentionally a stub/pointer: says "run `just ci`" and links to `docs/contributing.md`. Reasonable pattern (short root pointer, full doc elsewhere), not a red flag by itself.
- **`docs/contributing.md`** (7.8K) — substantial and well-organized: required-reading order (FOUNDATIONS → ROADMAP → PORT → AGENTS.md → architecture/crates.md), the `just ci` gate contents, a "Planning a Large Change" template (Problem/Alternatives/Contract/Reference check/Plan), Conventional Commits with examples, git hygiene rules, code-style pointers, the 6-point "ready for review" checklist, and a "Reporting Bugs" section demanding a *failing test* as the reproduction. This is a strong, opinionated contributor doc — arguably better than most OSS projects' CONTRIBUTING files. One drawback: it *requires* reading four other large documents (FOUNDATIONS.md 40K, ROADMAP.md 118K, PORT.md 135K, AGENTS.md 14.6K) before a first PR — a very high entry bar for a casual "good first issue" contributor (see §7).
- **`AGENTS.md`** (14.6K) — explicitly AI-agent-oriented ("Compact guide for AI agents working in the FLUI repository") but written in full prose with human-readable rationale, not YAML/config-speak; it doubles as a dense architecture/rules primer (three prime-directive rules, code navigation, tech stack, build/CI commands, Definition of Done). It is usable by a human contributor but reads as "agent-first, human-tolerant" rather than the reverse — a human onboarding would likely find `docs/contributing.md` more approachable and AGENTS.md secondary/reference material.
- **`CODE_OF_CONDUCT.md`** (1.1K) — present, short, reasonable ("be direct, technical, and respectful"), enforcement via GitHub moderation — adequate for project size.
- **`SECURITY.md`** (987B) — present, references GitHub private vulnerability reporting, lists security-sensitive areas (platform backends, hot reload/dylib loading, asset/network loading, GPU resources, unsafe, build tooling). Adequate.
- **Issue templates**: `.github/ISSUE_TEMPLATE/{bug_report.yml, feature_request.yml, architecture_change.yml, config.yml}` — present and reasonably scoped (an `architecture_change.yml` template is an unusual and good addition for a project with a strict layered DAG).
- **PR template**: `.github/PULL_REQUEST_TEMPLATE.md` present.
- **Labels**: rich label set exists (`bug`, `documentation`, `enhancement`, `good first issue`, `help wanted`, priority tiers, `area:*`, `tech-debt`, `refactoring`, `clean-code`, `testing`, etc.) — infrastructure for triage is in place.
- **"Good first issue" count: 0.** `gh issue list --label "good first issue" --state all` returned no results at all (open or closed) — despite the label existing, it has apparently never been applied. For a project explicitly wanting outside contributors, this is a concrete, fixable gap: the label exists but is unused, so a newcomer browsing issues for an entry point finds nothing tagged as approachable.
- **No Discussions/Discord/community-chat link** found in README, CONTRIBUTING, or docs/ — no evidence of a real-time community channel.

## 4. Design docs

- **ADRs**: 73 numbered ADRs in `docs/adr/` (ADR-0001 through ADR-0073), last 15 titles span deep engine/platform topics (text shaping, damage tracking, paint queue, renderer surface ownership, animation completion futures, display-list command representation, glyph atlas, frame disposition, keyboard events, iOS/macOS AppKit/UIKit binding via objc2, presentation/native execution, UIKit scene ownership). These read as current and substantive, not placeholder ADRs — titles map directly to recent commit activity (macOS/iOS backend work visible in git log).
- **`docs/FOUNDATIONS.md`** (40K) — the architecture "constitution": explicitly frames itself as forward-looking (target architecture, not current-state description), with an explicit non-circular reading order (Port Methodology → Foundations → Roadmap) and a stated benchmark ("released Flutter... defines the minimum observable behavior, not the ceiling"). Well-written and self-aware about its own role, but very large for a "read before your first PR" requirement.
- **`docs/PORT.md`** (135K), **`docs/ROADMAP.md`** (118K), **`docs/ROADMAP-TRACKER.md`** (148K — largest doc in the repo), **`docs/BETA.md`** (77K), **`docs/runtime-contract.toml`** (270K) — these are enormous. Spot-checked dating: `docs/PORT.md` contains dated inline annotations (e.g. "Registry addition (2026-09-14, ADR-0063)", "current stable: 1.98.1, released 2026-09-01", a per-crate `ARCHITECTURE.md` status table with entries like "rewritten as a current-state document 2026-09-18") — these are current (within days of the audit date, 2026-09-22) and internally consistent with recent commit activity, not stale artifacts. This project appears to actively maintain these docs rather than let them rot, which is unusual given their size.
- **Assessment**: these are not obviously "accretion that should be archived" in the sense of being abandoned — they show live editing dated to the last few days. But their *sheer size* (PORT.md 135K + ROADMAP.md 118K + ROADMAP-TRACKER.md 148K + runtime-contract.toml 270K ≈ **670K of prose/data a contributor is nominally asked to read** before a "large change") is a genuine onboarding cost regardless of freshness. This is architecture/process documentation for an internal engineering methodology (the Flutter-port verification discipline), not documentation aimed at a framework *user* — the two audiences are conflated under `docs/`, and a newcomer cannot tell from the directory listing which docs are "read this to use FLUI" vs. "read this to contribute to the port methodology."

## 5. Website / hosting

- **No mdBook** (`find` for `book*` dirs turned up nothing besides an unrelated `platforms/web/favicon.png`), no `book.toml`.
- **No GitHub Pages workflow** — `.github/workflows/` contains `ci.yml`, `weekly.yml`, `coderabbit-trigger.yml`, `dependabot.yml`; none reference `pages` or `mdbook`.
- **No docs.rs configuration** found (crate is unpublished/pre-crates.io anyway, per README/SECURITY.md, so this is expected for now, not a defect).
- **No landing page** beyond `README.md` on GitHub.
- **Zero screenshots or GIFs in the repo** (`find . -iname "*.png" -o -iname "*.gif"` outside `target/`/`node_modules/` returns only `platforms/web/favicon.png`) — for a GPU-rendered UI framework with a working `widgets_gallery` example, this is a significant missed opportunity: there is no visual proof anywhere in the repo (or evidently on GitHub) of what a running FLUI app looks like.

## 6. Public-facing identity

- **Cargo.toml metadata**: `[workspace.package]` sets `version = "0.2.0"`, `edition = "2024"`, `rust-version = "1.97"`, `license = "MIT OR Apache-2.0"`, `authors = ["Flui Contributors"]`, `repository`. Individual crates carry good `description` fields (e.g. flui-widgets: "User-facing Flutter-style widget catalog for FLUI..."; flui-material: "Material Design theming foundation for FLUI — ColorScheme, Typography/TextTheme, ThemeData..."), and several carry `keywords`/`categories` (`["ui","widget","flutter","flui","gui"]`, `categories = ["gui", "rendering::engine"]` on flui-engine). This metadata is currently inert (nothing is published to crates.io) but is in good shape for when publishing happens.
- **Badges**: README has CI status, license, and MSRV badges — no crates.io/docs.rs badges yet (correctly, since unpublished), no Discord/coverage badges.
- **No logo** found anywhere in the repo.

## 7. Newcomer 30-minute journey (narrative)

**Minute 0–5 (app-author path):** Land on `README.md`. Get a clear pitch, an honest "pre-release, build from source" caveat, a crate-status table, and a working `cargo build --workspace && cargo run --example widgets_gallery` quick start. This part works well — a newcomer can get a window on screen in under 5 minutes if the build succeeds.

**Minute 5–15:** Curious what else exists, they open `examples/README.md` expecting an index — and find only 3 of 35+ examples documented, none of which is `widgets_gallery` (the one README told them to run) or `hot_reload_counter`/`material_demo`. They now don't know which examples are "supported demos" vs. internal test fixtures, and there are no screenshots to skim instead of running each one. They likely `cargo run --example` a few things at random.

**Minute 15–25:** Wanting to actually build something (say, a counter or a form), they look for a tutorial or cookbook. There isn't one. They fall back to reading the `widgets_gallery.rs` source and the facade crate's rustdoc (`//!` in `src/lib.rs`), which is genuinely good and explains `StatelessView`/`StatefulView`/`InheritedView`/feature flags reasonably well — but it's reference material, not a guided walkthrough, so they have to reverse-engineer "how do I add local state" or "how do I navigate between screens" by grepping `flui-widgets` source (e.g. `navigator.rs`) rather than reading a doc page. A newcomer coming from Flutter has no page translating `setState`/`BuildContext`/`StatefulWidget` into FLUI terms — that mapping exists in `docs/PORT.md`, but that document is written as an internal port-verification methodology, not discoverable or readable as a user migration guide, and at 135K is not something a 30-minute evaluator will open.

**Minute 25–30:** If instead evaluating as a potential contributor, they hit `CONTRIBUTING.md` → `docs/contributing.md`, which explicitly asks them to read FOUNDATIONS.md (40K) + ROADMAP.md (118K) + PORT.md (135K) + AGENTS.md (14.6K) before a first PR. They check the issue tracker for a "good first issue" and find the label exists but has zero issues tagged with it, open or closed. They likely bounce at this point unless highly motivated — the on-ramp for a first-time human contributor is currently steep, even though the CI/tooling/architecture discipline behind it is excellent.

**Unanswered questions a newcomer accumulates:** What does a running FLUI app actually look like (no screenshots)? Which examples are worth running? How do I do routing/forms/async/theming beyond the one gallery example? Coming from Flutter, what's my `setState` equivalent, concretely, in one page? Is there a chat/Discord if I get stuck? Is there an easy issue to start with?

## Top 10 docs/onboarding deliverables needed for beta (ranked)

1. **Add real screenshots/GIFs of running examples** to README and a new examples index — zero currently exist in the repo; this is the single highest-leverage, lowest-effort fix (capture `widgets_gallery`, `material_demo`, `cupertino_demo`, `hot_reload_counter` running).
2. **Write a "Build your first app" tutorial** (counter, then a small todo/form app) as a dedicated `docs/tutorial.md`, walking `StatelessView`/`StatefulView`/`BuildContext`/local state/navigation incrementally — the single biggest structural gap vs. Flutter/iced/egui/Dioxus.
3. **Rewrite `examples/README.md`** to index all 35+ examples (not 3), tagged by topic/platform/difficulty, matching what `docs/getting-started.md`'s table already does better.
4. **Write a Flutter→FLUI concept-mapping page for app authors** (StatefulWidget→StatefulView+ViewState, BuildContext→capability-scoped BuildContext, setState→typed state cell/local state API, Navigator, Key), extracted and reframed from the internal PORT.md mapping content into user-facing language.
5. **Add a widget catalog reference** (even a generated one) with per-widget rendered screenshots for `flui-widgets`/`flui-material`/`flui-cupertino`, analogous to Flutter's widget catalog.
6. **Start a cookbook** covering the top ~10 "how do I" tasks (navigation, forms/input, async data, theming, animations, hot reload workflow).
7. **Populate the "good first issue" label** — it exists with zero issues tagged, open or closed; triage 5–10 real, scoped issues for external first-timers before advertising for contributors.
8. **Split "read before contributing" into a tiered path**: a short (~1 page) fast-start for trivial PRs (docs, tests, small bug fixes) versus the full FOUNDATIONS/ROADMAP/PORT/AGENTS.md stack currently required uniformly for any change.
9. **Stand up a minimal docs site** (mdBook or GitHub Pages from rustdoc) once/if the crate nears publishing — currently there is no hosted documentation surface at all, only in-repo Markdown.
10. **Add a community channel link** (Discord/Discussions) to README/CONTRIBUTING — none currently exists, so a stuck newcomer has no synchronous escape hatch beyond opening a GitHub issue.

**Not broken / worth preserving:** the enforced `#![deny(missing_docs)]` discipline in ~25 crates, the facade crate's `//!` teaching doc, `docs/getting-started.md`'s troubleshooting table, `llms.txt`'s curation, the actively-maintained (dated, cross-referenced) ADR/PORT/ROADMAP corpus, and the issue/PR template + label infrastructure — these are stronger than most pre-1.0 Rust projects and should not be disrupted while fixing the gaps above.
