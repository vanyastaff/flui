# Платформенный слой — требования (уровень 1)

- **Статус:** черновик, редакция 2 (после ревью), ждёт владельца
- **Ограниченное утверждение:** R3 исполняется по
  [ADR-0172](../../../adr/ADR-0172-host-owned-system-preferences.md), остальные
  разделы сохраняют статус черновика. Реализация R3 ещё не завершена.
- **Дата:** 2026-10-06
- **База:** `main` @ `d56188c14`
- **Уровень 0:** [../release/requirements.md](../release/requirements.md) (D1: `flui` 0.2.0 на
  crates.io 2026-12-31; R2: публикуются все крейты, нужные `flui`)
- **Смежные спеки:** [send-flip](../send-flip/), [text-ime](../text-ime/),
  [persistence](../persistence/), [teardown](../teardown/), [focus-keyboard](../focus-keyboard/),
  [naming](../naming/); на ветках: flui-animation reduce-motion, flui-interaction matrix (X1, X2)
- **Горизонт:** 1.0. Требования помечены релизом, к которому они верны: **0.2** — к первой
  публикации, **0.3** — до первого крейта возможности, **1.0** — к стабилизации.

Спека задаёт, что должно быть верно про платформенный слой: какие крейты, что в каждом, кто за
что отвечает, и как к 1.0 в него входят необязательные возможности ОС, не наращивая долг с
каждым релизом. Как — [design.md](design.md); порядок — [tasks.md](tasks.md); cross-crate
решения — ADR-0151…0154.

## Зачем

Платформенный слой вырос по частям, и его границы больше не говорят, что где лежит:

- контрактный крейт `flui-platform-api` (Stable; фасад реэкспортирует его целиком как
  `flui::platform`) держит рядом со словарём ~2 000 строк реализации и политики text store,
  тестовые двойники, backend-таблицы, haptics без реального бэкенда и элементы без потребителя
  выше бэкенда; его сигнатуры называют типы `ui-events` (а через них `keyboard-types`, `dpi`),
  что запрещает ADR-0089 (Proposed; ADR-0151 принимает его правило для контракта);
- версия контракта сейчас идёт с поездом, а крейт возможности со своей версией ломается при
  каждой несовместимой смене версии контракта (опыты ADR-0153: конфликт `links = "flui_train"`
  или два разных трейта окна); как развязать — вопрос к 0.3;
- бэкенд `flui-platform` держит словарь без потребителя выше себя, заглушку `LinuxPlatform`,
  наследный `window.rs`, публичные OS-типы и модули `shared`/`traits`, запрещённые спекой naming;
- системные настройки не имеют производителя: `AccessibilityFeatures` никто не пишет и не
  читает, `text_scale_factor` всегда 1.0, локаль системы не доставляется, `GestureSettings` —
  константы; две работы планировали ещё два отдельных производителя;
- новая возможность доходит до виджета правкой flui-runtime, flui-view и flui-app; пакет добавить
  её не может; ADR-0084 (открытый шов) — 0 строк кода;
- любой сервис ОС (геолокация, сенсоры, камера, уведомления…) сейчас может жить только в
  бэкенде ядра — путь к монолиту, который выходит вместе с поездом;
- имя `flui-platform-api` — из трёх частей, вопреки правилу владельца `flui-<слово>`.

После публикации каждое из этого — breaking change или долг, растущий с каждым релизом.

## Пользовательские сценарии

**Автор приложения** (зависит от `flui`):

1. пишет `flui::platform::…` и видит только словарь и трейты без OS-типов и чужих крейтов;
2. получает системную настройку (масштаб текста, контраст, «меньше движения», локаль, тайминги
   жестов) значением из окружения виджета, до первого окна и после каждого изменения в ОС;
   переопределяет её политикой приложения («всегда/никогда/как в системе»);
3. на платформе без возможности получает значение `Unsupported` с причиной — не панику, не
   `Ok(None)`, похожий на отмену, не выдуманные данные;
4. добавляет сервис ОС одним крейтом возможности; компилирует и объявляет разрешения только для
   тех, что использует; манифесты ОС не правит руками;
5. тестирует всё это в headless с подменой провайдера и скриптом ответов пользователя.

**Автор пакета или крейта возможности:** объявляет возможность и регистрирует её у приложения, не
меняя фреймворк; держит свой OS-код у себя; выпускает свой крейт по своему графику, и крейт
совместим с любым FLUI той же мажорной версии контракта.

**Контрибьютор FLUI:** по имени крейта видит, где контракт, где OS-код ядра, где необязательная
возможность; знает закрытый список того, что ядро делает с ОС само.

### R3. Системные настройки (решение Q2)

| ID | Релиз | Требование | Проверка |
|---|---|---|---|
| R3.1 | 0.2 | `SystemPreferences` в контракте — единая принятая модель системных настроек; один производитель и один принадлежащий хосту набор native-подписок, независимый от пользовательских окон | native lifetime; headless: одна принятая смена достигает каждого живого потребителя без дублирования источников |
| R3.2 | 0.2 | Значение есть в realm до первого окна | тест: realm без окна читает настройки |
| R3.3 | 0.2 | Потребители не используют `SystemPreferences` в своей логике напрямую: interaction строит `GestureSettings`, анимации — политику движения, `MediaQuery` — то, что видит виджет | ревью; тест на каждого потребителя, падающий без доставки |
| R3.4 | 0.2 | Политика приложения поверх ОС («как в системе / всегда / никогда» для reduce motion) — во фреймворке (realm), не в контракте | ревью |
| R3.5 | 0.2 | Типы: `Motion` с `Scaled(DurationScale)`, где `DurationScale` — конечное s > 0, а масштаб ОС отображается одним `Motion::from_duration_scale`: 0 и −0.0 → `Reduce`, ровно 1 → `NoPreference`, иное конечное > 0 (субнормальные тоже) → `Scaled`, отрицательное и неконечное → `InvalidPreference::DurationScale` (на эту таблицу ссылается R8 спеки flui-animation reduce-motion); жесты с прямоугольниками double-click и drag в логических `Size` (ADR-0098), touch slop (`Distance`) и диапазоном скоростей fling (`FlingSpeeds`, min ≤ max, логические px/с); колесо — отдельная группа (`WheelStep::Lines(n)` или `Page`, символы на горизонтальный шаг); каждое поле жестов и колеса — `Option`, `None` где у ОС нет значения; приватные поля и builder; некорректное значение — `InvalidPreference`, не паника | компиляция (E0639 на литерале), тесты валидации |
| R3.6 | 0.2 | Смена настройки в ОС перестраивает виджет, читающий её, и меняет поведение распознавателя | тест headless, падающий без доставки |
| R3.7 | 0.2 | Принятый snapshot и delivery debt различаются; commit до callback/wake; отсутствие/замена/panic hook и competing failures не теряют принятый хвост | одна ошибка, две конкурирующие и следующее здоровое обновление через public host path |
| R3.8 | 0.2 | Начальный seed, два runtime, поздние runtime/presentation; отказ или закрытие sibling не прекращает fanout; старый revision не откатывает новый seed | headless frame/consumer proof; отдельный откат доставки |
| R3.9 | 0.2 | FIFO сохраняет input/frame barriers; coalescing касается только соседних совместимых принятых снимков; native invalidation не выдаётся за атомарный снимок ОС | порядок через реальные consumers; invalidation во время sampling |
| R3.10 | 0.2 | Native mouse-геометрия сохраняет свои единицы до проекции для конкретного presentation/DPI; ширина rectangle и допустимое смещение различаются; wheel preference применяется один раз | границы rectangle, разные DPI, disabled/page/line и pixel-based input |
| R3.11 | 0.2 | Изменение gesture settings имеет явную политику для активной последовательности; используется существующий GestureArenaScope, authored override сохраняется | callbacks текущей/следующей последовательности и live dependency update |
| R3.12 | 0.2 | Политика размеров текста сохраняет authored styles, описывает разные размеры и native mapping; layout, intrinsics, hit testing и editable caret согласованы при live update | реальные текстовые потребители; scoped override; возврат настройки; revert proof |

Уточнение R3.5 по ADR-0172: logical `Size` описывает результат проекции для
потребителя. Native-источник не получает право объявить пиксели одного монитора
host-global logical геометрией. Сигнатуры эскиза §6 design.md уточняются при
реализации; этот текст не утверждает представление нелинейного font sizing.

## Вне объёма

- Сами крейты возможностей (геолокация, сенсоры, камера, уведомления, защищённое хранилище,
  биометрия, share, файловые диалоги, трей/меню) — отдельная спека после 0.2; здесь — только
  что им должен дать слой (R6) и правила класса (ADR-0154).
- Перенос `PlatformAccessibility` из `flui-semantics`: требует своего словаря дерева доступности
  (ADR-0089 §3).
- Свой словарь указателя и клавиатуры: ведёт работа interaction pointer-vocabulary; R1.5 ждёт её.
- Снятие `+ Send` с колбэков окна (ADR-0082 §4 шаг 2): send-flip / text-ime.

## Критерии готовности

- **0.2:** design.md, ADR-0151…0154 утверждены; R1.1–R1.4, R1.7, R1.8, R2, R3, R5 закрыты;
  R4 — закрыт или целиком перенесён в 0.3 по правилу R4.10; гейты зелёные на каждом PR;
  PR честно говорит, что запускалось, а что только компилировалось.
- **0.3:** R1.6, R1.9, R1.10, R6 закрыты первым крейтом возможности.
- **1.0:** R1.5 закрыт; каждая заявленная ОС исполняется в CI; каждая официальная возможность
  проходит свою conformance-таблицу на каждой заявленной ОС.
