# Три стиля описания виджетов — требования (уровень 1)

- **Статус:** черновик
- **Дата:** 2026-10-05
- **База:** `main` @ `4915054c8`
- **Уровень 0:** [../release/requirements.md](../release/requirements.md) R18; там же D3 (`!Send`
  до 0.2.0) и D5 (решения 0.2.0 не закрывают параллельный кадр)
- **Связанные:** [../send-flip/requirements.md](../send-flip/requirements.md) (event-callback
  `Fn(&mut EventCx<'_>) -> R`, `!Send`-захваты); `docs/FOUNDATIONS.md` C2, C3; ADR-0086, ADR-0088.

## Зачем

Описание дерева — самая частая поверхность (FOUNDATIONS C3: метрика принятия). Сегодня есть
только `new()` с setter'ами, а макрос собирает лишь кортеж детей. Форма фиксируется до 0.2.0:
после публикации каждое её изменение ломает пользователей.

## Пользовательский сценарий
Разработчик пишет экран «счётчик заметок» и выбирает стиль по вкусу; ревьюер читает любой.
Ниже — желаемый опыт, **не дизайн**: синтаксис макроса, разделитель свойств и детей, наличие
`.build()` и `..Default::default()` решают design.md и ADR.

```rust
// Макрос
column! { main_axis_alignment: MainAxisAlignment::Center;
    Text::new(format!("Заметок: {}", count.get())),
    padding! { padding: EdgeInsets::all(8.0);
        button! { on_pressed: move |cx: &mut EventCx<'_>| count.update(cx, |n| *n += 1);
            Text::new("Добавить") } },
}
// Struct-литерал
Column { main_axis_alignment: MainAxisAlignment::Center, children: (
    Text { data: format!("Заметок: {}", count.get()), ..Default::default() },
    Padding { padding: EdgeInsets::all(8.0), child: Button {
        on_pressed: callback(move |cx| count.update(cx, |n| *n += 1)),
        child: Text::new("Добавить"), ..Default::default() } },
), ..Default::default() }
// Builder (сегодняшняя форма)
Column::new((
    Text::new(format!("Заметок: {}", count.get())),
    Padding::new(EdgeInsets::all(8.0)).child(
        Button::new().on_pressed(move |cx| count.update(cx, |n| *n += 1)).child(Text::new("Добавить"))),
)).main_axis_alignment(MainAxisAlignment::Center)
```

Все три дают одно дерево и одни semantics; `count: Signal<u32>` (`!Send`) захвачен без обёрток.

## Текущее состояние

**Каталог (подсчёт `rg` по `impl … View for`, `impl_*_view!` и derive `StatelessView`/
`StatefulView`, затем `pub struct`).** Публичных виджет-типов **179**: `flui-widgets` 130 (ещё 24
непубличных), `flui-material` 42 (+2), `flui-cupertino` 7; facade (`src/`) своих виджетов не
имеет. **Ни у одного нет `pub` полей** — struct-литерал вне крейта сегодня невозможен ни для
одного виджета. У каждого публичного типа есть `new` в том же файле; `new` бывает без
аргументов (`Center::new()`, `crates/flui-widgets/src/layout/center.rs:20`; `GestureDetector`,
`interaction/gesture_detector.rs:231`) и с обязательными позиционными (`Text::new(data)`,
`text/text.rs:35`; `Padding::new(padding)`, `layout/padding.rs:28`; `SizedBox::new(w, h)`,
`layout/sized_box.rs:23`). Setter'ы — `fn x(mut self, …) -> Self` (410 в `flui-widgets`), без
`.build()`. Один ребёнок: поле `Child` (61 виджет; `crates/flui-view/src/child/child.rs:33`,
`Option<BoxedView>` внутри) или `BoxedView` (37), задаётся `.child(impl IntoView)` и обычно
необязателен. Много детей: generic `C: ViewSeq` у `Column`, `Row`, `Flex`, `ListBody`, `Stack`
(`flex/flex.rs:246`: приватные `style: FlexStyle, children: C`, `Column::new(children)`;
`stack/stack.rs:23`), `Vec<BoxedView>` по умолчанию; builder-функции у `ListView` и др.
Generic-виджетов 11 (10 + 1 в material). Поля-callback'и — у 23 виджетов `flui-widgets` и 21
material; event-setter в форме `F: Fn(&mut EventCx<'_>) -> R + 'static, R: EventOutcome`
(`gesture_detector.rs:238`, `packages/flui-material/src/chip.rs:424`).

**Макросы.** `column!`/`row!` (`crates/flui-view/src/macros/mod.rs:42`, `:159`) строят только
кортеж детей для `ViewSeq` (кортежи арности `0..=16`, `seq/tuple_impls.rs:63`; `Vec<V>` —
`seq/vec_impls.rs:20`); на 17+ — `compile_error!` с советом `vec![child.boxed(), …]` (`:138-149`),
закреплено trybuild-фикстурой `crates/flui-view/tests/ui/column_17_compile_error.rs`.
Документация модуля показывает `Column { children: column![…] }` (`macros/mod.rs:10-12`, `:32`,
`:156`) — это не компилируется (поля приватны) и стоит в блоке `text`, поэтому doctest его не
ловит. Там же id задачи спеки `FR-034` (`:23`, `:138`, `:255`) и голое `C2` (`:1`, контракт
FOUNDATIONS без ссылки); `cargo xtask markers` их не ловит. `flui-macros` даёт derive `StatelessView`, `StatefulView`,
`InheritedData`, `Diagnosticable`, `Animatable`, `Routable` (`crates/flui-macros/src/lib.rs:110-324`)
— генерации builder/литерала нет. `flui-sdk` не реэкспортирует `column!`/`row!` отдельно
(доступны через `widgets`). Вывод типа closure: closure, связанное через `let`, не получает
сигнатуру `cx` (фикстура `tests/ui/let_bound_event_closure_without_helper.rs`), нужен
`callback(…)`; inline-closure в setter выводится.

**Места вызова.** Notes (`examples/two_screens/tree.rs`) пишет `Column::new(column![…])`
(`:191`, `:249`, `:269`, `:353`); так же book (`book/src/widgets/catalog.md:43`). Всего `column![`/
`row![` — 49 вхождений в `.rs`. `docs/FOUNDATIONS.md:103` и `crates/flui-widgets/src/lib.rs:32`
говорят о `bon`-builder'ах, но `bon` нет ни в одном манифесте — документ расходится с кодом.

### Предыдущая реализация (до переписывания)

В старом крейте `crates/flui_widgets` (удалён в `16ca09544`, 2026-02-08) все три стиля уже были.
`git show 4a204b489:crates/flui_widgets/src/layout/column.rs`:

- `:8-32` — документированы три стиля: литерал `Column { …, children: vec![…], ..Default::default() }`,
  `Column::builder()…children(vec![…]).build()`, макрос `column! { поле: значение, … }`;
- `:66-104` — `#[derive(bon::Builder)]` на структуре со **всеми `pub` полями**; умолчания одним
  местом через `#[builder(default = …)]`, `on(T, into)` для конверсий; `impl Default` (`:242`);
- `:78-79`, `:118-129` — сгенерированный setter детей скрыт (`children_internal`), вместо него
  ручное расширение `impl<S: State> ColumnBuilder<S> where S::Children: IsUnset`;
- `:131-145` — `build()` переопределён ради `validate()`, ошибка лишь `tracing::warn!` в debug;
- `:262-290` — `column![a, b]` и `column! { поля ; [дети] }` раскрываются в builder, каждый
  ребёнок через `.into_element()` в `Vec` (динамический `Children`).

`570ca7606` («Resolve bon builder conflicts for Child/Children API», 2025-11-20): typestate `bon`
конфликтовал с ручными `child()`/`children()`, понадобились `IsUnset`-ограничения; в `Row`,
`Stack`, `IndexedStack` добавлен `child(&mut self, …)` рядом с устаревшим `set_children`
(`row.rs:245-256` в том коммите) — мутирующие методы смешаны с builder'ом.

**Что работало:** одно определение полей и умолчаний на три стиля; читаемый литерал. **Что
мешало:** церемония `.build()`; typestate против кастомных setter'ов детей; `Default` делает
литерал «всё необязательно» — обязательных полей нет, пустая колонка компилируется; только
`Vec`-дети с боксингом каждого ребёнка; проверки в рантайме (`warn`), а не при компиляции;
ошибки в макросе указывают внутрь раскрытия. **Почему удалено:** не задокументировано (тело
`16ca09544` пустое, соседние коммиты 2026-02-08 причин не называют; обзор архитектуры
2026-09-25 предлагает убрать `bon` как зависимость `flui-tree`, о стиле виджетов не говорит).

**Что цель сохраняет.** От старой: три стиля, одно место для полей и умолчаний, литерал с
именами полей. От сегодняшней: обязательные параметры не пропустить (`Text::new(data)`),
типизированные дети кортежем без боксинга, setter'ы без `.build()`, вывод `cx` в inline-closure,
свобода менять внутреннее представление (`FlexStyle`) без поломки пользователей.

## Требования

Одно требование — один тест (вид в скобках); таблицы — строка на виджет или случай.

- **R1.** КОГДА виджет facade или официального пакета публичен, СИСТЕМА ДОЛЖНА давать для
  него все три стиля из одного определения. Проверка: consumer-тест-таблица по реестру
  виджетов, сверяемому с публичными типами (как `RENDER_OBJECT_TYPES`); виджет без строки или
  без одного из стилей — падение (consumer-тест).
- **R2.** КОГДА одно и то же содержимое записано тремя стилями, СИСТЕМА ДОЛЖНА строить
  одинаковое дерево элементов, render-объектов и semantics. Проверка: таблица по каталогу
  (строка — виджет с непустыми полями и детьми), сравнение дампов трёх деревьев после кадра в
  `flui-testing` (consumer-тест).
- **R3.** КОГДА обязательный параметр (сегодня позиционный аргумент `new`, например `data` у
  `Text`) не задан, СИСТЕМА ДОЛЖНА отказывать при компиляции в каждом стиле, а диагностика
  должна называть поле и виджет и указывать на место вызова пользователя. Проверка: три
  trybuild-фикстуры с `.stderr` (trybuild).
- **R4.** КОГДА необязательный параметр не задан, СИСТЕМА ДОЛЖНА подставлять одно и то же
  умолчание во всех стилях, и это умолчание ДОЛЖНО быть указано в rustdoc поля. Проверка:
  doc-тест на виджет, сравнивающий три стиля без параметра со значением из документации (doc test).
- **R5.** КОГДА у виджета много детей, СИСТЕМА ДОЛЖНА принимать любое их число во всех стилях
  без перехода на другой синтаксис; если граница остаётся, она одна для трёх стилей, описана в
  rustdoc, а диагностика на ней называет предел и обход. Проверка: `column` с 17 и 64
  разнотипными детьми в трёх стилях компилируется и строит дерево, либо trybuild на границе
  (consumer-тест + trybuild).
- **R6.** КОГДА дети разнотипны и их число известно статически, СИСТЕМА ДОЛЖНА сохранять
  конкретные типы детей без боксинга в каждом стиле, как сегодня `Column::new((a, b))`; динамические
  дети (`Vec<BoxedView>`, итератор) принимаются всеми стилями. Проверка: consumer-тест на тип
  результата (`Column<(Text, Padding)>`) и на `Vec` (consumer-тест).
- **R7.** КОГДА у виджета один ребёнок, СИСТЕМА ДОЛЖНА сохранять сегодняшнюю обязательность:
  необязательный (`Padding`, `Center`) можно опустить, обязательный — ошибка компиляции,
  называющая `child`. Проверка: trybuild на виджете с обязательным ребёнком в трёх стилях (trybuild).
- **R8.** КОГДА ребёнок не реализует `View`/`IntoView`, СИСТЕМА ДОЛЖНА выдавать ошибку,
  указывающую на выражение ребёнка и называющую требуемый трейт, во всех стилях, без
  внутренних сгенерированных типов в первой строке. Проверка: trybuild ×3 (trybuild).
- **R9.** КОГДА callback задаётся в любом стиле, СИСТЕМА ДОЛЖНА принимать
  `Fn(&mut EventCx<'_>) -> R, R: EventOutcome` с захватом `!Send`-значений (`Signal`, `Rc`) и
  выводить тип `cx` у inline-closure не хуже, чем сегодняшний setter. Проверка: consumer-тест
  с `Signal` и `Rc` в трёх стилях + trybuild на closure `|| …` без `cx` (consumer + trybuild).
- **R10.** КОГДА пишется генерик-виджет (`Column<C>`, `Stack<C>`, material с параметром),
  СИСТЕМА ДОЛЖНА выводить параметры типов без аннотаций и turbofish во всех стилях там, где
  сегодня их не нужно. Проверка: consumer-тест без аннотаций по генерик-строкам реестра (consumer-тест).
- **R11.** КОГДА поле неизвестно или указано дважды (литерал, макрос), СИСТЕМА ДОЛЖНА
  отказывать при компиляции, называя поле и виджет и указывая на токен пользователя.
  Проверка: trybuild на неизвестное и дублирующееся поле в литерале и макросе (trybuild).
- **R12.** КОГДА в builder один и тот же параметр задан дважды или заданы взаимоисключающие
  setter'ы (например `child` и `children`), СИСТЕМА ДОЛЖНА вести себя документированно и
  одинаково со смыслом в других стилях (ошибка компиляции или «последний побеждает» — решает
  design.md). Проверка: trybuild или consumer-тест, закрепляющий выбранное (trybuild/consumer).
- **R13.** КОГДА макрос использован неверно (пропущен разделитель, свойства после детей,
  выражение вместо имени поля), СИСТЕМА ДОЛЖНА указывать на ошибочный токен и показывать
  ожидаемую форму, а не ошибку внутри раскрытия. Проверка: trybuild ×3 случая (trybuild).
- **R14.** КОГДА в виджет добавляется необязательное поле в 0.x, СИСТЕМА ДОЛЖНА давать
  задокументированное обещание для каждого стиля: какой код пользователя продолжает
  компилироваться. Обещание записывается в ADR и в rustdoc. Проверка: fixture-крейт с вызовами
  трёх стилей собирается против версии с добавленным полем; ломается ровно то, что ADR назвал
  ломающимся (consumer-тест).
- **R15.** КОГДА собирается Notes, СИСТЕМА ДОЛЖНА укладываться в границы относительно базы:
  чистая сборка `two_screens` — не более +10 %, инкрементальная после правки `tree.rs` — не
  более +10 %, размер release-бинаря — не более +3 % (границы предлагаются, утверждает владелец).
  Проверка: замер на базе и на ветке, одна машина, три прогона, медиана (measurement).
- **R16.** КОГДА пользователь открывает rustdoc виджета, СИСТЕМА ДОЛЖНА показывать на одной
  странице все параметры с умолчаниями и обязательностью и пример каждого стиля;
  вспомогательные сгенерированные типы не появляются отдельными страницами в списке крейта.
  Проверка: проверка rustdoc JSON по реестру (тест-проверка) + doc-тест примеров (doc test).
- **R17.** КОГДА пользователь набирает код в rust-analyzer, СИСТЕМА ДОЛЖНА давать дополнение
  имён полей в литерале, setter'ов в builder и имён полей внутри макроса. Проверка:
  скриптованный LSP-запрос completion к rust-analyzer на фикстуре трёх стилей (measurement).
- **R18.** КОГДА автор стороннего пакета пишет виджет только на `flui-sdk`, СИСТЕМА ДОЛЖНА
  давать ему те же три стиля тем же механизмом, без прямых зависимостей кроме `flui-sdk`.
  Проверка: fixture-пакет на `flui-sdk` с виджетом в трёх стилях + строка в
  `crates/flui-sdk/tests/surface.rs` (consumer-тест).
- **R19.** КОГДА генерируется код стилей, СИСТЕМА НЕ ДОЛЖНА добавлять bound `Send`/`Sync` к
  полям, детям и callback'ам и не должна закрывать opt-in маркер параллельного кадра (D5).
  Проверка: consumer-тест виджета с `!Send` полем через `flui-sdk` в трёх стилях (consumer-тест).
- **R20.** КОГДА существующий код пишет `Column::new(column![…])`, `X::new(…).setter(…)`,
  СИСТЕМА ДОЛЖНА либо компилировать его без изменений, либо давать механическую замену,
  описанную во фрагменте `changelog.d/`, и все места вызова в репозитории (Notes, examples,
  book, пакеты) переведены. Проверка: сборка examples и doctest book (consumer-тест).
- **R21.** КОГДА пользователь читает tutorial и Notes, СИСТЕМА ДОЛЖНА показывать все три стиля
  на компилируемых примерах, а Notes — использовать каждый хотя бы на одном экране.
  Проверка: doctest/`mdbook test` глав tutorial + `rg` по `tree.rs` в тесте Notes (doc test).
- **R22.** КОГДА документация показывает стиль, СИСТЕМА ДОЛЖНА компилировать пример (не
  `text`/`ignore`), а id вида `FR-NNN` ДОЛЖНЫ ловиться гейтом `markers`.
  Проверка: doctest модуля макросов + строка-фикстура в тестах `cargo xtask markers` (doc test).

## Вне scope

- DSL вне Rust-выражений (`rsx!` в духе Dioxus, файлы `.slint`), горячая перезагрузка разметки.
- Новые виджеты, их поведение, render-объекты, `CustomPainter`; параллельный кадр (D5; только R19).

## Открытые вопросы

1. **Struct-литерал и semver 0.x (решает ADR).** (а) `pub` поля + `..Default::default()`, как
   Bevy `Node { …, ..default() }`: добавление поля не ломает литерал с `..`, но ломает литерал
   без него; обязательные поля несовместимы с `Default` (боль старой реализации), а приватность
   представления (`FlexStyle`) теряется. (б) Литералоподобный макрос (`Column! { … }`),
   раскрывающийся в builder: поля приватны, обязательность проверяется, но это не настоящий
   литерал из формулировки R18. (в) `#[non_exhaustive]` запрещает литерал вне крейта целиком,
   поэтому с литералом не сочетается. Нужен выбор владельца и, при (а), список полей,
   становящихся публичным контрактом.
2. **Граница детей.** Снять предел 16 (раскрытие в вложенные кортежи, свой `ViewSeq` для
   длинных списков) или оставить документированную границу (R5)? iced `column![]` боксит
   каждого ребёнка без предела; FLUI сегодня держит типы детей (R6).
3. **Терминатор builder'а.** Без `.build()` (как сегодня) обязательные параметры остаются
   позиционными в `new`; typestate (`bon`, `typed-builder`) даёт именованные обязательные поля
   ценой `.build()` и конфликтов с кастомными setter'ами (`570ca7606`).
4. **Генератор.** Свой derive в `flui-macros` (путь через `flui-sdk`, контроль диагностик) или
   внешний крейт (`bon`/`typed-builder`: зрелость против `cargo xtask deps`, времени сборки и
   качества ошибок, R3/R11/R15)?
5. **Грамматика макроса.** Разделитель свойств и детей, позиционные обязательные аргументы
   (`text!("…")`), нужен ли макрос для каждого из 179 виджетов или для контейнеров и листьев с
   обязательными полями — при сохранении R1.
