## Зачем

`flui-testing` начинался как один headless-хост и вырос по одному модулю на вопрос. Числа ниже
сняты на `main` @ `aa45aa8` поиском по именам (`rg`), так что это кандидаты, а не доказанные
дубли.

| Что | Сколько | Где |
|---|---|---|
| Публичные модули `flui-testing` одним плоским списком | 26 | `crates/flui-testing/src/lib.rs` |
| Способы смонтировать дерево и управлять им внутри `flui-testing` | 4: `HeadlessHost` (122 публичных метода), `LaidOut` (113), `Harness` (37), `Tester` (73) | `src/host.rs`, `src/widgets.rs`, `src/widgets/harness.rs`, `src/tester.rs` |
| Сценарные API для автора | 2: `Tester` с `Expectation` и `flui_driver::{Window, ElementLocator, expect}` с `Expect` | `crates/flui-testing/src/tester.rs`, `crates/flui-driver/src/{window,expect}.rs` |
| Семейства поиска | 3: `find` (локаторы протокола), `a11y::A11yQuery`, `LaidOut::find_by_render_type` и `find_text` | `src/find.rs`, `src/a11y.rs`, `src/widgets.rs` |
| Словари ввода | 4: `dispatch_pointer_*`, `replay::PointerScript`, глаголы `Tester`, воспроизведение `recording` | там же |
| Файлы, которые зовут `lay_out*` | около 197 | `crates/*/tests`, `packages/*/tests` |
| Файлы на `Tester` (`rg -lw` `Tester::mount`, без `RenderTester`) | 16 | там же |
| `struct Probe` и `ProbeState` в тестах при готовом `widgets::ProbeRoot` | 20 и 6 | `crates/*/tests` |
| Двойники `Mock*`, `Fake*`, `Scripted*`, `Recording*`, `Counting*` | около 150 в 20 крейтах | `crates/*`, `packages/*` |
| Рукописные `fn pump`, `advance`, `tick`, `settle` в `tests/` и `benches/` | 80 (28 в `flui-widgets`) | там же |
| Тестов и строк тестового кода | 4 833 `#[test]`, около 435 000 строк под `tests/` | рабочее пространство |

Чего нет совсем: золотых снимков экрана на уровне виджета (пиксели проверяет только readback-набор
`flui-engine`, которому нужен адаптер), проверки правил доступности одной строкой (аналог
`meetsGuideline` из `flutter_test`), общих стратегий для property-тестов (32 блока `proptest!`,
каждый со своими генераторами) и тестов по модели состояний над сценарным API.

Автор приложения видит только `flui::testing` (`Tester`, `find`), а тесты самого фреймворка в
основном стоят на `LaidOut`, которого в фасаде нет. Поэтому форма, которую мы советуем авторам,
не та, на которой проверен фреймворк, и сценарий, написанный для headless, на устройстве
переписывается под `flui-driver`.

## Требования

- **R1. Один способ на глубину.** Для render-объекта, для дерева виджетов в кадре, для целого
  приложения и для настоящего устройства есть по одному типу, и более глубокий построен из менее
  глубокого. Параллельных типов и методов-одноразовых проб нет.
- **R2. Один словарь.** Поиск, ввод и ожидания одни и те же в тестах фреймворка, в тестах
  приложения, в драйвере и у агента. Сценарий пишется один раз и идёт headless, на устройстве и от
  агента.
- **R3. Инструмент на каждое утверждение.** Поведение, геометрия, команды рисования, пиксели,
  семантика и правила доступности, время и анимация, фоновая работа, возможности платформы,
  владение и утечки, паники, стоимость (ADR-0396), устойчивость (property, модель состояний,
  фаззинг). У каждого назван аналог во Flutter 3.50.1 или причина отличия.
- **R4. Тест доказывает то, что делает продукт.** Кадр это `UiRuntime::pump`, ввод идёт путём
  ввода рантайма, двойник стоит на шве возможности, время виртуальное, процессного состояния нет.
- **R5. Неправильный вызов не компилируется** там, где это достижимо типами (ADR-0303): чтение
  геометрии до кадра, действие по неоднозначному локатору.
- **R6. Отказ это диагноз.** Сообщение называет локатор, ближайших кандидатов, срез дерева, кадр и
  время; у каждого глагола есть `try_`-двойник с типизированной ошибкой.
- **R7. Дёшево собирать и запускать.** Новых крейтов рабочего пространства нет, у крейта остаётся
  один бинарь на каждый вид цели (`tests`, `perf`, `golden`, `device`), время сборки кита и граф линковки теста не растут.
- **R8. Встроено.** Автор приложения получает каждый инструмент через `flui::testing` и
  `flui test`, не подключая сторонних средств; соединение с устройством даёт `flui-driver`, который цель `device` берёт dev-зависимостью (ADR-0238 §8).
- **R9. Миграция заканчивается.** Каждый шаг переносит всех пользователей старой формы и удаляет
  её, либо помечает `#[deprecated]` с записью в `docs/gaps.md`. `main` рабочий после каждого PR.
