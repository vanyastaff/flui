# Persistence: сохранение и восстановление состояния Notes — требования (уровень 1)

- **Статус:** черновик
- **Дата:** 2026-10-05
- **База:** `main` @ `4915054c8`
- **Уровень 0:** [../release/requirements.md](../release/requirements.md) (R5, R6)

Спека задаёт наблюдаемое поведение: что переживает перезапуск Notes и что видит пользователь,
когда хранилище подводит. Как это устроено (API, крейт, формат, capability), решает `design.md`;
cross-crate контракт оформляется ADR.

## Пользовательский сценарий

**Автор приложения** (зависит только от `flui` с фичей `material`):

1. объявляет, что приложение сохраняет: данные (заметки, настройка compact-строк) и состояние
   сеанса (черновик, стек маршрутов, позицию списка); формат может меняться между версиями
   приложения, и файл от прежней версии должен читаться или давать явную ошибку;
2. загружает данные с диска через тот же `FutureBuilder` с состояниями loading/error/Retry,
   что уже есть в Notes; реальный IO заменяет нынешний fixture готовности;
3. не пишет кода под платформу: каталог данных, атомарную запись и отказ платформы без
   файловой системы даёт framework, ошибки приходят значениями, не паникой;
4. тестирует «закрыть и запустить снова» в headless-тестах через `flui::testing`, без
   настоящего диска и без реального времени.

**Пользователь Notes:**

1. переименовывает заметку и сохраняет её, листает список до строки ~5000, открывает другую
   заметку, начинает править заголовок и не сохраняет, открывает Settings;
2. закрывает окно; запускает приложение снова: видит «Loading notes», затем Settings поверх
   редактора с тем же черновиком; Back ведёт в редактор, ещё раз Back — в Home на той же
   позиции списка; сохранённая заметка с новым заголовком;
3. если файл повреждён или диск недоступен, видит ошибку и Retry; приложение отвечает, правки
   в памяти не пропадают, повреждённый файл молча не затирается, а закрытие с несохранёнными
   правками не проходит без явного выбора.

## Текущее состояние

- Всё состояние Notes живёт в памяти, в `Shared` над `Router`: заголовки, выбранная заметка,
  черновик, `ScrollController`, счётчик попыток, compact-флаг, статус
  (`examples/two_screens/tree.rs:35`–`44`); заголовки генерируются при старте (`tree.rs:50`).
  README: «restarting resets it», «no disk persistence» (`examples/two_screens/README.md:14`, `:28`).
- Загрузчик — fixture готовности без данных (`NotesLoader`, `tree.rs:19`; `impl Default` с первой
  неудачной попыткой, `tree.rs:82`–`99`). Loading/error/Retry — `FutureBuilder::keyed` с ключом-
  счётчиком попыток (`tree.rs:260`–`276`); Retry делает `saturating_add` (`tree.rs:272`), так что
  на `u32::MAX` ключ перестаёт меняться.
- `FutureBuilder` отменяет подписку и инвалидирует поколение при замене ключа и unmount
  (`crates/flui-view/src/element/future_builder.rs:243`–`248`, проверено в
  `tests/fixtures/notes_flow.rs:821`); future обязан быть `Send` (`future_builder.rs:62`).
- Futures widget-кода крутит `AsyncDriver` на owner-потоке, внутри кадра
  (`crates/flui-scheduler/src/async_driver.rs:407`–`412`; `crates/flui-runtime/src/execution.rs:8`–`12`),
  через `LifecycleContext::async_driver` (`crates/flui-view/src/context/build_context.rs:421`).
  IO-пул (`ExecutionServices::spawn_io`, `execution.rs:516`) до widget-кода не доходит:
  `TaskSpawner` выдаётся только через `ServiceContext` (`crates/flui-app/src/app/lifecycle.rs:335`–`345`).
- Позиция списка — `ScrollController` над `Router`, переживает навигацию (`notes_flow.rs:730`);
  `with_initial_scroll_offset` зажимает значение при первой раскладке
  (`crates/flui-widgets/src/scroll/scroll_controller.rs:185`–`199`).
- `Router::from_location` строит back-stack из одного location
  (`crates/flui-widgets/src/router/router.rs:130`–`148`); `RouterHandle` отдаёт только верх стека
  (`crates/flui-widgets/src/router/handle.rs:211`–`228`). ADR-0093 §2: стек — то, что сохраняет
  restoration (`docs/adr/ADR-0093-router-is-the-primary-navigation-api.md:123`); шаг 8 (`:247`–`248`)
  не выполнен. API восстановления нет нигде в `crates/`, `packages/`, `src/`
  (`crates/flui-widgets/src/app/widgets_app.rs:56`–`59`, `crates/flui-widgets/src/navigator/mod.rs:77`);
  ADR о persistence нет. Каталога данных приложения нет ни в одном крейте.
- Жизненный цикл: платформа сообщает `WindowExecutionState::Suspended`
  (`crates/flui-platform-api/src/window.rs:193`–`198`) и `CloseRequested` после вето (`window.rs:305`);
  вето регистрируется только через `AppConfig::with_close_request_handler`
  (`crates/flui-app/src/app/config.rs:419`), web и Android его не спрашивают
  (`crates/flui-app/src/app/close_request.rs:70`), flush при закрытии отложен (`close_request.rs:52`–`55`).
  Widget видит `AppLifecycleState` (`Resumed`/`Inactive`/`Hidden`/`Paused`/`Detached`,
  `crates/flui-scheduler/src/frame.rs:230`) через `lifecycle_handle` (`build_context.rs:537`–`542`).
  Headless-хост: `set_lifecycle_state` (`crates/flui-testing/src/lib.rs:323`) и `close_lifecycle`,
  который дерево не снимает (`lib.rs:332`–`334`).
- В workspace есть `serde`/`serde_json` (`Cargo.toml:240`–`241`) и `tempfile` (`Cargo.toml:264`);
  фича facade `serde` покрывает только value-типы (`Cargo.toml:790`–`795`). Web-бэкенд без
  файловой системы: `crates/flui-platform/src/platforms/web`.

## Требования

Уровни: **H** — headless widget/frame tier (`flui::testing`, виртуальные часы, двойник хранилища
или временный каталог); **C** — consumer (`tests/facade_consumer.rs` гоняет
`tests/fixtures/notes_flow.rs` через facade); **N** — нативный прогон процесса (датированный,
входит в R14 уровня 0). «Перезапуск» в H и C — новый mount нового `NotesApp` поверх того же
хранилища после снятия первого дерева (`close_lifecycle` дерево не снимает, его снимает тест).

### Восстановление (R5)

- **R1.** КОГДА пользователь сохранил заметку и приложение перезапущено, СИСТЕМА ДОЛЖНА
  показывать её с сохранённым заголовком, остальные заметки — без изменений. H, C, N.
- **R2.** КОГДА пользователь переключил compact-строки и приложение перезапущено, СИСТЕМА ДОЛЖНА
  показывать список с той же высотой строк. H, C.
- **R3.** КОГДА при закрытии в редакторе был несохранённый черновик, СИСТЕМА ДОЛЖНА после
  перезапуска открыть ту же заметку с тем же текстом черновика; заголовок в списке остаётся
  сохранённым, пока пользователь не нажмёт Save. H, C.
- **R4.** КОГДА при закрытии стек был `Home → Note{id} → Settings`, СИСТЕМА ДОЛЖНА после
  перезапуска показывать Settings, а две активации Back — вести в `Note{id}`, затем в Home. H, C.
- **R5.** КОГДА список был прокручен на смещение `p`, СИСТЕМА ДОЛЖНА после перезапуска
  показывать его на `p` (±1 логическая единица); восстановленные черновик, маршрут и смещение
  видны на первом кадре после загрузки данных, без промежуточного кадра со значениями по
  умолчанию (Home, смещение 0, пустой черновик). H, C.
- **R6.** КОГДА загрузка данных не удалась, СИСТЕМА ДОЛЖНА показывать экран ошибки с Retry, не
  применять сохранённый сеанс и не изменять его на диске; после успешного Retry сеанс применяется
  как в R3–R5. H.
- **R7.** КОГДА восстановленное значение недопустимо (смещение за новым экстентом, маршрут на
  несуществующую заметку, черновик удалённой заметки), СИСТЕМА ДОЛЖНА применить
  документированный fallback (зажатие, Home, отбрасывание черновика) без паники и без ошибки
  загрузки данных. H.
- **R8.** КОГДА состояние сеанса нечитаемо, а данные целы, СИСТЕМА ДОЛЖНА загрузить данные и
  стартовать в Home на смещении 0 без экрана ошибки данных. H.
- **R9.** КОГДА это первый запуск и файла нет, СИСТЕМА ДОЛЖНА стартовать с начального состояния
  без экрана ошибки. H, C.
- **R10.** КОГДА идёт загрузка, СИСТЕМА ДОЛЖНА показывать loading, выпускать кадры (IO не
  выполняется в build/layout/paint), а Reload — заменять загрузку, как сейчас заменяет fixture. H.
- **R11.** КОГДА запись не завершается (двойник хранилища блокирует её), СИСТЕМА ДОЛЖНА
  продолжать выпускать кадры и обрабатывать ввод: набор в черновике и прокрутка работают. H.

### Жизненный цикл и закрытие

- **R12.** КОГДА пользователь закрывает окно штатно и хранилище исправно, СИСТЕМА ДОЛЖНА записать
  данные и сеанс до завершения процесса; если в этот момент идёт Save, закрытие ждёт его
  завершения. Ни одно изменение не теряется. H (запрос закрытия у headless-двойника), N.
- **R13.** КОГДА окно уходит в `Hidden` или `Paused` (платформенное `Suspended`), СИСТЕМА ДОЛЖНА
  записать сеанс; при возврате в `Resumed` — НЕ перечитывать диск поверх состояния в памяти. H
  (`set_lifecycle_state`), N.
- **R14.** КОГДА закрытие запрошено, а несохранённые правки нельзя записать (запись идёт или не
  удалась, файл повреждён или от более новой версии, загрузка не удалась после правок вроде
  compact-строк), СИСТЕМА ДОЛЖНА удерживать окно через вето закрытия и показывать причину с Retry
  и явным «закрыть без сохранения»; повреждённый или более новый файл не перезаписывается. На
  платформе, где вето не спрашивается, СИСТЕМА ДОЛЖНА документировать потерю: всё, что изменено
  после последней успешной записи. H, N.
- **R15.** КОГДА Save подтверждён хранилищем, СИСТЕМА ДОЛЖНА сохранить заметку при аварийном
  завершении сразу после этого; статус «Saved note N» появляется только после подтверждения.
  Проверка — двойник с барьером фиксации: снятие дерева до барьера теряет правку (перезапуск
  показывает старый заголовок, статуса нет), после барьера — сохраняет. H, N.
- **R16.** КОГДА сохранение отложено (debounce, повтор после сбоя), СИСТЕМА ДОЛЖНА отсчитывать
  время по часам realm, а не по системным: на виртуальных часах сценарии детерминированы. H.

### Ошибки хранилища (R6)

- **R17.** КОГДА файл повреждён (невалидные байты, обрезан, чужой формат), СИСТЕМА ДОЛЖНА
  показывать ошибку с Retry без паники и не перезаписывать эти байты до явного действия
  пользователя; после исправления файла Retry загружает его. H.
- **R18.** КОГДА файл или каталог недоступен (нет прав, путь занят каталогом, носитель отключён),
  СИСТЕМА ДОЛЖНА отдавать приложению отдельный вид ошибки, отличный от «повреждён», и показывать
  отдельное сообщение с Retry; приложение остаётся интерактивным. H, N.
- **R19.** КОГДА каталога данных нет, СИСТЕМА ДОЛЖНА создать его при первой записи; КОГДА его
  нельзя создать, — вести себя как R18 и работать в памяти. H, N.
- **R20.** КОГДА запись не удалась, СИСТЕМА ДОЛЖНА показывать ошибку записи с Retry, сохранить все
  правки в памяти, оставить на диске прежнее целое состояние, а Retry — записать актуальное
  состояние памяти, а не снимок на момент сбоя. H.
- **R21.** КОГДА запись прервана посередине, СИСТЕМА ДОЛЖНА при следующем запуске загружать
  прежнее или новое целое состояние, никогда не смесь и не «повреждён». H (инъекция сбоя), N.
- **R22.** КОГДА атомарная замена файла временно отклонена (файл держит антивирус или индексатор,
  sharing violation на Windows), СИСТЕМА ДОЛЖНА повторить замену ограниченное число раз, затем
  вести себя как R20; прежний файл цел. H (двойник), N (Windows).
- **R23.** КОГДА профиль пользователя содержит не-ASCII символы, каталог данных перенаправлен
  (redirected AppData, OneDrive) или полный путь длиннее 260 символов, СИСТЕМА ДОЛЖНА сохранять и
  восстанавливать как в R1. N (Windows).

### Сценарии отказа

- **R24. Отмена.** КОГДА окно закрывается до завершения загрузки или после её ошибки, СИСТЕМА
  ДОЛЖНА отменить загрузку и НЕ записывать поверх файла ни пустое начальное, ни частично
  загруженное состояние (правки после ошибки — по R14). H.
- **R25. Повтор.** КОГДА причина устранена, СИСТЕМА ДОЛЖНА завершать Retry успехом без перезапуска;
  N повторных Retry подряд дают ровно один применённый результат. H.
- **R26. Исчерпание счётчика.** КОГДА Retry или Reload нажаты больше раз, чем вмещает счётчик
  попыток, СИСТЕМА ДОЛЖНА продолжать запускать новую загрузку либо явно отказывать с сообщением;
  молча игнорировать нажатие нельзя. H.
- **R27. Unmount.** КОГДА дерево снимается во время загрузки или записи, СИСТЕМА ДОЛЖНА освободить
  загрузку (подсчёт `Drop`, как `notes_flow.rs:821`), не применять её результат к снятому дереву,
  а запись довести до целого состояния или отменить без порчи файла (R21). H.
- **R28. Устаревшее завершение.** КОГДА загрузка заменена Reload или Retry, СИСТЕМА ДОЛЖНА
  применять только последнюю; КОГДА запись A начата раньше записи B, а завершилась позже, на
  диске должно остаться состояние B. H.
- **R29. Паника.** КОГДА паникует код приложения, который вызывает persistence (сериализация,
  десериализация, миграция, обработка результата), в том числе во время закрытия, СИСТЕМА ДОЛЖНА
  локализовать её по [PANIC-POLICY](../../../PANIC-POLICY.md), показать ошибку с Retry, не трогать
  файл и данные в памяти; первый сбой остаётся определяющим при последующих, следующая операция
  работает; payload паники, чей `Drop` сам паникует, не приводит к abort за пределами описанного
  в PANIC-POLICY. H.
- **R30. Ресурсы.** КОГДА диск заполнен, СИСТЕМА ДОЛЖНА вести себя как R20 и R21. КОГДА файл
  больше документированного предела, — отказывать с отдельной ошибкой «слишком большой», не читая
  его целиком и не останавливая кадры; 10 000 заметок укладываются в предел с запасом. H.
- **R31. Версия.** КОГДА файл записан прежней версией формата, СИСТЕМА ДОЛЖНА мигрировать его либо
  показывать ошибку с Retry, не затирая файл. КОГДА файл от более новой версии, — отказывать с
  ошибкой «файл от более новой версии» и никогда его не перезаписывать (R14 при закрытии). H.
- **R32. Второй экземпляр.** КОГДА второй процесс Notes работает с тем же хранилищем, СИСТЕМА ДОЛЖНА
  не допускать нечитаемого файла и молчаливой потери изменений любого из экземпляров. H (модель),
  N (Windows).
- **R33. Неподдерживаемая платформа.** КОГДА нет файловой системы или каталога данных (wasm32),
  СИСТЕМА ДОЛЖНА собираться (`cargo xtask wasm-check`), сообщать «хранение недоступно» значением,
  работать в памяти с видимым указанием, что данные не сохранятся, и не паниковать. H, сборка wasm.

### Facade и realm

- **R34.** КОГДА consumer-проект зависит от `flui` с фичами по умолчанию плюс `material`, СИСТЕМА
  ДОЛЖНА проходить R1–R5 через facade. C.
- **R35.** КОГДА consumer собирает `flui` с фичами по умолчанию и persistence не использует,
  СИСТЕМА НЕ ДОЛЖНА тянуть `serde_json` в граф обычных зависимостей. C (рядом с
  `ordinary_facade_graph_excludes_test_support`).
- **R36.** КОГДА в одном процессе живут два realm, каждый со своим хранилищем, СИСТЕМА ДОЛЖНА
  держать их независимыми: запись, ошибка или восстановление в одном не меняют другой. H.

## Вне scope

- Размер и положение окна; восстановление нескольких окон (ADR-0091 Proposed).
- Web history (`pushState`/`popstate`) из шага 8 ADR-0093; на wasm только деградация R33.
- Process death на Android/iOS (системный save/restore instance state): платформы `experimental`.
- Автоматическое восстановление прочего состояния виджетов: выделение и курсор, фокус,
  IME-композиция, незавершённые анимации и переходы, fling-скорость списка.
- Синхронизация, облако, шифрование, сжатие, выбор места хранения пользователем.
- Undo между запусками; более одного черновика.
- Гарантии при потере питания сверх атомарной замены файла на целевой ОС.
- `Computed`/`Effect` (ADR-0075, Proposed) как зависимость.

## Открытые вопросы для design

1. **Граница framework / приложение.** Что входит в `flui` (каталог данных как capability в
   `flui-platform-api`, IO-канал для widget-кода через `LifecycleContext`, чтение полного стека
   `Router`, вето закрытия на widget-уровне для R14), а что остаётся кодом Notes; какой ADR
   фиксирует контракт и как он соотносится с отложенными widget-capability `TaskSpawner` и вето.
2. **Данные против сеанса.** Один файл или два; когда пишется сеанс помимо закрытия и
   `Hidden`/`Paused` (debounce после изменения) и какое окно потерь черновика и позиции допустимо
