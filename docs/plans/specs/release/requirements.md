# Первый релиз FLUI на crates.io — требования

- **Статус:** черновик; утверждает координатор по делегированию владельца. Решения владельца
  D1, D3–D6 действуют.
- **Сверено с:** `main` @ `e13b7ce` (2026-11-12)
- **Срок:** без даты. Релиз выходит, когда пройдены все ворота готовности (раздел «Ворота
  готовности»); дату назначают после последних ворот. Состав и статусы работ ведёт
  [tasks.md](tasks.md).

Этот документ задаёт, что значит «первый релиз для сообщества» и как доказать, что он готов.
Решения по каждой фиче принимает её спека в `docs/plans/specs/<feature>/`; здесь только то, что
нужно для релиза, и чем это доказывается. Номера требований постоянны: на них ссылаются спеки
фич.

## Пользовательский сценарий

Rust-разработчик, который раньше не видел FLUI:

1. находит `flui` на crates.io и docs.rs, читает README с честной матрицей платформ;
2. создаёт проект через `flui create` или добавляет только `flui` (с фичей `material`) и
   проходит учебник книги: шаг за шагом собирает приложение заметок, то самое, по которому идёт
   приёмка (`tests/fixtures/acceptance_app/`);
3. запускает его на своей десктопной ОС. Приложение рисуется через wgpu, переходит между
   экранами, грузит заметки с диска (с индикатором загрузки, ошибкой и Retry), редактирует текст
   (в том числе через IME), проверяет форму, листает длинный список, работает с клавиатуры и со
   скринридером;
4. закрывает окно и запускает снова: заметки, черновик, текущий экран и позиция списка на месте;
5. пишет тесты своего приложения через `flui::testing`: находит виджет по тексту, роли или
   идентификатору, нажимает, вводит текст и проверяет результат, не считая координат;
6. запускает приложение с `flui run --agent` и даёт агенту вести его через `flui mcp`;
7. находит ошибку, открывает issue по шаблону и видит в release notes список известных
   ограничений.

## Ворота готовности

Релиз не получает даты, пока не пройдены все пять ворот. Каждые ворота проверяются там, где
живёт их правило; этот документ его не копирует.

| Ворота | Где правило и проверка |
|---|---|
| Рендер | ворота G1–G7 спеки [`render-scaling`](../render-scaling/requirements.md); пока у ADR-0304, ADR-0305 или ADR-0306 есть пункт в [`docs/gaps.md`](../../../gaps.md#accepted-adr-sections-not-built-yet), ворота не пройдены |
| Цена контрола | запись [An interactive widget costs eighteen elements](../../../gaps.md#an-interactive-widget-costs-eighteen-elements) закрыта: каталоги Material и Cupertino на узле ADR-0322, сценарий `perf_raw_button_over_text` держит её числа |
| Снимок публичного API | R3 |
| Тестовый API авторов | R19 |
| Имена крейтов | R21 |

## Требования к релизу

Каждое требование проверяется командой, тестом или датированным прогоном. Требования к
поведению приложения приёмки детализируют спеки фич; здесь каждое проверяется строкой
приёмки через фасад.

### Поставка

- **R1.** КОГДА внешний проект без checkout FLUI зависит только от `flui` версии релиза
  (из crates.io; до публикации — из локального staging-реестра с теми же `.crate`-файлами),
  СИСТЕМА ДОЛЖНА собирать его и проходить приёмку headless. Доказательство: consumer по
  реестру, а не по path-зависимости.
- **R2.** КОГДА публикуется версия релиза, СИСТЕМА ДОЛЖНА публиковать все крейты, которые
  транзитивно нужны `flui` и `flui-cli`, в порядке зависимостей; `cargo package` каждого
  проходит без `--allow-dirty` и без path-зависимостей. `flui-native` зависит только от
  опубликованных адаптеров AccessKit; возможность, которой в их релизе нет, отвечает
  типизированным отказом, пока AccessKit не выпустит правку (решение 16 аудита main: запросы в
  upstream подаёт владелец).
- **R3.** КОГДА меняется публичный API `flui` или крейта, который он реэкспортирует, СИСТЕМА
  ДОЛЖНА показывать изменение в проверяемом снимке поверхности на PR. Корни крейтов
  реэкспортируют выбранные имена, а не крейты целиком (ADR-0089 §5–§6), и проверка охватывает
  фичи, а не только фичи по умолчанию на хосте.
- **R4.** КОГДА consumer собирает `flui` с фичами по умолчанию, СИСТЕМА НЕ ДОЛЖНА тянуть
  `flui-testing`, hot reload, Material, Cupertino, HTTP-клиент и TLS-стек в граф обычных
  зависимостей. HTTP — фича фасада, выключенная по умолчанию (ADR-0088 §6); виджет без неё
  получает типизированный отказ возможности. Доказательство:
  `ordinary_facade_graph_excludes_test_support` (`tests/facade_consumer.rs`) с HTTP и TLS в
  запрещённом списке.

### Приложение приёмки (поток целиком, через фасад)

- **R5.** КОГДА пользователь закрывает окно и запускает приложение снова, СИСТЕМА ДОЛЖНА
  восстанавливать заметки, несохранённый черновик, текущий маршрут и позицию списка. Спека:
  `persistence`.
- **R6.** КОГДА файл состояния повреждён, недоступен или его запись не удалась, СИСТЕМА ДОЛЖНА
  показывать ошибку с Retry без паники и без потери данных в памяти. Спека: `persistence`.
- **R7.** КОГДА пользователь вводит текст через IME с композицией на сертифицируемой
  платформе, СИСТЕМА ДОЛЖНА показывать preedit и вставлять подтверждённый текст в позицию
  курсора. Спека: `text-ime`.
- **R8.** КОГДА пользователь работает только с клавиатуры, СИСТЕМА ДОЛЖНА давать дойти до
  каждого интерактивного элемента всех экранов и активировать его. Спека: `focus-keyboard`.
- **R9.** КОГДА экран приложения отрисован через wgpu, СИСТЕМА ДОЛЖНА давать readback,
  совпадающий с эталоном в пределах зафиксированного допуска; точки выборки различают
  правильную и сломанную отрисовку.
- **R10.** КОГДА окно закрыто или UI-рантайм уничтожен, СИСТЕМА ДОЛЖНА освобождать все
  elements, render objects, контроллеры и незавершённые futures этого рантайма (доказывается
  подсчётом `Drop`) и завершать процесс с кодом успеха. Спека: `teardown`.
- **R11.** КОГДА пользовательский callback паникует, СИСТЕМА ДОЛЖНА действовать по
  [PANIC-POLICY](../../../PANIC-POLICY.md): сбой локализован, следующий кадр строится или
  приложение выходит с диагностикой; ничто не зависает. Спека: `teardown`.
- **R12.** КОГДА приложение запущено на сертифицируемой платформе, СИСТЕМА ДОЛЖНА публиковать
  его дерево доступности в API ОС, а скринридер — озвучивать и активировать элементы каждого
  экрана. Доказательство: датированный прогон.
- **R13.** КОГДА приложение работает на эталонной машине, СИСТЕМА ДОЛЖНА укладываться в
  опубликованный бюджет: время кадра при прокрутке длинного списка, память, время холодного
  старта. Бюджеты фиксируются измерением; отчёт содержит профиль фаз кадра (build, layout,
  paint, raster, present), по которому решается, нужен ли параллельный кадр (D5). Счётчики
  кадра держат гейты `cargo xtask perf --check`.

### Платформы и качество

- **R14.** КОГДА платформа объявлена в README как поддерживаемая, СИСТЕМА ДОЛЖНА иметь для неё
  датированный нативный прогон приёмки (R5, R7–R10, R12) на SHA релиза. Состав (D1): нативно
  сертифицируется Windows (IME через TSF, Narrator, GPU readback); Linux проверяется в CI
  (приёмка headless и окно на нативном хосте) без сертификации IME и скринридера; macOS, Web,
  Android и iOS — `experimental`. Статус каждой позиции берётся из
  [`platform-parity.toml`](../../../../crates/flui-native/platform-parity.toml).
- **R15.** КОГДА создаётся тег релиза, СИСТЕМА ДОЛЖНА иметь зелёный `cargo heli xtask ci` на
  этом SHA, зелёные CI main и ночные прогоны за последние 7 дней (или открытый и разобранный
  issue на каждый красный), версию релиза во всех манифестах и слитый `CHANGELOG.md`.
- **R16.** КОГДА релиз выходит, каждый открытый issue с меткой `priority: critical` или
  `priority: high` должен быть закрыт либо перечислен в release notes с обходным путём. Сверка
  с main — в [tasks.md](tasks.md#открытые-issue-critical-и-high).
- **R17.** КОГДА разработчик открывает docs.rs, книгу или README, СИСТЕМА ДОЛЖНА давать
  учебник, который воспроизводит приложение приёмки с нуля на опубликованной версии. Каждый
  фрагмент кода книги включается из компилируемого файла и собирается в CI; rustdoc собирается
  на docs.rs без ошибок; README честно описывает матрицу платформ, MSRV и лицензию.

### Форма API

- **R18.** КОГДА разработчик описывает дерево виджетов, СИСТЕМА ДОЛЖНА давать для каждого
  виджета фасада и официальных пакетов одну форму: конструктор с обязательными параметрами и
  setter'ы для остальных, без `.build()`. Многодетный контейнер принимает детей одним значением
  `ViewSeq` (кортеж, массив или `Vec`), макросов-выражений нет (решение 13 аудита main). Где
  стоит единственный ребёнок и как называются обработчики и контексты, задаёт одно записанное
  правило с табличным тестом. Struct-литерал — после стабилизации `default_field_values` (D6).
- **R19.** КОГДА автор пишет тест своего приложения, СИСТЕМА ДОЛЖНА давать один вход
  `flui::testing`: приложение монтируется так же, как его монтирует рантайм, поиск идёт
  локаторами по тексту, роли и идентификатору (те же, что у драйвера, `flui-semantics::agent`),
  действия `tap` и `enter_text`, ожидания `expect`. `HeadlessBinding` и другие тестовые
  драйверы из фасада уходят (ADR-0083 §4); тест, который кладёт `flui create`, написан в этой
  форме. Ошибки раскладки видны автору с местом создания виджета (переполнение Flex сейчас
  молчит).

### Агент и имена

- **R20.** КОГДА разработчик запускает debug-сборку с `flui run --agent` на Windows, Linux или
  macOS, СИСТЕМА ДОЛЖНА давать агенту через `flui mcp` перечислить окна, прочитать дерево
  семантики (роль, метка, состояние и действия каждого узла), выполнить действие узла и
  управлять часами анимации (ADR-0239). Статус в README — experimental: протокол версионирован
  как 0.x без обещаний совместимости; мобильные и веб-транспорты и инструменты протокола,
  которых нет в `flui mcp` (ожидания, инспекция, запись), не обещаются. Доказательство: ночной
  прогон `an_agent_drives_the_acceptance_app_on_the_desktop` (приложение приёмки, только через
  `flui mcp`) и `an_agent_presses_the_counter_on_a_live_device` на каждом десктопе; macOS без
  зелёного ночного прогона помечается «без прогона». Страница книги об агенте в ворота не
  входит.
- **R21.** КОГДА публикуется версия релиза, СИСТЕМА ДОЛЖНА публиковать все крейты под именами,
  которые проект уже занял на crates.io; список имён подтверждает владелец до первой
  публикации (действие необратимо).

### Что после публикации меняется только ломающим выпуском

- **R22.** КОГДА фича объявлена в манифесте публикуемого крейта, СИСТЕМА ДОЛЖНА давать ей
  действие: пустых фич и фич без потребителя в релизе нет (для `signals` — ADR-0085 §5).
- **R23.** КОГДА `flui create` создаёт проект, СИСТЕМА ДОЛЖНА класть в него dev-профиль,
  который оптимизирует зависимости, как в workspace; время холодной сборки такого проекта
  записано базовой линией и не растёт.
- **R24.** КОГДА приложение запускается, СИСТЕМА ДОЛЖНА давать один вход `run_app` на всех
  платформах, без паники на Android; незавершённый API нескольких окон не входит в prelude и
  стоит за нестабильной фичей.
- **R25.** КОГДА приложение навигирует между экранами, СИСТЕМА ДОЛЖНА давать одну публичную
  форму навигации — Router (ADR-0093), включая `MaterialApp::router` и `CupertinoApp::router`;
  именованные маршруты и двери `NavigatorHandle`, которые ADR-0093 убирает, в релиз не входят.
- **R26.** КОГДА публичный `enum` может получить вариант после релиза, СИСТЕМА ДОЛЖНА
  помечать его `#[non_exhaustive]`; закрытые перечисления названы правилом, которое держит
  clippy.
- **R27.** КОГДА автор пишет состояние виджета, СИСТЕМА ДОЛЖНА давать одну форму состояния и
  его возможностей: сигналы и handles создаются в `create_state`. `StateCell` и `Option`-поля,
  которые заполняются в `init_state`, не остаются в каталогах и примерах.

## Сценарии отказа (обязательны в спеках фич)

Каждая спека фичи разбирает те из них, что к ней относятся: отмену, повтор, unmount во время
работы, stale callback после замены, панику в пользовательском коде, исчерпание ресурса (диск,
GPU device lost, исчерпание ID) и неподдерживаемую платформу (фича есть в API, но платформа её
не реализует: деградация явная, без паники).

## Вне scope

- Android и iOS: `experimental`, примеры собираются, сертификации нет.
- Нативная сертификация macOS, Linux (IME, скринридер) и Web (D1).
- Hot reload через патчер кода (ADR-0311 §7) и `flui run --hot` как обещание релиза.
- Транспорты агента на мобильных и в браузере как обещание релиза; стабильный протокол драйвера.
- Многооконность сверх одного окна приложения как стабильный API (R24).
- Полный паритет Material 3 и Cupertino; новые семейства виджетов (правило ворот в
  `AGENTS.md`); CPU-рендерер.
- Стабильность API после 0.x: релиз версии `0.N`, semver по правилам 0.x.

## Пересмотр решений

Принятый ADR или прошлое решение владельца — точка отсчёта. Спека фичи пересматривает его, если
изменились требования или исследование нашло решение лучше; пересмотр идёт по
[ADR Policy](../../../../AGENTS.md#adr-policy): новый ADR с `Supersedes:`. Пересмотр решения
владельца идёт владельцу одним вопросом.

## Решения

- **D1 (владелец, 2026-10-05).** Публикация на crates.io. Нативная сертификация — только
  Windows; Linux — через CI; остальные платформы `experimental`.
- **D2 (координатор, 2026-11-12).** Агент входит в первый релиз как experimental в объёме R20:
  всё, что для него нужно, уже на main, а без него сообщество не увидит главного отличия
  проекта.
- **D3 (владелец).** UI-поверхности owner-local (ADR-0136): `CustomPainter` и
  event-callback'и не требуют `Send`, слушатели пишут через `WriterSource` (ADR-0086).
- **D4 (владелец).** Один owner-поток на процесс; UI-рантайм окна — единица изоляции, а не
  параллелизма (ADR-0091). Политика окна — `WindowPolicy::Isolated` или `Shared`.
- **D5 (владелец, 2026-10-05).** Параллельный кадр в первый релиз не входит, но ни одно его
  решение не закрывает параллельную раскладку позже без ломки API.
- **D6 (владелец, 2026-10-05).** Форма виджета — конструктор с setter'ами (R18); настоящий
  struct-литерал добавляется после стабилизации `default_field_values` без ломки API, поэтому
  параметры виджетов держатся плоскими.
- **D7 (предложено).** Номер версии: `0.2.0` (сейчас `0.2.0-dev` в корневом `Cargo.toml`).
