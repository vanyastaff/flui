# Релиз FLUI для сообщества — требования (уровень 0)

- **Статус:** черновик, ждёт утверждения владельцем. D1 решён владельцем 2026-10-05.
- **Дата:** 2026-10-05
- **База:** `main` @ `4915054c8`
- **Срок:** релиз 2026-12-31; RC 2026-12-15.
- **Связанные документы:** [ROADMAP](../../../ROADMAP.md) (B0–B4), [BETA](../../../BETA.md),
  [migration plan](../../2026-09-25-architecture-migration-plan.md), [design/](../../../../design/README.md).
  Карта фич, статусы и календарь — в [tasks.md](tasks.md).

Этот документ задаёт, что значит «релиз для сообщества», и как доказать, что он готов. Он
сводит ROADMAP B1/B2/B4 к одному датированному рубежу. Порядок и состав работ задаёт
`tasks.md`, решения по каждой фиче — её спека уровня 1.

## Пользовательский сценарий

Rust-разработчик, который раньше не видел FLUI:

1. находит crate на crates.io и docs.rs, читает README с честной матрицей платформ;
2. создаёт пустой проект, добавляет только `flui` (с фичей `material`) из crates.io и проходит
   tutorial из book: шаг за шагом собирает приложение Notes;
3. запускает его на своей desktop-ОС. Приложение рисуется через wgpu, переходит между экранами,
   грузит заметки с диска (с индикатором загрузки, ошибкой и Retry), редактирует текст
   (в том числе через IME), проверяет форму, листает список из 10 000 строк, работает
   с клавиатуры и со скринридером;
4. закрывает окно и запускает снова: заметки, черновик, текущий экран и позиция списка
   на месте;
5. пишет на нём widget-тесты через `flui::testing`;
6. находит ошибку, открывает issue по шаблону и видит в release notes список известных
   ограничений.

## Требования к релизу

Каждое требование проверяется одной командой или одним датированным прогоном. Требования
к поведению showcase детализируют спеки уровня 1. Здесь каждое такое требование проверяется
через acceptance Notes.

### Дистрибуция и consumer

- **R1.** КОГДА внешний проект без checkout FLUI зависит только от `flui` версии релиза
  (из crates.io; до публикации — из локального staging-реестра с теми же `.crate`-файлами),
  СИСТЕМА ДОЛЖНА собирать его и проходить headless-acceptance Notes. Доказательство:
  consumer-проверка по реестру, а не по path-зависимости.
- **R2.** КОГДА публикуется версия релиза, СИСТЕМА ДОЛЖНА публиковать все крейты, которые
  транзитивно нужны `flui`, в порядке зависимостей, и `cargo package` для каждого должен
  проходить без `--allow-dirty` и без path-only зависимостей.
- **R3.** КОГДА меняется публичный API `flui`, СИСТЕМА ДОЛЖНА показывать изменение в
  проверяемом снимке поверхности (public-API snapshot или api-closure) на PR, чтобы
  поверхность facade менялась только осознанно.
- **R4.** КОГДА consumer собирает `flui` с фичами по умолчанию, СИСТЕМА НЕ ДОЛЖНА тянуть
  `flui-testing`, hot reload, Material или Cupertino в граф обычных зависимостей
  (есть: `ordinary_facade_graph_excludes_test_support`).

### Showcase Notes (поток целиком, через facade)

- **R5.** КОГДА пользователь закрывает окно Notes и запускает приложение снова, СИСТЕМА ДОЛЖНА
  восстанавливать заметки, несохранённый черновик, текущий маршрут и позицию списка.
  Спека: `persistence`.
- **R6.** КОГДА файл состояния повреждён, недоступен или его запись не удалась, СИСТЕМА ДОЛЖНА
  показывать ошибку с Retry и без паники, не теряя данные в памяти. Спека: `persistence`.
- **R7.** КОГДА пользователь вводит текст через IME с композицией на сертифицируемой
  desktop-платформе, СИСТЕМА ДОЛЖНА показывать preedit и вставлять подтверждённый текст
  в позицию курсора. Спека: `text-ime`.
- **R8.** КОГДА пользователь работает только с клавиатуры, СИСТЕМА ДОЛЖНА давать дойти до
  каждого интерактивного элемента всех экранов Notes и активировать его. Спека: `focus-keyboard`.
- **R9.** КОГДА экран Notes отрисован через wgpu, СИСТЕМА ДОЛЖНА давать readback, совпадающий
  с эталоном в пределах зафиксированного допуска. Точки выборки при этом должны различать
  правильную и сломанную отрисовку. Спека: `render-proof`.
- **R10.** КОГДА окно закрыто или realm уничтожен, СИСТЕМА ДОЛЖНА освобождать все elements,
  render objects, контроллеры и незавершённые futures этого realm (доказывается подсчётом
  `Drop`) и завершать процесс с кодом успеха. Спека: `teardown`.
- **R11.** КОГДА пользовательский callback в Notes паникует, СИСТЕМА ДОЛЖНА действовать по
  [PANIC-POLICY](../../../PANIC-POLICY.md): сбой локализован, следующий кадр строится или
  приложение выходит с диагностикой; ничто не зависает. Спека: `teardown`.
- **R12.** КОГДА включена фича `a11y`, СИСТЕМА ДОЛЖНА публиковать дерево доступности Notes
  в OS API сертифицируемых платформ, а скринридер должен озвучивать и активировать элементы
  каждого экрана. Доказательство: датированный протокол ручного прогона. Спека: `a11y-native`.
- **R13.** КОГДА showcase работает на эталонной машине, СИСТЕМА ДОЛЖНА укладываться в
  опубликованный бюджет: время кадра при прокрутке 10 000 строк, память, время холодного
  старта. Бюджеты фиксируются измерением, а не заранее. Отчёт содержит профиль фаз кадра
  (build, layout, paint, raster, present) на showcase и хотя бы одном тяжёлом экране:
  по этим цифрам решается, нужен ли параллельный кадр после 0.2.0 (D5). Спека: `measurements`.

### Стиль написания приложений

- **R18.** КОГДА разработчик описывает дерево виджетов, СИСТЕМА ДОЛЖНА давать для каждого
  виджета facade и официальных пакетов builder (`Column::new(…)` с setter'ами), а для
  многодетных контейнеров ещё и макрос-выражение (`column![…]`). Оба стиля генерируются из
  одного определения виджета и дают одно и то же дерево. Tutorial показывает оба стиля, Notes
  пишется в одном. Третий стиль, struct-литерал (`Column { … }`), — цель после стабилизации
  `default_field_values` (D6). Он потребует публичных полей (RFC 3681, «Privacy
  interactions»), поэтому параметры виджетов уже сейчас держатся плоскими. Это пожелание владельца (2026-10-05): декларативный widget-стиль — главное
  лицо фреймворка. Спека: `authoring-styles`.
  **Решение владельца (D6, 2026-10-05).** На stable Rust struct-литерал не может одновременно
  дать обязательные поля, добавление полей без ломки API и приватное внутреннее устройство.
  `default_field_values` на rustc 1.99.0 даёт E0658 (rust-lang/rust#132162). Поэтому в 0.2.0
  входят builder (`Column::new(…)` и setter'ы, без `.build()`) и макрос-выражение
  (`column![a, b].spacing(8.0)`). Оба форматирует rustfmt, оба понимает rust-analyzer.
  Настоящий литерал `Text { data, .. }` добавляется после стабилизации фичи, без ломки API:
  определения виджетов с самого начала проектируются под это.
- **R19.** КОГДА новичок проходит первый час с FLUI, СИСТЕМА НЕ ДОЛЖНА повторять известные
  боли других фреймворков из топ-10 исследования [`dx/research.md`](../dx/research.md). Каждый
  пункт закрыт требованием в спеке-владельце или явно перенесён в release notes с причиной.
  Новые спеки, которые из этого возникли: `layout-diagnostics` (молчаливые ошибки раскладки) и
  `testing-dx` (поиск виджетов в тестах и ввод текста по finder'у, а не по координатам).

### Платформы

- **R14.** КОГДА платформа объявлена в README как поддерживаемая, СИСТЕМА ДОЛЖНА иметь для неё
  датированный нативный прогон acceptance Notes (R5, R7–R10, R12) на SHA релиза.
  Остальные платформы помечены `experimental` и в R14 не входят. Состав (D1): нативно
  сертифицируется **Windows** (IME через TSF, скринридер Narrator, GPU readback). **Linux**
  проверяется в CI: headless-acceptance Notes и `live-smoke`, без сертификации IME и скринридера.
  macOS, Web, Android и iOS — `experimental`.

### Качество и гигиена

- **R15.** КОГДА создаётся тег релиза, СИСТЕМА ДОЛЖНА иметь зелёный `cargo xtask ci` на этом SHA,
  зелёные CI main и scheduled-прогоны за последние 7 дней (или открытый и разобранный issue
  на каждый красный), версию релиза во всех манифестах и слитый `CHANGELOG.md`.
- **R16.** КОГДА релиз выходит, каждый открытый issue с меткой `critical` или `high` должен быть
  закрыт либо явно перечислен в release notes с обходным путём. Сейчас это
  #1043 (critical), #1040, #1091, #1092, #1037, #1039, #1041.
- **R17.** КОГДА разработчик открывает docs.rs, book или README, СИСТЕМА ДОЛЖНА давать tutorial,
  который воспроизводит Notes с нуля на опубликованной версии; rustdoc собирается на docs.rs
  без ошибок; README честно описывает матрицу платформ, MSRV и лицензию.

## Сценарии отказа (обязательны в спеках уровня 1)

Каждая спека уровня 1 разбирает те из них, что к ней относятся: отмену, повтор, unmount
во время работы, stale callback после замены, панику в пользовательском коде, исчерпание
ресурса (диск, GPU device lost, переполнение ID) и неподдерживаемую платформу (фича есть
в API, но платформа её не реализует: деградация явная, без паники).

## Вне scope

- Android и iOS: остаются `experimental`, примеры собираются, сертификации нет.
- Нативная сертификация macOS, Linux (IME, скринридер) и Web: они остаются `experimental` (D1).
- Hot reload на Subsecond (ADR-0094) и `flui run --hot` как обещание релиза.
- `flui mcp` и agent workflow ROADMAP B3. Предлагаю вынести в следующий релиз; при желании
  вернуть — отдельное решение.
- Многооконность сверх одного окна приложения (ADR-0091 Proposed).
- Полный паритет Material 3 и Cupertino; CPU-рендерер.
- Стабильность API после 0.x: релиз версии `0.N`, semver по правилам 0.x.

## Принятые решения можно пересматривать

Принятый ADR или прошлое решение владельца — точка отсчёта, а не ограничение. Design-фаза
каждой фичи пересматривает их, если изменились требования, исследование или эксперимент
нашли решение лучше, либо текущее решение мешает выполнить требование этого релиза.
Пересмотр оформляется по [ADR Policy](../../../../AGENTS.md#adr-policy): в `design.md` —
сравнение с действующим решением на фактах (код, измерения, первичные источники), затем
новый ADR с `Supersedes:` и `Superseded-by:` в старом. Тихо разойтись с принятым ADR нельзя.
Если пересмотр затрагивает решение владельца (как D3), он идёт владельцу одним вопросом.

## Решения

- **D1 (решено владельцем 2026-10-05).** Публикация `0.2.0` на crates.io. Нативная
  сертификация — только Windows; Linux — через CI (headless и live-smoke); остальные платформы
  `experimental`. Отвергнуты: три desktop-платформы (нужны ручные прогоны на Mac и Linux,
  наибольший риск по сроку) и релиз без crates.io (выше порог входа для сообщества).
  Следствие: `send-flip` стоит на критическом пути (D3).
- **D2 (предложено).** Номер версии: `0.2.0`. Согласуется с ROADMAP B0, сейчас `0.2.0-dev`.
- **D3 (зафиксировано владельцем 2026-09-25, migration plan; пересмотрено 2026-10-05).**
  Переход на `!Send` (W5-A5) делается целиком до 0.2.0, ADR-0086 принимается с поправкой §5:
  слушатели пишут через захваченный `WriterSource`, без `cx` в сигнатуре. Отсечка: если
  `send-flip` не смержен к 2026-11-24, 0.2.0 публикуется без перехода, а переход
  анонсируется на 0.3. Частичного перехода не бывает: `CustomPainter: Send + Sync` не может
  держать `!Send`-контроллер как источник перерисовки, модель стала бы противоречивой.
- **D4 (принято 2026-10-05: владелец поручил решить оркестратору; основание — эксперимент
  [`realm-model/experiment.md`](../realm-model/experiment.md)).** Один owner-поток на процесс.
  Realm — единица изоляции (GlobalKey, scheduler, teardown, граница паник), а не параллелизма.
  Многопоточность — там, где работа параллельна: воркеры, raster-поток. Общее между окнами
  состояние — app-scope `!Send` граф на этом потоке: читается в `build` любого realm и пишется
  через `EventCx`. Он может выйти после 0.2.0 без ломки API. Политика «поток на realm»
  добавляется позже новым вариантом `#[non_exhaustive] WindowPolicy`. До 0.2.0 нужно:
  исправить ложное обещание в доке `SeparateRealms`, чтобы rebuild realm'а будил своё окно,
  и написать ADR, который заменяет вердикт ADR-0027 о конкурентных realm'ах, его §1 и абзац
  ADR-0091 §1 о спайке.
- **D5 (владелец, 2026-10-05).** Параллельный кадр (стиль и layout независимых поддеревьев
  на нескольких ядрах) в 0.2.0 не входит, но ни одно решение 0.2.0 не должно его закрывать:
  возможность параллельной раскладки добавляется позже без ломки опубликованного API
  (например, opt-in маркер, который требует `Send` только от объектов, согласных на это).
  Исследование начинается после 0.2.0 по профилю фаз из R13.
