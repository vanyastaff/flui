# Where FLUI falls short

> **Last reviewed:** 2026-10-17 · **Last updated:** 2026-10-17 · **Change:** minor (Android IME and drag and drop through `FluiView`)

The work list. One entry per shortfall, ranked by how much it stops someone from choosing FLUI for a
production app on that environment. Each entry says what is missing, the evidence, who it hurts, an
agent wall-clock estimate, and the parity document that tracks it. Every entry blocks a ready
platform ([`platform-parity.md`](platform-parity.md)). Pick from the top, check open pull requests
first (`gh pr list`), and when a gap closes, update this file and the parity document in the same
pull request.

## Ranked

| # | Gap | Environments | Evidence | Who it hurts | Hours | Doc |
|---|---|---|---|---|---|---|
| 1 | **No text input on mobile and the Web**: no IME connection, soft keyboard, keyboard insets or input hints | iOS, Android, Web | No `UITextInput`; Android serves fields through `FluiView`'s `InputConnection` (ADR-0237), run with Samsung Keyboard on a Galaxy S21 (composition, commit, Escape, the action key, the keyboard shown and hidden), never with Gboard, `CursorAnchorInfo` placement, keyboard insets, paste through `OnReceiveContentListener` or stylus handwriting; the Web now serves fields through `EditContext` or a hidden textarea, run only through Chrome's own input-method path in headless Chrome, with no soft keyboard, insets or input hints | Every app with a text field | 45–75 | [Text input](platform-parity.md#text-input) |
| 2 | **Dark mode is wrong everywhere** | all | Windows always reports Dark because FLUI forces the DWM dark flag and reads it back; macOS and Linux always report Light; mobile never reads it; Web has no change listener | Every themed app | 4–8 | [System preferences](platform-parity.md#system-preferences) |
| 3 | **No accessibility on mobile and the Web; desktop off by default and untested with a screen reader** | iOS, Android, Web; desktop | AccessKit has iOS and Android adapters but none for the Web (it needs a parallel ARIA DOM); the desktop adapters sit behind the `a11y` feature; the runs read one control, not a Narrator, VoiceOver or Orca session; no locked adapter routes custom actions or `ShowContextMenu`, so gesture alternatives (ADR-0216) keep a control on every path | Blind and low-vision users; anyone who must meet accessibility law | 30–50 | [Accessibility](platform-parity.md#accessibility) |
| 4 | **No system back** | Android, iOS, Web | From targetSdk 36 Android delivers neither `onBackPressed` nor `KEYCODE_BACK`, so only predictive back works; iOS needs its own edge swipe; the Web needs History or Navigation API routing | Every multi-screen mobile or web app | 10–16 | [Input](platform-parity.md#input) |
| 5 | **Most implemented rows never ran on their environment** | all | 🟡 dominates every column of the parity summary; device checks exist for a handful of rows, and the macOS and iOS drivers are Python and Swift | Every claim of support | 40–80 | [Summary](platform-parity.md#summary) |
| 6 | **Native Linux backend (Wayland and X11)** replaces the winit fallback | Wayland, X11 | winit leaves the clipboard inert on pure Wayland, reports no occlusion on Wayland, has no pen, no pinch, no theme, no window bounds | Linux users | 150–250 | [Summary](platform-parity.md#summary) |
| 7 | **Clipboard is broken on three environments; no rich formats** | Android, Wayland, Web; all for rich | Android is an in-process mock; pure Wayland without data-control is inert; Web reads only its own writes | Every app with copy and paste | 14–22 | [Clipboard](platform-parity.md#clipboard-and-drag-and-drop) |
| 8 | **File dialogs, open URL, reveal, trash, message box and share exist on Windows only, or nowhere** | all | Every non-Windows backend answers a file dialog with "cancelled"; `open_url` is real on Windows and Web only, and nothing calls it | Every document app; any app with a link | 25–42 | [System services](platform-parity.md#system-services) |
| 9 | **No native drag and drop** | all | The core runs: in-window sessions, sessions that reach the other windows of their runtime on the source's capture where the backend places its windows, escalation to an OS session, identity and delivery to receivers in `flui-runtime`, exercised headless (ADR-0211). Windows has OLE as both target and source (`IDropTarget` per window, `DoDragDrop` started on the owner window's next turn, frames for every window while its loop rests), run only within one process (`ole_drag_and_drop_on_real_windows`), never with Explorer, another app, a held mouse button, pen or touch. The `Draggable` and `DropTarget` widgets run on it headless, with the cursor, Escape and the keyboard and assistive cut, copy and paste. The Web takes and starts HTML drags (a drag starts only from a press the runtime lifted before the browser's threshold), run in headless Chrome with constructed events. Android takes and starts drags on `FluiView` (ADR-0237): on a Galaxy S21 a drag the probe started dropped its text on its own window, and one crossed into Chrome, which declined it; no drag from or into another app has completed. Still missing: `NSDraggingDestination` and every other native drag source and target. Planned in the [interaction spec](plans/specs/flui-interaction/completeness/tasks.md) (ADR-0211; T28–T31, T35, T37 and the per-OS tickets) | Document, media and file-manager apps | 22–36 | [Clipboard and drag and drop](platform-parity.md#clipboard-and-drag-and-drop) |
| 10 | **Apps can't control their windows** | desktop | No API for title, position, state or constraints; Windows ignores min/max size and resizable; no state readback on macOS and Linux; Windows and X11 flash a blank first frame; no placement restore | Every desktop app | 18–32 | [Windows](platform-parity.md#windows) |
| 11 | **No custom title bar, popups or owned windows** | desktop | Undecorated Windows windows can't be dragged or resized; no caption hit-testing or snap layouts; menus, tooltips and dropdowns can't leave the window | Apps with modern chrome; every menu and dropdown | 22–36 | [Windows](platform-parity.md#windows) |
| 12 | **No native menus** | macOS, iPadOS; Windows | No macOS menu bar (no Quit or Edit menu), no native context menus, no Dock menu or jump list | Every macOS app | 20–32 | [Menus](platform-parity.md#menus) |
| 13 | **Lifecycle holes** | all | Session end is never delivered and `flui-app` can't register it; Android never dispatches visibility or execution state; Web ignores page freeze and context loss; no sleep, wake or memory-pressure events | Apps that save state or hold resources | 20–35 | [App lifecycle](platform-parity.md#app-lifecycle) |
| 14 | **No deep links, URL schemes, file associations or single instance** | all | `on_open_urls` is never called; packaging (app identity) not audited | Apps opened from links, files or a second launch | 15–25 | [App lifecycle](platform-parity.md#app-lifecycle) |
| 15 | **Most system preferences are read on Windows only** | all but Windows | Contrast, languages and regional formats, Linux and Web text scale, accent colour, gesture timings. Gesture presets per platform and pointer kind, accessibility floors, per-display geometry and headless injection landed with the [interaction spec](plans/specs/flui-interaction/completeness/tasks.md) (ADR-0212) | Users who rely on accessibility settings or another locale | 20–35 | [System preferences](platform-parity.md#system-preferences) |
| 16 | **Pointer and keyboard gaps** | various | No pen on macOS or Linux; the Windows precision-touchpad pan and pinch (DirectManipulation) have never run on a touchpad, and no injector reaches it, so its golden recording can only come from a `native-capture` run on one (injected touch, pen, mouse and wheel already record theirs through `cargo xtask device windows-input`); Android touchpad pinch and two-finger scroll and its pen hover and tilt ran only from `uinput` devices through `cargo xtask device android-input`, with no hardware touchpad or stylus; no precise-scroll phases on the Web, whose trackpad pinch (decoded from Control-held wheel and WebKit gesture events) ran only with constructed events in headless Chrome; iPad pointer and hardware keyboard missing; no cursors on mobile; keyboard layout read on Windows only. Pointer, scroll and pinch work is planned per OS in the [interaction spec](plans/specs/flui-interaction/completeness/tasks.md) (T36 DirectManipulation is implemented and awaits a touchpad run; T40–T44) | Pen, trackpad and iPad users | 30–50 | [Input](platform-parity.md#input) |
| 17 | **Mobile system UI** | iOS, Android, Web | No status-bar, navigation-bar or immersive control (Android enforces edge-to-edge from targetSdk 35); no orientation lock; haptics has both tiers and the frame queue (ADR-0210), but its macOS and iOS paths never ran on a device, the Web's ran only in headless Chrome (activation refused, then `Submitted`, no motor), Android ran only feedback and amplitude waveforms (on a Galaxy S21 without primitives; envelopes and compositions never ran), and Windows pen haptics ran only on a host with no haptic pen, while Windows touchpad and mouse haptics (`InputHapticsManager`) wait for a `windows` crate that ships it ([interaction spec](plans/specs/flui-interaction/completeness/tasks.md)); no safe area on the Web or for the macOS notch. System gesture exclusion is implemented on Android and iOS; it ran on an Android device, never on iOS | Every mobile app | 14–24 | [System UI](platform-parity.md#system-ui) |
| 18 | **Displays and frame pacing** | Windows, Android; all for changes | Windows reports no refresh period and always the primary display; Android hard-codes its display; no display-change events anywhere | High-refresh and multi-monitor users | 10–16 | [Displays and metrics](platform-parity.md#displays-and-metrics) |
| 19 | **Desktop shell services** | desktop | No tray, notifications, taskbar progress or badge, global shortcuts, launch at login, keep-awake or secure storage | Background, messaging and utility apps | 37–60 | [System services](platform-parity.md#system-services) |
| 20 | **Text services** | all | No spell check, system edit menu, autofill or handwriting | Writing apps; sign-in forms; tablet users | 22–36 | [Text input](platform-parity.md#text-input) |
| 21 | **Storage isn't wired** | all | `FileStore` exists, but `flui-app`'s `host_storage` returns `None`; Android `app_path` is fake; the Web has no store | Apps that persist settings or documents | 6–10 | [System services](platform-parity.md#system-services) |
| 22 | **No native views inside the UI** (web view, map, video) | all | Not in the contract; the design shapes compositing, hit-testing and accessibility | Apps that embed a map, browser or player | 30–60 + owner decision | [Windows](platform-parity.md#windows) |
| 23 | **Window looks**: backdrop materials, transparency, icon, capture exclusion | desktop; mobile for capture | Windows forces Mica; macOS Liquid Glass unreachable; no window icon on Windows or Linux | Apps with a native look; apps showing sensitive data | 9–16 | [Windows](platform-parity.md#windows) |
| 24 | **Unaudited rows** | desktop, Web | App identity and packaging, live resize | Unknown | 2–4 | [Windows](platform-parity.md#windows) |
