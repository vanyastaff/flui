# Where FLUI falls short

> [!NOTE]
> **Last reviewed:** 2026-10-21

The work list. One entry per shortfall, ranked by how much it stops someone from choosing FLUI for a
production app on that environment. Each entry says what is missing, the evidence, who it hurts and
the parity document that tracks it. Every entry blocks a ready platform
([`platform-parity.md`](platform-parity.md)). Pick from the top, check open pull requests first
(`gh pr list`), and when a gap closes, update this file and the parity source
(`crates/flui-native/platform-parity.toml`, which renders the parity document) in the same pull
request.

An entry is named by its heading, never by a number: the rank is only the order of the entries, and
moving an entry changes nothing that refers to it. Documents link the heading's anchor
(`gaps.md#no-system-back`), and code names an entry with `flui_native::testing::gap::GapId`, whose
slugs the test `every_gap_id_is_a_gaps_entry` holds to these headings. Renaming a heading renames
its anchor: update the links and the `GapId` slug in the same pull request.

## Entries

### No text input on mobile and the Web

> **Environments:** iOS, Android, Web · **Who it hurts:** Every app with a text field · **Parity:** [Text input](platform-parity.md#text-input)

- No IME connection, soft keyboard, keyboard insets or input hints. The window contract carries where the keyboard rests, docked with its inset or floating with its frame, and the inset's motion (ADR-0277, ADR-0373); Android (from API 30) and iOS report them with the keyboard's motion, the Web at rest; none has run on a device. iOS compares a keyboard's bottom with the view's, so a floating keyboard straddling the bottom of a short Stage Manager window reads as docked: telling the two apart needs the screen's bounds, which the host does not read. A shortcuts bar dropped floating is published as no keyboard, since UIKit announces it with a zero frame and does not say where it is. No widget reads a floating keyboard's frame yet (`MediaQuery::floating_keyboard_of`): `Scaffold` keeps its body whole under it, which is the point, and `EditableText` does not scroll its caret out from under it.
- **Runs on iOS:** an invisible `UITextInput` responder (ADR-0255 decision 11) serves the focused field's store as the window's store host, the one AppKit's text input serves it through: it takes the system keyboard when a field takes focus, edits the field's text, composition and selection through the store, answers ranges and rects from the field's layout, and sends Return and Backspace as key presses (type-checked; the Simulator run below predates the store host); on the iOS 27.1 Simulator the Japanese Romaji and nine-key Pinyin keyboards composed `日本語` and `你好` into an `EditableText` (2026-10-28).
- **Missing on iOS:** a run of the store host on the Simulator and a device, input hints and keyboard insets on a device (type-checked, unrun), hiding the keyboard checked on screen and a run on a device. The responder answers `selectionRectsForRange:` with one rectangle per line of the range, and while a field is served a `UITextInteraction` in editable mode on the window's view gives it UIKit's caret, selection highlight, handles, loupe and edit menu, beginning only where the window's own hit test finds the field, or near a shown selection handle where nothing else takes the press, so a control over the field or beside a handle keeps its tap; the rectangles are cut to the part of the field the window shows (its ancestors' clips included), the caret is held inside it, and only a move of the field itself (not a caret move, and never during marked text or the interaction's own gesture) makes the interaction ask for them again. The host answers `SelectionUi::Platform`, so the field draws none of those and its own taps, long presses and drags stay out of it while it holds the input, and the edit menu's Cut, Copy, Paste, Select and Select All reach the field as `EditCommand`s through its store, only the field the menu was offered over; focus leaving a field dismisses the menu (type-checked, unrun). Owed to the Simulator run: whether UIKit draws its cursor and handles for a responder whose own frame is empty, whether the input delegate's selection will/did-change pair makes the interaction re-read its geometry, whether UIKit draws a caret held at the edge of the shown part when the real one is scrolled out (UIKit documents no "no caret" answer), whether `dismissMenu` on the interaction's `UIEditMenuInteraction` (iOS 16) or `UIMenuController.hideMenu` (iOS 13–15) closes its edit menu, and whether a paste from the edit menu shows the paste prompt: the field reads the pasteboard inside `paste:` (`ClipboardHandle::read_text` reads the platform clipboard at once on iOS) and only inserts the text at a later owner turn, and Paste is offered from `hasStrings`, which reads no content. Marked text is drawn from the store: the composition's underline and the selection inside it; the store holds one composition range, so the clauses UIKit's attributed marked text separates are not drawn apart. The field draws kana and kanji as missing-glyph boxes on the Simulator: its font fallback has no CJK face there.
- **Missing on every host:** a multiline field. Return reaches a field as the Enter key (UIKit's lone `"\n"`, AppKit's `insertNewline:`, a hardware key), which a single-line field answers with submit; a multiline field has to insert its line break through its store on Enter, on every host. The built-in store's `rect_for_range` spans the carets at a range's two ends, which is the range's box only on one line: a multiline field answers the union of the range's boxes, as the store's contract says and the iOS selection rectangles read it.
- **Runs on Android:** it serves fields through `FluiView`'s `InputConnection` (ADR-0348), run with Samsung Keyboard on a Galaxy S21 (composition, commit, Escape, the action key, the keyboard shown and hidden, and through a manual Android run a field submitted by Done while the keyboard still composed).
- **Missing on Android:** never run with Gboard, `CursorAnchorInfo` placement (the caret and composing character boxes, type-checked), the keyboard's insets below API 30 and their animation (the insets ran on a Galaxy S21, Android 15, 2026-11-16), the keyboard's Cut and Copy and extracted-text monitoring (built, ADR-0348), paste through `OnReceiveContentListener` or stylus handwriting. The keyboard's Cut, Copy, Paste and Select All (`FluiInputConnection.performContextMenuAction`) are the old form of a platform's edit command: they act on the Java mirror with the system clipboard and rules of their own, where the iOS edit menu's reach the field through its store (`TextStore::perform_edit_command`), so a concealed write and the clipboard's answer to a cut (ADR-0337) do not reach them. Moving them needs the action sent to the owner thread as an edit command in the mirror's in-order replay (after the edits the keyboard made before it, ADR-0348), the field performing it with its own actions, and the mirror refreshed from the field's answer instead of editing itself.
- **Runs on the Web:** it now serves fields through `EditContext` or a hidden textarea, run only through Chrome's own input-method path in headless Chrome.
- **Missing on the Web:** no mobile browser has run: the input hints, the 16 px editor that keeps iOS Safari from zooming, the keyboard opened in a tap's handler and kept from field to field by the window's one hidden editor, and reopening after Android's Back are pinned only by constructed events in headless Chrome. A tap on a field whose editor kept its focus reopens the keyboard only where the browser reports it hidden (`navigator.virtualKeyboard`'s empty rectangle, Chromium); after Back on Firefox for Android, which reports nothing (a visual-viewport inset is no report), the tap moves no focus and the keyboard stays hidden. A composition live while the window republishes a field ran only in Chrome's synchronous order; an input method that commits after the value reset (Gboard on Firefox for Android, IBus) may reach the field again with the composed text, unrun. One case stays open on iOS: a field the application focuses after the tap's handler returned (at its next frame) gets the editor already focused with `inputmode="none"` and its own hints a frame later, outside the gesture, which Safari may not answer with a keyboard until the next tap on the field. The host cannot tell at the tap whether a field is under it: without a screen reader the runtime publishes no semantics tree (`flui-runtime` `presentation.rs` turns platform semantics on only when assistive technology is active), and only the served field's geometry is known. Closing it needs the runtime to answer at the tap whether the point takes text, or to focus a tapped field inside the dispatch.
- **Missing everywhere:** client queries (selected range, surrounding text, first rect) for dictation, reconversion and handwriting, and a session that survives a window move, resize, DPI change and focus loss, are rows of their own under [Text input](platform-parity.md#text-input). Other frameworks show the failures: macOS dictation silently drops text when `selectedRange` returns `NSNotFound` ([rust-windowing/winit#4666](https://github.com/rust-windowing/winit/issues/4666), [#3617](https://github.com/rust-windowing/winit/issues/3617)), a Korean input method stops editing inline after the window moves ([DioxusLabs/dioxus#5246](https://github.com/DioxusLabs/dioxus/issues/5246)), and the input-method output of egui carries a position only ([emilk/egui#7941](https://github.com/emilk/egui/issues/7941)).
- **The IME event order is pinned by rows on every host:** the backend conformance table drives the Linux hosts' `text-input-v3` client (which X11's IBus, Fcitx5 and XIM contexts feed too), TSF's document on Windows, the AppKit and UIKit client, Android's `FluiView` mirror and the Web's `EditContext` and hidden textarea through one composition (a preedit that grows, a picked candidate, a commit, a cancel) and holds the field's text, composing range and caret after each step, each as one edit (`each_input_method_path_holds_the_ime_rows_or_names_its_gap`).

### No accessibility on mobile and the Web

> **Environments:** iOS, Android, Web; desktop · **Who it hurts:** Blind and low-vision users; anyone who must meet accessibility law · **Parity:** [Accessibility](platform-parity.md#accessibility)

- Desktop is always on but untested with a screen reader. AT-SPI ends the tree when the bus says no screen reader runs; a Windows or macOS window builds it for its life once any client asked ([below](#a-windows-or-macos-window-builds-its-accessibility-tree-for-its-life)).
- **Runs on iOS:** every UIKit window answers UIAccessibility through `accesskit_ios`'s low-level adapter, and the semantics identifier reaches `accessibilityIdentifier`; on the iOS Simulator an XCUITest client read the tree, found a button by its identifier and pressed it (2026-10-28). No VoiceOver session ran, and no AccessKit action was sent.
- **Runs on Windows:** the semantics identifier reaches UI Automation's `AutomationId`: a `UIAutomationClient` read a counter's button by its identifier, invoked it twice and read the count (Windows 11, 2026-10-29). No Narrator session ran.
- **Android, type-checked:** every Activity window answers TalkBack through `accesskit_android`'s low-level adapter, which `FluiView`'s node provider forwards to on the Java main thread; a publish is applied there in order. No TalkBack session ran. The tree is built only while an accessibility service is enabled: a service's first question starts it, and when none is enabled any more nothing is built or posted until one returns and asks again; a question with none enabled (Assist structure, autofill compatibility) is answered from a placeholder and starts nothing ([parity](platform-parity.md#accessibility), "The tree ends when no assistive technology listens"); a device run turning TalkBack off and on is owed. Explore by touch comes from the native input queue, where NativeActivity takes it: a finger hovering over the touchscreen goes to the adapter, not to the app as input (ADR-0255 decision 3). Bounds are placed from the view's screen location, which a device run must check against the window surface the tree is drawn in.
- **Web, run in headless Chrome:** every canvas window mirrors its tree as a parallel ARIA DOM (ADR-0255 decision 18): one `flui-node` element per node, nested as the tree is, in a host `position: fixed` over the canvas with `pointer-events: none`, so the pointer still reaches the canvas. Until a screen reader activates a placeholder button only it finds, the page holds nothing else, since the browser never says one is running; nothing deactivates it. A click on an element reaches the composition root as the action its node supports, focus moves the tree's focus, and keys on an element reach the window as on the canvas. A link with an address is an `<a href>` whose click is the node's action, a slider a user can move is an `<input type="range">` the browser adjusts for a screen reader, a node that takes a scroll offset is a scroller over content as long as its extent, whose scroll asks for that offset, and a focused text field is a native `<input>` or `<textarea>` the window's text input edits its store through, so a screen reader reads and edits the field the input method edits; the store stays the source of truth, and the field gone or unfocused, the store is served on the canvas again. Static text in a `SelectionArea`, which publishes runs (ADR-0214), is selected as the page's selection both ways: a screen reader's selection there asks `SetTextSelection` in run positions, and the tree's selection is shown in the page unless the page holds a selection of its own text. A live region, an announcement's included, enters the page empty and is given its text once the page has rendered it, since a browser reads out no region inserted with its text; a background tab gives it its text when shown. `flui-native`'s `web_browser` tests read the tree back from the DOM, click a node, move a slider's input, scroll a scroller, type into a served field, select static text, give a live region its text after it renders and keep the host over a canvas in a scrolled or scaled container (a rotated container is not followed). A date, time or spin field is still served on the canvas alone, and no NVDA, VoiceOver or TalkBack session read it.
- The semantics identifier (ADR-0240) reaches `AutomationId`, `AXIdentifier`, AT-SPI's id, iOS's `accessibilityIdentifier` and the Web's `data-flui-id` attribute through `author_id`. It does not reach Android's `viewIdResourceName`: the published `accesskit_android` sets none, so UI Automator, Espresso and Appium cannot find a node by it until an AccessKit release maps `author_id` there (written, not yet sent upstream).
- The runs read one control, not a Narrator, VoiceOver, Orca or TalkBack session.
- No locked adapter routes custom actions or `ShowContextMenu`, so gesture alternatives (ADR-0216) keep a control on every path.

### No system back

> **Environments:** Android, iOS, Web · **Who it hurts:** Every multi-screen mobile or web app · **Parity:** [Input](platform-parity.md#input)

- Android: FLUI registers no `OnBackInvokedCallback` (ADR-0255 decision 3 registers one while the router can pop, and nothing publishes that yet). With `enableOnBackInvokedCallback`, which the generated manifest declares and targetSdk 36 implies, Android 13 and later deliver neither `onBackPressed` nor `KEYCODE_BACK`, so every back is the system's and a Router page never pops on it: from Android 12 the system moves the task to the background, since `FluiActivity` is the root launcher Activity, with its back-to-home animation; below 12 it finishes the Activity. Below Android 13 the Back key reaches the application as `GoBack` first, and the system takes one the application leaves unhandled.
- iOS has no system back: a Router page under `CupertinoApp`, or under `MaterialApp` on an Apple platform, pops on the edge swipe its page transition carries, which headless tests drive and no iOS device has run.
- The Web needs History or Navigation API routing.

### Native Linux host (Wayland and X11)

> **Environments:** Wayland, X11 · **Who it hurts:** Linux users · **Parity:** [Summary](platform-parity.md#summary)

- It replaced the winit fallback: `current_platform` picks the native Wayland or X11 host by the session (ADR-0151 §11), and an application of `flui-app` runs on each under Weston and Xvfb (`native_linux`). winit itself is deleted from the workspace, and `deny.toml` bans it.
- **X11 has its own host now** (`X11Platform`): one libxcb connection read by a loop on the owner thread, which waits with no timeout but the application's wake deadline; windows that publish what the server and the window manager hold, take every window command, and honour what the window manager supports; the RandR displays, the Settings portal, logind and memory pressure, and an AT-SPI bridge per window. Ran on WSL Ubuntu 24.04 under Xvfb with openbox, 2026-11-15: the window conformance, a mode set before mapping, the window manager's close asked of the handler, its ping answered as the owner's loop turns (`a_window_answers_the_window_managers_ping`), a frame asked for on another thread waking an idle loop, the exit with the last window, a wake deadline delivered once, a stream of events that leaves the frames their turns (a turn of the loop takes at most `MAX_TURN_EVENTS` events and reads a window once, after them) a window that outlives a window manager killed under it, and a stand-in window manager that speaks only ICCCM (it owns `WM_S0` and publishes no `_NET_SUPPORTING_WM_CHECK`) followed as one that runs. Its input is XInput 2 (pointers, touch, pens, unphased smooth scrolling), XKB (keys, compose, the layout and its changes) and the cursor theme; XTest's pointer, buttons, wheel and keys ran through it on the same server (2026-10-28) and replay from a native recording, while touch, pens and smooth scrolling are checked by the decoder alone, since Xvfb has no such device. Its clipboard owns and reads the `CLIPBOARD` selection on a connection and a thread of its own (ICCCM: `TARGETS`, `TIMESTAMP`, the text forms, `INCR` both ways); two of its clipboards exchanged text, large text included, through Xvfb (2026-10-30). Its primary selection is `PRIMARY` on the same connection: the application's selection is asked for its text at the loop's turn, only when another client reads it, and two of its clipboards exchanged it through Xvfb (2026-10-30). It takes XDND drops on its windows and starts drag sessions from them ([No native drag and drop](#no-native-drag-and-drop)). Its text input serves the focused field to IBus or Fcitx5 over D-Bus, one input context per window: each key of a composing field is asked of the input method and held, the keys behind it waiting in order, and a key the input method leaves unanswered within 200 ms, or the keys of a window losing the focus or closing, go as typed in their original order; commits, preedits and deletions around the caret reach the field's store, and the field's text, caret, purpose and caret rectangle reach the input method. It ran against a stand-in IBus on a private `dbus-daemon` with Xvfb (`text::linux::x11::bus_tests`, 2026-11-02), never with a real IBus or Fcitx5; a key the input method forwards back (`ForwardKeyEvent`) is logged and dropped With no daemon on D-Bus, the host speaks XIM to the server `XMODIFIERS` names, over the X transport: a key forwarded and sent back is typed, one the server keeps is taken, its on-the-spot preedit composes in the field, and a server that goes, or sends what no message reads as, leaves keys typed; it ran against a stand-in XIM server on Xvfb (`text::linux::x11::xim::tests`, 2026-11-02), never with a real XIM server. XIM has no surrounding text, purpose or deletion, and a server offering only the root-window style draws its preedit in its own window. **Still missing on it:** handing the clipboard to a clipboard manager on exit, which comes with the host's later parts; a run on a desktop X server with a touchscreen, a tablet and a touchpad.
- The X11 host's pen, touch, smooth scrolling, touchpad pinch (XInput 2.4, which Xvfb announces), a grab's cancel mid-press and a device unplugged and plugged back in are tested only synthetically: their XInput 2 events are built by the decoder's tests and the conformance table, never produced by a server, since Xvfb has no touch screen, tablet or touchpad and XTest drives only the core pointer and keyboard. What runs on Xvfb is a master pointer added and removed (`a_master_pointer_comes_and_goes_with_the_hierarchy`), a burst of XTest motions delivered as one move (`a_burst_of_motion_is_one_move_through_it`), and a real window through the backend conformance table (`the_x11_window_input_conforms`): XTest's pointer for the contact rows, a master pointer the server adds for a named device, the focus taken away for the platform's cancel and the menu keys, with the rows XTest cannot drive (touch, pen, pinch, a step's own stamp, a position that is not finite) and the input method's rows listed there with what each reports and why. A touchpad swipe (XInput 2.4) is held by its decoder alone too, and XInput has no hold.
- The native Wayland host has its foundation (`WaylandPlatform`): the loop, `xdg-shell` windows with the snapshot and commands, displays, preferences, lifecycle and AT-SPI, run against a headless Weston. Its windows ask the compositor for their frame (`xdg-decoration`), draw at a fractional scale (`wp_fractional_scale_v1`), are given no frame while suspended, and export themselves for each portal request that names them (`xdg-foreign` v2, ADR-0365); the AT-SPI bridge follows the compositor's activation. A window moved between two outputs of one scale names the display it moved to, run 2026-10-28 on Weston 13 with two outputs (X11 backend on Xvfb). Weston offers none of `xdg-decoration`, `wp_fractional_scale_v1` and `xdg-foreign`; the three ran on a headless sway 1.9 at scale 1.5, 2026-10-28 (WSL Ubuntu 24.04): sway honoured a floating window's frame request and overruled a tiled one's, the buffer was drawn at 1.5, and a second client imported the export and saw it revoked (since then the export lives for one request, not the window's life; the scripted compositor runs that in CI, and sway has not run it again). Which compositor runs which of these cases in CI is in [testing](testing.md#which-compositor-runs-which-wayland-case), and what none runs is below. A tiled window takes no `SetSize`, as the tiling holds its size. Its windows ask to be activated with an `xdg-activation` token, which names the last key, button, touch or keyboard focus the seats report ([Activation ignores the OS focus rules](#activation-ignores-the-os-focus-rules)). Its seats deliver input: keyboard through XKB (layout, compose and client-side repeat, read through the keyboard the X11 host shares), pointer and wheel, touch, pens (`tablet-v2`), pinches, swipes and holds (`pointer-gestures`) and cursors (`cursor-shape`); the cursor, a click, a wheel notch and a key ran from a Weston seat, while touch, pens, pinches, swipes and holds have run through their translation tests only, with no device, and no cursor shape has run: Weston 13 has no `cursor-shape`, so the cursor ran from the cursor theme (`XCURSOR_THEME`, `XCURSOR_SIZE`), the fallback for such compositors. A tablet pad's buttons, rings and strips are not read. Where the compositor draws no frame, the window draws its own ([No custom title bar, popups or owned windows](#no-custom-title-bar-popups-or-owned-windows)). Its text input serves the focused field to the input method through each seat's `zwp_text_input_v3`: preedit, commit and deletion around the caret reached the field's store and the field's text reached the input method, run 2026-10-31 under sway 1.9 with an input method of the test's own (`wayland_text_input`), never with IBus, Fcitx or a desktop compositor; a compositor without `zwp_text_input_v3` gives its windows no text input and says so in a warning, with no fallback to another input method path. It takes drops on its windows and starts drag sessions from them ([No native drag and drop](#no-native-drag-and-drop)). Missing there: a run under a desktop compositor (GNOME, KDE, Hyprland).
- No CI compositor runs every Wayland window case. `a_window_moved_to_another_output_names_its_display` needs two outputs and a compositor that returns a window to the output it left: Weston on its X11 backend with `--output-count=2` does (run 2026-10-28), sway leaves the window on the output it went fullscreen on, and CI starts neither for it. The window conformance kit and `a_window_maximized_before_fullscreen_returns_to_normal` run under Weston only: sway 1.9 tiles and offers `xdg_wm_base` 2 with no `wm_capabilities`, so it carries out no `SetMode(Maximized)` and the window cannot know in advance. Adapting those cases to a tiling compositor is the owner's decision.
- Under sway 1.9 the window conformance kit fails `presentation_is_reported_exactly_when_claimed`: sway answers each `wp_presentation_feedback` with `presented` (refresh 0) about 12 ms after it is asked, and the frame request after the shown frames carries no presentation report (traced 2026-11-15, WSL Ubuntu 24.04). Weston passes the case.
- A Wayland window opened with `visible: false` cannot be hidden: Wayland has no hide for a toplevel, so it stays unshown only until it draws its first frame, and no command shows or hides it later (`hides`/`shows` are `Unavailable`).
- Under Hyprland (Omarchy's compositor) the host takes the decoration the compositor chooses through `zxdg_decoration_manager_v1` (no title bar of its own), presents an alpha surface so the compositor's blur applies, and scales through `wp_fractional_scale_v1` and `wp_viewporter`. The native Wayland host does the decoration and the scale (not run under Hyprland); the alpha surface does not exist.

### Clipboard is broken on two environments

> **Environments:** Android, Web; macOS and iOS for an item provided lazily; all for rich · **Who it hurts:** Every app with copy and paste · **Parity:** [Clipboard](platform-parity.md#clipboard-and-drag-and-drop)

- No rich formats: the clipboard reads and writes plain text until a widget needs more, and the shape of that read is reserved by ADR-0312 §7 ([Accepted ADR sections not built yet](#accepted-adr-sections-not-built-yet)).
- Android reads and writes the system `ClipboardManager` through JNI; type-checked, no device run yet.
- The native X11 host owns and reads the `CLIPBOARD` selection on a connection of its own, run between two of its clipboards on Xvfb (2026-10-30); what it owns is gone when the application exits, as it hands nothing to a clipboard manager yet. A connection the clipboard thread loses, or breaks because a write sent nothing for two seconds, ends the clipboard for the rest of the process: its handles answer `Gone`, and nothing connects again.
- The X11 clipboard caps a write at two seconds plus its size at 16 KiB/s, sized from the first call to the socket and kept until a call sends all it was given. A call that cannot send all keeps that cap over the calls after it, which can carry the rest of a step's buffered answers, so on a slow link a step's writes can break the connection though they keep that rate overall; the cap would follow every byte given to the socket.
- The native Wayland host reads and writes its seats' selection through `wl_data_device`, run between two clients of Weston 13 (2026-10-30), and its primary selection through `zwp_primary_selection_device_manager_v1`, run between two clients of sway 1.9 (2026-10-30); `EditableText` and `SelectionArea` claim it for their selection and a middle press in a field pastes it, checked on the headless host, not between two applications.
- The Web reads the system clipboard through `navigator.clipboard` asynchronously, falling back to its own writes where the browser refuses; no browser run yet.
- AppKit and UIKit read the clipboard on the owner thread: a pasteboard item another application provides only when asked (`NSPasteboardItemDataProvider`, a lazily loaded `NSItemProvider`) holds the owner thread while that application answers. Windows reads on a clipboard thread of its own (ADR-0337 §3); these two hosts need the same move, and a run that measures the wait first, which needs a Mac. Android reads the item's own text and no content provider ([rule](../crates/flui-native/ARCHITECTURE.md#another-applications-content-is-read-off-the-owner-thread-its-size-first)), so a clip that is a URI or an intent pastes nothing.

### The OS shell services exist on Windows and macOS, and partly on iOS, Linux, Android and the Web

> **Environments:** iOS for folder dialogs and the icon's badge; Linux for the message box, the share sheet and the system information; Android for folder dialogs; macOS, iOS and Android runs owed · **Who it hurts:** Every document app; any app with a link · **Parity:** [System services](platform-parity.md#system-services)

- The cross-platform surface is `flui_platform::launch` (open a URI or a file, reveal, trash) and `flui-system`'s file dialogs and message box (modal to the widget's window, one dialog at a time), share sheet, autostart, global shortcuts, the launcher entry's progress and count, the user's folders, the jump list and the system information, behind the facade's `system` feature ([ADR-0154](adr/ADR-0154-capability-crates.md) §11); one contract per service, which every host's provider answers. The launch policy (the schemes a caller allows, local paths, no program opened) and the filters' meaning are the seam's, for every host ([ADR-0360](adr/ADR-0360-a-dialog-filter-means-one-thing-on-every-host-and-a-launch-names-the-schemes-it-allows.md)). The handle holds every pick's name to a request whose filters name extensions and file names only (`NotInFilter` otherwise), and a request that offers a filter of every file admits every pick ([ADR-0374](adr/ADR-0374-a-dialog-filter-may-name-a-file-exactly-or-admit-every-file.md)). A file named by nothing but a dot and a word (`.png`, `.env`) is one no extension matches, though a Windows or portal `*.png` pattern shows it, so picking it under an extension filter still refuses the answer; a filter that means such a file names it (`FileFilter::with_file_name(".env")`). Where the hosts differ on a request: a folder to open in that is gone is left out on every host, but a folder Windows' shell cannot name for another reason fails the request there and is a hint the other hosts may not use; hidden files are forced on Windows and macOS only, since the portal's chooser, iOS's picker and a browser's picker have no option for them; a message box whose buttons are labelled is refused on Windows (`NotYetOnThisHost`), where `MessageBoxW` cannot label a button and `TaskDialogIndirect` would, in a process that loaded the version 6 common controls. A save's contents replace the chosen file through a new file beside it, made with the replaced file's mode on Unix but not its owner, its access control list or its extended attributes, and on Windows not its explicit access control list or its alternate streams (`ReplaceFileW` would); where the file system refuses a new file beside the chosen one by design (a sandbox's document folder, a read-only folder, another device, a sticky folder) the contents are written into it, emptying it first, so a write that fails midway or a process killed during it leaves it cut short; any other failure leaves it whole. In the document portal's folder the portal's provider answers the granted name as it is, without the filter's extension a typed name would get elsewhere. Whether the keyboard focus is back on the widget that held it once a system dialog closes has not been run on any host. One conformance table runs every service against the scripted doubles and the platform's own providers (`every_provider_keeps_the_system_services_contract`).

The launcher opens each file on the portal's thread and judges the descriptor it hands on (its resolved name, an executable regular file). It opens whatever the path names before it judges, a named pipe or a device included and without `O_NOCTTY`, and hands a pipe's descriptor to the portal, where macOS examines the path first and refuses anything but a regular file or a folder unopened. The portal's filters send each extension in lower and in upper case (`*.png`, `*.PNG`), so a file named in mixed case (`Photo.Png`) on a case-sensitive file system is not shown, where Windows and macOS show it (ADR-0360 §4); a file name is sent as written and in both cases the same way. A save's typed name with no extension is completed by the provider after the portal answered, from the filter the portal reports as selected, so a backend that reports none leaves the name as typed, and so does a completed name a file already has, which the portal's dialog never asked the user about, and a file in the document portal's folder, where the portal granted the name it answered and no other. An application with no id has no launcher entry, and the background portal refuses it autostart outside a sandbox. No portal shows a message box or a share sheet: both answer `NotOnThisPlatform`, and the system information answers `NotYetOnThisHost`.
- **macOS** provides every service but the jump list (`flui-system`'s `macos` module, its rules in [its `ARCHITECTURE.md`](../crates/flui-system/ARCHITECTURE.md#macos-macos)): sheets on the widget's window, the launcher off the main thread judging the opened file with Launch Services, the login item, Carbon's hot keys, the Dock tile. Each provider's rules ran as a model on Windows and Linux; the AppKit calls are type-checked for macOS by CI, and nothing ran on a Mac: the owed runs are the rows' notes in the parity table. - **The Web** (`flui-system`'s `web` module) launches URIs, opens and saves files, picks a folder, shows a message box (a modal `<dialog>` beside the canvas, the buttons the request does not label labelled in English; `showModal` makes the whole document inert, so a box is modal to the page, every canvas window of it, rather than to its window as the contract says, and two windows' boxes stack) and shares (the Web Share API, where the browser has it) through the browser, tested in headless Chrome without a picker, a window or a share sheet; Chrome, Firefox and Safari runs with a real gesture are owed, as the parity rows say. A picked folder is handed over as its name and the files under it at their paths (`PickedForm::Folder`), read whole into memory within the request's `max_entries` and `max_bytes`: an application gets no handle to read a large folder piece by piece or to write into it, a folder that holds no file leaves no trace (through a file input, a picked folder with no file at all is answered as a cancel), a browser's chooser takes one folder whatever the request allows, and a file under it whose name holds a backslash refuses the answer, and a file's place is its names as the browser gave them (`FolderPath`), not a path of the host, so an application that writes the files to disk maps the names Windows reads its own way (`NUL`, `C:`, a trailing dot) itself. A page has no paths to open, reveal or trash, and no jump list or system information to report (`NotOnThisPlatform`). a document whose provider shows a name without the extension is refused by a request whose filters name extensions only; a save's typed name gets the first filter's extension only where Android maps that extension to a type and the provider adds it, and the answer names the document as its provider did; a picker whose dialog was dropped is finished only while FLUI runs, so one dropped under a full-screen picker goes when FLUI is shown again ([a stopped Activity runs no owner jobs](#a-stopped-android-activity-runs-no-owner-jobs)); a content provider that ignores a cancellation holds a worker's place until it answers (four per runtime); a link opens only in an activity that declares itself `BROWSABLE`; a file a view or a share handed over is served to its grantee for `FluiDocuments.OFFER_LIFETIME_MS` (or withdrawn at once when the start failed), so a grantee that reopens it later is refused, and a share whose chooser the user dismissed holds its offers that long, since Android reports no dismissal; while `FluiDocuments.MAX_OFFERED` offers are served a further view or share of a file answers `Failed(Os(EMFILE))`; a read the provider holds blocked inside one chunk keeps a worker after its dialog was let go; and the user's folders are named whether or not the application may read them on this Android version.

### No native drag and drop

> **Environments:** all · **Who it hurts:** Document, media and file-manager apps · **Parity:** [Clipboard and drag and drop](platform-parity.md#clipboard-and-drag-and-drop)

- The core runs: in-window sessions, sessions that reach the other windows of their runtime on the source's capture where the host places its windows, escalation to an OS session, identity and delivery to receivers in `flui-runtime`, exercised headless (ADR-0211). The `Draggable` and `DropTarget` widgets run on it headless, with the cursor, Escape and the keyboard and assistive cut, copy and paste.
- Windows has OLE as both target and source (`IDropTarget` per window, `DoDragDrop` started on the owner window's next turn, frames for every window while its loop rests), run only within one process (`ole_drag_and_drop_on_real_windows`), never with Explorer, another app, a held mouse button, pen or touch.
- The Web takes and starts HTML drags (a drag starts only from a press the runtime lifted before the browser's threshold), run in headless Chrome with constructed events.
- Android takes and starts drags on `FluiView` (ADR-0348): on a Galaxy S21 a drag the probe started dropped its text on its own window, and one crossed into Chrome, which declined it; no drag from or into another app has completed. A drop is read lazily from the clip the view holds, under each request's limits; that read is type-checked and its model run on Linux, not yet run on a device. A request for a URI's bytes gets five seconds from when it is asked for, its wait for a place included, as on Wayland and X11: past them it answers `TimedOut` and a cancel worker of the transport's has the view cancel its open and close its stream, keeping its place until its thread ends; a content provider that ignores the cancellation while the URI is still being opened keeps that place for as long as it blocks. Whether the close unblocks a read on a device has not been run. Requests past the four places wait in a queue of 64 and past it are refused `Busy`; the Wayland and X11 targets bound their running fetches but not the requests waiting for them.
- The native X11 host takes XDND drops (version 5) on its windows: types become representations (text once, HTML, every media type), each position is answered from the feedback the target cached, a refused drop finishes unaccepted, a source whose window goes mid-drag (it crashes or is killed) ends the drag as if it left and leaves a dropped offer answering `SourceGone`, and a fetch converts `XdndSelection` on the owner thread, `INCR` included, held to its limit and timed out. Run on Xvfb with a source on another connection (2026-10-30, `drag::linux::x11::tests`), never from a file manager or a browser.
- The native X11 host starts XDND drag sessions from its windows when a drag leaves them with a button held: it owns `XdndSelection`, finds the `XdndAware` window under the pointer, sends one position at a time, drops on a target that accepted and leaves one that refused or on Escape, and serves the session's representations from its provider, a payload past one property in `INCR` chunks, at most four at once, each let go of when its requestor stalls for five seconds or is destroyed. Still owed: `XdndProxy` and `XdndActionAsk`. Run on Xvfb with synthetic pointer events and a target on another connection (2026-10-31; `INCR` 2026-11-10, `drag::linux::x11::tests`), never into a file manager or a browser.
- The native Wayland host takes drops on its windows through each seat's `wl_data_device` (up to v3): types become representations (text once, HTML, every media type), each motion is answered from the feedback the target cached, with the action a v3 offer asks for, a refused drop cancels its source, and a fetch reads the offer's pipe off the owner thread, held to its limit and five seconds, the offer finished with the action once the target concludes. Run 2026-11-03 under sway 1.9 with a source of the test's own (`wayland_drag`), never from a file manager or a browser, nor under a desktop compositor.
- The native Wayland host starts drag sessions from its windows: a session starts from a press the window holds, under the serial of the pointer grab it began, with a data source of its own offering each representation under the type names it is read as and the session's actions; the source's `send` is served from the session's provider and written from a thread of its own, and the session ends dropped with the action the compositor chose once the target finishes, or cancelled. A session started under a grab whose release the compositor already had ends cancelled, by the compositor (sway, Weston) or by the release reaching the window. Run 2026-11-03 under sway 1.9 into a target of the test's own (`wayland_drag`) and on Weston 13 (`wayland_input`), never into a file manager or a browser, nor under a desktop compositor; no drag icon is drawn.
- An OS session names the press its drag began in (`OsDragRequest::press`), minted by the host's contact registry. Windows resolves the contact by it and refuses a press the window no longer holds; the headless platform's drag source refuses such a press too, from the presses its window's injected input opened. The scripted double of `flui-testing` (`HeadlessOsDrags`) does not: its windows receive no input (the agent hands it to the runtime), so it holds no presses to check against. Wayland (the grab now held), X11 (the buttons now held) and Android (the view's next start) do not read it: they start from the press the window holds when the host enters the session, which is the drag's own because the drag owner drops a session whose press was released before the host entered it. A release the OS has queued but the window has not read yet is not seen by either. A press id is unique within the contact registry that minted it, one per window on Windows: an id from another window could name a live press of this one. No path hands one window's press to another window's drag today; a process-wide mint closes it if one appears.
- **No drag image.** An OS session shows the platform's default icon, a fixed shadow (Android), or none (Wayland). Win32's `IDragSourceHelper`, AppKit's `NSDraggingItem`, `UIDragPreview`, Android's `DragShadowBuilder` and `wl_data_device.start_drag`'s icon surface each take an image and a hotspot; `OsDragRequest` carries none, because nothing produces one: the drag's feedback is a view in the window's overlay, and the engine has no snapshot of a view into an image the owner thread could hand the OS.
- **A source that goes mid-drag** (it crashes, or is killed) ends the drag on X11, which hears its window's end, and on Wayland, whose compositor sends `leave`. Windows has nothing that hears it: an OLE source that dies without `DragLeave` would leave the window's `IDropTarget` hovering until the next drag, which no run has shown or refuted. On Wayland a dropped offer whose source went reads as an empty answer, which the protocol does not tell apart from one the source wrote empty. AppKit takes no drops yet.
- **Still missing:** `NSDraggingDestination`, and every other native drag source and target.
- Planned in the [interaction spec](plans/specs/flui-interaction/completeness/tasks.md) (ADR-0211; T28–T31, T35, T37 and the per-OS tickets).

### An OS drop on a committed window can land on a receiver the OS did not ask

> **Environments:** all · **Who it hurts:** Apps whose drop targets spring-load or autoscroll under a resting pointer · **Parity:** [Clipboard and drag and drop](platform-parity.md#clipboard-and-drag-and-drop)

- The OS resolves a drop from the answer the window cached for the last move, and a committed window's drop then hovers the drop's position once more before it lands (ADR-0211 §16). When the tree under a resting pointer changes with no hover to see it (a spring-loaded folder opens, an OS drag's autoscroll moves content: only an in-window session hit-tests again after an autoscroll frame), that hover can leave the receiver that answered and enter another. The drop then lands on a receiver whose answer the OS never took, or on none while the source was told it was taken, and `DropTracker::finish` does not check the drop's action against the receiver's answer.
- **Missing:** an OS drag's hover hit-tests again after a frame that changed the tree under it, and a drop lands on the receiver whose answer the OS took, with the action that receiver answered.

### Window control has run only on Windows, an X11 test server and the AppKit conformance kit

> **Environments:** desktop · **Who it hurts:** Every desktop app · **Parity:** [Windows](platform-parity.md#windows)

- **Runs:** title, mode, fullscreen, position, size and constraint commands with a state readback ship on every desktop host ([ADR-0237](adr/ADR-0237-window-state-and-host-notices.md)). A position is a point of the display it names ([ADR-0364](adr/ADR-0364-a-window-position-names-its-display-and-commands-carry-checked-geometry.md)); its conversion through two monitors of different DPI has run only as a pure table on Windows and X11, never on two real monitors, and a monitor unplugged under a window has not run on any host ([parity](platform-parity.md#windows)).
- **macOS:** the AppKit window conformance kit passes on an M1, macOS 27.0, 2026-10-27 (nextest flui-native 233/233); the fixture after review: appkit_window 3/3, nextest flui-native 237/237, 2026-10-27. A hand run on the same Mac, 2026-10-28, one display: every command and opening option, a title-bar drag (the position follows, y grows downward, the top stops under the menu bar at y = 30), the green button (full screen) and Option-click (zoom and back), the yellow button, a Dock click (`reopen`, then `Show` brings the window back), a corner resize held to the constraints, the title-bar close of one of two windows, a borderless window taking keys, a quit Apple Event ([#1736](https://github.com/vanyastaff/flui/issues/1736)). A minimized window read `visible: false` and `SetSize` went below the minimum; both are fixed. Still owed: a second display; sleep, lock and memory-pressure notices; session end.
  - **A window at its maximum size reads `Maximized`.** AppKit's `isZoomed` holds for any frame equal to the standard frame, which the window's maximum size bounds, so a window resized by hand or by `SetSize` to its constraints' maximum (900×700 on a 3440×1320 usable area) publishes `Maximized` with a `normal_geometry`, though it does not fill the usable area. Win32's `IsZoomed` stays false for a window dragged to its maximum. Telling a zoom from a frame that equals the standard one needs a decision on what the backend tracks.
  - **`normal_geometry` after a macOS tile is stale.** Dragging a window to the top edge fills the screen through the system's tiling, which no delegate method reports; the window reads `Maximized` with the `normal_geometry` recorded before its last move, while AppKit returns it to where it was dragged from.
- The native X11 host's window passes the window conformance under openbox on Xvfb (2026-10-27), the snapshot compared with what the server reads back; not yet under a desktop's window manager or on a HiDPI server.
- Neither Linux protocol lets a client read the title shown back, so the snapshot holds the one last set.
- Wayland never reports minimized.
- **Occlusion.** Every host keeps the window's show state (`visible`), its minimized mode and its occlusion (`occluded`) apart, and a minimized window stays shown; the conformance checks that without a readback of the host's own. A covering by other windows is told where the window's `reports_occlusion` says so (ADR-0357; the [parity row](platform-parity.md) lists each host); elsewhere a covered window keeps its frames, and its surface withholding them past the budget is reported once (`surface_withholds_frames`). Open:
  - **Win32 tracks no covering** (`reports_occlusion` is `NOT_YET_ON_THIS_HOST`), so a covered window keeps drawing frames nobody sees. A tracker on the owner thread was built and withdrawn (ADR-0357 §2): a window its own program raised over the others (`SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE|SWP_NOMOVE|SWP_NOSIZE)`) still read covered 3 s later, no subscribed WinEvent having fired; it counted `WS_EX_TOOLWINDOW` and per-pixel transparent `WS_EX_NOREDIRECTIONBITMAP` windows as covering and ignored a capture in progress, so a visible window drew nothing and lost its pointer sequences; and it woke the owner for every show or hide of any window of any process. A correct one runs off the owner thread, as Chromium's `NativeWindowOcclusionTrackerWin` does, excludes what covers nothing case by case (tool windows, per-pixel transparent DirectComposition windows, cloaked and minimized windows, a capture in progress), measures every rectangle in one pixel space at the monitors' DPI, follows its own windows' moves, and reports a change to the owner as a posted fact. A session that loses its display (a remote client disconnecting, another session taking the console) hides the windows as a lock does; it has run with the session messages sent by hand, not in a remote session ([parity](platform-parity.md#windows)).
  - **The frame a covered window owes its surface** (`flui-runtime`'s `ARCHITECTURE.md`): on AppKit, the one host that both tells a covering and keeps a covered window's last frame, a covered window draws one frame once it has drawn nothing for a quiet period with work waiting, so its uncovering shows the content of then; a locked or sleeping session owes nothing. It has run headless only. The frame is asked of the covered window itself, once per instant, and served for that window alone (ADR-0389); it stays due until it runs, however late its request is served. Not measured on a Mac: whether AppKit runs a display pass for a covered window when its timed request asks for one (a window it runs none for keeps the content of before the covering until it is uncovered, and no loop turns for it), and the displays sleeping or the screen saver starting without a lock, or a fast user switch, which reach the runtime as no notice, so a changing covered window draws one frame per quiet period then unless the surface refuses it ([parity](platform-parity.md)).

  What no run covers: on a desktop X11 window manager (the native X11 host hears a covering as `VisibilityNotify`, run with a full-screen window of another client over it on Xvfb, `a_covered_window_reads_occluded_and_shown`, which the conformance cannot read back), and on AppKit by hand; Cmd-H on macOS takes `isVisible` from the application's windows, so a hidden application reads as hidden, not occluded.
- Placement restore ran only on Windows; live resize is not audited.
- **A snapshot names its display twice.** `WindowState::display` and the display its outer
  position names are two public fields, kept equal only by `WindowState::successor`: a state
  built with `WindowState::new` and `with_display` can name one display in the field and
  another in the position. The field is the only fact a host without positions has (Wayland,
  Android, iOS, the web), so it cannot go; deriving it from the position where there is one
  makes `display` a method over a private field, a change to every reader of the snapshot
  (sixteen files across the hosts, the runtime and the engine), to `WindowStateParts` and to
  the native recording's window state.
- **The snapshot against the window system** (`window_conformance`'s `the_snapshot_agrees_with_the_window_system`: metrics, focus, activation, visibility and capabilities read back by the fixture's own means) ran on headless, on Win32, on AppKit (an M1, macOS 27.0, 2026-10-27), and on the native Linux hosts in CI, the X11 host under openbox on Xvfb and the Wayland host on Weston.
  - UIKit: not run, type-checked only, queued in [#1840](https://github.com/vanyastaff/flui/issues/1840).
  - Web: not run; the browser suite has no fixture that reads the canvas back apart from the window.
  - Android: not run; the conformance needs a device fixture.
- **A capability absent in one state reads as absent for good.** `CapabilityAbsence` names three
  reasons, none of them "not in this state" ([ADR-0254](adr/ADR-0254-window-contract.md) §6
  admits no reason worth trying again). AppKit reports a fixed-size window's `maximizes`, and a
  full-screen window's `hides` and `sets_frame`, as `NotOnThisPlatform`, and the capability comes
  back when the window's flags change; the X11 and Wayland hosts do the same for what the window
  manager or the compositor stops offering. A caller that reads the reason is told the platform
  never has it, where the window would take the command after a resize flag or a mode change.
- **A bare headless platform delivers a read's announcement with its next delivery.** A revision
  a read publishes, and the state cell's diagnostics, wait in the window's FIFO for an owner
  turn, which every host asks its loop for. A `HeadlessPlatform` driven without its owner loop
  (`OwnerPlatform`) has no loop to ask: what waits is delivered ahead of the window's next
  delivery, and never when none comes.
- **Android cannot close its window:** `WindowCommand::Close`'s capability is `Absent` there (one native window, which the application does not finish), so a programmatic close answers `CloseRequestError::Refused`.
- **Scales still checked by hand:** every display, window and pointer-reading scale a host reads is a `DevicePixelRatio` built once where it enters (`display::scale`, `crates/flui-native/ARCHITECTURE.md`), and the native recording codec refuses a ratio no screen has on read (`CodecError::Ratio`). Two kinds of number keep their own finite-and-positive check, since neither is a device pixel ratio and neither is bounded by the range a screen can have: the zoom of a DirectManipulation transform (`input::assembly::touchpad`), which is a pinch; and the ratios the Web host measures between two boxes (`window::web` for the keyboard's occlusion, `accessibility::web::dom` for the canvas), which a CSS transform sets and which are zero or not a number for a collapsed box. Below the hosts, the rendering pipeline holds its device pixel ratio as a `DevicePixelRatio` (`PipelineOwner::set_device_pixel_ratio` and `device_pixel_ratio`), but hands the number on as an `f64` past it: the semantics owner and `MediaQueryData::device_pixel_ratio`; carrying the type through those is its own change.
- **A window larger than a renderer draws:** `MAX_SURFACE_EXTENT` (`flui-platform`) is the upper bound of a surface's side; the renderer enforces its device's own limit, which can be lower (8 192 on the GLES 3.0 and WebGL2 fallback adapters), so a window between that limit and the bound is still refused by the renderer. Win32, X11 and the headless host clamp a `SetSize`, an opening size and a size limit to the bound, by the hosts' one extent rule (`window::state::device_extent`, and `window::state::device_limits` for a limit), and the Wayland host lowers its buffer scale until the content fits it. AppKit's `SetSize`, which takes points, is not clamped, and a window the system itself makes larger (a resize by hand or a maximize across monitors on Win32, X11 and AppKit, an Android window, a page's canvas) publishes that size: the renderer then refuses the surface until the window is smaller, where the Wayland host would have drawn it at a lower scale.
- **A window asked for larger than the work area opens past it on Win32 and X11:** Win32 fits only a restored placement to the monitor's work area, and X11 leaves it to the window manager. The Wayland host holds the size a window opens at within the compositor's `configure_bounds` (`wayland_scripted::a_window_opens_within_the_compositors_bounds`, against the test's own compositor; a run under mutter or KWin is a row of the parity table). AppKit is not audited for it.
- **No close request on the Web and Android:** neither host ever asks a window handler's `close_requested` (a page's unload and an Activity's finish are not requests the application can refuse), so an application's close veto never runs there.

### A window system slower than the mode wait publishes its steps

> **Environments:** desktop · **Who it hurts:** Apps and placement records that read each snapshot of a window changing mode · **Parity:** [Windows](platform-parity.md#windows)

- A request that changes a window's mode and that the window system carries out in steps is published once on X11, Wayland and AppKit: the snapshot keeps the mode the window left while the window system answers (`WindowStateCell::expect_mode`; the rule is in crates/flui-native/ARCHITECTURE.md, "A mode change the window system answers in steps is published once"). The wait is bounded by `MODE_SETTLE` after a read finds the mode asked and by `MODE_ANSWER_LIMIT` overall, on AppKit by its animation limit while a transition animates.
- **Slower than the wait:** a window manager or compositor whose next step comes later than `MODE_SETTLE` after the window first reads the mode asked, or which takes longer than the wait overall (an animated maximize or fullscreen under mutter or KWin is the likely case), still publishes the mode in between. Only openbox on Xvfb and the test's own compositor have run.
- **Out of minimized:** a minimized window asked for maximized or fullscreen publishes the modes it passes through as it is shown again (openbox on Xvfb: normal, then maximized). The host holds no mode over them, because the only mode it could keep is minimized, and a snapshot never says minimized of a window on screen.
- **A window moved as it arrives:** a window the user moves within `MODE_SETTLE` of its arriving in normal mode from another mode names the rectangle it had before the change as `normal_geometry` until the wait ends, and its own from then on.
- **Missing:** a run under mutter, KWin and Weston measuring how long each takes between its steps; an end of the wait the window system states (a configure serial, `_NET_WM_SYNC_REQUEST`) where one exists, which would also end the wait of a window that arrived; a mode for the steps out of minimized that is neither minimized nor one the window has not reached.

### No custom title bar, popups or owned windows

> **Environments:** desktop · **Who it hurts:** Apps with modern chrome; every menu and dropdown · **Parity:** [Windows](platform-parity.md#windows)

- The contract names a title bar the application draws inside a frame the system keeps (`WindowFrame::AppTitleBar`, admitted where `WindowCapabilities::app_title_bar` is available). The headless host, Win32, macOS, the native X11 host (where the window manager lists `_NET_WM_MOVERESIZE`), the native Wayland host (where it can draw a frame of its own) take it.
- A window without the system's frame (`WindowFrame::None`) is dragged and resized from the regions it marks on Win32 alone.
- The contract has caption hit-testing: move, resize, caption-button and cut-out content regions, resolved in paint order by `chrome_hit` and honoured per kind (`InputCapabilities::input_region`, ADR-0286), and `flui-widgets` marks them (`WindowTitleBar`, `WindowCaptionButton`, `WindowResizeArea`, with buttons and fields in a bar cut out by themselves). Win32 answers `WM_NCHITTEST` from them (moving, resizing from a band along the top, `HTMAXBUTTON` for the snap layouts, the caption buttons' pointer messages delivered to the application's buttons) and drops the caption in `WM_NCCALCSIZE`; it is type-checked and not run yet, and whether the desktop window manager draws its own caption buttons through a transparent material over such a bar is unknown. On macOS the window keeps a transparent system title bar under full-size content: a left press on a move region drags the window (`performWindowDragWithEvent:`), a double-click does what `AppleActionOnDoubleClick` names, the system keeps the resize borders and the traffic lights, which the application hides or moves; it is type-checked and not run yet, and whether the system's title-bar view takes clicks meant for the content under it is unknown. The native X11 host has no decorations (`_MOTIF_WM_HINTS`) and answers each press itself: a move or a resize is a `_NET_WM_MOVERESIZE` request sent once the pointer grab is let go of, a double-click toggles `_NET_WM_STATE` maximized, and a secondary press stays the application's, since no request opens every window manager's menu; it ran under openbox on Xvfb with XTest (a drag on the bar moved the window, a drag on its right edge widened it, a double-click maximized it), and has not run under GNOME or KDE. The native Wayland host asks the compositor for no frame and keeps the resize margins of its own frame without its title bar: a press on the bar moves the window through `xdg_toplevel.move` with the press's serial once the pointer travels, a double-click maximizes it and a secondary press shows the compositor's window menu; it ran on Weston 13 with XTest (a drag on the bar moved the window, a drag on the corner margin resized it, a double-click maximized it), and has not run under GNOME, KDE or a compositor that insists on drawing the frame. No design package builds a title bar from the parts.
- Menus, tooltips and dropdowns can't leave the window.
- On Wayland, where the compositor draws no frame (GNOME, Weston) or leaves it to the client, the native host's window draws its own: a title bar with the title and the buttons `wm_capabilities` offers, margins it is resized from, moved and resized through `xdg_toplevel.move`/`resize` with the press's serial, and the compositor's window menu on a secondary press. It ran on Weston 13's desktop shell (X11 backend on Xvfb, XTest, 2026-10-28): the bar read back from the screen, a drag moved and a corner resized the window, the buttons maximized and closed it. **Still missing:** it is the host's own neutral frame, light or dark after the desktop (an application that wants its own title bar asks for `WindowFrame::AppTitleBar`, above); no touch or pen drags it; no shadow is drawn; the window menu, tiled edges and a fractional scale have not run (Weston 13 has no window menu or tiling, sway draws its own frames), nor has GNOME. Its title is shaped over the bundled faces and the host's, read by a scan of its own, which an application's font collection does not share yet.

### No native menus

> **Environments:** macOS, iPadOS; Windows · **Who it hurts:** Every macOS app · **Parity:** [Menus](platform-parity.md#menus)

- No macOS menu bar (no Quit or Edit menu), so the shortcuts its items carry do nothing: Ctrl-Cmd-F leaves a full-screen window full screen.
- No native context menus, no Dock menu or jump list.

### Lifecycle holes

> **Environments:** all · **Who it hurts:** Apps that save state or hold resources · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle)

- Session end is delivered on Windows (checked with sent messages), macOS, iOS, Android, the Web and Linux (there as a notification).
- The Web reports page freeze, context loss and page hide only against a fake page, not yet from Chrome.
- Sleep, wake and lock reach Windows, macOS and Linux (Linux checked only against a stand-in for logind), and memory pressure Windows, macOS, iOS, Android and Linux.
- A GPU device whose rebuild keeps failing is given up after about twelve seconds, or about ninety when its driver hangs every request (ADR-0267, ADR-0305 §8). On the desktop the application gets it back with `AppHandle::retry_render_device`; Android and iOS have no such entry, so a given-up window there stays blank until the platform takes its surface away and gives it back (the user leaves the application and returns), which has the owner probe for a device to replace the given-up one (ADR-0305 §8). No device loss has run on real hardware: the rows use the stand-in renderer. The web never gives the rebuild up: it builds a new context at each animation frame until one attaches, and with no `retry_render_device` on the page its application is not told of builds that keep failing.

### Links and files open everywhere, but no Windows package or Apple entitlement declares them

> **Environments:** Windows, Apple · **Who it hurts:** Apps installed from a package, apps opened from a universal link · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle)

- Every host reports what the system opens the application with, and `flui-app` routes it to the window's Router and to `Application::on_open_files` ([ADR-0339](adr/ADR-0339-an-opened-url-has-one-destination-decided-at-the-runner.md)). One instance keeps a later launch's links and files on Linux and Windows (ADR-0254 §4). What has run where, and the device runs still owed, are the rows of [App lifecycle](platform-parity.md#app-lifecycle).
- `flui build` makes no MSIX package, so a packaged Windows application declares no `uap:Protocol` or `uap:FileTypeAssociation`; an unpackaged run registers its schemes and file types itself ([ADR-0307 §4](#accepted-adr-sections-not-built-yet)).
- The Apple packagers sign nothing, so the `associated-domains` of the manifest reach no `com.apple.developer.associated-domains` entitlement and a universal link does not open the application ([ADR-0307 §4](#accepted-adr-sections-not-built-yet)).
- On X11 neither the first launch nor a forwarded one completes its startup notification, so a launcher that shows one waits for its own timeout.
- A Linux window carries the application id as its Wayland app id and X11 class, and the desktop entry `flui build linux` writes matches it (ADR-0351); no shell (GNOME, KDE) has matched one on a desktop yet, and Windows sets no AppUserModelID ([App identity](platform-parity.md#app-lifecycle)).

### A later launch is acknowledged before its link is routed

> **Environments:** Linux, Windows · **Who it hurts:** A user who opens a link the running application refuses · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle)

- A later launch of a single-instance application hands its links to the running instance, which answers it as taken once the application holds the launch, before the runner admits each link ([ADR-0339](adr/ADR-0339-an-opened-url-has-one-destination-decided-at-the-runner.md) §6). A link the runner then refuses (one the application does not declare, one for a window that closed) is only logged: the later process has exited believing its link was opened, and the user sees nothing.
- Telling it needs the hand-back to wait for the runner's answer and carry a refusal: a new answer in the Windows pipe frame and the Linux `org.freedesktop.Application` reply, and an `AppHandler::opened` that returns what became of each URL to the host. Until the hand-back carries it, a refusal reaches no host.

### Some exits of a window's installation have no test

> **Environments:** Headless · **Who it hurts:** Nobody at run time; a test of a window's installation exits · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle)

- An opened URL that enters a window before its installation commits is on loan to it, and every end of the installation but its commit returns the URL ([ADR-0339](adr/ADR-0339-an-opened-url-has-one-destination-decided-at-the-runner.md) §5). Tested: the GPU refusing the window's slot, through the headless kit (`a_link_whose_window_cannot_open_causes_one_attempt_and_is_refused`); a window closed after its installation was submitted during an owner turn and before it commits, in-crate on the runner's deferred publication (`a_link_into_a_window_closed_before_it_commits_is_refused`); a main window that fails before its UI runtime is built, so no loan exists, through the kit (`a_link_whose_window_fails_before_its_runtime_is_refused_after_one_attempt`); a link that arrives while the main window is opening for another reason (the application asked for it), bound to that opening and refused when it fails, through the kit (`a_link_that_finds_the_main_window_opening_is_refused_when_that_opening_fails`); the guard's commit, drop, drop while unwinding, drop under a borrow of the loop's state and a panic in its navigation, in its model.
- Not tested: a panic that escapes the window's UI runtime while `finish_install` opens a lent URL into it (`navigation_panicked`): no application code reaches it, since the URL is queued as owner work, whose panics the runtime contains, and the Router resolves it in a post-frame callback the runtime contains (`a_panic_in_the_navigation_of_a_link_that_reopens_the_main_window_is_contained_by_its_runtime`); the loan's side of it is tested in its model. Also not tested: a root that fails to attach, a cancelled installation (its `Installation` dropped unanswered), a logical or native publication refused in `commit_install`, and an initialization that ends other than ready. The headless kit installs and commits a window within one owner turn, and these failures have no injection point; an installation that drops its window takes the same exit as the tested ones (`InstallationWindow`'s drop).

### System preferences missing or never run

> **Environments:** all · **Who it hurts:** Users who rely on accessibility settings or another locale · **Parity:** [System preferences](platform-parity.md#system-preferences)

- Missing: text scale on the Web and on Linux desktops other than GNOME, and gesture timings.
- Accent colour and scroll-bar behaviour ([ADR-0359](adr/ADR-0359-system-preferences-carry-the-accent-colour-and-the-scroll-bar-behaviour.md)): Windows read both on Windows 11 but no run changed them live; Linux ran against a stand-in portal only; macOS is type-checked, its appearance-resolved accent and the light/dark notice included. The Web reports no accent: a browser that resists fingerprinting resolves the CSS `AccentColor` to a fixed colour a page cannot tell from the user's, and no run has shown which browsers resolve it truthfully. Android reports no accent: its dynamic colour is a set of tonal palettes, and the consumer that would read it is a Material dynamic colour scheme, not yet built; a Material application does not follow any host's accent yet. No host reads a track-click setting but macOS.
- A snapshot read fails value by value: on Windows a getter that fails keeps the value accepted before it and owes a bounded retry, on macOS a value AppKit cannot give is no observation, on Linux each portal key stands alone ([ADR-0359](adr/ADR-0359-system-preferences-carry-the-accent-colour-and-the-scroll-bar-behaviour.md) §5); iOS and the Web have no getter that fails. Android still fails its whole read when its one JNI batch fails or reports a negative gesture timeout, and retries it on the fixed interval of `preferences::read` rather than the bounded `Retries` schedule.
- Never run: regional formats ([ADR-0278](adr/ADR-0278-regional-formats-are-the-unicode-locale-extension-keys.md)). Every host reads them: Windows from Region settings, Linux from `LC_TIME`, `LC_MEASUREMENT` and GNOME's clock format, macOS and iOS from Foundation's locale and calendar, Android from its calendar, the 24-hour setting and Android 14's `fw` and `nu` keywords, and the Web from `Intl`. None has run on a device or in a browser. The Web reports only what its `Intl` defaults to, and Android reports no units, since Android 14's regional preferences offer a temperature unit rather than a measurement system. A date or time pattern the user typed (a custom Windows short date) is not carried, since its syntax is the host's own.
- Never run: every host reads contrast and the preferred languages, but macOS and iOS are type-checked only, the Web ran on Node rather than in a browser, and Linux ran against a stand-in portal rather than a desktop session.
- Windows text scale is applied linearly. WinUI scales larger text less by an undocumented curve, so large text grows more than in a WinUI control at the same setting.
- Gesture presets per platform and pointer kind, accessibility floors, per-display geometry and headless injection landed with the [interaction spec](plans/specs/flui-interaction/completeness/tasks.md) (ADR-0212).
- Layout direction, per-app language, and system fonts and fallback are separate rows, tracked by [Locale edge: layout direction, per-app language, system fonts and fallback](#locale-edge-layout-direction-per-app-language-system-fonts-and-fallback).

### Pointer and keyboard gaps

> **Environments:** various · **Who it hurts:** Pen, trackpad and iPad users · **Parity:** [Input](platform-parity.md#input)

- **Missing:** no pen on macOS or Linux; no iPad hardware keyboard; the iPad pointer (trackpad scroll, pinch, rotation, hover and the secondary button) is type-checked only, never run on an iPad; no cursors on mobile; keyboard layout read on Windows, Wayland and X11 only (not on macOS, iOS, Android or the Web).
- The keyboard layout has no reader above the host: Windows, X11 and Wayland read it and its changes into the core host's sealed input position, and the headless platform can switch it (`HeadlessInputDevices::set_keyboard_layout`), but `Platform` does not publish either until the menu feature brings their consumer, shortcut labels (ADR-0151 §9), so a layout change reaches no application.
- Windows: the precision-touchpad pan and pinch (DirectManipulation) have never run on a touchpad, and no injector reaches it, so its golden recording can only come from a `native-capture` run on one (injected touch, pen, mouse and wheel already record theirs through a manual Windows run).
- Android: touchpad pinch and two-finger scroll and its pen hover and tilt ran only from `uinput` devices through a manual Android run, with no hardware touchpad or stylus. Its widgets ran with `uinput` touches, `input` stylus and mouse events and hardware key events through a manual Android run, with no physical keyboard, key repeat or dead key.
- Web: the runner names the compile target (`TargetPlatform::Unknown`) as the tree's `PlatformConvention`, not the browser's OS, so a Safari tab on macOS follows the platform-neutral conventions: Control jumps by word and the clipboard and refresh chords use Control.
- A scroll says whether the platform reversed the device's direction (`ScrollEvent::inversion`) on macOS (`isDirectionInvertedFromDevice`), in WebKit (`webkitDirectionInvertedFromDevice`) and on the native Wayland host (`wl_pointer.axis_relative_direction`, seat version 9; translation test `a_scroll_carries_the_direction_the_compositor_reports`); none has run with natural scrolling switched on. Windows, X11, Android, iOS and the other browsers report no such flag, so their scrolls say `Unknown`. No widget reads it yet: the slider's wheel handling is its first consumer.
- A dead key carries its accent (`Key::Dead`) on Windows (`WM_DEADCHAR`; the Windows dead-key rows of `flui-native`'s contract tests), on X11 and Wayland (the dead keysym) and on Android (the key map, where a hardware dead key is also composed with the next key; pure tests only, no physical keyboard run). The DOM names no accent, so the Web reports `Key::Dead(None)`; macOS and iOS compose dead keys as the input method's marked text.
- Web: no precise-scroll phases, and its trackpad pinch (decoded from Control-held wheel and WebKit gesture events) ran only with constructed events in headless Chrome.
- The native Linux hosts' touch, pens, pinches, touchpad swipes and holds and smooth scrolling ran only through their translation tests, never on a session with a touchscreen, tablet or touchpad.
- Touchpad holds and swipes ([parity](platform-parity.md#input)): fingers resting on a touchpad (`TouchpadHold`, which stops a scrollable's fling and an interactive viewer's inertia; an `AnchoredDrag`'s settle to an anchor goes on) reach a window on Windows (a DirectManipulation viewport running before its slop), macOS (a scroll's `MayBegin`) and Wayland (`zwp_pointer_gesture_hold_v1`, gestures version 3), and a swipe of three fingers or more (`TouchpadSwipe`, a gesture for `SwipeGestureRecognizer`, never a scroll) on Wayland and X11 (XInput 2.4). The Wayland host's gesture objects run through the wire against the scripted compositor (`wayland_scripted`); the other hosts are held by their decoders alone, and no touchpad has run on any. Not delivered, by the platform: X11 has no hold; Windows keeps three- and four-finger swipes for the shell (reading them would mean the precision touchpad's raw HID reports); AppKit reports only a finished swipe direction (`swipeWithEvent:`); Android's navigation takes multi-finger swipes and reports no resting fingers; UIKit and the Web report neither. The backend conformance table has no hold or swipe rows yet: each host is held at its own seam.
- Pointer frames (`PlatformInput::PointerFrame`): only Windows touch and pen report them, read from the frame's own history and delivered once per frame id, and that path has run on synthetic data only (injected touches on a hosted Windows runner): no two-finger touch run on a Windows touch machine yet. The native Wayland host frames the touches each `wl_touch.frame` closes, as one pointer frame per surface (translation tests only, no touchscreen run). Android frames the fingers of one `ACTION_MOVE` (cross-checked in CI, no run on a device), and iOS (a touch set) still reports each contact on its own, as frames of one.
- A click into a macOS window that is not key moves the window from the move area of a title bar the application draws, is delivered marked `is_first_click` inside a `FirstClick` widget's box, and anywhere else only activates the window (`acceptsFirstMouse:`, the press model `input::apple::title_bar::first_mouse`); the gesture binding admits a marked press only when its hit path runs through a `FirstClick` box, and hands it only to that box's subtree, so a widget painted over the box does not receive it (the `first_click` rows of `flui-widgets`' `input_regions` table). Never run on a Mac. The `native-capture` journal records AppKit's readings before the view marks a press, so a journal replay delivers a first click unmarked; the input recording carries the mark. On Windows, X11 and Wayland FLUI delivers the activating click unmarked, by those desktops' convention (Win32's `WM_MOUSEACTIVATE` is left to its default, `MA_ACTIVATE`), so a `FirstClick` box changes nothing there.
- Pointer, scroll and pinch work is planned per OS in the [interaction spec](plans/specs/flui-interaction/completeness/tasks.md) (T36 DirectManipulation is implemented and awaits a touchpad run; T40–T44).

### The pointer grabs and the cursor images have run on no device

> **Environments:** desktop, Web; iOS, Android · **Who it hurts:** Canvas, CAD, 3D and video applications · **Parity:** [Input](platform-parity.md#input)

- Every host takes a `Cursor` (an icon, an image, or none) and the grab, level, resize-step and proportion commands where its window system has them, each capability naming why it is absent elsewhere ([ADR-0354](adr/ADR-0354-a-window-shows-the-cursor-its-region-asks-for-holds-the-pointer-only-while-focused-and-says-when-the-user-resizes-it.md); the tables are each host's `capabilities` and `crates/flui-native/src/window/capabilities.rs`). An application reaches the commands through `WindowHandle` and reads the grab and the level in the snapshot; a widget asks for any cursor through `MouseRegion::cursor`. UIKit locks an iPad's pointer from iPadOS 14 through its root controller's `prefersPointerLocked`, for a scene that fills its screen, and an Activity takes the mouse from API 26 through `FluiView`'s pointer capture; neither shows an image or hides the cursor (`cursor_image` is unavailable, and an iPad's pointer takes a `UIPointerStyle`, which this host does not set).
- A widget does not turn a locked pointer's `PointerEvent::RawMotion` into a callback of its own: it reaches the hit path's handlers and the global routes as a pointer event.
- **Not built:** the web reports a locked pointer's motion after the browser's acceleration, since `web-sys` offers no `unadjustedMovement` option. A native recording journals no raw input: a Win32 recording taken while the pointer was locked replays without its motion.
- **A Win32 lock does not rescale its point.** ADR-0354 §2 has a lock keep its point of the content when the window changes scale; the Win32 host keeps the point in device pixels (`Held::Locked`), so a window moved from a 200% display to a 100% one locks at the content's far corner, and the other way at a quarter of the way in. The entry closes when `WM_DPICHANGED` rescales the held point and `a_grab_is_held_while_focused_and_let_go_with_the_focus` checks the point across a scale change.
- **Not run on a device:** the Win32 lock with a physical mouse and a remote session's absolute reports; the AppKit lock and image cursor; the X11 lock and confine under a window manager (Xvfb does not hold XTest motion to a grab, so the tests check the grab is held, not where the pointer can go); Wayland's pointer constraints on GNOME and KDE (Weston only); the web's pointer lock in Chrome, Firefox and Safari; the iPad lock with a trackpad and a mouse (a mouse connected during a lock, two scenes, the sign and unit of `GCMouse`'s deltas); Android's pointer capture with a mouse (`onPointerCaptureChange` reaching `FluiView`, the relative motion reaching the native input queue, its unit). The rows are under [Input](platform-parity.md#input).
- The entry closes when each of the runs above has a parity row marked from a device run.

### Version floors and the GPU fallback not run on devices

### No presentation feedback

> **Environments:** iOS, Android, virtual displays · **Who it hurts:** Every animated app; every latency claim · **Parity:** [Displays and metrics](platform-parity.md#displays-and-metrics)

- Windows (DXGI frame statistics, run) and the native Wayland host (`wp_presentation_time`, run under Weston 13) report when each frame reached the screen, on the event timeline; a recording keeps the report with the frame's input, and no step of the frame reads it (ADR-0368). Headless injects one.
- macOS reports (run): the AppKit view is backed by its own `CAMetalLayer`, which wgpu draws into and whose `nextDrawable` adds `addPresentedHandler:` to each drawable; the display pass moved from `drawRect:` to `updateLayer`. On an M1, macOS 27.0, 100 Hz (2026-10-28): 29 reports for 30 presses of `counter`, the shown times a multiple of 9.999 ms apart, the handler 0.34–0.49 ms after the showing; the conformance row saw a report 13 ms before the next request. During a live resize Metal reports most drawables never shown (80 of 102); whether the window shows fewer frames there than with wgpu's own layer is not measured, and no one has looked at a resize by eye.
- A virtual display reports nothing (`NotOnThisDevice`): a Windows desktop driven only by the Microsoft Basic Render Driver (a Hyper-V machine such as a `windows-latest` runner) shows `SyncRefreshCount` 0 in every frame statistic, and a Mac that is a hypervisor's guest (a `macos-latest` runner, "Apple Virtual" display) gets `presentedTime` 0 for every drawable. Windows reads the adapters at startup; macOS reads `kern.hv_vmm_present`, a proxy, so a guest with a display that does report is still told it has none, and a virtual display on bare metal is not caught. The `Native` path is owed one run on real Windows and Mac hardware after this detection.
- iOS reports nothing (`NotYetOnThisHost`): a UIKit view whose layer class is a `CAMetalLayer` (FLUI's or the plain class) showed nothing on the iOS Simulator (iOS 27.1), while the same app with wgpu's sublayer draws; the simulator's drawables have no `addPresentedHandler:` either. A device run decides whether the layer class works there.
- Android reports nothing (`NotYetOnThisHost`): the time a frame was shown belongs to the Vulkan swap chain wgpu presents through, and wgpu reads none. The path left is wgpu reading `VK_GOOGLE_display_timing` (`vkGetPastPresentationTimingGOOGLE`) and handing it to the presenter as DXGI's statistics are handed over. The loop now runs its frames on the choreographer's callback (ADR-0269), and on API 33 its preferred frame timeline's `expectedPresentationTimeNanos` fills `FrameRequest::target_present`; that names when a frame is due on screen, never a report that it was shown. Type-checked only, not yet run on a device.
- The Web (a `requestAnimationFrame` timestamp is a frame's start) and X11 (the Present extension reports a completion to the GPU driver's connection) have no presentation time a toolkit can read, and their windows say so. A compositing X11 window manager that synchronises frames sends one in `_NET_WM_FRAME_TIMINGS`, which the X11 window does not read yet ([Live resize](#live-resize-is-unaudited-and-unscheduled)).
- Animations still tick on the vsync instant, never the presentation time (ADR-0347 decision 2). A presentation report names the frame it describes (ADR-0347 decision 6), but the frame telemetry does not yet match a report to the produced frame it names, so its input-to-present histogram still ends at the submit.

### No HDR, wide gamut or colour management

> **Environments:** all · **Who it hurts:** Photo, video and design apps; every app on an HDR display · **Parity:** [Displays and metrics](platform-parity.md#displays-and-metrics)

- The engine requests a surface colour capability per window (`AppConfig::surface_color`, [ADR-0256](adr/ADR-0256-surface-colour-is-requested-and-converted-at-presentation.md)) and converts to Display P3, scRGB, extended sRGB or HDR10 at presentation; no run on an HDR or P3 display backs it yet, and no Metal space has run.
- Every display carries its colour profile (`DisplayDescription::color`: `SurfaceColorSpace` and `Headroom`, or why there is none), read on Windows, macOS, iOS, Android, Wayland and the Web, and a profile change is a new snapshot revision; the engine sets a surface up for the colour of its window's display. Only an SDR Windows monitor has run; no HDR or P3 display, and the Apple, Android and Wayland reads are type-checked only.
- A profile change reconfigures the window's surface before its next frame (ADR-0256 §6, amended), but no host ran a real change: Windows, macOS and Wayland observe the change type-checked or synthetically only, iOS and Android re-read only on their other display events.
- X11 reads no colour (`_ICC_PROFILE` is not parsed). Windows has no broadcast for the SDR white level, so a moved slider is read at the next other display event. Android sets the window's `ColorMode` for the requested surface but does not listen to `Display.registerHdrSdrRatioChangedListener`: the listener needs a Java class in `FluiView`, so a moved HDR/SDR ratio is read only at the next configuration change or resume. The Web reports capability only and no headroom.
- Sources are still sRGB: images with a profile, video and HDR images enter the working space as sRGB values.

### Sandbox-aware file access is partial

> **Environments:** all desktop and mobile · **Who it hurts:** Every app distributed through a store or Flatpak · **Parity:** [System services](platform-parity.md#system-services)

- A pick reopened after a restart goes through `flui-system`'s grants ([ADR-0380](adr/ADR-0380-a-pick-carries-a-grant-that-outlasts-the-process-and-no-reacquired-path-is-one-the-sandbox-keeps-closed.md)): built on every host but the Web, run on a simulated sandbox and against the stand-in portal, and never in a sandboxed process; the owed runs are the parity row's note.
- Not built: a Windows process in an AppContainer (FLUI's window and dialogs are Win32's; the future-access list, `StorageApplicationPermissions.FutureAccessList`, is not used, so a path grant there answers `Revoked` when the file system refuses the path), and a browser's lasting access, a `FileSystemHandle` kept in IndexedDB as an object, not bytes (`NotYetOnThisHost`). A save carries no grant, and its location is reopened through an open dialog; an iOS or Android folder dialog still answers `NotYetOnThisHost`. Android trims the persisted permissions of an application to a bounded number, the oldest first, and nothing releases one the application no longer needs.
- A Flatpak's sandbox is read from its `/.flatpak-info`, as Flatpak wrote it (flattened, with no entry that takes one back): its own folders, its private `/tmp` (Flatpak unsets `TMPDIR`), the document portal's and its manifest's `filesystems`. An `xdg-*` entry is resolved through the `user-dirs.dirs` the sandbox sees, and one it does not configure is not reached, as Flatpak ignores it; on a host whose file the sandbox does not see, a folder Flatpak does expose is then refused. A `host-os` entry is read as `/run/host` and `host-etc` as `/run/host/etc`, where Flatpak mounts them. A path the manifest hides with `--nofilesystem` under an exposed folder is a tmpfs the description does not show: a grant to it is not refused by the handle, and resolves `Missing` where the hidden file is not there, rather than `Revoked`. Snap's confinement is not read: a Snap is treated as no sandbox.
- The macOS bookmark needs the `com.apple.security.files.bookmarks.app-scope` entitlement, which `flui build` does not write: without it a sandboxed pick carries no grant.
- A packaged Windows application's store is copied into the package's folders by one instance at a time, and another waits for the lock with no deadline. On FLUI's default pools the host runs the store's calls on the IO runtime's blocking threads, so the wait holds none of the IO workers HTTP, image loads and background work share, and one find serves every call that arrives meanwhile. But every storage answer of that instance waits while the lock's holder keeps it: a holder that stalls without crashing (the system releases a crashed one's lock) holds back that instance's storage until it lets go ([ADR-0380 §4](adr/ADR-0380-a-pick-carries-a-grant-that-outlasts-the-process-and-no-reacquired-path-is-one-the-sandbox-keeps-closed.md)). An embedder's own IO pool (`ExecutionServices::with_host`) has no blocking threads: the calls run in its IO task, so there a stalled holder also holds that IO task, and through it the embedder's pool.
- The manifests a sandbox reads are part of the same gap; which of them `flui build` generates is under [Distribution is unaudited](#distribution-is-unaudited). Tauri's autostart plugin shows the cost: it writes a launcher path that cannot run outside the Flatpak sandbox ([tauri-apps/plugins-workspace#3166](https://github.com/tauri-apps/plugins-workspace/issues/3166)).

### Secure text entry and concealed clipboard entries are partial

> **Environments:** all · **Who it hurts:** Every sign-in form; password managers · **Parity:** [Text input](platform-parity.md#text-input), [Clipboard and drag and drop](platform-parity.md#clipboard-and-drag-and-drop)

- A protected field keeps its keystrokes from other processes and input-method learning on Windows (the TSF password input scope), Android (the password variation with `IME_FLAG_NO_PERSONALIZED_LEARNING`), the Web and macOS (secure event input held while it has focus in the key window, type-checked, not run on a Mac). iOS sets `isSecureTextEntry` from the focused field's store status (type-checked, not run on a device). On Linux the native Wayland host sends `text-input-v3` the content type of the store's status, a protected field as the password purpose with the hidden-text and sensitive-data hints, and shows it no surrounding text (`a_protected_field_shows_the_input_method_no_text`, unit-tested over the wire seam); the native X11 host sends IBus and Fcitx5 the same purpose and hints and no surrounding text for a protected field, unit-tested for the mapping (`a_field_states_its_purpose_in_each_protocol`).
- A clipboard write can be concealed (`ClipboardWrite::concealed`, ADR-0152 §6), and every host answers what it does with one as a `Concealment`. Windows, macOS and iOS keep it out of the system's history and sync (Windows writes its three formats, read back on Windows 11; macOS and iOS type-checked, not run; no run watched a history skip the entry); X11, Wayland and Android only mark it, and only a clipboard manager or keyboard that reads the mark honours it (on Weston up to 14 a concealed write made under the same input as an ordinary one is not put on the clipboard, with a warning: that compositor keeps the earlier, unmarked source); the Web has no mark, so a concealed write there is an ordinary one, and the scenario `a_concealed_write_stays_out_of_history` fails on it as this gap.
- Android's `ClipDescription.EXTRA_IS_SENSITIVE` (API 33) is only a rendering hint, so the Android cell of the concealed-clipboard row can be at most partial by design; below API 24 a clip carries no extras at all.
- An expiring concealed write (`ClipboardWrite::expires_after`, ADR-0363) clears itself only where the host can tell its own entry: the Web has no conditional clear, so its entry stays until something replaces it (`ExpiryClearing::Unavailable`); iOS and Android hear no session lock, so their entries clear at their time alone; an Android application without input focus cannot see the clipboard, so a time that comes in the background clears the entry only when the application is next in front (`ExpiryClearing::AtTimeOrInFront`), and an application never brought back leaves it to the system; macOS, iOS and Android check and clear in two calls, so a copy another application makes between them is cleared too. A clipboard manager, or a compositor's own clipboard (Weston's), that copied the entry while it was offered keeps its copy. No session lock has cleared a real entry on any host yet (the owed runs are in the [parity row](platform-parity.md#clipboard-and-drag-and-drop)).
- Platform-edge diagnostics have no redaction check: protected-field text, clipboard payloads and URLs with tokens must never reach the `tracing` targets or the `native-capture` journal, which carries input method and text store text (redacted unless a recording keeps it, with a test for each row family that carries text) but has no check across all of it (the [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) lists them under "Data to exclude").

### Input latency modes and high-rate sampling are partial

> **Environments:** all but Windows and the Web · **Who it hurts:** Drawing, games and anything that tracks a finger or pen · **Parity:** [Input](platform-parity.md#input)

- An application sets `InputLatency` for every window it opens with `AppConfig::input_latency`.
- Android asks the Activity's decor view for unbuffered pointer dispatch (`View.requestUnbufferedDispatch`, API 30+), which `ViewRootImpl` applies ahead of `NativeActivity`'s native input queue; type-checked, not run on a device. Below API 30 the system batches input once per frame.
- iOS attaches the touches UIKit coalesced into a move and the ones it predicts (type-checked, no run on a device). Pencil force, altitude and azimuth that UIKit later revises (`touchesEstimatedPropertiesUpdated:`) are not reported: the pointer vocabulary has no revision of a delivered sample, so a stroke keeps the first estimate. The shape it lands in ([ADR-0346](adr/ADR-0346-a-key-down-says-its-kind-a-dead-key-its-accent-and-a-scroll-its-direction.md) §4) keys a revision by a ticket the host mints with the estimated sample (UIKit's `estimationUpdateIndex`): `PointerSample::estimation: Option<EstimationTicket>` and a `#[non_exhaustive]` `PointerEvent::SampleRevised { pointer, estimation, sensors }`, never a pointer id and a time, which a reused id or a coarse timestamp makes ambiguous; it lands with the iOS producer and the first stroke or ink consumer, and a scenario that covers Pencil estimates fails on this gap until then. The Apple Pencil Pro squeeze (`UIPencilInteraction`) is not read either, and the vocabulary has no event for it until a host produces one. Holding a reading back until its estimate settles was rejected: it adds the latency this entry is about.
- The Linux and macOS paths are not audited.
- Timestamp conversion is a hazard of its own: Win32 `GetMessageTime` is 32-bit milliseconds that wrap every 49.7 days, Wayland event times have an undefined base, and Android's event time is uptime milliseconds. Windows pointer ticks are rebased across the wrap (`NativeTime::TickMillis`); the native Wayland host reads a stamp through the same rule only when it lies within a second of `CLOCK_MONOTONIC` and stamps the event on arrival otherwise (Weston's X11 backend stamps on the X server's clock); the X11, Android and Web conversions are not audited.

### Activation ignores the OS focus rules

> **Environments:** Windows, Wayland · **Who it hurts:** Apps brought forward by a link, a second launch or a notification · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle)

- Windows follows the foreground rules: an activation the rules refuse flashes the window's taskbar button and leaves the foreground with the application the user works with, a right handed over (`AllowSetForegroundWindow`) brings it forward (run with two processes, 2026-10-28). Opening a link, file or folder hands the right only to the handler process the shell started, by its id; a handler already running (a browser, Explorer) is handed nothing and comes forward under the OS's own rules, which may leave it behind (the PID hand-over not run against a real handler). A later launch of a single-instance application hands the right to the running instance before its launch ([Links and files open everywhere, but no Windows package or Apple entitlement declares them](#links-and-files-open-everywhere-but-no-windows-package-or-apple-entitlement-declares-them)), not run yet.
- The Win32 snapshot says `focused: true` and `active: true` for a window of a process the user is not working with: they are its thread's focus and activation, not the system's. `WM_ACTIVATEAPP` does not tell them apart (Windows sends it for the thread's own activation of a background process, seen in a two-process run, 2026-10-28), so the fix needs the foreground's changes (`EVENT_SYSTEM_FOREGROUND`) to reach each window, which the host does not watch yet.
- The native Wayland host asks with an `xdg-activation` token and uses the launcher's `XDG_ACTIVATION_TOKEN` for the first window it holds; a token names the last key, button, touch or keyboard focus its seats report, the serial a compositor weighs before it moves the focus (with no input yet, an activation asks for attention: sway marks the window urgent). Weston 13 has no `xdg_activation_v1`, so under it only the refusal is checked; the whole path runs under sway ([which compositor runs which case](testing.md#which-compositor-runs-which-wayland-case)).
- macOS cooperative activation (`NSApplication.yieldActivation(to:)`, macOS 14) is documented by Apple, which also marks `activate(ignoringOtherApps:)` deprecated; neither is audited.

### Live resize is unaudited and unscheduled

> **Environments:** desktop, Web · **Who it hurts:** Every user who resizes a window by dragging its edge · **Parity:** [Windows](platform-parity.md#windows)

- No environment has been audited: the row "Live resize without jitter" is ❔ on Windows, macOS, Wayland, X11 and the Web, and [Window control has run only on Windows, an X11 test server and the AppKit conformance kit](#window-control-has-run-only-on-windows-an-x11-test-server-and-the-appkit-conformance-kit) and [Unaudited rows](#unaudited-rows) mention it only in passing.
- Windows handles the modal loop a drag opens inside `DefWindowProc` ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-entersizemove)): between `WM_ENTERSIZEMOVE` and `WM_EXITSIZEMOVE`, and inside a menu loop, a timer of the window delivers due deadlines while the loop holds the thread (`owner::windows::modal_loop`), each `WM_SIZE` of the drag asks for the frame at the new size inside that message instead of waiting for a `WM_PAINT`, and touchpad gestures pause (`crates/flui-native/src/window/windows/proc.rs`). A drag onto a display of another scale keeps the content's logical size (the window answers `WM_GETDPISCALEDSIZE`), the timer is set only for what is due, and the snapshot says the user is placing the window while the loop runs (`WindowInteraction::UserPlacing`) and resizing it from its first `WM_SIZING` (`UserResizing`, ADR-0354 §4; `a_resize_by_the_frame_is_a_live_resize_until_the_loop_ends`), as AppKit states it between `windowWillStartLiveResize:` and `windowDidEndLiveResize:` and Wayland while a configure carries `resizing`. No scripted drag has measured it, and no drag between two monitors of different scale has run. winit reports that its `ControlFlow` is ignored in that loop and that continuous redraws make a drag choppy ([rust-windowing/winit#3272](https://github.com/rust-windowing/winit/issues/3272), [#4708](https://github.com/rust-windowing/winit/issues/4708)).
- Metal presents asynchronously to Core Animation transactions unless `CAMetalLayer.presentsWithTransaction` is set ([Apple](https://developer.apple.com/documentation/quartzcore/cametallayer/presentswithtransaction)); Wayland needs an `ack_configure` before the committing frame and frame callbacks to pace the redraw. None of these is audited here.
- The native X11 host answers `_NET_WM_SYNC_REQUEST` on two XSync counters: after the frame the resize's configure asked for, or at once for a configure that asked none, whatever the frame's handler did; under a window manager that lists `_NET_WM_FRAME_DRAWN` the extended counter is odd while each frame draws (`window::linux::x11::protocols`). Run under openbox on Xvfb, which paced a drag on a window's edge by the counter (`openbox_paces_an_interactive_resize_by_the_windows_counter`), and against a stand-in window manager on Xvfb for the order and the extended counter (`a_synchronised_resize_is_answered_after_its_frame`, `a_window_manager_that_paces_frames_sees_each_one_drawn`). Owed: a drag under mutter, KWin and xfwm4 with a compositor, looked at for content of the old size at the edge. The window paces no frame by the compositor's `_NET_WM_FRAME_DRAWN` and reads no `_NET_WM_FRAME_TIMINGS`.
- The X11 answer follows the frame's hand-over to the GPU, not its presentation, so one tear is left per resize step: the host hears no presentation (Present's completion goes to the GPU driver's connection), and Vulkan's FIFO swap chain presents at a later refresh from the driver's own queue. A window manager that waits for the counter may then draw the new size once around content of the old size. Matching the answer to the presented frame needs a presentation report X11 does not have: `_NET_WM_FRAME_TIMINGS` under a window manager that synchronises frames, or the Present extension's completion on a connection the host reads. No test reads pixels.
- macOS sets `presentsWithTransaction` on the view's layer for each display pass of a live resize and clears it after, so wgpu presents that drawable in the transaction that carries the new window frame; the frame renders inline in `updateLayer`, so the wait wgpu adds holds the main thread only while an edge is dragged. A drawable that still misses the layer's size keeps its own size at the view's top-left corner (`layerContentsPlacement`, AppKit's name for the backing layer's `contentsGravity`) where the default stretched it, and the window sets the layer's `contentsScale` to its backing scale when it is made and at every change of that scale, since contents that are not stretched are laid out by it. All three are type-checked, not looked at by eye: whether a resize shows a strip of background where it showed a stretched frame, whether that reads better, and whether a frame on a Retina display fills its window (a contents scale of 1 there would show it at twice the size) are not judged.
- The engine presents with `Fifo`, which blocks on vsync and ghosts a stale frame during the Windows modal resize loop; its own notes name `DXGI_SCALING_NONE` as the only real fix, which wgpu 30 does not expose. A resize-jitter probe saw no size-mismatched acquire in a 40-resize burst into the Metal swapchain; the compositor-side half is unobserved.
- It is among the most-reported defects of comparable frameworks ([emilk/egui#903](https://github.com/emilk/egui/issues/903) is a fast-resize flicker). A reference run should record its trade-off in the row note: Flutter 3.50's Windows embedder blocks the platform thread for up to 100 ms for a frame at the new size (`kWindowResizeTimeout`, [`flutter_windows_view.cc:26-29`](https://github.com/flutter/flutter/blob/ab2912035e/engine/src/flutter/shell/platform/windows/flutter_windows_view.cc#L26-L29)).
- Pass criteria: a scripted two-second border drag with every presented frame captured, content size equal to window size in every captured frame, callbacks counted during the modal loop, and the p99 frame time recorded.

### A maximized Win32 window is restored to the rectangle the system scaled

> **Environments:** Windows · **Who it hurts:** A user who changes the display scale, or moves a maximized window to a monitor of another scale, and then restores it · **Parity:** [Windows](platform-parity.md#windows)

- A normal window keeps its content's logical size across a scale change (it answers `WM_GETDPISCALEDSIZE`), and so does the rectangle a fullscreen window returns to; the rectangle a maximized window returns to (`WINDOWPLACEMENT::rcNormalPosition`) is left to the system, which may scale it linearly, so the restored content can be a few pixels off its logical size.
- What the system does to that rectangle cannot be observed without changing a scale, which no test on the development machine does; the run is owed in the `scale-factor-and-dpi-changes` row of `crates/flui-native/platform-parity.toml`.
- A window without a frame is maximized to its monitor's work area through `WM_GETMINMAXINFO`, whose position and size Windows documents for the primary monitor and adjusts for another; only one monitor has run.

### No present-mode, queue-depth, VRR or tearing control

> **Environments:** desktop, iOS, Android · **Who it hurts:** Games, drawing and latency-sensitive apps · **Parity:** [Displays and metrics](platform-parity.md#displays-and-metrics)

- The engine chooses each surface's present mode from what paces it (`Fifo` where the display does, `Mailbox` or else `Immediate` on Wayland, whose compositor does: ADR-0356), and the queue depth is the application's `FrameLatency`; nothing lets the platform layer or the app choose a present mode, variable-refresh behaviour or tearing.
- A Wayland window drawn on the GL fallback (ADR-0244 §1) keeps `Fifo`: wgpu's GL backend offers no other mode on Linux and sets no swap interval, so Mesa's EGL may wait in `eglSwapBuffers` for the frame callback a compositor sends no surface it does not draw, and the raster thread with it, which then draws no other window. Vulkan, the first backend tried, presents without that wait (`native_linux::an_app_whose_window_is_never_drawn_still_quits`); the GL path has not run against a compositor that withholds callbacks, and closing it needs wgpu to offer `Immediate` (swap interval 0) on EGL.
- An X11 window that is not shown (minimized, unmapped, under Xwayland on a hidden workspace) still presents in `Fifo`, which X11 paces by the display: Mesa's X11 WSI completes such a present only when the server's Present extension fakes the window's vblank, about once a second for an unmapped window, so an animating hidden window may hold the owner thread up to a second per frame; on a raster thread it would hold every window's frames, so X11 stays inline until a run on a real X server (ADR-0305 §10). Not confirmed: no X server this machine runs creates a socket the tests reach (WSLg mounts `/tmp/.X11-unix` read-only), and CI's Xvfb runs no case that animates a hidden window. If a run shows it, the X11 host's surface target states the pacing it has (`SurfaceTarget::frame_pacing`), as Wayland's does.
- Every present hands the compositor the whole image: the engine's damage bounds what a frame redraws, into a retained target blitted whole to the swapchain (`crates/flui-engine/src/damage.rs`), not what it presents. No dirty rectangles reach DXGI `Present1`, Wayland's buffer damage or the EGL damage extension, since wgpu 30 exposes none, so a typed glyph recomposes the whole window.
- Presentation feedback ([No presentation feedback](#no-presentation-feedback)) is read-only and "Refresh rate and frame pacing" covers rates only; control over how frames are presented is the other half.
- Windows tearing needs `DXGI_FEATURE_PRESENT_ALLOW_TEARING` and `DXGI_PRESENT_ALLOW_TEARING`, which can only be used with sync interval 0 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/variable-refresh-rate-displays)); Wayland has `wp_tearing_control_v1`, `fifo-v1` and `commit-timing-v1`.
- Queue depth costs latency: the default DXGI queue of up to three frames adds about 16–32 ms of input latency in another framework ([libsdl-org/SDL#15656](https://github.com/libsdl-org/SDL/issues/15656)).
- The Web has nothing to control: `requestAnimationFrame` is its only cadence.

### Launch handoff on mobile and the Web

> **Environments:** iOS, Android, Web · **Who it hurts:** Every mobile and web app in its first second · **Parity:** [Windows](platform-parity.md#windows)

- The OS shows a splash before the first frame on these environments, and the first frame must match it: Android 12 and later through the `SplashScreen` API ([Android documentation](https://developer.android.com/develop/ui/views/launch/splash-screen)), the iOS launch screen, and the page background before a Web app's wasm loads.
- Nothing aligns them today: the generated Web page sets no background before the wasm loads and its manifest `theme_color` is `#FFFFFF`, the generated Android manifest sets no splash or window background, and iOS declares an empty `UILaunchScreen`.
- The parity row "Show without a blank first frame" covers the desktop only, where the window is created hidden and shown after the first presented frame; Electron does the same with a hidden window shown on `ready-to-show` and a `backgroundColor`.
- A dark-mode user should see the dark splash and the dark first frame, not a white flash between them.

### Quality-bar partials with no entry

> **Environments:** all · **Who it hurts:** Everyone who relies on a platform claim; maintainers who cannot replay a failure · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- Honest absence: the nine spellings of "not here" are one now, `Unsupported` with its reason in every contract error (ADR-0151 §4). Other layers show what silent spellings cost: winit setters return `()` while their documentation lists platforms as unsupported, `tauri-plugin-geolocation` resolves to a zeroed position on the desktop, and `tauri-plugin-notification` reports a permission it did not check.
- Replay: every stream the `native-capture` journal records (pointers, keys and wheels, system notices, session ends, reopens, input method events, close requests and closes, the locks a pull-model input method holds on the focused text store, reads of the system preferences and displays, window snapshots) replays on the headless host, but the text store locks have been captured only from the input method paths' models; no capture of a real input method has run on any host. The `flui-driver` crate and its Windows lane exist, but the driver records no native input yet, its Windows OS-input runs on the desktop that takes the user's input are owed (rows of `crates/flui-native/platform-parity.toml`), and the other OS lanes are not written.
- The `native-capture` journal does not record what each frame presented.
- Not every unsupported cell in the parity tables names its reason, and nothing checks the cells against the code's `Unsupported` reasons.

### Power-aware pacing and throttling

> **Environments:** all · **Who it hurts:** Every user on battery or a thermally limited device · **Parity:** [System preferences](platform-parity.md#system-preferences)

- Power state (battery, low-power mode, thermal) is not in the contract, and nothing pauses background work for it. One host reads one part of it for its own pacing: macOS holds the built-in panel's refresh period at 1/60 s or longer while Low Power Mode is on (`NSProcessInfo.isLowPowerModeEnabled`, macOS 12 and later) and reads the displays again when the power state changes, so the period reaches consumers as a new display revision. That a ProMotion panel refreshes at 60 Hz there while its mode and its display link still say 120 is taken from Rune's source ([`display_link.rs`](https://github.com/anomalyco/rune/blob/dev/crates/rune/src/platform/display_link.rs)), not measured here; the rule runs on Linux (`a_macos_screen_paces_at_its_mode_its_link_or_the_low_power_rate`, `a_power_mode_change_is_a_new_display_revision_only_where_the_period_changed`) and the AppKit half is type-checked only. The notification's name is a macOS 12 constant, looked up by name so the binary still loads on macOS 11; where the lookup finds none on macOS 12 or later, the host warns once and observes nothing, and the period then follows Low Power Mode only when the displays are read again for another reason (a change of screen parameters, a window that changes display or scale, a wake from sleep).
- The native signals exist: Apple's `ProcessInfo.thermalState` and `isLowPowerModeEnabled` with a change notification, Android's `PowerManager.getCurrentThermalStatus()` and `addThermalStatusListener`, Windows battery saver through `SYSTEM_POWER_STATUS.SystemStatusFlag` and `RegisterPowerSettingNotification`, and the Linux portal's `PowerProfileMonitor.power-saver-enabled`.
- Apple's `CADisplayLink.preferredFrameRateRange` is only a hint that Low Power Mode, a critical thermal state and accessibility settings can override, so an app that asks for 120 Hz still has to follow the state.
- iOS asks its display link for the screen's best rate only while a presentation animates or a pointer is down (the runtime's frame-rate demand, as on Android), and leaves a still screen to the system's rate. On a still screen the link pauses: it runs only while a frame is asked for, and a request from any thread resumes it on the main thread (type-checked, no device run). The Web's frame loop stands still the same way once the refresh estimate has its window of frames, and a request resumes it (run in the wasm32 suite on Node, not in a browser).
- The check forces each state and asserts a delivery within one event-loop turn and a frame-rate or work reduction.

### GPU memory stays held while a window is idle or unseen

> **Environments:** all · **Who it hurts:** Apps left open in the background, on laptops and phones; machines with little video memory · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle)

- The raster host gives GPU memory back (`RasterHost::reclaim`, `crates/flui-app/src/app/runner/raster_host.rs`) only when the OS reports memory pressure (`owner_dispatch.rs`, `host_memory.rs`). A window that is minimized, hidden, cloaked or has drawn nothing for a long time keeps its spare targets and caches until such a notice, which a desktop rarely sends.
- Rune frees spare layer targets beyond the most recent few megabytes once a window has drawn nothing for a while, sooner under pressure, and its scratch targets too once the window cannot be seen.
- The check: a slot whose window is unseen, or has rendered nothing for a set time, trims once as a moderate pressure notice would, its next frame rebuilds what it needs, and a test reads the slot's held bytes before and after.

### Locale edge: layout direction, per-app language, system fonts and fallback

> **Environments:** all · **Who it hurts:** Apps in right-to-left or non-Latin languages; users who set a language for one app · **Parity:** [System preferences](platform-parity.md#system-preferences)

- [System preferences missing or never run](#system-preferences-missing-or-never-run) names languages and regional formats only. Layout direction, per-app language, and system fonts and fallback have no reading in the platform layer.
- Android 13 adds per-app language preferences and `setApplicationLocales` ([Android documentation](https://developer.android.com/guide/topics/resources/app-languages)); iOS has a per-app language setting; a right-to-left layout follows from the locale.
- Text layout resolves fonts through `fontdb` in `flui-painting`. DirectWrite `IDWriteFontFallback`, Android `fonts.xml` and `AFontMatcher` (API 29), CoreText and fontconfig are the platform answers to which font draws a character the requested family lacks. The collection puts such an answer (`SystemFallback`) ahead of FLUI's tables ([ADR-0271](adr/ADR-0271-the-host-feed-asks-the-platform-which-faces-fall-back.md)). DirectWrite gives it on Windows, CoreText on macOS and iOS, fontconfig on Linux and the BSDs, `AFontMatcher` on Android from API 29 and `fonts.xml` below it; Windows, Apple and Android are type-checked, not run. When the first preferred locale changes, the feed's thread asks again and installs the new answer. The order follows the app's first locale only: a paragraph in another language falls back in that order, since the fallback key carries no per-paragraph locale yet.
- `EditableText` lays its text out left-to-right whatever the ambient `Directionality`: `Text` and `RichText` without a direction follow the ambient one, so in a right-to-left field the label and hint have a right-to-left base and the typed text a left-to-right one ([#1116](https://github.com/vanyastaff/flui/issues/1116)).
- The check is a locale matrix (en-US, ar-EG for right-to-left, ja-JP, hi-IN with its numbering) on every OS: list order, first weekday, 12 or 24 hour clock, per-app override, and CJK and emoji text without missing-glyph boxes.

### Accessibility bridge fidelity (properties and announcements)

> **Environments:** desktop, iOS, Android, Web · **Who it hurts:** Screen-reader users: a control announced without its value, hint or state, or a change nobody hears · **Parity:** [Accessibility](platform-parity.md#accessibility)

- [No accessibility on mobile and the Web](#no-accessibility-on-mobile-and-the-web) is about missing adapters; a bridge that exists can still drop properties or announcements, and the two fail independently of the tree and actions.
- Another framework's Linux bridge drops a field's `value` and `hint` ([flutter/flutter#194638](https://github.com/flutter/flutter/issues/194638)) and gives no AT-SPI announcement for live regions, snack bars, alert dialogs or route changes, only for an explicit announcement call ([flutter/flutter#194045](https://github.com/flutter/flutter/issues/194045)).
- The parity rows "Properties (value, hint, description, state)" and "Announcements and live regions" are ❔ on Windows and macOS, run on X11 against an AT-SPI client (below), and ❌ where there is no adapter at all.
- Each needs a check with the real assistive technology on each OS that reads role, name, value, hint, state, actions, focus order and announcements; a harness that registers AT-SPI listeners and matches only strings carrying a nonce keeps any other source from producing a hit.
- Assistive-technology focus reaches a widget on no native platform. The model is there: `Semantics::on_assistive_focus_within` tells a subtree when the screen reader's cursor enters and leaves it, a `Carousel` pauses its autoplay on it, and `PresentationCapabilities::assistive_focus` says whether the platform reports the cursor (`each_native_adapter_says_whether_it_reports_the_assistive_cursor` in `flui-native`). UI Automation, NSAccessibility and AT-SPI give an application no signal for Narrator's, VoiceOver's or Orca's cursor, and the browser gives a page none for any screen reader's. The published `accesskit_ios` and `accesskit_android` do track VoiceOver's and TalkBack's cursor, in private fields, so iOS and Android say `Unreported` until an AccessKit release hands it to the application: a handler told when VoiceOver's cursor moves, and an accessor that reads where TalkBack's is. Both changes are written against AccessKit and not yet sent upstream. Where the cursor is not reported, a `Carousel` pauses on keyboard focus, pointer and the app leaving the front, and the pause control it draws is what meets WCAG 2.2.2.
- Windows scroll by position is missing: the published `accesskit_windows` implements no UI Automation `ScrollPattern`, so Narrator and NVDA read no scroll position and scroll only through a position slider's `RangeValue`, though FLUI publishes the position from the top or left edge and takes `SetScrollOffset` (ADR-0273). An upstream pull request adds the pattern ([AccessKit/accesskit#816](https://github.com/AccessKit/accesskit/pull/816), open); it closes with the `accesskit_windows` release that has it.
- **Linux, run against a real AT-SPI client:** `flui-native`'s `linux_atspi` starts a session bus and the accessibility bus of its own (at-spi2-core) beside an Xvfb, publishes a window's tree through `accesskit_unix` and reads it back as Orca would: role, name, hint as the description, a field's text through the Text interface (from its runs; a value without runs reaches no AT-SPI interface), a slider's value and range, states and actions; announcements at their urgency, live regions whose own or child's label changes, a status that appears, and focus once the window is active, each matched by a nonce of the run; a node's screen extents follow the X11 window through two moves under openbox, its frame included, and on a headless Weston at scale 2 are relative to the window, below the title bar the window draws itself, in device pixels (`a_node_is_placed_where_its_window_moved_on_the_screen`, `a_wayland_window_reads_back_its_tree`). The X11 window reads where it is when the server sends it an event that can move it (`ConfigureNotify`, `ReparentNotify`, `_NET_FRAME_EXTENTS`, the focus). A window manager that moves a frame without the synthetic `ConfigureNotify` ICCCM 4.1.5 asks for leaves the old extents until the next such event, and no manager that does so has been found or run. A route change and a modal dialog appearing are told by name (ADR-0204 §5): heard on X11 as a polite announcement (`a_route_change_is_heard_by_its_name`); on iOS and Android as the platform's notice of a new screen, type-checked, with no VoiceOver or TalkBack run; on Windows, macOS and the Web as an announcement, not run there. No Orca session ran.

### A Windows or macOS window builds its accessibility tree for its life

> **Environments:** Windows, macOS · **Who it hurts:** Everyone on a machine where any assistive-technology client once asked a window for its tree: the window builds semantics every frame until it closes · **Parity:** [Accessibility](platform-parity.md#accessibility)

- Linux, iOS and Android end the tree when the platform says the last assistive technology left (the parity row "The tree ends when no assistive technology listens"); Windows and macOS start it on the first client's question and never end it.
- **Windows:** `UiaClientsAreListening` answers whether any UI Automation client listens, but it stays true once a client connected, until every one disconnects and some time passes; `SPI_GETSCREENREADER`, which `WM_SETTINGCHANGE` reports changing, says a screen reader declared itself, which Narrator and NVDA do and an automation client does not. Neither is read yet. Ending the tree on a screen reader's departure would need both: the flag's change to `false` as the moment, and the listening clients as the check that nobody else reads.
- **macOS:** `NSWorkspace.isVoiceOverEnabled` and `isSwitchControlEnabled`, observable by key-value observing, name two assistive technologies; an AX client such as Accessibility Inspector or an automation tool shows in neither. Neither is read yet.
- It closes with each host's signal read and passed to `BridgeShared::deactivate`, and the host's row of `each_native_adapter_ends_its_tree_when_its_platform_says_nobody_listens` naming its entry.

### A list that fills part of its viewport publishes its whole cache to a screen reader

> **Environments:** desktop, iOS, Android, Web · **Who it hurts:** Screen-reader users: swiping through a list under a header or inside padding, or through a `SingleChildScrollView`, reaches content kept built past the viewport, as if it were on screen · **Parity:** [Accessibility](platform-parity.md#accessibility)

- A node publishes AccessKit's `clips_children` when each of its children lies under a paint clip inside its own rect and has an area, and everything below each child lies inside the rect of the node above it (`PendingSemanticsNode::form` in `flui-rendering`), so a reader stops at the first row past each edge. A list that fills the viewport and overflows it gets it (`a_reader_reaches_the_row_past_a_lists_edge_and_scrolls_it_in`); a list whose rows fit the viewport paints without a clip and publishes none, and a row whose content overflows it keeps it off.
- A list under a header sliver that scrolls away, or inside `SliverPadding`, has a rect smaller than the viewport's clip, so it does not. Nor does a `SingleChildScrollView`: the node holding its content sits above its viewport, outside the clip. AccessKit's filter reads only the nearest filtered parent. The content is still not `visible` to the agent and `Tester`: the actionability check narrows by every clipping ancestor, the scroll view included. A list under a pinned header does get the flag: the viewport shrinks that list's clip by the room the header takes, so a row wholly behind the header counts as past the edge, a translucent header included, as Flutter's viewport clips it.
- It closes with a clip the viewport hands each sliver for its own extent, and with the scroll semantics node formed inside the viewport's clip.

### Add-to-app: no FLUI view inside an existing native app

> **Environments:** all · **Who it hurts:** Teams adding FLUI to an app they already ship · **Parity:** [Windows](platform-parity.md#windows)

- FLUI owns the process: the host creates the window and runs the loop (`FluiActivity`, a `NativeActivity`, on Android, `UIApplicationMain` on iOS, the Win32 pump, `NSApplication`, the root element it creates on the Web). A view placed into a window the app already owns — a child `HWND`, an `NSView`, a `UIView` under a foreign view controller, an Android `View` in a foreign `Activity`, an element of a page the app renders — has no host mode, so the only way in is to hand FLUI the whole window.
- What exists: the renderer draws into a `SurfaceTarget` (`HasWindowHandle + HasDisplayHandle`, [ADR-0254](adr/ADR-0254-window-contract.md)), so the surface can be foreign; input, focus, IME, accessibility and lifecycle still assume the host's own window procedure, responder chain or `Activity`.
- Other frameworks ship it as their enterprise path: Flutter's add-to-app ([Flutter documentation](https://docs.flutter.dev/add-to-app)) with `FlutterEngine` and `FlutterViewController` or `FlutterFragment`, Compose's `ComposeView` in a View hierarchy, SwiftUI's `UIHostingController`, Qt's `QWidget::createWindowContainer`.
- The design question is who owns the loop: an embedded view is driven by the app's loop and receives events from the app's window, so the owner thread's one call point for user code ([ADR-0151 §10](adr/ADR-0151-platform-layer-boundary-and-names.md)) has to run inside a foreign callback, and ADR-0151 names an external embedder as the first reason to reopen the crate split.
- The check is one screen of FLUI inside a foreign app on each OS: keyboard focus moving into and out of the view, IME and the assistive technology reaching it, and the app's own lifecycle pausing and resuming it.

### No gamepad, and no D-pad run on a TV

> **Environments:** all · **Who it hurts:** TV, console-style and Steam Deck users; games · **Parity:** [Input](platform-parity.md#input)

- No gamepad in the contract or on any host: no buttons, sticks, triggers or rumble from XInput or GameInput on Windows, `GCController` on macOS and iOS (and tvOS's remote), Android's `SOURCE_GAMEPAD` and `SOURCE_JOYSTICK` axes (`AXIS_X`, `AXIS_HAT_X`, `KEYCODE_BUTTON_*`), the Web Gamepad API (polled through `navigator.getGamepads()`, with only connect and disconnect events) or evdev on Linux (Wayland has no gamepad protocol; a Steam Deck under gamescope has a controller as its only input).
- Android's D-pad arrives: the `ui_events` key table maps `KEYCODE_DPAD_UP`, `DOWN`, `LEFT` and `RIGHT` to the arrow keys and `KEYCODE_DPAD_CENTER` to Enter, and `DefaultFocusTraversal` binds unmodified arrows to `DirectionalFocusIntent`, so a remote can move focus; it never ran on Android TV or Fire OS, and a TV app also needs the `leanback` feature declaration and a banner that the Android packaging does not write.
- Without a pointer (Android TV, tvOS, a console) focus navigation is the whole input model: every widget must be reachable by direction with a visible focus ring, which no run has shown.
- The check is a remote on an Android TV device and a controller on Windows and a Steam Deck: every control of the interaction widgets reached by direction and activated by the centre button, and a controller's sticks and buttons recorded and replayed.

### No rotary input

> **Environments:** Windows, Android; Apple later · **Who it hurts:** Surface Dial and Wear OS users · **Parity:** [Input](platform-parity.md#input)

- No rotary vocabulary in the contract: a rotation in detents from a device of its own arrives nowhere — the Surface Dial through `RadialController` on Windows (per window, with the tool menu the OS draws), Wear OS's bezel or crown as a `MotionEvent` with `AXIS_SCROLL` from `SOURCE_ROTARY_ENCODER` ([Android documentation](https://developer.android.com/training/wearables/user-input/rotary-input)), the Digital Crown on watchOS and visionOS.
- Wear OS is a form factor of the Android host, not a column: its lists are expected to scroll by rotary input, so a watch app without it fails review on the first screen.
- The check is a Surface Dial on Windows and the rotary input of a Wear OS emulator turning a scroll view by detents, recorded and replayed.

### No compute lane off the UI thread on the Web

> **Environments:** Web · **Who it hurts:** Web apps that decode images or lay out large documents · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- `Background::compute` (ADR-0272) runs its job inline on the UI thread on wasm32, because `ExecutionServices` is sequential there (ADR-0047): a long decode blocks the frame it was started in. The answer still settles at the next owner turn, so widget code is the same everywhere.
- The lane belongs on Web workers: a worker pool that runs a `ComputeJob` needs shared memory (`SharedArrayBuffer`, which needs cross-origin isolation headers) or a job shape that crosses `postMessage` by value.
- The check is a browser run of a large image decode started through `Background::compute` with the frame clock showing no frame longer than its budget.

### The Web never wakes when a dropped frame's backoff ends

> **Environments:** Web · **Who it hurts:** Web apps whose frame was dropped · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- The native owners arm a timer on the deadline `AppHandler::wake_deadline` reports (`AppRuntime::next_wake`, which includes the backoff deadline, `crates/flui-native/src/owner/wake_deadline.rs`); the web owner (`crates/flui-native/src/owner/web.rs`) asks for none, and its animation-frame loop stops when no frame is asked for.
- So a page whose frame failed, with no completion demand standing (a callback of the failed frame, or a `PostFrameHandle::schedule_frame` request), waits past the end of the dropped-frame backoff (ADR-0334 §1) until input or another frame wakes it, and the input its presentation holds waits with it.
- Only the commit anchor's re-arm of completion demand (`PresentationState::rearm_completion`) keeps a page with such demand going: it asks for a frame at every owner turn of the backoff, each refused by the backoff gate, so every host spins through the wait instead of sleeping until it. Gating that re-arm on the backoff needs the web wake first, or the page would stall until input.
- The check is a browser run in which a sink answers `Failed` once and the page presents its tree within the backoff with no input.

### Images decode on the UI thread without background lanes

> **Environments:** hosts without `BackgroundCapability` · **Who it hurts:** Embedders whose host registers no background lanes · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- `Image::memory`, `Image::file` and any provider with a `DecodeJob` decode on the background lanes (ADR-0272), and `Image::asset` and `Image::network` load through their UI runtime's `ImageCache` on them (ADR-0279, ADR-0387). A host that does not provide `BackgroundCapability` gets the job run on the UI thread instead, so the image still shows but its decode costs that frame. `flui-app` and the headless host provide the capability; an embedder's own host may not.
- Decoded images are not shared between widgets: two `Image::memory` widgets with equal bytes decode twice. A decoded-image cache owned by the UI runtime (never by the process) is the follow-up.
- `Image::decode` bounds each block its decode asks for by `MAX_DECODED_IMAGE_BYTES`, except one inside `png` 0.18.1: `parse_iccp_raw` inflates a compressed colour profile (iCCP) with `fdeflate::decompress_to_vec_bounded`, whose `Vec::resize` grows the buffer by doubling, so a profile that inflates past half the limit can ask for one block over it. Reaching it needs an iCCP chunk of about 125 KiB, past the fuzz job's 4096-byte inputs. `png::Decoder::set_ignore_iccp_chunk` would skip the chunk, but `image`'s `PngDecoder` builds its `png::Decoder` inside `with_limits` and exposes no way to set it, so `Image::decode` cannot turn that path off. Read in the source, not reproduced.
- The check is a host without the capability decoding a large image with the frame clock showing the cost, and a cache hit test once the runtime cache exists.

### The Web host embeds only as the whole viewport or the page's own canvas

> **Environments:** Web · **Who it hurts:** Pages that embed a FLUI app beside their own content, and users who zoom · **Parity:** [Windows](platform-parity.md#windows)

- A window is either a root of the host's own fixed over the layout viewport or the page's `<canvas id="flui-canvas">`, whose layout the page owns. There is no mount element: a page cannot hand the host a `<div>` to build its root in, so an embedder writes the canvas and its sizing itself.
- Two FLUI instances on one page each get a root of their own, overlapping over the viewport; a page canvas has one owner, and a second instance is refused it.
- The canvas takes every touch (`touch-action: none`), so a pinch over it never zooms the page: a low-vision user's pinch zoom is the application's to answer. Page zoom (Ctrl and +) reaches the window as a new device pixel ratio; a browser's text-only zoom does not reach it.
- The textarea path reads each edit from `input` and composition events, not `beforeinput`; Safari's and Firefox's composition event order is pinned only by constructed events in Chrome, and no Safari, Firefox or mobile run has checked it.

### The driver agent cannot reach a page in Safari

> **Environments:** Web (Safari) · **Who it hurts:** Agents and tests that drive a FLUI app in Safari · **Parity:** none yet (the driver agent has no row)

- A page's agent is reached through the browser's own remote protocol (ADR-0288 §6): `flui run --agent` speaks WebDriver BiDi to Firefox and the DevTools protocol to Chrome, Chromium, Edge, Brave and Opera, which need no driver of their own. Safari has neither: `safaridriver` speaks classic WebDriver, which has no channel or binding a page can report through, so `flui run --agent --device browser:safari` is refused, naming this entry.
- The likely shape is a third dialect of the CLI's `BrowserLink` once `safaridriver` serves WebDriver BiDi, or one over classic WebDriver that polls the page for its lines.

### The driver agent cannot reach an app in the iOS Simulator

> **Environments:** iOS · **Who it hurts:** Agents and tests that drive a FLUI app on iOS · **Parity:** none yet (the driver agent has no row)

- `flui run --device <simulator>` builds the app, installs it and launches it once through `simctl`, and hands it no agent endpoint or launch token, so `flui run --agent` on a Simulator is refused, naming this entry. The nightly iOS run of the counter scenario (`an_agent_presses_the_counter_on_a_live_device`) fails as this entry.
- The likely shape: the Simulator shares the Mac's file system, so the desktop's Unix socket and token can reach the app through `simctl launch`'s `SIMCTL_CHILD_` environment, and the iOS runner serves the agent as the desktop runners do. A device needs a transport of its own (a forwarded port, as on Android).
- The check is the counter scenario passing on a Simulator, then on a device.
- The check is `flui run --agent` in Safari on macOS, `flui mcp` reading the app and acting on it, and a reload reconnecting.

### The CLI speaks to the driver agent through a client of its own

> **Environments:** all · **Who it hurts:** Contributors, who keep two clients of one conversation in step · **Parity:** none (a tool's internals)

- `flui mcp` and `flui record` reach an app's agent through `crates/flui-cli/src/agent/client.rs`, beside `flui-driver`'s socket connection, which speaks the same conversation (ADR-0238 §2). A change to the envelope, the hello or the timeout rule is made twice until the CLI is a front end of `flui-driver`.
- The flui-driver spec's CLI and MCP task moves `flui drive`, `flui mcp` and `flui record` onto `flui-driver` and deletes the CLI's client; the check is `rg agent::client crates/flui-cli` finding nothing.

### An interactive widget costs eighteen elements

> **Environments:** all · **Who it hurts:** Every screen with many controls; every catalog built on the wrappers · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- `RawButton` and Material's `InkWell` mount one element and one render object for their behaviours (the private node of [ADR-0322](adr/ADR-0322-a-control-mounts-one-element-for-its-behaviours.md) §1; `crates/flui-widgets/src/interaction/raw_button.rs`, `packages/flui-material/src/ink_well.rs`), and so do the Material controls built on `InkWell` for those behaviours. Every interactive control of `flui-material` and `flui-cupertino` is on the node; the decoration around a text field keeps its `MouseRegion`, as Flutter's `InputDecorator` does, since it tracks hover for a field whose own interaction the text field owns. On the wrappers a button holding a `Text` was 18 elements, 8 render nodes, 421 allocations and 46 KB at mount; an `InkWell` over a `Text` was 15 elements, 9 render nodes, 200 allocations and 33 KB, and on the node is 3 elements and 2 render nodes, its ink included; its allocations and bytes are held by `packages/flui-material/perf/baseline/ink_well_over_text.toml` (`perf_ink_well_over_text`). The `ButtonStyleButton` buttons describe themselves on their well's node: an `ElevatedButton` over a `Text` is 11 elements and 5 render nodes, its allocations and bytes held by `elevated_button_over_text.toml` (`perf_elevated_button_over_text`). `Checkbox`, `Switch` and `Radio` describe themselves on their well's node too: each is 4 elements and 2 render nodes in place of an empty box, down from 5 and 3, held by `checkbox_alone.toml`, `switch_alone.toml` and `radio_alone.toml`. A `FilterChip` carries its button description and its selection on its well's node: over a `Text` it is 15 elements and 10 render nodes, one of each fewer than before, held by `filter_chip_over_text.toml`. A tab and a `NavigationBar` destination describe themselves on their well's node, which carries the selection and folds the icon and label beneath it into one node (`Description::merges_descendants`): a `TabBar` of two text tabs is 41 elements and 24 render nodes in place of an empty box, down from 45 and 28, and a `NavigationBar` of two destinations is 51 and 26, down from 55 and 30, held by `tab_bar_alone.toml` (`perf_tab_bar_alone`) and `navigation_bar_alone.toml`. A `Chip` describes itself on its well too, a node of its own whether or not it is a button, as Flutter's `RawChip` is, its switch the chip's `enabled`: over a `Text` it is 14 elements and 9 render nodes, down from 15 and 10, held by `chip_over_text.toml` (`perf_chip_over_text`). `CupertinoButton` is its own node, its tap, long press and description on it: over a `Text` it is 9 elements and 6 render nodes, down from 13 and 8, its allocations and bytes held by `packages/flui-cupertino/perf/baseline/cupertino_button_over_text.toml` (`perf_cupertino_button_over_text`). Each item of a `CupertinoTabBar` is one interactive node, its selection described on it and its tap on it, in place of a `Semantics` and a `GestureDetector`: a bar of two items is 33 elements and 18 render nodes in place of an empty box, down from 41 and 22, held by `cupertino_tab_bar_alone.toml` (`perf_cupertino_tab_bar_alone`). A `ListTile` describes itself on its well, whose switch is the tile's `enabled` and which, with no handler, takes no tap, focus, live bindings or hover, as Flutter's `InkWell` without callbacks: over a `Text` it is 17 elements and 8 render nodes, down from 18 and 9, held by `list_tile_over_text.toml` (`perf_list_tile_over_text`). The second render node is the ink's `CustomPaint`, the price of the ink: it stays mounted at rest, because inserting it over the child at the first hover would remount the child and lose its state.
- What a `RawButton` adds to the `Text` it holds is counted by `perf_raw_button_over_text` (`crates/flui-widgets/tests/perf.rs`) and recorded in `crates/flui-widgets/perf/baseline/raw_button_over_text.toml`: the elements, the render nodes and the allocations are at the entry's numbers, and the bytes are about 3.6 KB, some 550 B over. What they hold is the node's view, held twice, in its parent and in its element (it carries a role and an identifier in place of the description, which the node builds while the window collects semantics); the focus node with its notifier, its listener and its measured rectangle; and what any element and render node cost to build, lay out and paint the first time. The levers measured so far, about 160 B, each change a public shape: a `FocusNodeRegistration` that holds its node by `Weak` (about 48 B); `ElementCore`'s `element_parent` and `sliver_slot` moved to a cold record (about 32 B); one source shared by the `RebuildHandle` and the signal `WriterSource` an element carries (about 48 B); and the recognizer slot's matching data kept once (about 32 B). The rest needs fewer allocations or a smaller element record.
- The entry closes when a `RawButton` adds to its child at most 2 elements, 1 render node, 40 allocations and 3 KB, asserted by that scenario. The `Text` itself is recorded by the same scenario (`text_allocations`, `text_bytes`) and is not this entry's condition. Until then no new widget family starts on the wrappers (`AGENTS.md`, "Working here").
- The scenario's baseline is below the migration threshold of ADR-0322 (2 elements, 1 render node, at most 40 allocations and at most 5 KB) and only falls: the run fails when a counter goes over it. The Material and Cupertino controls are on the node. The entry stays open until the bytes reach 3 KB.

### A label change allocates over a hundred times a frame

> **Environments:** all · **Who it hurts:** Every app that updates text while it animates or scrolls · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- `perf_scaling_a_label_change_costs_the_same_on_any_tree_size` (`crates/flui-widgets/tests/perf.rs`) changes one label over 500 and 5 000 buttons. The cost no longer grows with the tree: its allocations are equal at both sizes, and the callgrind step of CI's `perf-gates` job holds the instruction counts within 5%. Each frame still allocates more than a hundred times. The `label_change_*.toml` files of `crates/flui-widgets/perf/baseline/` hold the count, four frames per row.
- From a backtrace per allocation of that scenario, where each part goes:
  - **Text** (shaping and the shaped paragraph, about half): a painter whose text changes shapes into the buffers of the layout it dropped, so Parley allocates a fresh `Layout` only for a painter shaping for the first time; each shaping still fills Parley's style and break lists, and FLUI copies the spans' text, styles and run colours into the shaped paragraph. This lane is `flui-painting`'s `TextContext` and `TextPainter`, and it outlives the retained scene.
  - **Paint and layers** (about a third): fragment op vectors, display-list commands, and the `LayerTree` and `FragmentComposer` rebuilt every frame. This lane is the retained scene, `docs/plans/specs/render-scaling/` (RS4, RS8).
  - **View rebuild** (about a sixth): each rebuilt level hands its child to the reconciler in `ChildViews`, a child it holds as a `BoxedView` shared and unboxed, and the element clones the offered view without boxing it. What is left is the clone itself: an element copies the view it is offered, and a view that owns heap data (a `Text`'s string) allocates in that copy. This lane is `flui-view`'s element update path.
  - **The root's environment:** each rebuild of `MediaQueryRoot` copies the whole `MediaQueryData` (224 bytes) into a fresh `MediaQuery` view, one `Rc` (`crates/flui-runtime/src/media_query_root.rs`), so every field the data gains costs each full reassemble its size (`full_reassemble.toml`); the root could hand on a shared snapshot that a preference change replaces.
- The entry closes when a label change allocates at most 40 times a frame, held by those rows. It is measured after the retained scene lands; until then a bless on `main` (`FLUI_PERF_BASELINE=bless`) ratchets each row a change lowered.

### A clip in a node's own content under an ancestor's scale below 1

> **Environments:** all · **Who it hurts:** Apps that scale a scene node down (a thumbnail, a zoomed-out canvas), a window whose device pixel ratio is below 1 (a browser zoomed out, whose ratio transform sits above every boundary) over content a fractional clip cuts · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- A node's stored subtree bound is kept in its own space, and a clip in its content that cuts content away whole keeps the strip within one device pixel of that content, measured by the transforms and followers inside the content ([ADR-0304](adr/ADR-0304-the-scene-is-retained-and-damage-is-the-footprint-of-its-patch.md) §4). A transform above the node that scales by less than 1 is not known there and is taken at 1, so content up to `1/scale` units short of the clip falls outside the strip. The cull then drops the node, and the damage that reads the stored bound misses the pixel the clip's anti-aliased edge shares with that content: a placement of the node, a slot added for it, a composited update of an effect above it. A partial frame leaves that pixel stale. A repaint inside the node and a change of the clip itself map through the whole chain and take the pixel.
- `an_ancestor_scale_below_1_still_loses_the_pixel_a_content_clip_shares` (`crates/flui-layer/tests/scene_damage.rs`) pins the cull's miss and a placement's.
- The entry closes when a stored bound carries what the surface map needs to keep the strip under any scale, and that test asserts the cull keeps the node and the placement damages the pixel.

### An overflow clip cuts off paint but not semantics or input regions

> **Environments:** all · **Who it hurts:** Screen-reader users, who reach a child a `Stack`, `Wrap` or `FittedBox` clips out of view, and apps whose clipped-off child reports an input region (a system-gesture exclusion) the OS then honours · **Parity:** [Quality bar](platform-parity.md#quality-bar)

### Only Win32 says when the user places a window, and not for every placement

> **Environments:** desktop, mobile, web · **Who it hurts:** Users whose window could not read its remembered placement at launch and who then move it · **Parity:** [Windows](platform-parity.md#windows)

- `WindowState::interaction` states, on the report that carries a change, that the user is placing the window through the window system ([ADR-0343](adr/ADR-0343-the-owner-promises-turn-deadlines-and-the-window-states-user-placement.md) §2). A placement the run could not read is replaced only by a change whose report says `UserPlacing`, so wherever a host does not say it, a window that opened at its default because its read timed out, was refused or panicked keeps the stored placement and the user's move is not remembered that run.
- X11, UIKit, Android and the web state `WindowInteraction::Unknown` always; AppKit and Wayland state `UserResizing` during a live resize by the frame (ADR-0354 §4) and `Unknown` otherwise, so a move there is not remembered either. Each has a signal for the rest: AppKit's `inLiveResize` and the delegate's `windowWillMove:` during a title-bar drag, X11's `_NET_WM_MOVERESIZE` and a ConfigureNotify while the pointer button that started it is down, Wayland's `xdg_toplevel.move`/`resize`, which the client itself sends from a press; UIKit's scene resize in Stage Manager, Android's freeform resize and the browser window's resize are the user's too, and none is read.
- Win32 states it inside its size-move loop and for the `SC_MAXIMIZE`, `SC_MINIMIZE` and `SC_RESTORE` the user works. A Win+Left/Right or Win+Shift+Arrow snap moves the window outside both and reads `None`. A drag that ends in a snap whose rectangle lands after `WM_EXITSIZEMOVE` (an order not observed on this machine: input injected under the test runner did not reach the size-move loop) loses its placement only when nothing moved during the loop (outline dragging, Snap Layouts); once the drag moved the window, the recorder already counts the user's change and writes the snapped placement.
- The other way round, an application's command applied in an owner turn a Win32 modal loop gives during a drag (a `SetPosition` from a timer) is reported inside the loop and reads `UserPlacing`.
- The entry closes when each host states `UserPlacing` from its signal and `None` when it ends, with a test of the host that a move it reports during the signal reads `UserPlacing` and one after it reads `None`; on Win32, when a snap's placement reads `UserPlacing` and an application command inside the loop does not.

### Window placement restores neither a scale change on the same display nor an OS's tiled state

> **Environments:** desktop · **Who it hurts:** Users of a remembered window on a display whose scale changed between runs, or who tiled the window · **Parity:** [Windows](platform-parity.md#windows)

- A placement keeps the window's size in its display's logical pixels and records the scale, but `WindowPlacement::resolve` rescales only when the window opens on another display. A display that is the same (same `persistent_key`) at a different scale (125 % last run, 150 % now) restores the logical size, so the window covers more physical pixels than it did; Win32's `SetWindowPlacement` has the opposite defect (physical workspace coordinates, wrong at another DPI), and `tauri-plugin-window-state` and `electron-window-state` store physical pixels and carry it. Which is right is a decision: the logical size follows the system's own text scaling, the physical one what the user dragged.
- A window tiled by the system (Windows Snap, the macOS tiling of a top-edge drag, a GNOME half-screen) is remembered by what the host reports: Win32 reports a snapped window as `Normal` at the snapped rectangle, so it comes back at that rectangle, untiled; AppKit's stale `normal_geometry` after a tile is under [Window control has run only on Windows, an X11 test server and the AppKit conformance kit](#window-control-has-run-only-on-windows-an-x11-test-server-and-the-appkit-conformance-kit). No contract mode names a tiled state.
- The check is the placement table of `flui-platform` with a same-key display at another scale, and a run on Windows of a snapped window closed and reopened.

### No widget hot reload on Android and the Web

> **Environments:** Android, Web · **Who it hurts:** Developers who iterate on widget code on a phone or in a browser · **Parity:** none yet (hot reload has no row)

- Desktop and iOS reload widget code in place through `DevReloadHook` (ADR-0311 §4): a worker edit reassembles every UI runtime with its `State` kept. The Android runner drives only the scene hook, so `flui run --scene` reloads a `Scene` plugin, not the widget tree. The web drives no reload hook: `flui run --device browser:<browser>` reloads the page on every rebuild, and the page's state with it ([`hot-reload.md`](hot-reload.md), "WASM / Web").
- The likely shape on Android is the desktop's worker path, pushed to the device as the scene plugin is; on the Web, which has no `dlopen`, a code patcher (ADR-0311 §7).
- The check is a widget edit on an Android device and in a browser that reloads with a stateful counter's value kept.

### The window and capability areas of flui-platform import each other

> **Environments:** all · **Who it hurts:** A contributor who changes either area and has to build both; the rule that a crate's top-level modules import in one direction (AGENTS.md, "Rules a reader holds") · **Parity:** none (module graph)

- `flui-platform`'s areas import in one direction except these two. `PlatformWindow::portal_parent` takes a `capability::Resolver<capability::PortalParent>` (`crates/flui-platform/src/window/platform_window.rs`), and `capability::WindowRef` holds the window it names as a `Weak<dyn PlatformWindow>` beside its `WindowId` and `SurfaceTarget` (`crates/flui-platform/src/capability/window_ref.rs`). The two files named each other before the crate was grouped by area.
- The entry closes when one of the two areas stops naming the other, which is a change to the window contract or to the capability seam (ADR-0254, ADR-0151 §2), owned by the platform-layer feature.

### Two versions of zbus on Linux

> **Environments:** Linux · **Who it hurts:** Every Linux application, which compiles both D-Bus stacks · **Parity:** none (build graph)

- `flui-native` and `flui-system` speak D-Bus through zbus 6, while `accesskit_unix` 0.24.1, the newest release, reaches zbus 5 through `atspi`, so the default graph on Linux carries both with their `zvariant`, `zbus_names` and macro crates (`cargo tree -p flui -i zbus@5.19.0`). Moving FLUI's own D-Bus code back to zbus 5 would trade a current API for an unmaintained one (RUSTSEC-2026-0370 to -0372 in `deny.toml`).
- The entry closes when `accesskit_unix` moves to zbus 6: then the workspace resolves one zbus, the three advisories leave `deny.toml`, and `crates_linux` in `perf/size.toml` falls.

### Shaders are parsed from WGSL on every launch

> **Environments:** Windows, macOS, Linux, Android, iOS · **Who it hurts:** Every native application, which links naga's WGSL front end and parses its shaders before the first frame · **Parity:** none (build graph)

- `flui-engine` hands WGSL text to `create_shader_module`, so the first frame pays naga's parse and validation: 6.6 ms and 0.8 ms for the engine's 20 standalone modules (release, best of 20). Lowering them to `naga::Module` at build time would cut module creation from about 0.7–1.0 ms to 0.1 ms each on lavapipe, but buys no size: wgpu 30 enables `wgpu-core/wgsl` on every native target, because `wgpu-core` parses its own indirect-validation and timestamp shaders, so the front end stays linked (4,149,240 B with text, 4,191,296 B with `naga-ir` alone), and a serialized module adds 1.7 MiB of decoder.
- Driver pipeline compilation (6–10 ms a pipeline) dwarfs the parse. The first format's pipeline library is built on a worker from the slot's attach (ADR-0305 §1): with 100 ms of first build before the first frame, a cold first capture on lavapipe drops from 210–239 ms to 140–173 ms (bench `first_frame`, Mesa's cache off); what is left there is lavapipe's compilation at the first queue execution. On Vulkan the context's `wgpu::PipelineCache` is kept between runs in the application's machine-local storage (`crates/flui-engine/src/pipeline_store.rs`), for drivers without a disk cache of their own. Only what the warm-up built is saved: the runners stop admitting storage writes before the context retires, so another format's pipelines, effects and variants built on first use compile again at each launch. What the cache saves at launch has not been measured on an Android device.
- The entry closes when wgpu lets a native build drop the WGSL front end and the engine's shaders reach it as IR generated at build time, with the binary size and first-frame time measured before and after.

### A release build links the development agent's owner side

> **Environments:** all · **Who it hurts:** Every release application, which carries code only the driver agent reaches · **Parity:** none (build graph)

- `flui-app` serves the agent only under `cfg(driver_agent)` (a debug build, or the `driver` feature; ADR-0239), but `flui-runtime` compiles its owner side on every build: `UiCommand::Agent` is a variant the owner's drain matches, so the window methods (`ui_runtime::agent*`), the protocol types they answer with (`flui-protocol`), `flui_view::__runtime::Reply`, the recording wire conversions and `flui-semantics`' agent reads stay reachable in a release binary although nothing can send that command there. In the release counter CI's `size` job measures (Linux x86_64, symbols kept) they come to about 324 KB of the 21.7 MB.
- The entry closes when the agent's owner side, its command variant and the crates' agent modules compile only under the conditions `cfg(driver_agent)` reads (debug assertions or the `driver` feature), and `counter_release_bytes` and `counter_wasm_bytes` in `perf/size.toml` fall by what they measure.

### The native hosts' parsers of foreign bytes have no fuzz target

> **Environments:** Linux, Windows · **Who it hurts:** Applications whose process reads what another process sends: an input method's replies, clipboard and drag payloads, a compositor's arrays · **Parity:** none (robustness)

- `cargo xtask fuzz` runs two targets, `image_decode` and `agent_wire` ([testing.md](testing.md#fuzzing)). The parsers inside `flui-native` (the XIM codec, clipboard text, drag offer kinds, the Windows drag crossing, Wayland configure arrays) have property tests that draw their bytes at random and no coverage-guided run: they are `pub(crate)`, and a fuzz target is an example, which sees only its crate's public API.
- The entry closes when each has a target, reached through an item the crate's `testing` feature exports.

### JNI calls are hand-written signature strings

> **Environments:** Android · **Who it hurts:** Anyone who changes a JNI call: a misspelt class, method or descriptor compiles and fails only on a device · **Parity:** [Quality bar](platform-parity.md#quality-bar)

- `flui-native`'s Android host and `flui-system`'s Android providers call the SDK through `jni` with class names, method names and descriptors written by hand (`jni_str!`, `jni_sig!`); no compiler checks them, and each was read against `android.jar` once. ADR-0377 §5 sets the direction: typed bindings with `jni` 0.22's `bind_java_type!`, generated from `android.jar` by `jbindgen` and checked in.
- The entry closes when both crates call the SDK through generated bindings, the generation is a documented `xtask` step, and no hand-written descriptor of an SDK method is left.

### A stopped Android Activity runs no owner jobs

> **Environments:** Android · **Who it hurts:** Applications whose work must run while a full-screen activity covers FLUI: a request's ticket dropped while the picker it started is showing, a completion's closure, a timer · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle) (Activity results for capability providers)

- A paused Activity that stays on screen runs its owner jobs, frames and input (ADR-0366 §1). A stopped one runs none of the application's: the UI runtime's posted owner jobs and commands run in turns the window's redraw drives (`AppRuntime::owner_turn_window_poke` asks the window for one and declines while the window is not `Running`), and a stopped Activity draws no frame. A full-screen activity started for a result (a file or ringtone picker) stops FLUI, so a provider's code that would drop the ticket while the picker shows runs only when the user returns. The loop's own turn still runs: it drains `FluiHost`'s queue and routes answers, and the result bridge's sweep ends a request whose ticket was dropped before the Activity stopped and asks Java to cancel its activity.
- Seen in a device run on a Galaxy S21 (Android 15, 2026-11-16); dropping the ticket right after the launch, before the Activity stopped, cancelled the picker.
- The entry closes when a stopped Activity serves owner turns that carry no frame (posted jobs, completions, wakes) and only drawing waits for `onStart`, with a device run of a ticket dropped while a full-screen started activity is on top.

### An Android formatter loses keys typed faster than it answers

> **Environments:** Android · **Who it hurts:** Fields whose application rewrites the text on each edit (masks, upper-casing, length limits) · **Parity:** [Input](platform-parity.md#input) (IME composition and candidate placement)

- The application's text wins a race with the keyboard (ADR-0348 §3): a formatter that rewrites the text in answer to a replayed edit publishes a text snapshot, and a key the keyboard reported before the view took it is dropped while the keyboard restarts on the formatted text. Typing faster than one owner turn per key loses keys in such a field. A formatter that rewrites the composed word restarts the keyboard on every key where the keyboard composes every word (Gboard's Latin layouts).
- Read from the model (`a_text_snapshot_that_raced_an_edit_wins_and_restarts`). On a Galaxy S21 (Android 15, Samsung Keyboard, 2026-11-16) 20 letters tapped from `adb` about 100 ms apart while the application upper-cased the text every 700 ms all reached the field: the loss needs typing faster than that, which no run provoked.
- The entry closes when a text snapshot caused by replaying the view's own edit no longer counts as a race against the reports that followed it, with a test and a device run of a formatter under fast typing.

### android-activity logs a spurious looper callback sixty times a second

> **Environments:** Android · **Who it hurts:** Developers reading logcat, whose buffer the lines wrap · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle) (Event loop, startup and wake-ups)

- `android-activity` 0.6.1 (`native_activity/mod.rs:225`) logs "Spurious ALOOPER_POLL_CALLBACK" about sixty times a second on a Galaxy S21 (Android 15, 2026-11-16), enough to wrap the logcat buffer; nothing else was seen to go wrong.
- The entry closes when the loop no longer leaves a callback the looper reports as spurious, or the crate no longer logs it at that rate, checked in logcat on a device.

### A phone's background hold waits only for writes already running

> **Environments:** iOS · Android · **Who it hurts:** Applications whose earlier write failed or was refused just before the application left the screen · **Parity:** [App lifecycle](platform-parity.md#app-lifecycle) (Session end)

- When a phone's session end leaves writes in flight, the process is held until they end (ADR-0350 §2). A value owed but not started then (an earlier write failed, or the IO pool refused it) is not written in the background: nothing starts a write off the owner thread, and the owner gets no turns while an Android Activity is stopped. The value is named in the log as unstored.
- The entry closes when the hold starts and retries the owed values within its window, with a headless test of a failed write stored in the background.

### Desktop probes drive the desktop the user works on

> **Environments:** Windows · **Who it hurts:** Contributors whose machine runs the probes, and the probes, which fail when the user moves the mouse · **Parity:** none (test infrastructure)

- nextest runs every Windows test on a desktop of its own ([`testing.md`](testing.md#the-windows-test-desktop), ADR-0355), but injected input and the cursor belong to the desktop that takes the user's input. `windows_foreground`, the contract rows in `NEED_THE_INPUT_DESKTOP`, the drop through OLE's loop (`a_drag_into_a_window_of_this_process_drops_through_the_loop`), flui-native's `text_services_probe` and desktop-mcp's `#[ignore]` tests therefore run only on the user's desktop, by hand or on the nightly runner, and a person using the mouse or keyboard meanwhile breaks them; desktop-mcp's server drives whatever desktop it runs on. flui-driver's Windows lane reads the desktop it runs on and sends nothing off the input desktop, so its OS-input runs (`windows_desktop::the_device_check_scenarios_run_through_the_os_lane`, `the_conformance_scenario_runs_through_the_os_lane`, `a_foreign_mouse_move_mid_run_ends_it_and_releases_its_input`) and its compositor capture (`the_compositor_captures_the_apps_window_alone`, a window there having no area) are `cannot_verify` on the test desktop and pass only on the input desktop, where its user-activity guard ends a run on the first input it did not send.
- A form that runs unattended on the test desktop sends what the probe injects as the window messages input becomes (`WM_POINTER*`, `WM_KEYDOWN`/`WM_CHAR` through the window's own queue) or acts through UI Automation patterns, and reads positions from the window instead of the cursor; what only real input proves (the foreground lock, the input method's own keyboard hook, the OS's pointer routing) stays a run on a device. A separate session for the probes (a loopback remote session, Windows Sandbox) would give them a desktop that takes input without the user's, at the cost of a sign-in or an optional Windows feature.
- The entry closes when each listed case either runs on the test desktop with what it proves unchanged or is a row of `crates/flui-native/platform-parity.toml` run on a device.

### The headless host lacks the runner's host bridge, and its owner-turn rows run only headless

> **Environments:** headless (`flui-testing`) · **Who it hurts:** Application authors whose test on `HeadlessHost` or `Tester` should prove what a runner does · **Parity:** none (test infrastructure)

- The close, quit and session-end steps and the built-in composition live in `flui-runtime` (`owner_turn`, `capability::BuiltIns`), and the runner and the headless host both call them. What the headless host still composes without: the host bridge that carries activity results (its registry passes `HostBridge::new()` in `crates/flui-testing/src/host/registrations.rs`, where a runner offers its own), and the native-window capability, which names a type of `flui-app` (`native` feature). A widget that reaches `flui::native` or an activity result is tested on `flui_app::testing`.
- The table `close_guard_hosting` (`crates/flui-testing/tests/close_guard.rs`) runs on the headless host alone; the runner's suite (`crates/flui-app/tests/runner_close.rs`) pins the same rules in rows of its own, so a divergence between the two hosts' side of a step (what a close, a teardown or a flush does to each host's state) shows only where both suites cover it.
- The entry closes when the headless registry offers a host bridge that delivers activity results, and the `close_guard_hosting` rows run on `flui_app::testing`'s runner as well as on the headless host.

### Some shipped native arms are compiled by no CI job

> **Environments:** macOS (x86_64), Android (32-bit and x86 ABIs), Windows, macOS, Linux · **Who it hurts:** Applications built for an Intel Mac or a 32-bit Android ABI, and applications built without a feature a crate's own tests turn on · **Parity:** none (build coverage)

- CI's `cross-typecheck` job lints four triples (`x86_64-pc-windows-msvc`, `aarch64-apple-darwin`, `aarch64-linux-android`, `aarch64-apple-ios`; ADR-0383 §6). `flui build` also ships x86_64 macOS (`platform-support.toml` gives it a floor) and the armeabi-v7a, x86 and x86_64 Android ABIs, and flui-native has arms only those reach: `cfg(not(target_arch = "aarch64"))` in `display/apple/macos.rs` and `display/apple/mod.rs`, `cfg(not(target_pointer_width = "64"))` in `owner/android/ndk.rs`. The nightly legs run arm64 macOS and x86_64 Android, so neither reaches them.
- Every native run compiles `--all-targets`, so the features a crate's own dev-dependency on itself names (flui-native's `testing`, `http` and `single-instance`, flui-app's with `unstable-windows`) are on in its library: the arm an application gets without them, such as flui-native's `single_instance` stub on Windows and Linux, is compiled by no Windows or macOS run.
- The entry closes when a leg compiles x86_64 macOS and a 32-bit Android ABI, and each native leg lints `--workspace --lib --bins` with default features, the configuration an application builds.
