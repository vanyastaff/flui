## Decisions this decomposition fixes (read before dispatching any task)

**D1 — The per-child boundary is a code REGION (the user-hook windows), not the whole insert, and never a payload filter.** `mount_or_substitute` catches around exactly two windows inside `ElementTree::insert_with_provisional_order`: the fresh element's `mount` (user `create_render_object` / `did_mount_render_object`, reported before it runs as `InsertedChild::Minted`) and the retake's `update` (user `update_render_object` / `did_update_view`, reported as `InsertedChild::Retaken`). Framework-raised panics outside those windows keep propagating exactly as today: `retake_active_global_key`'s debug-only eager "duplicate GlobalKey children are not allowed" rejection and `register_global_key_with_collision_check` — the ADR-0050 model (`crates/flui-view/AGENTS.md` bullet 1; memory `global-key-duplicate-model-diverges`) and the two pins `tests/global_key.rs::duplicate_global_key_panics_in_debug` / `tests/global_key_duplication.rs::one_key_twice_under_the_same_parent_is_rejected` stay untouched. A `BUG:` raised INSIDE a window (the adoption `with_mut` inside `RenderBehavior::on_mount`) is contained and classified `internal_invariant: true` (AC7) — the region decides, the prefix only labels. Consequence for the sparse path: `sparse_children::mount_sparse_child` today wraps the WHOLE insert; after the extraction a framework panic between the windows propagates through a lazy list as it does through a dense parent. No sparse test pins the old shape (`rg -n "duplicate" crates/flui-view/src/element/sparse_children.rs` → prose only). ★ `chief-architect` rules on D1 before task 3.2 is dispatched; the alternative (whole-insert region, flipping the two GlobalKey pins to "substituted + reported") is recorded as rejected unless the ruling says otherwise.

**D2 — Inside PR-2b, seam (b) lands before seam (a).** Seam (b) (per-insert/per-update inside `reconcile_children_by_id`) flips no existing pin and needs only the PR-2a primitives; seam (a) (the phase-1 `Err` arm) flips four pins across two crates (D3) and needs the new `ElementTree::replace_child_with`. Neither depends on the other: seam (a) runs in the failing CHILD's drain iteration, after its parent's phase-2 reconcile already committed `child_ids`; seam (b) runs inside the PARENT's phase-2. (b) first is the safe order.

**D3 — The spec's "flipped pin" is the wrong test; here are the real ones.** `tests/inherited_dependency.rs::init_state_panic_leaves_the_slot_intact_not_a_hole` mounts `PanicOnInit` as the ROOT (`tree.mount_root`), and a root without a parent still propagates under seam (a) (spec: Flutter `runApp` fatal) — it stays green and is KEPT as the root-propagates pin (rename to say "root"). The pins seam (a) actually flips: (1) `tests/inherited_dependency.rs::did_change_dependencies_panic_leaves_the_slot_intact_not_a_hole` (the dependent is `tree.insert`ed under the provider — a child); (2) `src/owner/build_owner.rs::tests::scoped_drain_unwind_restores_foreign_work_reasons_dependency_and_flags` (`DependencyPanicView` is a child of the scope root); (3)+(4) `crates/flui-widgets/src/localization/localizations.rs::tests::{locale_of_panics_with_no_localizations_ancestor, of_panic_message_names_the_requested_type}` — `#[should_panic]` driven by an `init_state` probe mounted as a CHILD of `flui_widgets::testing::mount`'s scope wrappers. Seam (c) (PR-2a) additionally flips `crates/flui-app/src/app/ui_realm.rs::frame_failure_containment::a_dispose_panic_is_contained_to_its_own_presentation_and_the_sibling_still_frames` (it drives a REAL `dispose` panic). Every flip is re-targeted in the task that causes it, never deferred.

**D4 — PR-1 lives in `crates/flui-rendering/tests/layout_poison.rs` with one testing-gated accessor.** `PipelineOwner::layout_poison` is a private field; `LayoutPoison::is_poisoned` is `pub(super)`. A same-crate unit test cannot use `flui_objects::RenderPadding` (flui-objects links the NON-test build of flui-rendering, so its `RenderBox` is a different trait than `crate::traits::RenderBox` in a `cfg(test)` build), so the fixture goes into the integration binary and gets `#[cfg(any(test, feature = "testing"))] pub fn is_layout_poisoned(&self, id: RenderId) -> bool` on `PipelineOwner` — the same gate `parent_data_seeds` already uses (`pipeline/owner/mod.rs`). Not a public production accessor. The parent that "continues on the substitute" is `flui_objects::RenderPadding` (already a fixture in that file): every box parent continues, because the child-layout callback in `subtree_arena.rs::layout_subtree_borrowed_impl` returns a `Size` and never an `Err` — `Size::ZERO` on the failing walk, the poisoned node's `geometry_box().unwrap_or(ZERO)` stand-in on every later walk.

**D5 — PR-0 is ONE commit; the census is seven production copies plus one test copy, and the test helpers go too.** Production: `flui-platform/src/shared/panic_boundary.rs::panic_payload_message`; `flui-app/src/app/ui_realm.rs::UiRealm::draw_frame_entered` (`Err(payload)` arm); `flui-app/src/app/close_request.rs::panic_message`; `flui-rendering/src/storage/entry.rs::RenderEntry::layout_leaf_only`; `flui-rendering/src/pipeline/owner/subtree_arena.rs::layout_subtree_borrowed_impl` and `::layout_sliver_subtree_borrowed_impl`; `flui-view/src/view/error.rs::FlutterError::from_panic`. The spec's eighth is `flui-rendering/src/pipeline/owner/cell.rs::tests::with_mut_reentry_panics` — a `#[cfg(test)]` copy. Three more test-only helpers carry the same dance (`flui-view/src/owner/build_owner.rs::tests::panic_message`, `flui-view/src/owner/global_key_scope.rs::tests::panic_message`, `flui-widgets/src/overlay/tests.rs` — the last two lines carry `PORT-CHECK-OK-DOWNCAST` markers that disappear with them); they migrate in the same commit so the acceptance grep is an exact zero, not a list of exceptions. Five fallback spellings, all KEPT at their call sites (no asserted message changes): `OPAQUE_PANIC_PAYLOAD = "non-string panic payload"` (platform), `"(non-string panic payload)"` (the three rendering sites), `"panic during build (non-string payload)"` (`from_panic`), `"<non-string panic payload>"` (the tracing renderings in `ui_realm.rs::report_frame_failure` and `close_request.rs`'s handler-panic site, and the test helpers), and `None` (the typed `Option<Box<str>>` on `FrameFailureKind::SegmentPanic.message`, `close_request::panic_message`'s pin). `close_request::panic_message` and its `cfg_attr(dead_code)` dance are deleted; its pin (`a_panic_payload_keeps_its_message`: literal → `Some`, formatted → `Some`, `panic_any(41_u8)` → `None`) moves to `flui_foundation::panic`'s unit tests verbatim. `is_internal_invariant` has exactly one production caller today (`draw_frame_entered`'s `starts_with("BUG:")`); PR-2a adds the second.

**D6 — `RecoveredPanic` carries `internal_invariant: bool`, computed at push time.** The spec's shape (`{ element, parent, view_type_id, hook, error }`) cannot satisfy AC7 ("reported with `internal_invariant: true`") once PR-3 redacts the message in release — classification must happen in flui-view on the raw payload, before any redaction. `RecoveredPanic::from_payload(..)` computes it with `flui_foundation::panic::{payload_text, is_internal_invariant}`; PR-3's `FrameFailureKind::RecoveredPanic` gains the same field (shared-contract row below).

**D7 — `RecoveredPanic.parent` is `Option<ElementId>` and is `None` at the `Dispose` seam.** `ElementCore` does not record its parent id (`ElementCore::mount` ignores its `_parent` argument; only `ElementNode::parent()` knows it), and `StatefulBehavior::on_unmount` sees only `core`. AC13 requires `element`, `view_type_id`, `hook` — not `parent`. Seams (a) and (b) fill it (they run at the tree/drain level where it is known); the dispose seam pushes `None`, documented on the field. `api-design-lead` may instead have `ElementCore::mount` store the parent (the argument is already there) if a consumer wants it — a retake must then update it in `retake_active_global_key`; that cost is why the default is `None`.

**D8 — `LifecycleHook::{Build, InitState, DidChangeDependencies, Mount, Update, Deactivate, Dispose, UnmountRenderObject, Listenable}`, and seam (a) learns which hook by a marker, not by guessing.** The phase-1 closure runs `notify_dependency_change` (→ `did_change_dependencies`) and then `build_into_views` (→ `init_state`, then the already-caught `build`). `StatefulBehavior` calls `owner.note_entering_hook(LifecycleHook::InitState)` / `DidChangeDependencies` immediately before each user call (a plain `Cell`-backed field on `BuildOwner`, threaded through `ElementOwner`); seam (a)'s `Err` arm reads it. `Mount` covers `create_render_object` + `did_mount_render_object`; `Update` covers `did_update_view` + `update_render_object` (the `FlutterError.details` breadcrumb carries the finer name). Seam (c)'s four removal-path hooks (spec v2) get their own variants so AC6's per-hook report is exact.

**D9 — AC6's report half is PR-3's; PR-2a's AC6 evidence is the flui-view drain.** Until PR-3 forwards the drain, a contained removal-path panic is observable only as `BuildOwner::take_recovered_panics()` → `[{ hook: Dispose | Deactivate | UnmountRenderObject | Listenable, .. }]` plus `tracing`. The flui-app headline test (D3) `a_dispose_panic_is_contained_…` drives a REAL `dispose` panic that seam (c) contains; with spec v2 also bounding `deactivate`, no real user-hook escape path is left on the removal side — the test is re-targeted in the SAME task (3.3) to the `set_segment_probe` route five sibling tests already use, with the doc stating that the real-path containment claims now live in flui-view's suite (the realm-level containment of a user hook that IS still unbounded — the realm pre-phase — is a separate residual, named in ADR-0048).

**D10 — Drain first, then the seams that feed it.** Inside PR-2a the order is 3.1 drain type + `take_recovered_panics()` + `build_or_recover` feed → 3.2 extraction (the primitives push `Mount`/`Update`) → 3.3 seam (c) (pushes the four removal-path hooks). A seam whose report has nowhere to go for a commit is the "shipped seam never wired" class this repo keeps finding; the drain costs one type and five `ElementOwner` construction sites and has its own born-red test.

**Gate per task.** Every task ends green on `just gate` (fmt-check → text-check → inventory-check → runtime-conformance-check → panic-policy-check → port-check → clippy `--workspace --all-targets --locked -D warnings` → doc-strict) plus the crate suites named in its row. PR-level: `just ci` (= gate + `test-ci` + `test-doc`). Sizes: S ≤ ~150 changed lines in ≤ 3 files; M ≤ ~400 lines in ≤ 6 files; L beyond. ★ = sign-off required before the row is marked done. nextest filters use `-E`; flui-rendering's integration tests are ONE binary (`--test rendering_it`), flui-view's are ONE binary (`--test view_it`) except `error_view_recovery` (its own target, process-global builder).
