# Survey: reentrant focus changes during notification (issue #1040)

Read from primary sources on 2026-09-15; third-party text is reported, not adopted.

## Flutter (reference, tag 3.44.0, `.flutter/packages/flutter/lib/src/widgets/focus_manager.dart`)
- `requestFocus` doc: *"The node is notified that it has received the primary focus in a microtask, so notification may lag the request by up to one frame."* — deferral is the contract.
- `applyFocusChangesIfNeeded`: applies `_markedForFocus` (a single slot — the LAST request before the microtask wins), notifies dirty nodes, then `notifyListeners()` once if `previousFocus != _primaryFocus`. A `requestFocus` issued from a node's `_notify` sets `_markedForFocus` and `_markNeedsUpdate` schedules the next microtask → it becomes the NEXT transition, published after this one. Chronological by construction; a ping-pong pair livelocks across microtasks but yields frames.
- `_HighlightModeManager.notifyListeners` snapshots the listener list and skips a listener removed during dispatch (`if (_listeners.contains(listener))`), catching and reporting listener exceptions per listener.
- Issue tracker (`gh search issues --repo flutter/flutter`, six queries around requestFocus/listener/reentrancy): no report of stale or reversed manager notifications — the deferral removes the failure mode by design; the closest hits are lifecycle gaps (flutter#156285 `onFocusChanged(false)` not called on detach).

- Origin of the deferral — flutter/flutter#9074 (2017, "Improve focus management"), PR body verbatim: *"Focus notifications trigger by tree mutations are now delayed by one frame, which is necessary to handle certain complex tree mutations. In the common case of focus changes being triggered by user input, the focus notificiation still arives in the same frame."* — the microtask was introduced for tree-mutation coherence; reentrancy safety is a consequence, not the motive.
- Tracker search widened (13 queries over open+closed: listener/stale/microtask/loop/`_markedForFocus`/`applyFocusChangesIfNeeded`; commit search on `focus_manager.dart` back to 2017): no design-level report of stale or reversed manager notifications exists — consistent with the deferral removing the failure mode. flutter#143556 (2024, `_suspendedNode`) and #191508 (2026, a `ViewFocusEvent` handler measuring a just-mounted overlay) are the nearest: both are "focus work ran at a moment the tree was not ready", the class the one-frame delay was built for.

## Jetpack Compose (`androidx.compose.ui.focus.FocusTransactionManager`, introduced 2023-06, fetched via mirror commits)
- KDoc, verbatim: *"This manager provides a way to ensure that only one focus transaction is running at a time. We use this to prevent re-entrant focus operations. Starting a new transaction automatically cancels the previous transaction and reverts any focus state changes made during that transaction."*
- Commit message: *"if the user performs a requestFocus() from an onFocusChanged call, we revert the state of the previous transaction before performing the new requestFocus()"*; the test `reentrantRequestFocus_byCallingRequestFocusWithinOnFocusChanged` notes *"Before introducing the focus transaction system this would cause a crash (b/275633128)."*
- Follow-up fix (b/319817633, b/312524818): *"When a focus transaction is cancelled we now send an onFocusEvent"* — reverting silently left observers stale, so cancellation itself had to become an observable event. `requestFocus` passes `onCancelled = { if (node.isAttached) dispatchFocusCallbacks() }`.
- Shape: last-wins with REVERT of the in-flight transition, plus cancellation notifications to keep observers coherent.

## Browsers (WHATWG HTML)
- The spec once had a *"locked for focus"* flag on `focus()` — a nested `focus()` on the element being focused was ignored. whatwg/html#11177 (2025): *"`locked for focus` is used to prevent calling focus() on the same element synchronously, this doesn't seem to be implemented in Webkit and Blink, and Gecko seems to have it half implemented … Webkit/Blink seems to just rely on the `too much recursion` error."* Removed by whatwg/html#11182 (2025-04); web-platform-tests #51920 now asserts it is NOT implemented.
- Shape: synchronous nested dispatch; per-element `blur`/`focus` events fire at commit time, so ordering is chronological by construction; the only bound on a ping-pong is the engine's recursion limit.


## GPUI (zed-industries/zed `crates/gpui/src/window.rs`, main, downloaded 2026-09-15)
- `Window::focus` only records intent: sets `self.focus = Some(handle.id)`, bumps `focus_generation`, calls `self.refresh()`. **Focus-changed events are computed at draw time** in `Window::draw`, as a diff of the rendered frame's focus path: `previous_focus_path = self.rendered_frame.focus_path()` … swap frames … `current_focus_path = …`; `if previous_focus_path != current_focus_path { … focus_listeners.retain(|l| l(&WindowFocusEvent { previous_focus_path, current_focus_path }, ..)) }`.
- Reentrancy is handled by deferral to the NEXT frame, verbatim: *"Focus listeners may move focus (e.g. a dock forwarding focus to its active panel). `Window::focus` suppresses `refresh` while a draw is in progress, so schedule another frame here to render the new focus state and dispatch the resulting focus events."* (`if self.focus != focus_before_listeners { self.refresh(); }`).
- They hit the loop, verbatim: *"The focus-lost fallback (e.g. a workspace refocusing itself) may target an element that isn't part of the element tree, in which case scheduling a redraw below would dispatch focus-lost again, looping forever. Only track focus movement caused by the focus listeners."* — a real ping-pong bug in production, mitigated by narrowing what counts as listener-caused movement, not by a budget.
- Zed's issue tracker (focus + reentrant/stale/loop/handle): nothing — the design records the incident in a source comment, not an issue.

## Masonry / Xilem (`masonry_core/src/passes/update.rs`, main, fetched)
- `request_focus` writes a pending slot (`global_state.next_focused_widget`); `run_update_focus_pass` commits it (`focused_widget = next_focused`) and delivers `Update::FocusChanged(false)` to the old widget and `FocusChanged(true)` to the new one — last-wins, applied in a pass after event handling, Flutter's family.
- Their own reentrancy note, verbatim: *"Note: handling of the Ime::Disabled event sent above may have changed the next focused widget. In particular, focus may have changed back to the original widget we just disabled IME for."* Tracker: linebender/xilem#390 ("Improve focus handling", open since 2024-06: *"uses architecture inherited from Druid that could be strongly simplified"*), #1143 (`has_focus_target` flag broken) — no reentrancy report.

## Qt (widgets)
- Synchronous nested dispatch: `QWidget::setFocus` from inside `focusInEvent` runs recursively; `QApplication::focusChanged(old, new)` is emitted per change, synchronously, and skipped for `Qt::NoFocusReason` (QTBUG-77364 fixed `setFocusProxy` bypassing the signal path). The loop class is documented in the wild ("Infinite focus loop in QT", 2025: a dialog opened from `focusInEvent` re-acquires focus on close → recursion); Qt's tool against it is `QFocusEvent::reason()` so a handler can decline to react to its own cause — no engine-side bound.

## What this settles for FLUI
- **Ordering:** FIFO application after the in-flight notification = Flutter's observable contract ("a nested request is the next transition") without the up-to-one-frame lag; every accepted request is published (a superset of Flutter's last-wins batching, confined to the reentrant window). Chosen over Compose's revert model because revert forces a second notification kind (cancellation) to keep observers coherent — more surface, no gain for a synchronous manager — and over the browsers' unbounded recursion.
- **Bound:** a synchronous drain needs an explicit budget (Flutter yields frames, browsers hit a recursion error, Compose reverts, GPUI shipped a "looping forever" bug and narrowed the trigger, Qt hands the handler a `reason()`); FLUI warns once and drops the rest — the house rule for caller-induced loops. GPUI's `focus_generation` counter is the same idea as the issue's "revision/commit check"; FLUI's queue makes the revision implicit (a queued request is applied after, never compared against).
- **Listener removal during dispatch:** Flutter skips a listener removed mid-dispatch; FLUI's `notify_listeners` must do the same (verify; it is part of "one defined contract").
- **Oracle:** the issue's scenario publishes `[(A, B), (B, C)]`; the node-replacement path keeps `[(child, sibling)]` (no outer edge when primary did not move).
