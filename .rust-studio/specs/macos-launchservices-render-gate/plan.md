# Plan — macOS launch-route render gate, and the blank-window record it closes

Status: **closed as a gate plus a corrected record (2026-09-20, real Mac).** The defect the record
named — a LaunchServices-launched bundle showing a blank window while the same bundle rendered when
started directly — **did not reproduce** in any of the measurements taken here (three launch routes
on the fixture the record used, and on a second artifact built through the CLI). What was missing
was not a fix but a *checker*: the observation had no denominator and no oracle, so it could neither
be confirmed nor retired. This task adds the checker (`scripts/check-macos-launch-render.py`,
`just macos-launch-render`), validates it against a genuinely blank window, and rewrites the record
to what was measured. The residual is stated in §6, not hidden: the original observation's cause is
still unattributed, and this gate cannot run in CI.

## 1. Task and where it comes from

`docs/BETA.md:399-401`, in the beta-preparation report's Priority #1 ("close the remaining
real-launch problems: iOS safe areas, CLI and input verification, the blank window when launching
macOS through LaunchServices"):

> A separate LaunchServices/background launch still showed a blank window; that rendering/startup
> issue remains open and is not covered by the direct-launch result.

The direct-launch counterpart in the same record is a normal result: "native UI interaction advanced
0 → 1 → 2, then closing the window logged both window close and platform quit and returned exit code
0 without a signal."

Read literally, this is a *user-facing* claim about the most ordinary way a macOS app is started —
a double-click in Finder — and it was the only entry in Priority #1 with no probe behind it. The
task is therefore twofold: measure it with a denominator, and if it does not reproduce, replace the
sentence with the measurement rather than quietly deleting it.

## 2. What was established empirically

All on the same host, 2026-09-20, macOS on Apple silicon, GUI session active, Screen Recording
granted to the controlling terminal.

### 2.1 The frame source runs under LaunchServices

`frame_pump_probe` (the `just macos-frame-pump` fixture, which counts frames from a real visible
window whose callback re-arms itself) staged into a minimal `.app` and started with `open`:
**300 frames at ~100 fps, `FRAME_PUMP_PROBE_RESULT=PASS`**, wall clock ~3.5 s — the same as the
direct run. Frames arrive under LaunchServices. This alone refutes "startup never reached the frame
pump" as an explanation, though not "it rendered frames into a window that stayed blank".

### 2.2 The artifact the record used renders under every route

The exact artifact class the record describes — generated by `flui create --local=<workspace>` and
built by `flui build desktop` into `target/flui-out/desktop/ls_counter.app` (83.16 MB, 1 m 26 s
build) — ran through the gate itself, 3 routes × 3 launches = **9 launches, 9 rendered**, 10
distinct colour buckets on every one of them. Its window content is 99.94 % a single colour and
0.06 % ink, and the ink is exactly where a rendered label belongs: one compact cluster, x[346,453]
y[103,137] inside an 800×632 window, in antialiased blue-purple glyph colours. The window was
present in each arm (800×632, layer 0) and the app was alive at capture time.

That thin margin is recorded rather than rounded up: a 0.06 % ink share would not distinguish this
bundle from a window that had drawn almost nothing, and it is the reason the in-repo fixture is
checked by colour (§3) instead. What the counter bundle does establish is that the CLI's own build
output renders under both LaunchServices routes.

### 2.3 The in-repo fixture renders under every route, five times each

`examples/colored_box_app` (a `RenderColoredBox::red` through the full view → element → render →
scene → wgpu pipeline) staged into a minimal `.app`, 3 routes × 5 launches = **15 launches, 15
rendered**, every one with its own window number — 2437 2447 2455 2465 2473 / 2483 2491 2501 2509
2519 / 2527 2530 2531 2534 2535, no arm observing a predecessor's window (§4.2):

| route | launches | content region |
|---|---|---|
| direct `exec` | 5 | 100 % of samples within ±32 of `rgb(240,0,0)` |
| `open` (LaunchServices) | 5 | same |
| `open -g` (LaunchServices, not activated) | 5 | same |

Whole-image composition of one capture (800×632, title bar included): **94.92 % red, 4.87 % title
bar**, plus traffic-light pixels at the chrome row — i.e. the capture is the real window, chrome and
all, and the content area below the title bar is the fixture's red. The title bar is 32 px of 632 =
5.06 %, which is what the 4.87 % measures.

### 2.4 The recorded sentence appeared *after* the frame-pump fix

The sentence entered `docs/BETA.md` on 2026-09-19 (`0ae979fd`), i.e. two days **after** the AppKit
`setNeedsDisplay:`-inside-`drawRect:` defect was fixed (2026-09-17, `just macos-frame-pump`), and
that defect is the one that produced a rendered-but-frozen window with exactly this signature. The
likely reading is therefore that the observation predates the fix and the sentence was carried
forward. **This is inference, not measurement** — the observation has no log, no image and no
revision attached, so it cannot be attributed retroactively and is not claimed to be.

## 3. The gate

`scripts/check-macos-launch-render.py`, driven by `just macos-launch-render`.

- **Three arms**, in order: `direct` (`Popen`), `launchservices` (`open <bundle>`), and
  `launchservices-background` (`open -g <bundle>`). The direct arm is the control: if it fails too,
  the launch route is not what broke.
- **The oracle is pixels**, not frames and not process survival — a window can exist, hold a live
  frame pump, and still show nothing. The same lesson is already recorded in this repository for
  iOS arm 2 of `just ios-sim`, where the app kept logging frames while the screen stayed white
  because UIKit repainted an empty layer over the Metal layer.
- **The capture is `screencapture -x -o -l<window number>`**: the window's own backing store, not a
  screen region. A full-screen grab would photograph whatever is on top of an occluded or
  never-activated app and make the background arm a tautology — it would pass by photographing the
  *previous* window in the z-order.
- **The window number comes from `scripts/macos-window-list.swift`** (`CGWindowListCopyWindowInfo`).
  Enumerating windows requires a CoreGraphics caller: system Python has no pyobjc (`import Quartz`
  fails) and re-binding the CoreFoundation object graph through `ctypes` is a lot of load-bearing
  FFI for one integer. The helper is compiled once with `swiftc -O` and reused (`swift` would
  recompile on every poll).
- **The window is matched by owning PID, never by owner name** (§4.2).
- **Two oracles.** With `--expect R,G,B` the content region must contain that colour in ≥1 % of
  samples; without it, the region must hold ≥4 distinct colour buckets (32-wide per channel, so
  antialiasing inside one flat fill does not inflate the count). The `--expect` form is used for
  the in-repo fixture because its window is legitimately one flat colour and the flatness oracle
  alone would call it blank. Every launch also prints `ink=` — the share of samples outside the
  dominant colour — so a pass carries how much was drawn and not only that something was
  (§2.2 is why that matters).
- **Chrome is excluded** from the oracle's region: the capture includes the title bar, and sampling
  it would let traffic lights and window text stand in for a rendering app. Insets are
  proportional (6 % left/right, 13 % top, 5 % bottom) because the title bar is a fixed ~32 points
  while the capture is in device pixels.
- **Exit codes** are part of the contract: `0` all launches rendered, `1` a launch was refused /
  put no window on screen / put up a window with nothing in it, `2` the host could not be measured.
  The justfile recipe propagates `2` as a loud non-pass with its own message.

**Screen Recording is preflighted** with `CGPreflightScreenCaptureAccess()`. A denied capture and a
blank window look identical in the resulting image, so without this the gate could not distinguish
them; a denial exits `2` and decides nothing. This is the one input the gate takes from the host
rather than from the artifact.

### Rejected alternatives

| alternative | why not |
|---|---|
| whole-screen capture | occluded/backgrounded windows would photograph the wrong thing and false-pass (§3) |
| pyobjc `Quartz` for the window list | not installed on system Python, and not a dependency worth adding for one field |
| `ctypes` CoreGraphics object graph | unbounded FFI for `kCGWindowNumber` when a 20-line Swift helper is exact |
| in-app self-capture probe | changes shipped code for a verification gate, adds a dependency, and photographs the app with the app's own permission context |
| `readback_dump` | `#[cfg(test)]` + `#[cfg(feature = "testing")]`, driven by `FLUI_READBACK_DUMP_DIR`; unusable from a production-path launch |
| owner-name window matching | would accept a predecessor arm's window (§4.2) |

## 4. Validating the gate itself

A gate that passes is not evidence that it discriminates, so it was run against an artifact that
must fail.

### 4.1 Negative control — a genuinely blank window

A 20-line AppKit program (`NSWindow` + `makeKeyAndOrderFront`, nothing drawn) staged into a minimal
`.app`:

| oracle | direct | `open` | `open -g` |
|---|---|---|---|
| flatness (no `--expect`) | FAIL (1 bucket, ink 0.00 %, 100 % `(32,32,32)`) | FAIL | FAIL |
| colour (`--expect 240,0,0`) | FAIL (0.00 %) | FAIL | FAIL |

**3 of 3 launches failed under both oracles**, on the same routes where the fixture passed 15 of 15
and the counter bundle passed 9 of 9. The oracle separates "something was drawn" from "nothing was
drawn" and does not merely pass.

### 4.2 Two defects the validation exposed in the checker

- **Owner-name matching was a tautology.** An earlier revision matched the window by owner name, and
  three consecutive arms all reported *the same window number* — the first arm's window, whose
  process had not been reaped. A launch route that started nothing would have been reported as
  rendering, on the strength of the previous arm's window. Fixed: matching is by owning PID, and
  `stop()` now waits (bounded, 15 s) for the process to leave the table before the next arm starts.
  After the fix every run reports its own window number (the 15 in §2.3 are all distinct).
- **`open` refusing a bundle crashed the checker** instead of being classified. Fixed: a refused
  launch is a FAIL for that arm carrying `open`'s own message.

That second fix immediately earned its keep, because it caught a real launch-route difference: the
first blank control was compiled by `swiftc` with the *default* deployment target and came out
`minos 28.0` on this host, and LaunchServices **refused to open it** (`_LSOpenURLsWithCompletionHandler()
failed with error -10825`) while a direct `exec` of the same binary ran fine and put a window on
screen. LaunchServices enforces the bundle's minimum OS version where the shell does not. That is
exactly the class of route-dependent behaviour this gate exists to see, and it is why the control is
built with `-target arm64-apple-macos11.0`.

## 5. The record, corrected

The paragraph this task opened from lives under `docs/BETA.md` § "Native macOS last-window exit",
and it now carries the measurement instead of the open defect: the three routes, the launch counts,
the per-launch window numbers, the counter bundle's numbers, the control that fails, the Screen
Recording caveat, and the explicit statement that the old sentence's cause is unattributed. The
sentence itself is not deleted — it is quoted as the state the task opened from, so a reader can see
what changed and why. The `minos`/`-10825` finding from §4.2 is recorded here and in the recipe's
doc rather than in `BETA.md`, because it is a property of the throwaway control's build, not of any
shipped artifact.

## 6. What remains unverified

- **The original observation's cause.** Three arms do not reproduce it; that is a non-reproduction,
  not an explanation. If it recurs, the gate's per-launch images (`target/macos-launch-render/`)
  and logs are the record to attach.
- **This gate cannot run in CI.** It needs a real GUI session and a TCC-granted Screen Recording
  permission, neither of which a headless runner has — so it is a local, manual gate like
  `macos-frame-pump`, `macos-resize-jitter` and `macos-ime`, not a regression net.
- **Occlusion and display sleep** are untested: the window is matched and captured while the session
  is awake, and `screencapture -l` was never exercised against a fully occluded window in a
  minimized state.
- **The blank-window control covers a still window only.** A window that renders one frame and then
  freezes is the failure mode behind the 2026-09-17 frame-pump defect, and it is `just
  macos-frame-pump`'s job, not this gate's.
