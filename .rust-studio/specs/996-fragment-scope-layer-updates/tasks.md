## Decisions this decomposition fixes (read before dispatching any task)

**D1 — Interim consistency: the NEW method's default derives from the OLD hooks, and every reader switches to the new method at task 1.5.** The brief offered two shapes — (a) old hooks' defaults derive from `paint_effects` during migration, or (b) the walk switches at one commit after all producers migrated. Neither keeps every commit both green and small: (a) is not expressible for `paint_alpha(&self)` (it has no `size` to hand `paint_effects(size)`; a `Size::ZERO` stand-in is a hack and makes the walk build the 128-byte value up to three times per node in the interim); (b) leaves six producers carrying two live sources of truth with nothing reading the new one, and makes the final switch a ~20-file atomic commit. The third shape is what every task below assumes:

1. Task 1.5 adds `paint_effects(&self, size) -> PaintEffects` to `RenderBox` / `RenderSliver` / `RenderObject` with a default of `PaintEffects { opacity: paint_alpha().map(PaintOpacity::new), clip: None, transform: paint_transform(size) }` (in-crate literal construction; `#[non_exhaustive]` binds other crates only), adds the blanket forwards and `RenderNode::paint_effects()`, and re-points **all three readers** — the paint walk (`paint.rs` ~:559), the patch arm (`layer_patches_for` ~:466), and both `apply_paint_transform` defaults (`render_box.rs` ~:444, `render_object.rs` ~:567) — at the value. Behaviour-neutral by construction: for every node the default reproduces exactly what the hooks returned, at the same call site, under the same gates.
2. Each producer task (1.8–1.11) overrides `paint_effects` **and deletes its old hook overrides in the same commit**. The walk already reads the value, so nothing changes; a forgotten deletion is dead code that 1.13 turns into a compile error (loud, never silent).
3. Task 1.13 deletes `paint_alpha` / `paint_transform` from the three traits, the two blanket forwards and `RenderNode`, and flips the `paint_effects` default to `PaintEffects::NONE`. By then it has **zero overriders and zero callers** — a single commit touching flui-rendering only (plus the doc links it breaks), which is what "atomic with the last overrider" reduces to under D1.
4. `apply_paint_transform`'s default re-point therefore sits in **1.5**, not in the deletion: it must precede 1.11 (`RenderRotatedBox` relies on the default mapping), and `tests/transform_to.rs` + `harness_transform_to_*` are 1.5's neutrality oracle for it. At 1.13 the re-point is already done, so the transform hook's deletion is inert for coordinate queries.

**D2 — The `FragmentScope::Clip(PaintClip)` fold lands BEFORE the method task (1.3 < 1.5), deviating from the brief's order (deletions → fold).** From the moment `own_effect_layers` takes the value it must honour `effects.clip`, which needs `clip_layer(PaintClip, origin)`; writing that arm against a fold that lands later would mean either a value field the walk silently ignores for several commits (the "shipped seam never wired" class) or `own_effect_layers` written twice. Folding first means `clip_layer` is written once and `own_effect_layers` once against it.

**D3 — `paint_layer_blend` is deleted in 1.5, not 1.13.** Census (`rg -n "paint_layer_blend" crates --type rust`): zero overriders in production AND tests; one caller besides the walk (the `render_object.rs` unit test `default_effect_layer_hooks_are_inert`). Keeping a hook whose doc says "the pipeline passes it to `OpacityLayer::with_blend`" while the pipeline no longer reads it would be a false doc for ~8 commits. The `with_blend` arm of `own_effect_layers` and the "alpha–blend coupling" prose (`paint.rs` ~:646-651, ~:987-992) go with it. `PaintOpacity` has no `blend` field (spec: added when a producer exists).

**D4 — Homes.** `traits/paint_effects.rs` owns `PaintEffects`, `PaintOpacity`, `PaintClip`, and (from 1.14) `resolve_path_clip(target, size) -> Path`; all re-exported through `traits::*` (the spec's `paint::resolve_path_clip` name would put a public fn in the private `pipeline::owner::paint` module — the resolver is the value's semantics, so it lives beside the value; `api-design-lead` may relocate it in 1.14's brief, but it must be `pub` and one function). `PaintClip::PathTarget` uses the existing `flui_rendering::hit_testing::PathClipTarget` re-export — **no new re-export is needed** (spec's "becomes nameable" is already true).

**D5 — `PaintCx::with_clip(clip: PaintClip, f)` is added in 1.3** as the general scope constructor; `with_clip_rect/rrect/path` keep their signatures and become one-line wrappers over it (`with_clip_path` does the one `Arc::new`). It is what `RenderClip::paint` pushes through after `ClipGeometry::with_clip_scope` is removed (1.4) and before PR3 moves the clip into `paint_effects`; it stays wired afterwards through the three wrappers. Name is `api-design-lead`'s to confirm (no collision: `PaintCx` has `with_clip_rect/rrect/path/shader_mask/backdrop_filter/leader/follower/transform`).

**D6 — `Arc<Path>` (spec v4).** `PaintClip::Path { path: Arc<Path> }`; `ClipPathLayer` stores `Arc<Path>` with `new`/`set_clip_path` taking `impl Into<Arc<Path>>` so every existing `new(path, ..)` caller (`compositor/builder.rs:298`, `circle`, `oval`, its own tests) compiles unchanged and `clip_path() -> &Path` stays — `flui-engine` (`wgpu/layer_render.rs:198`) and `testing/snapshot.rs:858` only ever deref `&Path`, so **no engine ripple** (verified by reading both call sites). `Layer::ClipPath(Box<ClipPathLayer>)` keeps its `Box` (a `Layer` layout change is not this spec's; noted as optional follow-up). `RenderClip<Path>`'s `clip_shape` is stored shared — recommended shape: `ClipGeometry` gains `type Stored: Borrow<Self> + Clone + Debug + PartialEq + Send + Sync + 'static` (`Rect`/`RRect`/`Oval` → `Self`; `Path` → `Arc<Path>`) with `fn store(self) -> Self::Stored`, `resolve_clip` returns `S::Stored`, `to_paint_clip(stored: &Self::Stored, behavior)` clones the `Arc`; `set_clip_shape(Option<S>)` / `with_clip_shape(S)` / `clip_shape() -> Option<&S>` keep their public signatures (`Borrow` gives the `&S`). Alternative `Option<Arc<S>>` for every `S` (allocates for a 16-byte `Rect` on `set_clip_shape`) — `api-design-lead` decides in 1.4's brief; either satisfies AC11's pointer-equality.

**D7 — `effect_slots` capture-ordered (spec v4).** `capture()` is a pre-order DFS over the layer tree, so the first appearance of each `RenderId` in that walk IS paint order; the change is the container (`Vec<(RenderId, EffectSlots)>` built at first appearance) plus `layer_patches_for` iterating it in order and its `contains_key` gate becoming a scan (or a side `FxHashMap<RenderId, usize>` index — `systems-perf-lead`'s call; cost stays O(effect-owning nodes)). Behaviour-neutral for every existing single-target oracle; AC12 (PR3) pins the order. Own task 1.6 so 1.5 stays one kind of change.

**D8 — Docs split.** PR1's docs task (1.17) makes the ten `ARCHITECTURE.md` mentions, the harness comment, and the trait-level docs TRUE for the value (mechanical truth, no new claims); PR3's AC10 does the rewrite of trade-off 1 to the rule + enumeration command, the per-producer entries, the Deferred table, and the improvement statement. The spec's **market-survey section is docs-only — nothing to build**; PR3's AC10 entry may cite it. ADRs (0013/0014/0021) and `docs/ROADMAP-TRACKER.md` are dated records of what landed then and are not edited; `docs/research/*` is archival.

## Notes — decomposition risks and their disposition

1. **1.5 is the one task that cannot be split further.** A reader on the value without the defaults is a compile error; defaults without a reader are dead; the three readers must move together. It is M-sized (5 files, ~150 changed lines + prose) and fits one window; it is PR1's only non-S commit besides 1.4/1.12/1.17.
2. **Doc-strict is a real oracle here, not paperwork.** Deleting the hooks breaks intra-doc links in `render_{box,sliver,object}.rs`, `paint_cx.rs:580`, `paint.rs:1416`, `sliver_opacity.rs:12/:45`, `animated_opacity.rs:149`, `transform.rs:451`. 4. **1.14's `PathTarget` arm is dead until PR3.** Deliberate (spec order); unit-tested in 1.14; named in the PR1 description. If PR3 slips, it is a tracked seam with a test, not an unwired one.
5. **`paint_layer_blend` removal inside the "additive" task 1.5** is justified by the zero-overrider census (D3); `api-design-lead` signs 1.5 anyway.
6. **Perf of the value read** (one 128-byte sret per node per frame, plus one `Arc` bump per fixed-path clip) is accepted by the spec; 1.5 and 1.6 record before/after numbers on both bench shapes in their execution entries so PR3's AC9 has a baseline that already includes the value.
7. **`Arc<Path>` storage in `RenderClip<S>` (1.4) is the one place PR1 changes a render object's fields.** It is M and has an `api-design-lead` sign-off because the associated-type shape touches the sealed trait's contract; the alternative (`Option<Arc<S>>`) is acceptable if the associated type reads as over-engineering in review. 9. **The market-survey section of spec v4 is docs-only** — nothing to build; cited by 3.9.
10. **What is NOT in PR1, by decision (non-goals restated):** no producer gains patchability (that is PR3 — `RenderClip`, `RenderFlow`); no setter impact changes; no guard move; no `Layer::ClipPath` un-boxing; no ADR (spec: governing ADR none); no edits to ADRs/ROADMAP-TRACKER; `RenderBackdropFilter`/`RenderShaderMask`/physical model/`RenderFittedBox`/`RenderFlow` per-child transforms stay as the spec's Deferred table says.
