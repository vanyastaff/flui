# Plan — iOS touch input and Home/return retention, measured on a real simulator

Status: **closed as a gate plus a corrected record (2026-09-20, real Mac, iPhone 16e / iOS 26.2).** The
recorded gap was that "simulator UI automation timed out, so real touch input and retained displayed
counter state after Home/return remain unverified for this candidate" (`docs/BETA.md` § "iOS execution
lifecycle foundation"). What was missing was not a fix but an *instrument*: nothing in the repository
could put a `UITouch` into an iOS application, and nothing could tell whether a touch had reached a
widget. This task adds both (`scripts/check-ios-input.py`, `scripts/ios-input-probe.swift`,
`just ios-input-check`), measures the candidate the sentence names, validates the gate against
subjects that must fail, and rewrites the record to what was measured. The residual is stated in §6,
not hidden — including a layout observation the images surfaced that this gate does **not** close.

## 1. Task and where it comes from

`docs/BETA.md:491-493`, in the beta-preparation report's Priority #1 ("close the remaining real-launch
problems: iOS safe areas, CLI and input verification, the blank window when launching macOS through
LaunchServices"):

> Simulator UI automation timed out, so real touch input and retained displayed counter state after
> Home/return remain unverified for this candidate.

Read literally this is a claim about the *flagship* artifact — the app generated by `flui create` and
built by the CLI — and it is the one entry in Priority #1 with no instrument behind it. The task is
therefore twofold: build the instrument, and replace the sentence with its measurement rather than
deleting it.

## 2. What was established empirically

All on the same host, 2026-09-20, macOS on Apple silicon, iPhone 16e simulator
(`FDF4975B-ED8A-4010-8ADB-5AF46B0F1BF3`, iOS 26.2).

### 2.1 Nothing else can deliver a real touch

`xcrun simctl` has no touch subcommand (`io` offers `screenshot`, `recordVideo`, `enumerate`, `poll`);
`idb` is not installed; and driving the Simulator window through host UI automation needs the
Accessibility grant and photographs the host's desktop rather than the device. XCUITest synthesises
touches inside the simulator through the platform's own automation channel, so the touch is real and
the host needs no desktop permission. This is why the route was chosen, and it is what makes the gate
runnable on a machine where desktop scripting is denied.

### 2.2 The oracle has to be pixels

`flui-platform`'s `a11y` feature covers AT-SPI, UIA and NSAccessibility — not UIKit — so a UI test
cannot read a widget by identifier on iOS. The measurement is therefore a screenshot comparison, the
same discipline `just macos-launch-render` uses and for the same recorded reason: an application can
report state it never drew.

### 2.3 The candidate, measured

`dev.flui.beta-counter` — the generated sole-`flui` counter, the artifact the sentence names, as built
by the CLI on 2026-09-19 — and the in-repo `dev.flui.ios-demo`:

| stage | counter | demo |
|---|---|---|
| initial | `75a445c4` (ink 1.06 %) | `7512336b` (ink 2.81 %) |
| after a real tap | `a341befd` — digit `0` → `1` | `f0f7afd5` — `Selected: none` → `Selected: Item 0` |
| after Home + return | `a341befd` — retained | `f0f7afd5` — retained |
| after a fresh launch | `75a445c4` — reset | `7512336b` — reset |
| after a tap on no target | `75a445c4` — unchanged | `7512336b` — unchanged |

The changed pixels are one glyph and one line and nothing else: the counter's tap moved **817** pixels
inside a single 25×34 box at x[572,597] y[101,135] of 1170×2532; the demo's moved **8 383** across one
301×34 text run at x[434,735] y[197,231]. `docs/BETA.md` carries these numbers; the images and the
exact hashed region for every stage are under `target/ios-input*/<run>/`.

### 2.4 The frame the probe has to give the application

A tap only measures the touch path if the screen has stopped moving: comparing a settled frame against
a moving one is comparing noise. The probe polls two consecutive screenshots 0.4 s apart and accepts a
stage when they agree byte-for-byte, with a 25 s deadline; a screen that never stabilises is
CANNOT_VERIFY, not a verdict. §4.1 shows that arm reached.

## 3. The gate

`scripts/check-ios-input.py` driving `scripts/ios-input-probe.swift`, via `just ios-input-check <udid>`
(the in-repo demo) or `just ios-input-check-app <app> <udid> …` (any staged `.app`).

- **Four stages in one launch**, two of them controls: a real tap must change the display; Home then
  return must still display the change; a fresh launch must reset it (otherwise the return comparison
  could not have failed and proves nothing); a real tap at a point with no target must change nothing
  (otherwise the tap comparison does not distinguish a hit from any touch).
- **The instrument is built, not linked.** A `.xctest` bundle is compiled with `swiftc` against the
  simulator SDK's XCTest, the test host is Apple's `XCTRunner.app`, and the two are joined by a
  hand-written version-2 `.xctestrun` run with `xcodebuild test-without-building`. No Xcode project
  and no build system state is involved, so the gate does not perturb what it measures.
- **The runner's plist placeholders are substituted by hand** (`$(WRAPPEDPRODUCTNAME)`,
  `$(WRAPPEDPRODUCTBUNDLEIDENTIFIER)`): xcodebuild does not substitute them for a non-generated
  runner, and an unsubstituted `CFBundleExecutable` is reported as "missing its bundle executable",
  which points at the wrong problem. The checker re-asserts that none remain, so a future Xcode adding
  a fourth surfaces as itself.
- **XCTest's frameworks are embedded flat** into `ProbeRunner.app/Frameworks/`: XCTRunner links
  `@rpath/XCTest.framework/XCTest` with an rpath of `@executable_path/Frameworks`, and the simulator
  device has no `/Developer`.
- **Tap geometry and the compared region are inputs** (`--target-tap`, `--empty-tap`, `--region`),
  because both are properties of the application under test, not of the gate. §4.2 is why.
- **Exit codes** are part of the contract: `0` all four stages held, `1` a stage failed, `2` the host
  could not take the measurement. A harness that never ran must not be filed as a defect in the
  framework, and a framework defect must not be filed as a harness problem and retried.

### Rejected alternatives

| alternative | why not |
|---|---|
| `xcrun simctl` touch | no such subcommand; `io` has screenshot/recordVideo/enumerate/poll only |
| host UI automation (AppleScript / System Events) | needs the Accessibility grant, photographs the host's desktop, and the same approach was denied earlier in this work |
| `idb` | not installed, and not a dependency worth adding for one capability |
| reading widget state instead of pixels | no iOS accessibility tree to read; and state that reached a log is not state that reached the screen |
| `XCTAssert` verdicts inside the probe | one exit path for "the framework lost state" and "the harness never measured" — the two must stay distinguishable |
| `xcresulttool export attachments` for evidence | a result bundle carries a full build log per stage; the probe writes its own report and images instead |

## 4. Validating the gate itself

### 4.1 Arms that must not pass

| subject | expected | measured |
|---|---|---|
| `dev.flui.ios-demo`, Material, interactive | PASS | exit 0, all four stages |
| `dev.flui.beta-counter`, generated, interactive | PASS | exit 0, all four stages |
| a UIKit app that draws and installs **no** touch handling | FAIL | exit 1, "the tap changed nothing on screen", and its own relaunch control adds "so the return comparison above cannot fail and proves nothing" |
| an animating app, whose screen never stops changing | CANNOT VERIFY | exit 2, "the screen never stopped changing at 'initial'" |
| an unknown simulator | CANNOT VERIFY | exit 2, "not one available simulator" |

The touch-ignoring control draws a coloured field and a label (ink 11.05 %), so its failure is
attributable to the touch and not to a screen that was blank to begin with. Each failure mode the gate
can reach was reached.

### 4.2 Three defects the validation exposed, each of which had produced a confident wrong answer

- **A predecessor run's evidence was read as this run's.** The test host's container survives
  reinstallation and the probe wrote to a fixed path inside it, so screenshots from an earlier subject
  were copied into the next run's record — visibly byte-identical across stages that the run's own
  report said had changed. Evidence now goes to a directory named for the run
  (`FLUI_IOS_PROBE_RUN`), and the checker clears the probe's `tmp/` before starting. Same defect class
  as the macOS launch-route gate's owner-name window matching: a verification gate identifying its
  subject by something a previous run also carries.
- **The compared region cropped out the only pixels the tap was meant to change.** The generated
  counter draws its count at y≈95-133, immediately below the status-bar clock at y≈53-94, and the
  region's 6 % top inset excluded it — so a delivered touch and a lost one produced identical images
  and the gate reported the touch lost. The region is now a rectangle, and the first counter run was
  rerun to a PASS (`75a445c4 → a341befd`) once it covered the digit. The requirement is documented on
  the option itself: *the region must contain the pixels the target tap changes*.
- **A blank screen was read as a lost touch.** One run caught the application before it had drawn
  anything (ink 0.00 % over the whole comparison) and reported "a real touch did not reach a widget";
  there was no widget to reach. A first stage below 0.05 % ink is now CANNOT VERIFY — the same "was
  anything drawn at all" distinction the macOS gate draws with its colour oracle, and the reason that
  gate's blank control fails both of its oracles rather than one.

Two of the three would have shipped as false claims about the framework if the validation had only
been run against subjects expected to pass.

## 5. The record, corrected

`docs/BETA.md` § "iOS execution lifecycle foundation" now carries the measurement instead of the open
gap: the instrument and why it must be XCUITest, the per-stage hashes and inks for both subjects, the
pixel counts and bounding boxes, the controls that make the pass falsifiable, the arms that fail, and
the three harness defects. The old sentence is not deleted — it is quoted as the state the task opened
from, so a reader can see what changed and why. The two items this gate does not close (§6) are stated
in the same paragraph rather than left to be inferred.

`just ios-input-check` and `just ios-input-check-app` carry the operational detail; the
counter-specific tap geometry lives in the latter's doc, because it is a property of that artifact and
not of the gate.

## 6. What remains unverified

- **The counter bundle was re-measured, not rebuilt.** The artifact measured is the one the CLI
  produced on 2026-09-19. This is the candidate as it exists; it is not a fresh build of the current
  revision. Rebuilding it needs a `flui create` + iOS build that the host's free space could not take
  during this work.
- **A layout observation this gate does not close.** Both subjects draw under the system chrome: the
  counter's column and the demo's app bar title sit beneath the status-bar clock rather than below it,
  and the counter — whose template asks for `Center` — lays its column at the top of the screen
  (content at y 0-305 of 2532) instead of the middle. The committed macOS record for the same
  generated artifact describes its only ink cluster at y[103,137] of an 800×632 window, the same
  top-anchored position, so it appears shared across backends rather than an iOS property. **No cause
  has been measured** and nothing was changed; it is recorded as an observation with images.
- **This gate cannot run in CI.** It needs macOS, Xcode, a booted simulator and a compiled Swift test
  bundle — a local, manual gate like `macos-frame-pump`, `macos-launch-render` and `macos-ime`, not a
  regression net.
- **Multitouch, drag and cancellation are untested.** The probe sends single taps; the backend's
  `touchesMoved`/`touchesCancelled` paths (and `touch_to_pointer_events`' Move/Cancel arms) are
  exercised by no measurement here.
- **The `emptyScreenInk` floor is a floor, not a quality bar.** It separates "drew nothing" from "drew
  something" at 0.05 %; it does not detect an application that drew the wrong thing.
- **Evidence writes are reported, not guaranteed.** One run lost three stages' images with no error
  recorded (the cause was not reproduced; `try?` had discarded it). The probe now records a failed
  write as `EVIDENCE INCOMPLETE` and the checker prints it, so a recurrence is visible — but the gate
  does not fail on it, because the hashes it decides from are written to the report independently.
