# FLUI Examples

This directory holds the facade's minimal applications and native acceptance
executables. Internal examples live beside the crate or official package that
owns them; run those with an explicit `-p` package from the repository root.
WASM demos are separate crates with their own build step.

## Start Here

| Example | Run |
|---|---|
| **counter** — the minimal FLUI app: one `Signal` and a `RawButton` whose press writes it (start here — this is the README's own "Hello World" code sample, and the exact shape `flui create`'s `counter` template generates) | `cargo run -p flui --example counter` |

## Acceptance

| Example | Run |
|---|---|
| **acceptance_app** — the notes application the headless acceptance rows run (`tests/fixtures/acceptance_app/`, through `tests/facade_consumer.rs`), in a window for native runs | `cargo run -p flui --example acceptance_app --features material` |
| **acceptance_app_faults** — the same application with one injected panic, named by its argument (a `Fault` name, listed when the argument is missing) | `cargo run -p flui --example acceptance_app_faults --features material -- <fault>` |

## Hot reload

The maintained counter hot-reload application is generated by
`flui create my-app --hot-reload`; run it from the generated workspace with
`flui run`. The repository also keeps these development fixtures beside their
owning crates:

| Example | Location / run |
|---|---|
| **desktop_scene** — hot-reloadable scene plugin for desktop (Windows/macOS/Linux) | `crates/flui-engine/examples/desktop_scene`; two terminals, see below |
| **hot_reload_lifecycle_fixture** | `crates/flui-hot-reload/examples/hot_reload_lifecycle_fixture`; dev-only `app_plugin!` fixture for `flui-hot-reload`'s own integration test — not meant to be run directly |

**desktop_scene** is a `cdylib` plugin, not a binary — there is no
`cargo run -p flui-desktop-scene`. It is built in one terminal and loaded by a
separate host process in another (full workflow:
[`docs/hot-reload.md`](../docs/hot-reload.md#desktop-plugin-workflow)):

```bash
# Terminal 1 — rebuild the plugin on change (needs cargo-watch)
cargo watch -w crates/flui-engine/examples/desktop_scene -x "build -p flui-desktop-scene"

# Terminal 2 — run the host with in-process reload (Linux/macOS; see
# docs/hot-reload.md for the Windows .dll path)
FLUI_SCENE_PLUGIN=target/debug/libflui_scene.so cargo run -p flui-engine --example scene_render
```

## Web / WASM

| Example | Run |
|---|---|
| **web_demo** — Web/WASM platform demo | `cd crates/flui-native/examples/web_demo && wasm-pack build --target web --out-dir pkg`; serve `crates/flui-native/examples/web_demo/` over HTTP |
| **painting_demo** — Web/WASM painting + engine demo | `cd crates/flui-engine/examples/painting_demo && wasm-pack build --target web --out-dir pkg`; serve `crates/flui-engine/examples/painting_demo/` over HTTP |

The `painting_demo` crate contains browser code only and targets
`wasm32-unknown-unknown`. Its surface takes ownership of the `HtmlCanvasElement`
through wgpu's safe `SurfaceTarget::Canvas` API. Native workspace checks compile
an empty cdylib; they do not exercise the browser demo.

## Android

An Android app is a project generated by `flui create`. From its directory,
`flui build android` builds the APK and `flui run --device <id>` (ids from
`flui devices`) installs and starts it; see `crates/flui-cli/README.md`.

## Building facade examples

```bash
cargo build -p flui --examples       # facade examples that do not need a feature
cargo run -p flui --example          # list facade example targets
cargo run -p flui --example <name>   # run one facade example by name
```

For internal examples, name both the owning package and target, for example
`cargo build -p flui-engine --example scene_render`.
