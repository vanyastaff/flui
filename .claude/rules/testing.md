# Testing Quirks

Load before writing or debugging tests. Tier map: [`docs/testing.md`](../../docs/testing.md). `RenderTester`/`Probe` API and catalog rules: [`crates/flui-rendering/docs/TESTING.md`](../../crates/flui-rendering/docs/TESTING.md).

- **The singleton family is retired — there is nothing left to serialize against.** `AppBinding`, `SemanticsBinding`, and the `impl_binding_singleton!` macro with its `HasInstance`/`BindingBase` trait pair are **deleted**, not slimmed — their fields dissolved into `AppRuntime`/`UiRealm`/`PresentationState`, and `RenderingFlutterBinding`/`SemanticsBinding` left the graph the same way earlier. `UiRealm`'s transitional at-most-one-instance guard (`REALM_CLAIMED`, `UiRealmError::AlreadyExists`) and its dedicated test lock are deleted too, so any number of `UiRealm`s may be constructed and driven concurrently, on one thread or several (see `crates/flui-app/src/app/ui_realm.rs`: `two_realms_coexist_same_thread`, `two_realms_two_threads_no_shared_state`, `dropping_realm_a_cannot_wake_realm_b`, `cross_realm_duplicate_global_key_mounts_succeed_in_both`), and each realm builds its own `UpdateScheduler` (`RealmServices::construct()`, `crates/flui-app/src/app/runtime.rs`). `SINGLETON_WINDOW_TEST_LOCK`, `SCHEDULER_PHASE_TEST_LOCK`, and `SEMANTICS_TEST_LOCK` are deleted along with the state they guarded. **What is still genuinely process-global** is named per-symbol in `docs/runtime-contract.toml`'s ambient-reach ratchet — flui-assets' `Registry::global` and flui-painting's free-standing `FONT_SYSTEM`. A test mutating one of *those* needs its own `Mutex` scoped to that test module; do not reach for `--test-threads=1` or a lock from the deleted family.
- **CI runs nextest fully parallel, one process per test**, so anything the above does not cover is a real parallelism hazard.
- **`flui-platform`'s Linux suite runs in CI, filtered by mechanism, not by test name.** The `test` job runs `cargo nextest run -p flui-platform --all-features` (default features alone silently skip the entire winit backend — see `crates/flui-platform/AGENTS.md`) under two devices: `FLUI_HEADLESS=1` routes `current_platform()` to the `HeadlessPlatform` mock, which is what the tests calling `open_window` outside `Platform::run`'s `on_ready` callback need (a winit event-loop ordering requirement, not a display-server issue), and `xvfb-run` gives the 9 winit-internals unit tests that construct `WinitPlatform::new()` directly a real X11 connection for clipboard init. All 175 runnable tests pass this way; doctests need neither device. The Windows, macOS, and Android backends are never linked or executed anywhere — `cross-typecheck`'s clippy pass is their only coverage, and why each is excluded is in [`.claude/rules/ci.md`](ci.md). `just test-ci` mirrors the CI step and needs `xvfb-run` locally (`apt install xvfb` on Debian/Ubuntu).
- **Multi-window / `WindowPolicy`.** `flui_app::WindowPolicy` (`SeparateRealms` default, or `SharedRealm`) is the knob `flui_app::open_secondary_window` consults for a second top-level window; `flui_app::ExitPolicy` (default `OnLastWindowClosed`) governs when the platform loop exits once every hosted window has closed, live-wired through `flui_platform::traits::Platform::set_exit_policy_hook` (a default-no-op only the winit and headless backends override), which `runner/host.rs::install_exit_policy_hook` wires to `AppRuntime::should_exit`. Both modes are covered end-to-end under `HeadlessPlatform` in `crates/flui-app/src/app/runner/realm_dispatch.rs`'s `realm_dispatch_tests` (`two_realms_via_separate_windows_policy_share_nothing`, `one_realm_two_windows_policy_routes_by_presentation`, the live-loop exit-policy probe, the hot-restart probe) plus `crates/flui-platform/tests/headless.rs`'s hook-level tests — all through the public `Platform`/`PlatformWindow` surface (`open_window`, `.close()`, `on_quit`, `set_exit_policy_hook`), never internal `MockWindow` access.
  **Named gap, not silently assumed:** a window `open_secondary_window` opens carries no widget content and never renders a frame — rendering is one canonical frame-pump closure per *backend*, pinned by `crates/flui-app/tests/runner_frame_ordering.rs`, and `UiRealm::attach_root_widget` is wired to a realm's primary presentation only. A live two-window winit smoke test does not exist yet, but *not* because winit refuses an `EventLoop` off the main thread: `platforms/winit/platform/real_loop_tests.rs` has a `build_test_event_loop` helper (`with_any_thread(true)` on Linux/Windows, main-thread-only and `#[ignore]`d on macOS) and drives REAL winit loops with it under `xvfb-run` — the #713 close-arm test, the bootstrap-error propagation test, and the #919 programmatic-close test all run `event_loop.run_app` on an ordinary test thread under `xvfb-run`. That file (split out of `platform.rs` in #923) is where a new real-loop test belongs. What is missing is only the two-window *content* half.
- **Live E2E smoke (`just live-smoke`, CI's `live-smoke` step).** `tools/live-smoke` drives a REAL windowed demo with REAL X11 input (XTEST) under Xvfb and asserts on captured pixels and the exit code — the only executing coverage of the band ABOVE synthetic event dispatch (platform translation, the event-loop wake chain, window-close teardown), each of which has shipped broken while every synthetic gesture test stayed green. It also verifies hidden-surface gating against a REAL occlusion signal (#623): an input-transparent cover window drives X11 `VisibilityFullyObscured` → winit `Occluded(true)`, and the check asserts zero GPU submissions mid-fling while covered (oracle: per-present `flui.gpu` trace lines in the captured log), input still serviced at the translation layer, and no-input frame resumption on uncover. Its fling drags UPWARD on purpose — the arming wheel-ticks walk the offset toward the top, so a downward fling would drag into the room the arming just consumed and die against the top clamp with delivery perfectly healthy; that exact premise inversion is what once made this check fail on `main`, and the direction is documented at the drag itself. Wayland's close-path teardown ordering has its own variant, **`just live-smoke-wayland`** (CI's step of the same name): the demo under a headless weston compositor, self-closed through the platform's `FLUI_SELF_CLOSE_AFTER_MS` hook — the same `CloseRequested` arm a compositor close takes, and the only way to drive a Wayland close from a harness at all (no protocol lets one client close another's toplevel). Both harnesses also run `FLUI_SELF_CLOSE_ROUTE=programmatic`, closing through `PlatformWindow::close` instead: the route an application closing its own window takes, which on winit hid the window but never left the backend's tracking map, so the process never exited (#919), while the compositor-route and headless close checks all stayed green. And a wgpu surface torn down after its `wl_surface` segfaulted post-quit on Wayland (#713) while the X11 close check stayed green — Xlib tolerates the same out-of-order teardown. Skips with a message when `weston` is absent; CI installs weston explicitly so it can never silently skip there.
- **Test support belongs in `flui-testing`, and mounting goes through `HeadlessBinding::mount_root`.** The eight-step headless bootstrap — capabilities before mount, mount inside the owner scope, initial `build_scope`, render-root discovery, root constraints, the layout↔build fixpoint frame (**never a bare `PipelineOwner::run_frame`**), the lazy-sliver service pass, then bind — is owned once, in `flui_testing::bootstrap`. Its contract: the bootstrap frame is the same frame `pump_frame` runs. It was previously hand-rolled per harness and the copies drifted silently — a bare `run_frame` never services build-during-layout content, so a copy using one captured a `SliverAppBar`'s delegate child unbuilt, and no copy ran the service pass. Measured on the six demo trees the snapshot suite covers, the fixpoint changes nothing — all six use `ListView::new`'s static children, which a bare `run_frame` already builds; the drift was real but those demos were never the ones exposing it. `flui_widgets::testing::LaidOut` stays in flui-widgets only because it mounts widgets (`FocusRoot`/`VsyncScope`/`GestureArenaScope`) and flui-testing may never depend on the widget catalog — it is built on `mount_root` all the same.
- **Render-object harness** — every concrete `RenderBox`/`RenderSliver` must have harness tests. The catalog CI guard (`render_object_harness.rs`) verifies every exported type appears in `RENDER_OBJECT_TYPES` and has a matching `harness_*` test.
- **wasm32 is compiled in three ways and executed in one.** `wasm-check` (`cargo check` + `cargo clippy`) and `wasm-link-check` prove type-checking and linking; neither runs an instruction, and on wasm32 the link does not even fail on an undefined symbol (rust-lld turns it into an import — hence the committed allowlist). `just wasm-test` is the only step that EXECUTES: it DISCOVERS the crates declaring a wasm32 `wasm-bindgen-test` dev-dependency and runs their lib and `tests/wasm32.rs` targets on node via `wasm-bindgen-test-runner`; CI runs it at the end of the `wasm-check` job. Which target kind is possible depends on visibility — an integration test sees only the public API, a `pub(crate)` seam only a lib test. A plain `#[test]` fn compiles for wasm32 but never RUNS (`no tests to run!`); only `#[wasm_bindgen_test]` registers, so opting a crate in does not drag its native suite onto wasm. The gap it closes is real — swap `web_time::Instant` for `std::time::Instant` in `flui-foundation/src/clock.rs` and every compile-only step stays green while the code panics `time not implemented on this platform` on first execution. Put a test there only when the behaviour *differs* on wasm32 (or a native-target substitution exists precisely to keep wasm32 working); anything that would pass identically on native buys a wasm build and no coverage. Three versions must agree or the runner refuses to start — the locked `wasm-bindgen`, `wasm-bindgen-test` (pinned `=0.3.77`; the unpinned `"0.3"` resolves to 0.3.78 and bumps the workspace lock), and `wasm-bindgen-cli`, whose version the recipe and CI step both read out of `Cargo.lock`. Discovery rather than a crate list is deliberate — a list is how the next suite added goes silently unrun — and it asserts three things: that a suite was found at all, that EACH suite executed a non-zero count (an aggregate check lets exactly the newly added suite be the inert one), and that the total is non-zero. `ExecutionServices`' `Backend::Sequential` branch is executed by `execution.rs`'s `wasm_sequential_backend_tests` — it had to be a lib test because the type is `pub(crate)`. Still compile-only: flui-platform's web backend, which is wasm32-only and has no executing coverage at all. Tracked in #985.
- **Coverage**: `just coverage` (requires `cargo-llvm-cov`).
- **Visual self-verification (no window needed)** — to *see* what a widget tree renders, capture it to a PNG instead of screenshotting a live window: `cargo run -p flui --example screenshot -- <demo> [width] [height] [out.png]` (`<demo>` = `material` \| `cupertino` \| `vertical-slice`), then open the PNG. It mounts through `HeadlessBinding`, extracts the `LayerTree`, and rasterizes offscreen via `flui_engine::wgpu::HeadlessRenderer` (`crates/flui-engine/src/wgpu/headless.rs`) — the same GPU raster path as on-screen, so shadows/blends match. Add a `match` arm in `examples/screenshot.rs` for another tree. This exists because OS screenshot tools can't grab the live window under GNOME/Wayland+Mutter (the wgpu/Vulkan surface never lands in the X11 framebuffer, and `wlr-screencopy`/`grim` is unsupported) — a green harness test is necessary but "MVP reported as parity" hides in the pixels the test never looks at (see Definition of Done).
