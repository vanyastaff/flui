### Fixed

- The X11 clipboard no longer answers, or refuses, the window that takes a gone client's window id in place of the request that client left waiting for the primary selection's text: the server hands a gone client's ids to the next one, and the answer used to land on the new window. A request that waits, or text that goes `INCR`, now hears its requestor's window and is dropped as it goes, and an answer decided later is written once a mark sent behind it comes back, every event before the mark handled. A requestor the server will not let the clipboard hear for a reason other than being gone, or does not answer about in time, is refused rather than left waiting; a request into the clipboard's own window is never answered. X itself cannot tell a window that goes, and whose id a new window takes, in the moment between the clipboard's last exchange with the server and its write, nor the clipboard's mark from another client changing that property of the clipboard's window.
- The X11 clipboard waits on the server a bounded time, each wait with a deadline that other clients' events, a flood of them included, do not move: a reply that comes too late fails its request and leaves the server counted as held until an event shows it answers again, within that step; a write fails once it sends nothing for two seconds, or takes longer than two seconds plus its size at 16 KiB/s, so a slow link or a pause of the server's only delays it, and a write past either breaks the connection, which ends the clipboard for the rest of the process as any connection failure does. A server another client holds, or a dead link, no longer stalls it or holds up the application's exit: dropping the clipboard waits at most for the reply under way (two seconds) or the write under way (two seconds to its first call to the socket, then its allowance), and then 300 ms; once those 300 ms have passed, a write the socket takes at once still goes out. Commands sent with the clipboard's drop wait on no reply, and what needed one answers `Gone`. As it ends (dropped, its connection failing, or after a panic on its thread) the requests still waiting on the application are refused, no `INCR` transfer starts, no write takes a selection, and the answers owed are written, those it had to drop reported; answers already written but still in the connection's buffer when a flush past the deadline breaks the connection are lost without being counted.
- A client flooding the X11 clipboard with requests no longer holds up the answers it decided: each step handles a bounded number of events. A diagnostic subscriber that panics no longer costs a requestor its answer or refusal, nor ends the clipboard.
